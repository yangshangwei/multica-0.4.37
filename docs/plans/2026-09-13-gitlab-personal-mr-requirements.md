# 私有 GitLab 登录、个人授权与 MR 归属：需求文档

> 状态：**暂缓，未实施**。用户于 2026-09-13 明确要求只整理并保留讨论结果，暂不推动开发。
> 本文是后续需求评审入口；技术方案见[设计文档](2026-09-13-gitlab-personal-mr-design.md)。
> 整理时仓库：`main`，提交 `23d771ca77851de35265db5d269bf2d1034e6a43`。记录已有讨论和调研，不代表运行中的服务已具备拟议能力。

## 1. 背景与问题

讨论起点是“设置 → GitHub”和“设置 → 集成”的功能差异：团队使用自建私有 GitLab，希望在 Multica 中获得任务与代码协作的关联能力，并让智能体创建的 MR 正确归属实际发起人。

已确认的核心目标是：**张三经过验证并授权发起的运行，其新建 GitLab MR 必须由张三自己的 GitLab 账号创建；李四同理。** 任务分配给哪个智能体、运行在哪台机器，不得改变这个个人身份。

现有“设备自动登录”能区分客户端，但没有验证设备背后的员工。仅给设备 UID 增加一份 GitLab Token，不能满足这个目标。

讨论中认可了总体设计方向，但尚未确定部署路线、GitLab 版本、授权范围细节和旧账号归属清单。本文中的新菜单、按钮及状态是拟议设计，当前尚未实现。

## 2. 已有能力与本次新增目标

| GitHub 页对应功能 | 在研发场景中的用途 | 当前 GitLab 路径的调研结论 |
| --- | --- | --- |
| 平台连接 | 接收代码协作事件，建立任务与代码平台的联系 | 已有实例地址、Token、Webhook 接入；不使用 GitHub App |
| PR/MR 侧栏 | 从任务看到相关变更、状态并跳转到代码平台 | 已有统一侧栏；当前仍受 GitHub 侧栏/总开关影响 |
| 自动关联 | 将需求或 Bug 与具体代码改动联系起来 | 已按任务编号关联 MR |
| 合并后完成任务 | 减少人工遗漏状态更新 | 已有关闭关键字与多 PR/MR 聚合规则，不是“任意编号合并即完成” |
| CI 状态 | 从任务了解当前代码是否通过流水线 | 已有 GitLab 流水线摘要；复杂流水线和详情能力不等同于 GitHub |
| Co-authored-by | 在 commit 中标记智能体贡献 | 通用 Git 提交元数据，可用于 GitLab，不提供账号认证或 MR 作者证明 |
| 仓库登记 | 告诉智能体在哪个仓库开发 | 已支持通用 Git URL；登记 URL 不等于获得个人访问权限 |

以上来自源码调研与现有 VCS 适配器测试，不是对用户私有 GitLab 的端到端验证。讨论时截图显示集成加密密钥未成功加载；本轮没有配置服务器或连接 GitLab。

本次新工作重点是个人身份、授权和执行约束。现有集成、Webhook、任务关联及 CI 摘要应继续复用；菜单统一和高级 CI 作为后续改进保留。

## 3. 术语与身份边界

| 名称 | 作用 | 不代表什么 |
| --- | --- | --- |
| `MULTICA_VCS_SECRET_KEY` | 服务端加密保存凭据的部署级密钥 | 不是个人或机器人 GitLab Token，不代表任何 GitLab 用户 |
| 工作区 GitLab 连接 | 按工作区和实例保存接入信息、Token、Webhook secret | 不是每位成员的个人代码操作授权 |
| 设备 ID | 标识一个浏览器配置或桌面客户端 | 不能证明真实员工身份，也不是 GitLab 账号 |
| Multica 用户 ID | 现有用户、成员关系、任务和评论归属的内部主键 | 不能直接推导 GitLab 权限 |
| GitLab 身份登录 | 通过私有 GitLab 验证用户，并关联内部用户 | 登录成功本身不授予智能体代码操作权限 |
| 个人代码授权 | 本人允许在指定业务范围内使用其 GitLab 权限 | 不能被管理员的连接 Token 或别人的授权替代 |
| task / 一次运行 | 智能体的一次执行，归属于某个业务任务或对话 | 与业务任务（issue）不同；同一业务任务可能有多次运行 |
| MR 作者 / 操作人 | 作者是创建 MR 的 GitLab 用户；操作人是某次更新、评审、合并的用户 | 修改 commit 作者或后续操作 MR 都不会改变原 MR 作者 |

## 4. 目标用户与职责

| 角色 | 需要完成的事 |
| --- | --- |
| 部署管理员 | 配置可信 GitLab 实例、OAuth 应用/回调、服务端密钥；确认首次旧管理员身份认领和恢复路径 |
| 工作区 owner/admin | 管理工作区集成、仓库允许范围和成员权限；不能代替成员授予其个人 GitLab 权限 |
| 普通成员 | 使用自己的 GitLab 登录、授权、发起任务、查看执行身份并撤销自己的授权 |
| 智能体与运行时 | 在服务端确认的运行身份和权限范围内执行；不能自行选择其他账号或兜底凭据 |
| 自动化创建者 | 如需无人值守运行，另行明确授权自动化的项目、操作和期限 |

## 5. 需求范围

### 5.1 必须满足

| 编号 | 需求 |
| --- | --- |
| R01 | 提供私有 GitLab 真实身份登录，复用现有 `user`、成员、角色和历史关系；稳定身份使用实例及 GitLab 数字用户 ID |
| R02 | 登录与个人代码操作授权分开表达和管理；通过登录后可以使用工作区，未授予代码权限时不能替本人执行受保护的 Git/MR 操作 |
| R03 | 个人授权仅本人操作，显示明确账号、实例、授权状态和使用范围；工作区集成与个人授权数据分离 |
| R04 | 在产生个人 GitLab 操作前，固定本次运行的已验证发起人及授权范围；换智能体、换运行机、委派不能换人 |
| R05 | 拉取、缓存读取、推送和 MR 创建都必须满足个人与工作区权限交集；不能回落到机器所有者、机器人、共享 Token 或其他成员 |
| R06 | 支持多人并发；系统重试保留原主体，人工重新发起按本次已认证操作者处理；跨人评论不能改写进行中的个人授权 |
| R07 | 新建 MR 的真实 GitLab 作者必须与运行绑定的个人账号相同；本地页面不能仅靠姓名或 commit 信息宣称归属正确 |
| R08 | 李四接手张三已有 MR 时保留张三为原作者；若要求李四拥有新 MR，创建新的 MR 并保留历史关系 |
| R09 | 旧设备账号迁移需可信归属确认和本人登录证明；先保住可用管理员，再停用旧设备映射和旧凭据，防止旧会话借绑定升权 |
| R10 | 授权撤销、成员退出、权限收缩、Token 失效或账号不匹配时停止接纳新操作；保留结果与恢复入口，不偷偷换账号 |
| R11 | 创建 MR 遇到超时、断线、执行者崩溃或重复投递时进行结果核对，避免重复创建或假报成功 |
| R12 | 分离 Webhook 操作人与 MR 作者，其他人评审/合并不能改变本地展示的原作者 |
| R13 | 不同工作区、个人主体及不同运行的可变状态和凭据相互隔离；缓存不得绕过现有访问权限 |
| R14 | Web 和 Desktop 使用一致的身份、授权和任务语义，并处理旧客户端/旧 daemon 不具备能力的情况 |
| R15 | 保留现有 MR 状态、任务关联及 CI 摘要；集成中断、任务状态和代码授权状态有明确区分 |
| R16 | 只在用户明确恢复推动后进入实施；本文不是迁移、修改配置、调用个人账号或发布的授权 |

### 5.2 后续改进，不阻塞本次个人身份闭环

- 将 GitHub 专属连接设置与通用 PR/MR 侧栏、提交归因等设置分开。
- GitLab 仓库选择器、可合并性和更丰富的 CI/job 信息。
- 复杂流水线、merge train、历史数据补拉与共享只读对象缓存优化。

这些事项应保留在后续范围中，但不能用其完成情况代替 R01–R14 的身份保障。

### 5.3 不承诺的能力

- 通过设置 `git user.name/email` 或 Co-authored-by 改变 GitLab MR 创建者。
- 将已有 MR 的作者改成接手人。
- GitLab 与 Multica 全部任务、评审和审批的双向同步。
- 仅凭设备 UID、用户名或邮箱自动领取另一个内部账号。
- 在未验证隔离的共享宿主机 shell 中保证个人凭据不会串用。
- 撤回已经被 GitLab 接收或已准入发送的外部操作；此类操作需要对账。

## 6. 用户入口与使用流程

以下入口均是拟新增或扩展的产品设计。

| 使用者与动作 | 入口 | 发生时机 |
| --- | --- | --- |
| 成员登录 | Multica 登录页，按钮“使用公司 GitLab 登录” | 首次进入或会话失效时 |
| 成员管理个人授权 | 设置页左侧“我的账号”分组，新增“GitLab 账号”菜单 | 首次使用前，或以后查看、重新授权、撤销 |
| 成员在任务中补授权 | 任务发起/恢复入口，按钮“授权 GitLab 并继续” | 首次访问私有仓库前发现授权缺失，或授权需更新时 |
| 管理员管理平台连接 | 设置 → 工作区 → 集成，保留现有连接管理 | 部署与工作区接入时，不是成员个人授权入口 |

正常路径：GitLab 身份登录 → 返回 Multica → 按需授予代码操作权限 → 发起运行 → 展示本次执行账号 → 创建并核验 MR → Webhook 同步任务。

通过 GitLab 登录后，个人账号已绑定；“授权代码操作”只追加操作权限，不要求再建立一份账号绑定。登录与操作授权是两个目的，不意味着每次都要重复输入密码。

个人“GitLab 账号”页至少显示：实例、账号、身份验证状态、代码操作授权状态、授权使用范围、重新授权和撤销入口。不展示原始 Token。

首次任务缺少授权时保留需求/草稿，在第一次私有仓库访问前暂停。授权返回后核对同一已验证用户、实例和操作意图，再继续；取消授权不丢弃草稿，也不执行 GitLab 操作。

后续同一有效范围内直接使用已有授权；正常 Token 续期自动处理。撤销、不能续期、身份变化或扩大权限时提示重新授权。只有授权本人看到可操作的授权按钮，其他成员看到“等待某某授权”。

## 7. 关键业务场景

### 场景 A：张三与李四使用同一个智能体

张三和李四分别登录并授权。同一智能体接收两人的请求，产生两次独立授权运行。GitLab 上两个新 MR 分别显示张三和李四为作者，不能因为共用智能体或机器而都显示机器 owner。

### 场景 B：评论、重试与接手

张三的运行自动重试或调用子智能体，仍由张三授权。李四在同一任务下新增评论，不改写张三当前运行的主体；需要执行时形成李四自己的授权运行。李四手动重新发起也按新运行处理。

若更新的是张三已经创建的 MR，原作者仍是张三，后续操作人是李四。界面必须如实呈现，两者不混为一谈。

### 场景 C：授权失效或被撤销

停止接纳新的个人 GitLab 操作，保留本地产物和明确错误。本人重新授权后创建明确的新授权版本；不能借刷新回包复活已撤销的权限，不能用公共 Token 顶替。

已经准入发送的请求可能完成，系统需要显示在途/待核实状态和最终结果，不声称撤销能撤回远端事实。

### 场景 D：现有设备用户转为真人账号

由可信部署渠道核对旧管理员归属，本人完成 GitLab 登录。新登录及管理员权限验证成功后，再停用旧凭据。普通成员的旧身份同样需要受控认领，历史任务和评论的作者不批量重写。

### 场景 E：任务关联与研发“完成”

现有规则需要明确保留：标题/分支中的任务编号形成正式关联；正文只有普通引用属于参考关联。标题/正文的 `Closes/Fixes/Resolves MUL-123` 表达关闭意图。

至少一个带关闭意图的关联 PR/MR 已合并，且没有仍 open/draft 的正式关联 PR/MR 时，任务才会自动完成。该判断跨提供方聚合，不验证生产发布或业务验收。

团队究竟以“合并”“验收”还是“上线”作为完成节点尚未确认。本次不擅自改写现有状态流转；个人身份正确也不等于研发任务已经完成。

## 8. 验收结果

详细技术验收 AC1–AC19 见[设计文档](2026-09-13-gitlab-personal-mr-design.md)。业务验收至少包括：

| 场景 | 必须看到的结果 |
| --- | --- |
| 两个人并发创建 MR | GitLab 真实作者分别对应本人，Multica 展示一致 |
| 仅持有旧设备凭据 | 无法获得个人代码权限或借新绑定升权 |
| 同一人换设备登录 | 通过可信 GitLab 身份找到同一业务账号，不按新设备随意复制员工身份 |
| 系统重试与子任务 | 主体不变，不重复创建 MR |
| 另一成员接手 | 不串用原成员权限，不伪造原 MR 作者 |
| 撤销、过期、权限收缩 | 新操作停止；需重新授权时提示本人，结果可恢复、可核对 |
| 其他人评审或合并 | MR 原作者仍正确，操作人单独记录 |
| 原管理员迁移 | 新登录和权限可用，旧凭据失效，业务历史保留 |
| 多工作区与共享运行 | 不跨工作区或运行泄露代码、凭据、会话和可变状态 |

## 9. 已确认、建议与待确认事项

| 分类 | 内容 |
| --- | --- |
| 用户确认的目标 | 本人发起的新 MR 属于本人的真实 GitLab 账号；设备 ID 不足以授予个人权限；复用已有用户体系 |
| 已讨论的设计方向 | GitLab 身份登录与操作授权分开；个人菜单与任务内入口；冻结执行身份；作者核验；可审计迁移 |
| 条件推荐 | 个人独立环境采用 A；若选择多人共享服务器，推荐满足隔离要求的受控 Git/MR 执行方案 B |
| 当前状态 | 用户主动暂缓，只形成文档；没有实施、配置、部署或连接个人 GitLab |
| 启动前确认 | GitLab 版本/许可及可用 scope；A/B 部署与 OS；员工和旧 UID 映射；项目范围；研发完成节点；对账与授权有效期策略 |

A/B 尚未由用户作出选择，不能把 B 当成已确定的部署需求。目标环境无法证明隔离时，不开放相应个人执行模式。
