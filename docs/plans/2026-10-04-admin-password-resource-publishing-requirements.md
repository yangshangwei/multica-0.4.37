# 用户密码重置与资源发布：需求分析

状态：需求分析草案；未修改功能代码，未执行密码重置、上传或发布。本次依据当前工作区源码及已有方案核对，不等同于当前部署的功能验收。

## 结论：改哪里，是否新开页面

| 需求 | 已有能力 | 缺口 | 建议 |
| --- | --- | --- | --- |
| 给其他用户重置密码 | 账号详情内的“恢复密码”、临时密码、管理员密码复验、强制改密、会话/凭据撤销、审计与幂等 | 入口名称不直观、提示和错误反馈可加强 | 修改现有账号详情和操作面板；不新增独立密码管理页 |
| 从 Web 上传并发布 Skill | 部署目录、部署提供市场、工作空间上传/复制、两端动态发现 | 平台管理员上传、完整预检、目录写入、发布/更新/撤下管理 | 新增后台资源发布入口中的 Skill 页签；复用客户端 Skill 市场 |
| 从 Web 上传并发布 MCP | `<key>/mcp.json` 部署目录、版本校验、两端市场与配置/分配流程 | 后台目录发布 API、文件上传管理与写盘权限 | 同一后台资源发布入口的 MCP 页签；复用客户端 MCP 市场 |

建议导航：系统管理 → 资源发布 → Skill / MCP。上传和预览可使用抽屉或分步面板；客户端现有市场继续承担浏览、添加和分配。最终路由在实现设计时确定。

## 1. 目标和必要区分

目标是让平台管理员不必登录服务器手工拷贝文件，就能发布本部署可发现的资源。以下方案暂按“市场可见，由用户明确添加/配置/绑定”分析；是否需要自动下发/覆盖客户端，已单独向用户确认，尚未收到答案。

现有链路：

- Skill：部署模板 → 市场可见 → 复制为独立工作空间 Skill → 绑定智能体 → 新任务读取内容和附件。
- MCP：部署配方 → 市场可见 → 工作空间 owner/admin 填写参数并保存 → 明确分配智能体 → 智能体执行机器使用配置。

上传目录属于 **API 部署服务器**，不等于桌面电脑或智能体执行机器上的目录。市场发现、添加到工作空间、绑定智能体、安装运行依赖是四个不同步骤。

## 2. 密码重置：扩展现有功能

现有入口 `/admin/users` → 用户详情 `/admin/users/[id]` → 账号操作 → 恢复密码。已有接口 `POST /api/admin/users/{id}/recover-password`。

建议保留流程并优化：

1. 文案统一为“重置密码”，账号详情作为主入口；账号列表可增加进入该重置面板的快捷入口。
2. 明确区分“目标用户的临时密码”和“管理员自己的当前密码”；可增加确认输入、显示隐藏，以及受控生成/复制。
3. 必填操作原因；成功后说明临时密码需要人工交付，用户下次登录必须自行改密。
4. 显示不允许操作的原因，而非让管理员误以为功能不存在；区分用户名占用、格式错误、管理员密码错误和版本冲突。
5. 保留目标版本校验、幂等键、结果不确定时查询操作记录、密码不进入日志或审计正文。

现有权限/模式：密码模式下完整登录的 `super_admin` 可写；观察者/PAT/待改密会话不可写；该面板禁止重置自己；部署紧急禁用规则仍生效。普通禁用用户重置后仍禁用，不应暗中恢复账号。此能力不重置 Google/SSO/设备认证提供方的凭据。

**重要影响**：当前重置会使目标用户 Web/桌面会话失效，撤销 PAT、任务和 daemon 令牌，并取消其拥有运行时的相关任务、标记运行时离线、断开连接。成员关系、安装记录和历史保留。离线机器上的进程是否真正停止不能仅由令牌撤销证明。应在提交前清楚提示，并测试其他用户不受影响；不能把“不改桌面源码”说成“重置对桌面无影响”。

首期不建议另做永久密码替换、邮件/短信自动发送、批量重置或外部身份密码管理；这些需要单独确认。

## 3. Skill 发布需求

已有格式：`MULTICA_SKILL_TEMPLATE_DIR/<name>/SKILL.md`，可带支持文件；现有工作空间上传支持 `.skill`、`.zip` 和选择文件夹。

后台流程建议：选择包/文件夹（可评估单个 SKILL.md 快捷方式）→ 完整解析与校验 → 预览名称、说明、文件清单及冲突 → 发布 → 返回发布结果及市场入口。

首版应包括新增、明确更新和撤下：

- 仅管理部署提供内容，平台内置只读；同名冲突不可静默覆盖内置内容。
- 更新时核对管理员预览的内容指纹，防止覆盖另一管理员刚发布的版本；写入失败保持原有效内容。
- 暂存和历史文件不能被市场扫描为正式条目。
- 撤下停止后续发现/添加，保留已经复制到工作空间的 Skill 及其绑定。
- 现有部署模板 `version=0`，尚无可靠发布历史/自动升级模型。发布人、时间、管理版本/指纹及回滚历史属于新增管理能力，不能直接把现有字段当成已实现。

现有 importer 对非法/过大/二进制附件存在跳过行为；全局发布应完整预检，明确拒绝或列出不支持项，不能悄悄发布残缺包。首期建议支持当前运行链路可承载的文本说明/脚本附件；PNG、PDF及其他二进制资源若需要支持，必须核对并扩展存储和任务 bundle 契约。

## 4. MCP 发布需求

已有格式：`MULTICA_MCP_TEMPLATE_DIR/<key>/mcp.json`。首期建议只上传标准 manifest，标识单独填写/校验，提供示例下载；不上传或自动运行可执行程序。

预览名称、说明、类别、传输方式、运行前提、用户需填写的参数。复用现有严格校验器：stdio/Streamable HTTP、受限参数映射、内容版本哈希、未知字段/重复 JSON 键拒绝、默认 HTTPS 等。

- 凭据由各工作空间配置时填写，不能把管理员真实令牌写进公共 manifest。
- 身份继续采用 `(source, key)`；部署同名条目不覆盖内置条目。
- 更新/撤下只影响后续添加；已保存配置是独立快照，已有绑定不自动改变。
- stdio 依赖和命令必须在智能体执行机器可用；HTTP 服务须从该机器可达。上传 JSON 不会把二进制、Node/Python 依赖或脚本复制到每台桌面。

## 5. 发布存储是后端改造点

当前 Compose 将 Skill 与 MCP 模板目录都以 `:ro` 挂载。因此仅增加一个上传按钮无法完成需求。

建议新增明确启用的受控写入能力：由服务端固定发布根目录，使用持久化可写发布区，保留手工只读投放的兼容性。最终设计须确定单一有效目录或明确的读取合并/冲突规则，不能临时加一个上传目录却让市场继续读另一处。

发布接口不接受任意服务器绝对路径；只接受资源类型、合法标识和内容。复用平台管理鉴权并增加发布权限与审计，工作空间 owner/admin 不等于部署发布管理员。

必须保证文件路径受限、禁止符号链接逃逸/压缩穿越、限制压缩及解压后容量/数量、校验完成后原子替换、失败不破坏上一版。API 不执行上传脚本/命令或探测其中的外部服务。

多 API 实例需要共享/同步同一发布存储。当前目录的可见范围是同一部署的工作空间；若要按组织或工作空间区分资源可见性，需新增范围与授权模型，不能假定目前已有租户级目录隔离。

## 6. “直接看到”的可验收定义

现有两端市场在可见时每30秒刷新，重新进入、聚焦或重连也刷新；服务端目录内容每次请求扫描，不必为每次发布重启。

建议首期验收：发布成功后，手动刷新/重新进入立即读取；已打开且可见的市场在下一次约30秒轮询后显示（网络健康前提）。如果要求所有已打开窗口秒级同步，需要新增发布事件或失效通知，扩大共享层改动。

“无需每次发新版桌面”仅适用于已支持当前部署目录协议的客户端。MCP 的旧历史版本会过滤不认识的部署模板，首次启用仍需满足服务端、迁移512及客户端能力基线；不能承诺任意旧客户端都能自动识别。

## 7. 范围与建议拆分

| 工作包 | 范围 | 相对规模 |
| --- | --- | --- |
| A 密码重置体验 | 现有账号详情/操作表单、文案、错误提示、针对性回归 | 小 |
| B 后台资源发布基础 | 新后台入口、权限/API、上传暂存、目录持久化、预检/原子发布、审计 | 中到大，是主要工作量 |
| C Skill 接入 | 复用包解析并收紧全局发布预检、管理指纹、列表/发布/更新/撤下 | 中 |
| D MCP 接入 | 复用现有 manifest 校验、哈希/来源和消费市场 | 中偏小，依赖B |
| E 两端验收 | Web/真实Electron发现、添加/配置/绑定、旧版兼容、原有流程回归 | 中 |

建议先完成A，再做B并先接入格式较小的MCP，随后接入带多文件的Skill。无需重建两个客户端市场，也无需把每一项都做成独立全屏页面。

## 8. 验收场景

- 密码：非管理员拒绝；允许目标成功重置；旧登录失效；临时密码登录后强制改密；完成后恢复业务；其他用户会话不受影响；审计不含秘密；断网重试不重复重置。
- 发布：合法文件可预览并发布，非法文件不落入有效目录；只读/权限/空间不足有明确结果；同名、并发修改和发布中断不破坏旧版本。
- 消费：同部署Web和支持协议的Electron都能发现；Skill复制包含完整支持文件；MCP能配置并明确分配；没有自动执行或自动覆盖既有资源。
- 撤下：新用户不再添加，已有工作空间资源与绑定保留。
- 桌面：原有内置/自定义市场、登录与工作空间流程继续可用；不向个人 skill/MCP 配置目录隐式写文件。

## 9. 尚待确认的产品边界

1. 发布后只需市场可见、自行启用，还是自动下发/更新已有客户端资源？已发出澄清问题，当前方案按前者。
2. 密码重置是否接受现有“临时密码＋下次强制修改”？若要求永久密码或邮件链接，需改变范围。
3. Skill是否含二进制附件，MCP是否指连接manifest而非程序安装包？首期建议使用当前支持格式。
4. 发布覆盖本部署全部工作空间是否符合预期？是否存在多组织隔离、多API副本或必须秒级更新的要求？

这些是实现前需要确认/明确采用的边界，本草案尚不是自动安装或跨组织发布的执行授权。
