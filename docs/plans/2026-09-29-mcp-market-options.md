# MCP 市场方案对比

日期：2026-09-29  
状态：用户已选择 B 核心流程，随后补充 C 场景入口；运行时诊断、升级和开放目录继续后置  
依据：用户提供的 MCP 页面、当前 main 工作区代码、已有 MCP / skill / plugin 设计与实现  
方法：office-hours 产品方案探索；只读研究与文档输出

## 判断与推荐

建议把“可配置、可分配的 MCP 市场”作为目标，分两步交付：先完成精选目录与现有配置库的体验升级，再补来源身份、结构化配置和分配流程。

当前最有价值的结果是：用户能找到适合某个智能体的 MCP，完成必要配置，明确知道它是否已分配、是否启用、是否在目标运行时验证过。市场条目数量是后续扩展问题。

用户已明确第一版目标：“让用户更容易找到、配置并分配 MCP”。推荐围绕这条路径收敛。开放目录、第三方作者入驻、商业化需求尚未确认；没有用户研究数据证明它们应进入首版。所有新增能力均为提议，不代表当前已经支持。

## 当前实现：已有基础与明确缺口

| 方面 | 已实现 | 对市场设计的影响 |
| --- | --- | --- |
| 页面入口 | Web / Desktop 已有工作区 MCP 侧边栏入口，设置入口仍保留；共同使用 McpTab | 不需要先建设一个新入口；可在现有 MCP 页面升级 |
| 内置目录 | Chrome DevTools、Playwright、顺序思考，共 3 个无凭据 stdio 模板；后端内嵌、支持中英文 | 可以直接作为第一批精选内容；扩展显示信息无需立即建目录数据库 |
| 添加 | 点击模板预填已有表单，用户能改 command / args / JSON，再保存普通工作区配置 | 这不是受管理的软件包安装；按钮不应暗示已下载、启动或验证 |
| 工作区配置库 | 创建、重命名、替换完整配置、删除；管理受 owner/admin 权限限制 | 可复用现有 CRUD；配置实例应与市场条目分开 |
| 配置隐私 | 工作区列表只返回安全摘要，不返回已保存的 URL、命令、参数、headers、env | 新表单必须保留只写边界；不能为预览市场条目而读取工作区原始配置 |
| 配置存储 | 工作区 MCP 原配置存 JSONB；只写 API 不等于应用层加密。plugin 的 secret 使用独立存储机制 | 若扩大凭据型条目供给，需要明确工作区 MCP 凭据存储方案，不能把插件加密能力描述成现有 MCP 能力 |
| 智能体绑定 | 有独立的 agent_mcp_server 关系及逐智能体 enabled；添加到工作区不自动分配 | “添加到工作区”和“分配给智能体”仍是两个明确动作 |
| 生效时机 | 运行时在 task 领取 / 执行路径获取合并配置 | enabled 是配置状态，不是当前连接健康；修改也不能直接宣称正在运行的会话已更新 |
| 兼容性 | 有 MCP provider 支持名单和各 provider 的转换逻辑；不同传输支持仍有差异 | “支持 MCP”不等于“所有市场条目可运行”；应展示具体前提与验证状态 |
| 来源与版本 | 模板只有 key/title/description/config，保存后不记模板身份；已添加按名称判断 | 改名会失去目录关联；无法可靠提供多实例计数、升级或已验证版本 |
| 可复用 UI | skill 市场已有工作区/市场切换、搜索、分类、卡片、预览、空态与加载状态 | 复用交互和基础组件，不直接复用 skill 业务状态或把 MCP 塞进 skill 实体 |
| 插件基础 | 当前有工作区私有插件包、固定版本、配置与 secret、MCP broker、工具发现与审批 | 可参考底层机制，但插件的生效范围与工作区 MCP 的逐智能体分配不同，不能直接混用 |

历史边界：09-19 的预设需求明确只做无密钥模板，不做版本、来源、工具发现和连通性探测；Context7 曾按用户要求移除。那些是当时的范围选择，本轮可重新评估，但不能把它们写成现有能力。历史文档中的四语言等旧描述，以当前中英文实现为准。

## 三个方案

| 方案 | 产品定位 | 主要价值 | 工程规模 | 主要代价 |
| --- | --- | --- | --- | --- |
| A：精选模板市场 | 官方维护的 MCP 目录 | 容易发现、容易添加 | S，最小可行方案 | 仍主要解决预填配置，生命周期管理有限 |
| B：MCP 连接与分配中心 | 市场 + 工作区实例 + 智能体使用管理 | 从发现到可用形成完整流程 | M；含运行时诊断时升为 L | 要补身份、配置契约、状态和权限衔接 |
| C：从智能体出发的场景市场 | 先选智能体，再为它补充工具能力 | 更容易知道该选哪个、是否兼容、给谁使用 | M；自动化推荐另行评估 | 需要上下文和场景元数据，工作区整体发现能力较弱 |

规模为相对判断，包含必要测试与兼容处理，不是排期承诺。

### A：精选模板市场

页面改成“市场 / 工作区”两个视图。市场显示搜索、有效分类和卡片；工作区保留当前配置列表及管理动作。成功加载且工作区为空时默认市场，有实例时默认工作区，用户显式选择优先。请求失败不能被当作工作区为空。

卡片展示名称、一句话用途、内容来源、是否需要授权、运行前提。详情补官方文档与示例用途；“添加到工作区”继续打开现有预填表单。保存成功后提供“前往智能体分配”的明确入口。成员可浏览目录，写入动作按权限控制，这比当前仅管理员看到内置目录更适合发现体验。

首批仍用现有 3 条；不为凑出热闹页面填充虚假热门榜、下载量或评分。分类只展示实际有内容的项。浏览器类说明依赖智能体运行时中的 npx 和浏览器，不能让用户误以为在打开网页的电脑上启动。

工程上扩展内嵌模板展示元数据，沿用现有模板接口、配置弹窗与工作区创建接口，首版可不加数据库迁移。借用 skill 市场的交互模式，保持 Web / Desktop 共用视图。

限制：仍无可靠来源关联和版本管理。若保持现有名称判定，文案宜表达“工作区已有同名配置”，不能标成精确的“已安装此版本”。可先在保存成功后链接到刚创建的实例；改名后的跨会话关联不在 A 中承诺。

适合：希望尽快把截图里的设置型界面升级成可浏览市场，首批继续以无凭据模板为主。

### B：MCP 连接与分配中心（推荐目标）

在 A 的发现体验基础上，建立明确的三层关系：

```mermaid
flowchart LR
  A[市场条目：用途、来源、配方版本] -->|配置并添加| B[工作区实例：名称、私有配置]
  B -->|显式选择智能体| C[智能体绑定：启用或停用]
  C -->|目标运行时执行| D[运行结果与最近验证记录]
```

用户路径：浏览详情 → 填必填项 → 保存到工作区 → 选择有权配置的智能体 → 明确启用状态。保存和分配分步骤提交；分配失败时保留已保存实例，允许重试，不产生第二个实例，也不错误显示全部完成。

服务端当前允许人类 agent owner 或工作区 owner/admin 管理绑定；工作区配置写入仅限人类 owner/admin。新向导以这两个权限边界分别控制保存与分配，不能仅依据“能管理工作区配置”推断任意操作可用，也不能允许 agent actor 借新入口自行授权。

“添加到工作区”不是自动批量授权。添加成功后可以跳过分配；不应预选所有智能体。前端和后端要对齐已有分配授权，服务端始终是权限真相。无权分配的目标只读或不提供操作，不把新审批系统塞进本版。

**需要补的核心契约：**

1. 稳定身份：市场条目 ID 独立于实例名称；一个条目可创建多个实例，例如不同账号或环境。前提是现有工作区实例名称唯一性仍成立。
2. 可信来源：由后端按条目 ID 与版本解析安装配方，只允许填写声明的参数。开放 JSON 任意编辑时必须标为“自定义配置”，不能继续声称与已审核版本一致。历史实例保持“自定义/来源未知”，不按名称自动认领。
3. 版本语义：目录配方版本和上游程序版本分别记录。若标为已验证版本，就要固定包版本；当前模板中的 @latest 与未固定版本不足以支撑该承诺。升级需用户明确执行，不能在目录更新时静默重写工作区配置。
4. 结构化输入：用 input schema 描述 token、URL、路径、必填规则及说明，用户优先填写业务参数；高级 JSON 作为自定义入口。市场只能包含字段描述，不能包含用户凭据。
5. 安全摘要：服务端可新增“已配置 / 待补充”这类字段级摘要，但不回传原值。需要设计保留已有 secret、替换 secret 的明确语义，不能靠把掩码再提交当作密钥更新。
6. 状态分层：工作区显示实例数；实例显示分配对象及配置摘要；绑定显示启用/停用；诊断显示目标运行时、检查时间与成功/失败/未验证。不要用一个“已连接”混合这些含义。
7. 配置冲突：已有合并优先级允许 agent 自有配置或任务 overlay 覆盖同名工作区配置。绑定存在不等于该配置最终生效；分配时检测可知冲突，摘要以不泄露配置的方式提示来源优先级，运行时验证记录最终生效来源。

**诊断是单独的后续增量：**

- stdio 检查必须在所选智能体的目标运行环境执行，验证命令依赖、启动和 MCP 握手；Web 后端自身启动成功没有代表性。
- 远程连接也应验证实际执行路径的访问能力；拿到工具列表与某个工具成功完成业务操作是不同证据。
- 浏览详情绝不触发命令执行；用户点“验证连接”才发起受限检查。结果需要超时、日志脱敏和检查时间，不能永久展示绿灯。
- 复用已有 provider 支持判断；进一步细化 transport、系统和依赖支持。未知应显示“未验证”，不能乐观推断为兼容。
- 暂不承诺运行中会话热更新；清楚说明后续执行生效，已有会话按既有行为处理。

首版可支持无凭据模板及显式参数输入；带密钥条目要在结构化输入和凭据更新契约完成后再上架。OAuth 是独立接入项目，不因为仓库存在 helper 就当作可用安装流程。

适合：希望用户添加之后真的能给智能体用，并且能查明“配了却没生效”的原因。它最贴近 Multica 以智能体为任务负责人的产品定位。

### C：从智能体出发的场景市场

从“智能体详情 → MCP → 添加工具”进入，页面始终显示当前智能体和运行时。先展示工作区已配置、可分配的实例，再展示可新建的市场条目。已经有实例时直接复用，避免每个智能体都重复填写同一份配置。

发现方式以用途为主：例如“浏览器验收”展示 Playwright / Chrome DevTools 并说明各自用途，让用户选择；“规划与多步推理”展示顺序思考。初版用产品维护的场景标签和确定性规则，不增加推荐模型，不自动同时装上所有候选项。

用户路径：选择智能体 → 查看适合它的 MCP → 复用工作区实例，或填写参数创建实例 → 确认分配给当前智能体。运行时不支持的条目解释原因；缺少验证资料的条目标记“未验证”，不能静默过滤成无结果。

已有 agent owner 分配权限可复用；但 agent owner 未必有工作区创建权限。无创建权限时可以分配已有实例，新建入口说明由工作区 owner/admin 配置，不设计绕过权限的个人实例，也不承诺当前不存在的申请审批工作流。已经分配时显示管理动作，不重复创建绑定。

工程上复用 B 的实例与绑定分层，额外增加智能体上下文、场景标签、运行前提展示和兼容性筛选。若尚未引入可靠来源身份，则只按真实实例列表提供复用，不用模板名称猜测关联。实例信息只能是已有授权范围内的安全摘要。

优点是用户不用记住后续要分配给谁，更符合“给某个智能体补能力”的实际操作。缺点是用户需要先拥有并选择智能体；团队管理员横向管理所有连接仍需工作区 MCP 页。场景维护也会有持续成本。

适合：用户已经习惯从智能体详情出发，主要困难是“不知道给它配什么”。可以独立选择这种主入口，也可以在 B 完成后作为补充入口；两者共用配置流程和底层数据。

## 暂不进入首版的扩展

外部目录聚合、团队私有目录、公开作者投稿、评分、收费和统一 MCP / skill / plugin 能力市场均后置。它们不直接解决本次已确认的“找到、配置、分配”流程问题。本文没有选择或验证外部 registry 的具体接口、条款与可用性。

如果以后接外部目录，需要独立定义来源身份、安装配方转换、版本快照、下架处理与验证标准。发现条目不能直接等同于可执行安装；上游下架也不能默认删除用户配置。

插件复用边界：当前 plugin 有私有包、版本和 MCP 工具审批，但按已启用安装与 agent trigger 等条件进入执行上下文，与 workspace MCP 的显式 agent 绑定不同，不能直接合成一个“已安装”状态。

OAuth 现状：旧 remote MCP OAuth 持久化表已在 plugin v2 reset 中删除；仓库保留底层 OAuth helper，但当前非测试代码没有调用链。新市场若需要 OAuth，要重新定义连接归属、刷新、撤销、绑定和审计，再决定复用哪些低层代码。

## 推荐交付顺序

1. **发现体验（A）**：沿用现有 MCP 入口，增加“市场 / 工作区”、卡片、详情、搜索和添加后分配引导；现有 3 个模板作为真实内容。无需连带改插件系统。
2. **管理闭环（B 的主体）**：补稳定来源、多实例关系、服务端解析配方、结构化配置及明确的分配步骤。把“已有同名配置”升级为可靠的实例关联。旧实例不自动归类。
3. **可用性反馈（B 的诊断增量）**：目标运行时检查、最近失败原因、版本固定与显式升级。完成这一步后，才有依据宣传“已验证可用”。
4. **场景入口（C）**：验证用户是否主要从智能体出发，再把同一套目录与配置流程接入智能体详情。精选内容按实际需求扩充；外部供给体系另行评估。

页面建议：顶部仅保留一句“为智能体添加可调用的工具”。市场卡片回答“能做什么、需要什么、如何添加”；敏感配置只写规则放在配置动作附近；工作区列表承接实例管理。桌面宽屏用多列卡片，窄屏单列，详情不挤压当前已有列表。

## 验收与风险边界

- 现有模板仍能保存，手动 stdio / HTTP 和高级 JSON 路径保持可用；SSE / 未知 transport 不被表单静默改写。
- 添加成功默认不自动分配；分配、启停、撤销和删除均由服务端校验权限，并正确处理部分失败。
- 普通成员能够浏览市场，不能因此获得创建实例或配置他人智能体的权限。
- 目录失败、列表失败与空列表可区分，现有工作区配置仍可管理；旧 Desktop 与新后端、反向版本组合有合理降级。
- B 中重命名不丢失关联；同条目多实例可区分；自定义配置不冒用官方配方身份。
- 配置原值不出现在摘要、日志或诊断结果中；“保存”“启用”“验证成功”分别有不同证据。
- 浏览器、本地路径和外网访问能力按执行环境说明，不能把用户浏览器机器与智能体运行时混为一谈。
- 前端继续遵守 core 的数据/状态、views 的业务视图、ui 的基础组件边界；Web 与 Desktop 共用，Mobile 另行界定。
- 如需要迁移，不引入外键/级联；索引按仓库要求独立使用 CONCURRENTLY migration。

可观察指标：详情到成功创建的完成率、创建到首次分配的完成率、首次验证成功率、失败类别及完成用时。当前未测量基线，不能给出虚构的提升百分比。

下一步应先定下 B 的首批条目及其输入要求，并用现有 Playwright 条目走一遍“发现 → 添加 → 分配”的原型流程；以三个实际问题验证设计：是否理解在哪里运行、是否知道授予哪个智能体、失败后是否知道下一步。
