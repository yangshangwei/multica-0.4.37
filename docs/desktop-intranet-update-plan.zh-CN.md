# Multica 桌面端内网升级方案

记录日期：2026-09-24。

日常部署和升级操作参见[桌面端内网部署与升级操作手册](desktop-intranet-update-runbook.zh-CN.md)。

本文记录桌面端内网升级的现状分析、方案选择、部署与发布流程，以及实施和验收要求。2026-09-24 已实现本机 Nginx 下载存储、产物校验发布和离线元数据收集，操作见[本机桌面更新下载服务](desktop-updates-local.zh-CN.md)。本机 HTTP 验证已完成，实际内网终端的安装升级仍待验收。示例域名、路径和版本号需要替换为部署环境的实际值。

## 1. 目标与前提

需要支持两种使用方式：

1. 用户在桌面端点击检查更新，下载并安装新版本。
2. 管理员发布新版本后，桌面端定期发现更新，下载后提示用户安装。

部署有两个明确前提：

- 开发和构建环境可以访问互联网，但产品实际运行在无法访问互联网的内网。
- 桌面端安装包由管理员手工传入内网，不依赖内网服务器从 GitHub 或其他公网服务拉取。

推荐方案是：**复用现有 `electron-updater`，将完整发布文件手工导入内网，通过固定 HTTP/HTTPS 静态目录提供更新。**

客户端已经具备更新检查、自动下载、安装入口和自定义更新源。第一阶段的主要工作是补齐离线交付文件、配置静态服务和客户端，并完成真实升级验收。

本文讨论桌面程序自身的更新。服务端镜像升级、数据库迁移和独立安装的 CLI 升级仍按各自流程执行，参见[服务端离线升级操作文档](offline-upgrade.zh-CN.md)。

## 3. 方案选择

| 方案 | 工作量与使用方式 | 适用判断 |
| --- | --- | --- |
| 管理员分发安装包，用户覆盖安装 | 部署工作最少，但每次升级都需要用户操作安装器 | 保留为首次安装和故障恢复入口 |
| 内网静态更新目录 + 现有更新器 | 复用现有客户端能力，管理员手工发布文件，客户端检查、下载和安装 | **第一阶段推荐** |
| 自建发布管理服务 | 增加版本管理、上传、审批、实时通知、分批发布等能力 | 有明确管理需求后再建设 |

第一阶段使用一个稳定发布通道，先覆盖内网主要使用的平台和架构。无需新增业务数据库表、发布管理页面、上传 API 或桌面更新 WebSocket 事件。

如果内网主要使用 Windows x64，可以先验收这一组合，再扩展其他平台。当前没有用户终端分布信息，Windows x64 只是示例，不是已经确定的部署范围。

## 4. 更新链路与职责

```mermaid
flowchart LR
    A["联网构建环境<br/>生成完整发布文件"] -->|"管理员手工转入内网"| B["内网待发布目录<br/>核对文件与校验值"]
    B -->|"先发布产物，最后切换元数据"| C["固定 HTTP/HTTPS 更新目录"]
    C -->|"客户端手动或定期检查"| D["发现版本并下载"]
    D --> E["提示用户重启安装"]
```

| 角色 | 职责 |
| --- | --- |
| 构建环境 | 生成安装包、更新元数据和辅助文件；完成需要联网的签名、公证等步骤 |
| 管理员 | 转入内网、验证文件完整性、发布产物、切换元数据、保留历史版本 |
| 静态文件服务 | 稳定提供元数据、安装包与辅助文件，支持正常下载和 Range 请求 |
| 桌面客户端 | 根据版本和平台检查更新，下载、校验并调用安装流程 |
| 业务服务端 | 继续提供业务 API；第一阶段不承担安装包分发逻辑 |

更新服务可以与业务服务部署在同一台内网服务器，也可以独立部署。更新下载请求由 Electron 主进程发出，不应假定它会自动携带用户在业务页面中的登录状态。

## 5. 发布文件与目录约定

### 5.1 固定更新目录

示例更新地址：

```text
https://updates.company.internal/desktop/
```

示例服务器目录，Windows x64：

```text
/srv/multica/desktop-updates/
├── latest.yml
├── multica-desktop-0.5.0-windows-x64.exe
├── multica-desktop-0.5.0-windows-x64.exe.blockmap
├── multica-desktop-0.5.1-windows-x64.exe
└── multica-desktop-0.5.1-windows-x64.exe.blockmap
```

`latest.yml` 指向当前对客户端开放的版本。安装包使用带版本号的原始文件名，保留旧版本，避免同名文件内容在下载过程中被替换。

`updateUrl` 应指向包含元数据的目录，不是某一个安装包，也不是带 HTML 下载按钮的网页。只把文件放进共享盘还不够，需要通过 HTTP/HTTPS 提供。

### 5.2 各平台元数据

以下是当前稳定通道的命名约定。实际发布必须以本次构建生成的元数据和其中引用的文件为准。

| 平台与架构 | 元数据文件 | 需要交付的主要产物 |
| --- | --- | --- |
| Windows x64 | `latest.yml` | 对应 `.exe` 与 `.exe.blockmap` |
| Windows ia32，32 位 | `latest-ia32.yml` | 对应 `.exe` 与 `.exe.blockmap` |
| Windows ARM64 | `latest-arm64.yml` | 对应 `.exe` 与 `.exe.blockmap` |
| macOS Apple Silicon | `latest-mac.yml` | 对应 `.zip`、生成的 blockmap，以及用于首次安装的 `.dmg` |
| macOS Intel | `latest-x64-mac.yml` | 对应 `.zip`、生成的 blockmap，以及用于首次安装的 `.dmg` |
| Linux x64 | `latest-linux.yml` | 本次构建的 AppImage/deb/rpm 中实际分发的包及元数据引用文件 |
| Linux ARM64 | `latest-linux-arm64.yml` | 本次构建的对应架构包及元数据引用文件 |

macOS 自动更新需要 ZIP，只有 DMG 不足以组成完整的自动更新源。Linux 不同包格式的安装权限和行为不同，支持构建某种格式不代表已经验收该格式的更新链路。

发布时遵守以下规则：

- 使用打包工具生成的 YAML，不手工拼装版本号、文件名或 `sha512`。
- 保持产物原始名称；检查元数据引用的每个文件都能从内网访问，不包含意外的公网下载地址。
- 不将其他架构的元数据重命名为 `latest.yml`。
- 保留生成的 blockmap；旧版本 blockmap 有利于差量下载，但不保证每次都只下载差异，客户端可能回退到完整下载。
- `app-update.yml` 是安装包内部配置，不是服务器端的 `latest*.yml`，两者不能互相替代。
- 多架构构建可能将产物放在 `dist/<平台>-<架构>/`，收集时必须检查实际输出目录。

## 6. 内网静态服务部署

优先复用已有内网 Nginx、Caddy 或 IIS。若尚未部署这些服务，需要通过现有离线软件或镜像交付流程准备，不能让内网服务器临时从公网拉取依赖。

基础要求：

- 客户端能够解析域名并访问下载地址。
- 文件请求直接返回文件，不跳转到浏览器 SSO 登录页。
- 更新目录由发布人员写入，静态服务和客户端只读。
- 元数据不设置长时间不可失效的缓存。
- 支持大文件下载和 HTTP Range 请求，验证反向代理不会截断下载。
- 使用 HTTPS 时，客户端需要信任证书链；完全隔离的服务器不依赖公网自动签发证书。

现有 `updateUrl` 只接受 HTTP/HTTPS，不允许 URL 内包含用户名和密码，查询参数与片段也会被规范化清除。因此第一版不采用 URL token 或浏览器登录态保护下载；需要认证下载时，应单独设计主进程认证机制。

以下 Nginx 片段可以放入已配置域名和受信任 TLS 证书的 `server` 块。它只是配置示例，不是仓库已经部署的服务：

```nginx
location ^~ /desktop/ {
    alias /srv/multica/desktop-updates/;
    autoindex off;
    add_header Cache-Control "no-cache" always;
}
```

这里对整个目录使用 `no-cache`，先保证发布行为简单可预测；后续可以对不可变的带版本文件单独优化缓存。`no-cache` 允许缓存，但要求使用前重新验证。

配置好后，从实际客户端网络检查元数据和部分文件下载：

```bash
curl -fsS https://updates.company.internal/desktop/latest.yml

curl -sS -D - -o /dev/null \
  -H 'Range: bytes=0-1023' \
  https://updates.company.internal/desktop/multica-desktop-0.5.1-windows-x64.exe
```

第二条请求预期返回 `206 Partial Content` 和正确的 `Content-Range`。如果证书验证失败，应修复内网证书信任，不把跳过 TLS 校验作为客户端部署方案。

## 7. 客户端配置与首次接入

### 7.1 配置位置

| 系统 | 默认路径 |
| --- | --- |
| Windows | `%USERPROFILE%\.multica\desktop.json` |
| macOS | `~/.multica/desktop.json` |
| Linux | `~/.multica/desktop.json` |

真实路径由 Electron 的用户主目录决定；用户目录被重定向时需要使用实际位置。该配置是按用户读取的，不是机器上所有账户共享的一份配置。

在已有 JSON 中保留业务地址，新增 `updateUrl`：

```json
{
  "schemaVersion": 1,
  "apiUrl": "https://api.company.internal",
  "appUrl": "https://multica.company.internal",
  "updateUrl": "https://updates.company.internal/desktop"
}
```

`apiUrl` 是业务 API 地址，`appUrl` 是 Web 地址，`updateUrl` 是桌面更新目录。已有 `wsUrl` 或其他有效配置时一并保留。配置文件不是 CLI 使用的 `~/.multica/config.json`。

更新源在主进程启动时配置。修改文件后必须完整退出并重启 Desktop，仅关闭窗口、刷新页面或重新登录不能视为更新源已经切换。

Windows 上确认文件名不是 `desktop.json.txt`，并使用 UTF-8 保存。批量下发时应合并已有配置，避免覆盖用户已有的业务服务地址。

### 7.2 首次接入路径

| 客户端状态 | 接入方式 |
| --- | --- |
| 已安装版本包含 `updateUrl` 能力 | 下发或修改配置，完整重启后检查更新 |
| 已安装版本尚不支持 `updateUrl` | 先手工覆盖安装一次支持内网源的版本，再配置后续更新 |
| 尚未安装 | 管理员提供对应平台安装包，完成业务地址和更新地址配置 |

不能仅根据当前源码判断用户电脑里的旧安装包是否支持内网源，应使用实际版本核对或试验。

## 8. 每次发布的操作流程

### 8.1 构建正式版本

在具备对应平台构建条件的联网环境中，显式指定递增的稳定版本。以下是在 Bash/zsh 中构建 Windows x64 的示例：

```bash
MULTICA_DESKTOP_VERSION=0.5.1 \
  pnpm --filter @multica/desktop package -- --win --x64 --publish never
```

`--publish never` 表示不上传到公网发布服务；在当前打包配置下，仍应收集本地产生的更新元数据。每次构建都要确认实际输出，不以命令成功替代产物检查。

版本默认也可从 Git 标签推导，但独立内网发布宜显式核对最终写入应用和 YAML 的版本。不要直接将 `-dirty`、`-selective` 等测试版本作为稳定通道发布；预发布版本可能影响版本比较和通道选择。

打包脚本会清理 `apps/desktop/dist`。分多次构建不同架构时，每次构建完成后先归档产物，避免下一次构建清理前一次结果。

如果使用 `scripts/offline-installer.sh` 打包服务端和桌面端，应明确设置稳定的 `VERSION`。脚本已收集更新元数据并支持 `win-ia32`；测试用预发布版本需要显式加 `--allow-prerelease`，否则在构建开始前拒绝执行。

### 8.2 整理和转入内网

1. 收集所支持平台的安装包、ZIP、blockmap 和全部对应更新元数据。
2. 检查版本、架构、原始文件名、文件大小和元数据引用。
3. 为离线交付归档生成校验清单；其作用是验证人工传输完整性，不能替代系统代码签名。
4. 将归档和校验清单手工转入内网待发布目录。
5. 在内网复核校验值，再进入在线目录发布步骤。

### 8.3 发布到更新目录

1. 保留当前正式版本的元数据备份和历史安装包。
2. 将新版本产物先复制为临时文件，完整传入后改为最终的带版本文件名。
3. 确认元数据引用的所有产物已经完整可下载。
4. 将新元数据写入同一文件系统的临时文件，最后通过重命名替换正式 `latest*.yml`。
5. 如果代理缓存了元数据，使其重新验证或失效。
6. 从一台安装旧版本的试点客户端检查更新并完成安装。

**发布顺序是先产物，后元数据。** 不要让正式元数据指向尚未传完的安装包，也不要对在线 YAML 直接逐行修改。

各平台的元数据可分别切换，但每个文件必须始终指向完整可下载的同一版本产物。若要求所有平台同一时刻开放，需要额外的发布协调，第一版不默认提供这个保证。

### 8.4 客户端发现与安装

自动更新开启时，运行中的客户端按现有周期检查；在客户端保持运行、网络正常且没有休眠的前提下，通常在下一个检查周期发现版本。用户也可在设置中立即检查。

发现可用版本后后台下载，下载完成后提示重启安装。不要将这一流程描述为管理员强制重启所有客户端。客户端内置守护进程可能正在执行任务，重启对任务的影响需要实机验证，更新安排应留出用户处理工作的时间。

### 8.5 发布后的留存

保留构建版本、源码提交、发布平台、发布时间、产物校验清单和试点验收结果。不要立即删除旧安装包及 blockmap，也不要在发出更新后覆盖相同版本号的文件内容。

## 9. 平台差异与失败处理

### 9.1 平台约束

- **Windows：** 当前 CI 对 Windows 未启用代码签名，需要在实际终端策略下验证下载、安装、权限提升和重启行为。不能将开发机可以运行视为企业终端一定允许安装。
- **macOS：** 自动更新需要符合系统要求的代码签名。用于正式分发的签名、公证和票据装订应在联网构建阶段完成，并在断网机器上验收。离线组合脚本默认关闭签名身份自动发现，不能直接把默认本地构建当作已具备正式更新条件的产物。
- **Linux：** 按实际使用的 AppImage、deb 或 rpm 分别验证可写路径、权限提升和包管理器行为。第一阶段只承诺通过实机验收的格式。
- **客户端与后端：** 桌面升级和服务端升级是独立操作。发布前核对新旧客户端与目标后端的兼容性，并按变更需要安排升级顺序。

### 9.2 常见失败与处理方向

| 现象 | 优先检查 | 处理方向 |
| --- | --- | --- |
| 检查更新报 404 | `updateUrl` 是否指向目录、架构对应 YAML 是否存在 | 修正目录或补齐正确元数据 |
| 一直提示最新版本 | 当前版本、发布版本、预发布通道、元数据缓存 | 核对版本与通道，检查客户端实际请求 |
| 仍然访问 GitHub | 实际用户目录、配置字段、客户端版本、是否完整重启 | 确认支持内网源的客户端已加载配置 |
| 下载到登录页面 | SSO 或反向代理对静态目录的拦截 | 为更新器提供可直接读取的内网文件地址 |
| 下载校验失败 | 文件传输完整性、同名文件是否被覆盖、YAML 与安装包是否配套 | 重新发布一致的完整产物 |
| 下载成功但安装失败 | 签名、系统策略、目录权限、包格式与架构 | 在对应平台修复后重新验收，必要时覆盖安装 |
| 配置无效 | JSON 格式、编码、文件名、URL 格式 | 修正配置并完整重启 |

当前手动检查能够返回检查错误；后台下载错误主要记录在主进程日志中。清晰的下载失败提示和重试入口可以作为后续体验补充，不能视为当前已经完整提供。

### 9.3 撤回与恢复

停止提供坏版本的元数据，只能影响尚未检查到该版本的客户端，不能撤销已经下载或安装的更新。

发现问题时，先停止继续分发该版本并保留记录。已更新客户端优先通过发布更高版本号的修复版恢复，必要时采用受控的手工覆盖安装。第一阶段不承诺自动降级或自动回滚。

Windows ARM64 已在设置 `channel` 后显式恢复 `allowDowngrade = false`，与 Windows ia32 和 macOS x64 保持一致，并新增三种架构的回归测试。已安装的旧版本仍需按实际行为核对，源码修复不会自动改变旧客户端。

## 11. 验收标准

使用两个稳定版本 A 和 B，且 B 的版本高于 A。测试机器必须安装真实打包版本 A；开发模式会使用不同的配置路径和更新行为，不能替代正式安装验收。

| 场景 | 验收要求 |
| --- | --- |
| 首次接入 | 已安装版本加载内网 `updateUrl`；不支持该字段的旧版有明确的覆盖安装路径 |
| 手动升级 | 点击检查后发现 B，下载成功，重启后显示 B |
| 自动升级发现 | 开启自动更新后，在启动检查或正常运行的定时检查中发现 B |
| 关闭自动检查 | 完整重启后仍保留关闭状态，没有后续自动检查；手动检查仍可工作 |
| 下载后安装 | 立即重启安装与正常退出安装分别验收；关闭窗口与退出应用按实际平台区分 |
| 保留用户状态 | 业务服务器地址、更新源、更新偏好、登录状态和必要的本地配置符合产品预期 |
| 架构与包格式 | 每个计划支持的平台、架构、包格式都升级到对应产物 |
| 内网隔离 | 阻断公网后更新仍成功；更新元数据和产物请求均走内网，无公网重定向依赖 |
| 发布一致性 | 产物未发布完整时不切换正式 YAML；切换后不存在缺失引用 |
| 传输与故障 | 地址不可达、元数据缺失、文件损坏或中断下载时，旧版仍可启动并有可定位的错误信息 |
| 任务与兼容性 | 重启对本地执行任务的影响已确认；新客户端与目标后端能够正常协作 |
| 恢复 | 发布更高版本修复版或手工覆盖安装的恢复路径可执行，不假设自动降级 |

这里的公网隔离验收针对桌面更新链路，不表示整个产品及所有智能体依赖都已经完成离线能力审计。
