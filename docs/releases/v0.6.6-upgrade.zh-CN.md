# Multica v0.6.6 内网交付与升级说明

本次基于 main 已提交源码 `4797e6d971296e56f3edc4f6cb6d3f218d9f8d85` 制作 Linux amd64 服务端离线升级包和 Windows x64 桌面安装包，版本均为 `0.6.6`。交付目录为 `dist/release/v0.6.6/`。源码固定于本次发布计划确认时，构建使用独立工作树。

先升级服务端和 Web，核对健康、登录及原有数据，再升级桌面端。普通升级保留现有认证模式、账号和密钥；不会自动启用平台管理。本次为本地内网交付，v0.6.6 尚未因此发布为 GitHub Release。累计变更说明保留已发布的 v0.6.5 记录，本次提交变化标记为 `Unreleased`。

## 3. ENV 与宿主机检查

从 v0.6.5 升级，无需手工增删 `.env` 项。保留 `JWT_SECRET`、数据库账号密码、集成密钥、固定 `MULTICA_DEPLOYMENT_ID`、认证模式、URL、端口和现有覆盖文件。不要把 `.env.example` 覆盖到 `.env`，不要 `source .env`。

升级脚本会更新 `MULTICA_BACKEND_IMAGE`、`MULTICA_WEB_IMAGE`、`MULTICA_IMAGE_TAG`、`CHANGELOG_FILE` 和 `CHANGELOG_DIRECTORY`，使后续维护继续使用正确镜像。已有主 Compose 定制应转移到持久覆盖文件；升级和后续命令必须按原顺序提供全部 `--compose-file`。

隔离内网继续保留各系统的 `MULTICA_CLI_INSTALL_COMMAND_WINDOWS` / `_MACOS` / `_LINUX`。这些是公开安装命令，不能包含令牌、密码或带凭据 URL。桌面 `updateUrl` 与业务服务器配置分开管理。

首次初始化平台管理员时，部署目录所在 Linux 内核和文件系统必须支持 `renameat2(RENAME_NOREPLACE)`（主线内核 3.15 起）。这是宿主机要求，不由容器镜像提供。不支持时初始化返回 `credentials_file_publish_failed`，服务可能已经升级，但整次升级不会报告成功。保留现场，调整到支持的文件系统后单独重试初始化工具。

## 4. Linux 离线升级

目标机需 Docker、Docker Compose、Bash、curl 和 SHA-256 校验工具。安排维护窗口，停止业务和智能体写入，备份部署配置、数据库及 `backend_uploads`；已启用的资源卷、Skill/MCP 目录和外部对象存储也要备份。保留旧镜像。

在交付文件目录执行，部署路径按实际情况替换：

```bash
sha256sum -c multica-server-upgrade-v0.6.6-linux-amd64.tar.gz.sha256
mkdir -p /opt/multica-upgrade-v0.6.6
tar -xzf multica-server-upgrade-v0.6.6-linux-amd64.tar.gz \
  -C /opt/multica-upgrade-v0.6.6 --strip-components=1
cd /opt/multica-upgrade-v0.6.6
bash offline-upgrade.sh --deployment-dir /opt/multica
```

已有覆盖文件时，在最后一条命令追加原有列表，例如 `--compose-file docker-compose.local.yml`。脚本导入镜像、备份、安装配置和变更说明，重建容器并检查 `/healthz`，最后按条件初始化管理员。只有已核对的自动化流程才追加 `--yes`。

不要执行 `docker compose down -v`。数据库迁移由后端镜像入口运行，直接执行 `server` 二进制不会自动迁移。仅更新 Windows 安装包也不会更新服务器。

## 5. 账号与认证保留

| 现有部署 | 沿用配置 |
| --- | --- |
| 设备自动登录 | `MULTICA_AUTH_MODE=legacy`、`MULTICA_DEVICE_AUTH_ENABLED=true`、`MULTICA_CLOUD_URL=`；平台管理和受管安装保持关闭 |
| 密码登录，单 API | `MULTICA_AUTH_MODE=password`、`MULTICA_DEVICE_AUTH_ENABLED=false`、`MULTICA_PASSWORD_LIMITER_MODE=single`、`MULTICA_CLOUD_URL=` |
| 密码登录，多 API | 同样关闭设备认证和 Cloud，限流使用 `shared`，全部副本连接同一个 `REDIS_URL` |

保留原 `ALLOW_SIGNUP` 值。密码模式的 `false` 不影响已有账号登录；它不能禁止设备模式自动建号。保留客户端用户数据、`device-identity.json` 和 `%USERPROFILE%\.multica\desktop.json`。

若另行安排旧设备账号转密码账号，先阅读[完整迁移流程](../offline-upgrade.zh-CN.md#authentication-mode)：保留有效旧会话，设置成对的 UTC RFC3339 迁移截止时间，在原账号绑定用户名密码，核对 UUID、工作空间及任务，完成后同时清空迁移窗口。重新注册不会合并旧账号。丢失会话由运维使用受控 `password-recover` 恢复，不能靠切回设备模式解决。

绑定后本机运行时仍拒绝旧令牌时，在“设置 → 守护进程 → 重新连接此设备”刷新凭据；必要时使用刚绑定的原账号重新登录，无需清空数据。

已有密码模式且开启平台管理时，升级会按条件执行一次性初始化。没有平台角色和历史记录时，随机密码保存在**部署目录**的 `admin-initial-password.txt`，权限为 `0600`；不要将它放进交付包或普通日志。首次登录 `/login?next=%2Fadmin` 必须修改密码。已有角色或永久记录时不重置密码。

初始化失败后保留原文件，可修正原因并重试：

```bash
bash /opt/multica-upgrade-v0.6.6/initialize-platform-admin.sh \
  --deployment-dir /opt/multica
```

仍需追加原有全部覆盖文件。有效的单链接私有密码文件会复用；旧版遗留多硬链接且报告 `credentials_file_unsafe` 时，先核对文件归属、链接、部署 UUID 和数据库状态，不自动删链接或永久记录。完整首次启用、强制改密及凭据恢复步骤见[平台管理章节](../offline-upgrade.zh-CN.md#platform-administration)。

## 6. Windows x64 升级

1. 用 PowerShell 执行 `Get-FileHash .\multica-desktop-0.6.6-windows-x64.exe -Algorithm SHA256`，与交付校验和比对。
2. 从托盘完整退出 Multica，沿用原安装位置运行安装器，保留用户数据及身份文件。
3. 重启核对版本 `0.6.6`、原账号、工作空间、任务、业务地址、更新地址及本机守护进程状态。
4. 在实际安装目录检查 `resources\app.asar.unpacked\resources\bin\multica.exe version --output json`，确认 `version=0.6.6`、`os=windows`、`arch=amd64`；这不替代图形界面验收。
5. 使用既有内网更新服务时，先发布本次 EXE 和 blockmap，最后原子替换本次构建的 `latest.yml`。验证参数使用 `--expected-version 0.6.6`，保留现有 `updateUrl`。详见[桌面操作手册](../desktop-intranet-update-runbook.zh-CN.md)。

服务端升级包不包含桌面下载服务；沿用原有服务和工具环境。桌面手册中的旧版本号是示例，源码脚本/历史资料链接并不全部包含在本次文档压缩包中。

## 7. 验收与回滚

- `/healthz` 成功，数据库连通且没有待执行迁移；`/health` 显示 `v0.6.6`。数字迁移前缀上限仍为 570。
- `/api/config` 的认证模式、部署 UUID、管理开关和公开安装命令与原配置一致。
- 原账号能够登录 Web 和 Windows，原工作空间、任务、附件及客户端配置保留；设备身份没有重新生成。
- 若首次初始化管理员，完成强制改密，核对 `/api/admin/me` 的角色和后台总览、账号列表；重试初始化不重置密码。
- 在目标 Windows 终端完成覆盖安装或真实自动更新，并验证重启和用户状态。下载校验成功不等于安装验收通过。

验证记录区分本机 Docker Desktop 的 Linux amd64 容器演练、Windows 安装包静态检查，以及真实内网/原生 Windows 验收。校验和不表示代码签名或 SmartScreen 信任；实际签名和未验证项以本次 JSON 记录为准。

失败时先保存日志、备份和当前状态。脚本不自动回滚数据库或容器。优先向前修复；必须回退时，先停止写入，验证同一恢复点的数据库、配置、附件和资源备份，再按既有恢复方案切换。不要将 SQL dump 直接导入已迁移的非空库，也不要删表、删迁移记录或数据卷绕过保护。密码部署不以重新开启设备登录作为回滚方式。
