# Multica V0.6.5 内网交付与升级说明

本次从当前分支源码 `7ab8d038963dd920a611047997ac1904ee69a1eb` 构建，交付 Linux x86-64（`linux/amd64`）服务端离线升级包和 Windows x86-64（`x64`）64 位桌面安装器，应用版本为 `0.6.5`。Linux 包不适用于 32 位 x86，Windows 包不适用于 32 位 Windows。

本次为本地内网交付，不表示已经发布 GitHub Release。累计变更说明保留此前 v0.6.1 正式记录，本次分支变化列为 `Unreleased`；界面的当前服务端版本可以是 `v0.6.5`，最新正式发布记录仍为 `v0.6.1`，两者含义不同。文档及模板注释已随交付修正，不改变业务源码行为。

先升级服务端与 Web，完成健康、登录和原数据验收，再升级 Windows 客户端。普通升级保留原认证方式；不会自动开启平台管理或把设备账号改成密码账号。

## 3. `.env` 差异与合并

以下根据 v0.6.0、v0.6.1 标签与本次源码中的 `.env.example`、主 Compose 逐项比较。两个旧版本的配置差异结论相同：**模板新增 3 项、移除 1 项，保留项没有默认值改动；主 Compose 新增 4 项传入、移除 1 项。** 工作空间默认状态变化来自应用和数据库迁移，不是新增环境变量。

| 配置 | V0.6.0/V0.6.1 | V0.6.5 | 运维处理 |
| --- | --- | --- | --- |
| `MULTICA_CLI_INSTALL_COMMAND_WINDOWS` | 模板和主 Compose 未提供 | 新增，默认空；Windows 独立安装命令 | 使用内网 CLI 时填写实际 PowerShell 安装命令 |
| `MULTICA_CLI_INSTALL_COMMAND_MACOS` | 模板和主 Compose 未提供 | 新增，默认空；macOS 独立安装命令 | 按支持范围填写，优先于通用命令 |
| `MULTICA_CLI_INSTALL_COMMAND_LINUX` | 模板和主 Compose 未提供 | 新增，默认空；Linux 独立安装命令 | 按支持范围填写，优先于通用命令 |
| `MULTICA_CLI_INSTALL_COMMAND` | 模板已有，主 Compose 未传入 | 新增主 Compose 传入，默认空 | 保留已有值；新版仅作 macOS/Linux 备用，旧客户端仍可读取它 |
| `FF_ITERATIONS_I1` | 模板及主 Compose 默认 `false` | 已删除，服务端忽略残留值 | 在核对工作空间状态后移除旧配置；不要靠它关闭功能 |
| `MULTICA_PLATFORM_ADMIN_ENABLED` | 已有，默认 `false` | 默认不变；升级后增加初始化步骤 | 沿用原值；密码模式且值为 `true` 时核对固定部署 UUID 和初始化回执 |
| `MULTICA_MANAGED_INSTALLATIONS_ENABLED` / `MULTICA_DEPLOYMENT_ID` | 已有，默认 `false` / 空 | 不变 | 沿用原值和固定 UUID；首次启用管理另按第 5 节配置 |
| `FF_PROJECTS_P1` | 默认 `true` | 不变 | 沿用原值；不是迭代总开关 |
| 三项 `MULTICA_ADMIN_*_RETENTION_DAYS` | 已有，默认空 | 不变 | 保留策略值；不会因此启用自动删除 |

三项保留期的完整变量名为 `MULTICA_ADMIN_CONFIRMED_OPERATIONS_RETENTION_DAYS`、`MULTICA_ADMIN_ALERT_RETENTION_DAYS` 和 `MULTICA_ADMIN_AUDIT_RETENTION_DAYS`。它们不是此次新增项。

“添加电脑”的安装命令按以下顺序选择：目标系统专用命令优先；macOS/Linux 可用通用命令备用；只要有任一自定义来源，未配置系统便提示缺少安装命令，不回退公网。四项全空时仍使用公网默认安装命令，因此隔离内网需要配置实际支持系统的内网来源。平台命令不改变桌面更新源 `updateUrl`，也不会自动搭建 CLI 文件服务器。

所有安装命令均是 `/api/config` 可公开读取的文本，**不得放入令牌、密码、带凭据 URL 或其他秘密**。修改后在 Web/桌面端切换目标系统检查，不要用安装命令验证方式意外安装软件到服务器上。

合并顺序：

1. 在修改前备份部署 `.env`、主 Compose、全部覆盖文件和 `compose-command.txt`。备份放在仅运维可读的位置。脚本运行时的自动备份保存的是当时的内容，不一定是手工修改前的原始配置。
2. 修改已有同名项，缺少再添加；不要重复追加，不要 `cp .env.example .env`，不要 `source .env`。它是 Compose 配置文件，不是 Shell 脚本。
3. 保留数据库账号密码、`JWT_SECRET`、集成加密密钥、固定 `MULTICA_DEPLOYMENT_ID`、认证设置、迁移窗口、URL、端口、挂载目录和已有模板/资源配置。
4. 原主 Compose 内的本机定制需要先迁移到持久化覆盖文件；升级脚本会替换主 Compose。每次升级与后续维护都显式使用原顺序的全部覆盖文件。
5. 升级工具自动更新 `.env` 中的 `MULTICA_BACKEND_IMAGE`、`MULTICA_WEB_IMAGE`、`MULTICA_IMAGE_TAG`、`CHANGELOG_FILE` 和 `CHANGELOG_DIRECTORY`，其余值保留。三项平台命令不会被自动填入，旧迭代变量也不会从运维文件中自动删除。
6. 修改配置后重建后端；`docker compose restart` 不会应用容器环境变量变化。Shell 中同名 `export` 优先于 `.env`，应清理过期覆盖。可以用同一 Compose 文件列表执行 `config --quiet` 检查语法，不要把包含秘密的完整 `config` 输出贴进工单或发布日志。

## 4. Linux 离线升级

目标主机需要 Docker、Docker Compose、Bash、curl 和 SHA-256 校验工具；不需要安装 Node.js、pnpm 或 Go，不需要访问公网镜像仓库。确认 `uname -m` 返回 `x86_64`，为压缩包、导入镜像和数据库备份留足磁盘空间。

安排维护窗口，暂停用户与智能体写入，保留旧镜像。脚本自动导出 PostgreSQL，但不备份附件卷、资源发布卷或全部外部存储；应同时备份 `backend_uploads`、模板目录、外部对象存储及已启用的 `managed_resources`，保证恢复点一致。使用外部数据库的定制部署还应核对备份的是后端实际连接的数据库。

在存放交付文件的目录执行，示例部署路径为 `/opt/multica`：

```bash
sha256sum -c multica-server-upgrade-v0.6.5-linux-amd64.tar.gz.sha256
mkdir -p /opt/multica-upgrade-v0.6.5
tar -xzf multica-server-upgrade-v0.6.5-linux-amd64.tar.gz \
  -C /opt/multica-upgrade-v0.6.5 --strip-components=1
cd /opt/multica-upgrade-v0.6.5
bash offline-upgrade.sh --deployment-dir /opt/multica
```

已有覆盖文件时，将最后一条替换为实际文件列表，下面仅作顺序示例：

```bash
bash offline-upgrade.sh --deployment-dir /opt/multica \
  --compose-file docker-compose.resource-publishing.yml \
  --compose-file docker-compose.local.yml
```

只填写部署确实使用的文件，不为普通升级新增资源发布功能。覆盖文件里的旧版固定 `image` 会使升级停止；调整为跟随升级镜像变量后再重试。脚本依次导入镜像、核对版本、备份数据库/配置、安装累计说明、保存选定镜像与主 Compose、重建服务、检查 `/healthz`，最后检查管理员初始化。确认展示信息后继续，也可在已核对的自动化流程中追加 `--yes`。

## 5. 认证、账号与管理员

升级不改变认证方式，不会重置已有用户密码。保留 `JWT_SECRET`、数据库、客户端用户数据以及设备模式的 `device-identity.json`；不要为升级新建一个账号代替旧账号。

| 现有方式 | 必须保留的配置与行为 |
| --- | --- |
| 设备自动登录 | `MULTICA_AUTH_MODE=legacy`、`MULTICA_DEVICE_AUTH_ENABLED=true`、`MULTICA_CLOUD_URL=`；平台管理和受管安装保持关闭 |
| 密码登录，单 API | `MULTICA_AUTH_MODE=password`、`MULTICA_DEVICE_AUTH_ENABLED=false`、`MULTICA_CLOUD_URL=`、`MULTICA_PASSWORD_LIMITER_MODE=single` |
| 密码登录，多 API | 同样关闭设备认证和 Cloud；限流保持 `shared`，所有副本使用同一个 `REDIS_URL` |

`ALLOW_SIGNUP` 沿用原值：密码模式下 `false` 关闭普通注册但不阻止已有账号登录，也不阻止管理员维护初始化。它不能关闭设备模式的自动建号。

如本次另外安排设备账号转密码账号，必须使用[通用手册的完整账号迁移流程](../offline-upgrade.zh-CN.md#authentication-mode)：保留有效旧会话，设置成对的 UTC RFC3339 `MULTICA_PASSWORD_MIGRATION_CUTOFF` / `MULTICA_PASSWORD_MIGRATION_DEADLINE`，让用户在原账号上绑定用户名密码，核对原账号 UUID、工作空间和任务，然后同时清空窗口配置。直接重新注册不会合并旧数据。已丢失旧会话时走受控的 `server password-recover` 恢复，不把密码部署切回设备登录。

当部署已经是密码模式，且 `MULTICA_PLATFORM_ADMIN_ENABLED=true` 时，V0.6.5 升级脚本会尝试一次性初始化。**需设置本部署有效、固定的 `MULTICA_DEPLOYMENT_ID` UUID**；已有值保持不变。无有效 UUID 时，服务可能已经升级，但管理员步骤会失败，整次升级不会报告成功。

没有平台角色与历史初始化记录时，创建 `platform_admin`，随机初始密码保存在 **部署目录** `/opt/multica/admin-initial-password.txt`，不是解压目录。文件内容为 JSON，权限为 `0600`，使用执行升级的操作系统账号私下读取其中 `username`、`initial_password`。不存在通用默认密码，不在 `.env` 写入管理员密码，不把该文件放进发布包或普通日志。

使用实际 Web 地址的 `/login?next=%2Fadmin` 登录，首次必须改为不同的新密码。改密前不能访问后台或业务数据。已有管理员、观察者或永久初始化记录时保留现状，不重置密码，不自动提权普通同名账号；此时继续使用原管理员。成功改密后初始密码失效，可删除失效文件，后续升级不会重新生成。

升级后才启用后台，或初始化单独失败时，可修正配置、重建后端后重试：

```bash
bash /opt/multica-upgrade-v0.6.5/initialize-platform-admin.sh \
  --deployment-dir /opt/multica
```

此命令也必须按原顺序追加全部 `--compose-file`。回执 `initialized` 表示新账号与凭据文件可用；`already_initialized` 或 `preserved_existing_admin` 表示保留既有初始化/权限。原始凭据丢失、文件不匹配或同名账号冲突时，按[平台管理章节](../offline-upgrade.zh-CN.md#platform-administration)恢复，不删初始化记录，不通过反复升级生成新密码。普通 API 重启不会初始化账号。

首次需要完整平台管理能力时，还应按通用手册配置 `MULTICA_MANAGED_INSTALLATIONS_ENABLED`、固定 UUID、后端重建与终端上报；仅装新桌面端不会开启平台管理或授予管理员权限。

## 6. Windows 64 位桌面升级

1. 在目标电脑使用 PowerShell 计算 `Get-FileHash .\multica-desktop-0.6.5-windows-x64.exe -Algorithm SHA256`，与交付校验值逐字符比对。
2. 从托盘菜单完整退出 Multica，沿用原安装位置运行安装器。保留 `%USERPROFILE%\.multica\desktop.json`、Electron 用户数据目录和其中 `device-identity.json`，无需先卸载并清空数据。
3. 启动后核对版本 `0.6.5`，业务 API/Web 地址、更新地址、原账号、工作空间、任务和本地偏好仍正确。已有会话若需要重新认证，使用原认证方式和原账号。
4. 可在实际安装目录检查 `resources\bin\multica.exe version --output json`，确认版本及 `os=windows`、`arch=amd64`；这不替代图形界面登录和智能体连接验收。
5. 使用现有内网更新服务时，先放入本次 `.exe` 与 `.exe.blockmap`，最后原子替换本次构建生成的 `latest.yml`。保持原文件名及客户端 `updateUrl`，完整流程见[桌面内网更新手册](../desktop-intranet-update-runbook.zh-CN.md)。手册中的历史版本号属于示例，本次验证参数使用 `--expected-version 0.6.5`。

配置 CLI 安装命令的业务 `.env`、桌面下载服务的 `updates.env`、客户端 `desktop.json` 分属不同用途，不能互相代替。现有下载服务可以继续使用，本次服务端包不包含桌面下载服务部署。

配套桌面手册保留了指向仓库脚本和历史验收记录的相对链接；这些源码资料不全部包含在本次离线文档包中，需要从原仓库或现有更新服务部署目录获取。本次离线升级以本说明、`ENV-CHANGES-v0.6.5.zh-CN.md` 和 `offline-upgrade.zh-CN.md` 为准。需要使用桌面手册的 `publish` / `verify` 工具时，沿用已有工具环境；下载服务器仅有 Nginx 时，按该手册第 4.3 节的文件发布流程操作，不将历史链接视为本包缺失的安装依赖。

本次签名情况以构建记录和安装器实际签名为准，校验和不表示 Windows 代码签名或 SmartScreen 信任。交付前的非 Windows 检查不能声明原生 Windows 升级已经通过。

## 7. 目标环境验收

使用部署的实际端口、原 Compose 文件顺序和对应用户账号验收，保存不含秘密的结果：

- `/healthz` 成功，数据库连通且迁移达到 570；`/health` 显示服务端版本 `v0.6.5`。只看容器 `running` 或 `/health` 不足以证明迁移成功。
- `/api/config` 的 `auth_mode`、认证可用字段与原部署一致；平台管理开关、部署 UUID 和公开安装命令符合本次配置。
- 使用原账号完成 Web 和 Windows 登录，核对原工作空间、任务、附件与运行时连接；设备身份没有重新生成，密码账号没有变成另一账号。
- 在“添加电脑”中依次选 Windows、Linux，以及实际支持的其他系统，核对内网命令和目标 API/Web 地址；地址不能是目标电脑不可达的 `localhost` 或回环地址。
- 检查无设置记录、明确关闭、曾启用三类工作空间的分拣/迭代状态。需要关闭迭代时确认安排清除、进行中迭代结束和历史保留影响，按页面确认流程操作。
- 若触发管理员初始化，完成首次改密，确认 `/api/admin/me` 为 `super_admin`、总览与账号列表正常，旧初始密码不可再次登录。
- Windows 手工覆盖安装或真实自动更新后，核对版本、用户状态与本地配置。自动更新还需验证完整下载校验和 Range `206`，下载成功不等于安装成功。

## 8. 失败处理与回滚

失败后先保存原日志、备份位置与当前容器/迁移状态。脚本不会自动回退数据库或容器；管理员初始化失败也可能发生在服务已经升级之后。仅初始化未完成时，优先修正配置并单独重试初始化工具，不重复导入镜像或重置账号。

V0.6.5 的 568—570 降级会拒绝移除已有管理员初始化记录；567 降级仅恢复列默认值。已有项目/迭代数据还受更早的降级保护。不要关闭开关后直接跑 `migrate down`，不要删除迁移记录、管理员永久记录或数据卷绕过保护。

优先部署向前修复版本。必须回退时：

1. 停止所有 API、副本、智能体及其他写入方，备份当前故障现场；核对恢复点与所用数据库，明确升级后新增数据的处理方式。
2. 在隔离或空数据库验证升级前 `database.sql`，不要直接导入已经迁移的非空库。确认恢复成功后，按本部署已验证的数据库切换方案恢复。
3. 恢复同一备份点的 `.env`、主 Compose、原顺序覆盖文件、旧镜像、变更说明目录、附件与资源。原 `JWT_SECRET`、部署 UUID 和认证模式必须一致；不重新生成密钥，也不把密码模式切为设备登录。
4. 管理员凭据文件必须与恢复的数据库对应。若恢复到首次初始化前，妥善移走后来生成的密码文件，避免下次初始化时混用；不要将旧初始密码当作当前密码。
5. 重启后重新执行数据库健康、原账号登录、工作空间/附件/运行时验收，再开放写入。回滚方案必须在实际部署验证，备份文件存在不等于恢复演练成功。

桌面更新源恢复旧 `latest.yml` 只影响后续版本发现，不会让已升级的客户端自动降级，也不保证取消已开始的下载。保留旧安装器和配置备份；客户端恢复优先使用更高版本修复包，必要时安排受控手工安装并验收用户状态。
