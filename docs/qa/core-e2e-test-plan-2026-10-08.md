## 5. 新增缺口用例

断言以产品实际语义为准：先读服务端代码确认行为，再写断言，不臆造需求。每条都同时校验界面和服务端状态（API 或数据库）。

- G1 智能体执行闭环（P0）：注册模拟运行时与智能体；在浏览器创建任务并指派给智能体，校验恰好 1 条排队任务；模拟 daemon 依次领取、开始、上报进度与消息、完成；不刷新页面，确认任务详情依次显示运行中与完成、运行记录和消息可见。失败分支：第二次执行失败后界面显示失败，重新运行只新增 1 条排队；取消排队任务后状态为已取消，再次领取拿不到它。
- G2 跨用户实时协作与通知（P0）：属主与成员使用两个独立浏览器上下文。成员修改状态并发表 @属主 的评论；属主已打开的任务页无需刷新即更新；属主收件箱实时出现提及；标记已读后刷新仍为已读，未读数相应减少。
- G3 成员管理界面（P1）：属主在成员页通过界面邀请，受邀人在自己的上下文接受；属主改角色后，受邀人的管理能力随之出现或消失（界面与服务端 403 一致）；移除后对方失去访问。
- G4 我的任务与搜索（P1）：指派给自己的任务出现在“我的任务”，他人的任务不出现；命令面板按标题和编号搜到任务并打开详情。

## 6. 通过标准与失败处理

- 退出条件：301 条现有用例都在指定通道零重试实跑通过；G1—G4 通过，或已记录可复现的产品缺陷；P1 的静态检查、TS 单测与 Go race/vet 全部通过。
- 失败归因顺序：先查环境（端口、构建身份、`routes-manifest.json` 中的 API 端口、`/api/config` 实际配置），再查已知不稳定用例（`localized-template-defaults`、跨页面哨兵 `workspace-defaults:111` 与 `progress-reporting:261`），最后才判定为产品或测试问题。
- 补跑：失败用例单独补跑最多 2 次，首败与补跑记录都保留。补跑通过的标记为“不稳定”，不记为一次通过。
- 修复边界：环境问题只修环境，不放宽断言。陈旧的测试交互按当前界面契约修正，并保留原有断言强度。产品缺陷先记录复现步骤并暂停，与用户确认后才改产品代码。不提交代码。

## 7. 范围外、隔离与风险

- 范围外：真实模型推理质量；真实 OAuth/Composio、邮件、支付与 IM 外部服务；iOS 原生与 Windows/Linux 安装升级（由 v0.6.0 发布任务另行验收）；Firefox/WebKit；性能压测。
- 隔离：同一 checkout 中有 v0.6.0 发布任务处于暂停状态。不动 `multica-v060-rehearsal-*` 容器、`multica_e2e_1007_*` 数据库、`.artifacts/v0.6.0/`，也不动已有的 `check-*` 环境。不执行 `make up`（会触发 GC，回收被引用为证据的环境）。同一时间只运行一个生产 Web 构建。
- 风险：执行中若有对等会话修改受跟踪源码，源码指纹会失效，对应通道需重跑；生产构建会改写 `next-env.d.ts`，每次构建后从备份恢复。
