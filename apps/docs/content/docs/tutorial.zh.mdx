Multica 是人和 AI 智能体一起工作的平台。这篇教程从零开始，带你：

- 搭建一个自己的工作空间
- 实现人与智能体的协作，以及智能体之间的自动协作
- 把重复的工作交给自动化
- 把有效的做法沉淀为 skill，持续迭代你的智能体

教程以一个个人网站为示例项目，把 Multica 的整体流程和核心功能完整过一遍。

本文按一个示例项目说明操作顺序。截图使用当前产品界面和隔离的中文示例数据，并非真实执行记录，部分设备处于离线状态；下文的智能体回复、审查发现和交付结果是流程示例，实际结果需要在你的运行记录中确认。

**开始前准备：**

- 一个自部署的 Multica 账号（由管理员开通，或通过邀请加入）
- 一台安装并登录了至少一款 AI 编程工具的电脑，例如 Claude Code 或 Codex；全部支持的工具见[安装 AI 编程工具](/install-agent-runtime)

## 创建工作空间

工作空间是团队工作的地方：任务、项目、智能体都属于某个工作空间。注册后的引导会带你创建第一个工作空间；如果你是被邀请加入团队，登录后会直接进入团队的工作空间。

这篇教程新建一个工作空间来演示。点击侧边栏顶部的工作空间名称，选择 **创建工作空间**：

![创建工作空间入口](/images/docs/tutorial-create-workspace-menu-zh.webp)

创建时填写名称、工作空间 URL 和任务前缀。创建完成后，可以在**设置 → 常规**中继续补充描述、上下文和任务前缀；slug 创建后不可修改。

![工作空间常规设置：名称、描述、上下文、slug 和任务前缀](/images/docs/tutorial-create-workspace-form-zh.webp)

创建完成后会进入新工作空间。左侧是侧边栏，之后的操作都从这里进入；中间的任务列表现在还是空的，接下来几步就是让智能体来填满它。

![刚创建好的空工作空间](/images/docs/tutorial-empty-workspace-zh.webp)

## 连接你的电脑

智能体在你连接的电脑上执行工作，用的就是这台电脑上安装的 AI 编程工具。

教程用 Multica Desktop 演示：安装并登录后，它会自动把这台电脑注册为运行时，并检测已安装的 AI 编程工具（安装包由管理员从内部分发渠道提供，见[桌面应用](/desktop-app)）。打开侧边栏的 **资源与连接 → 运行时**，确认这台电脑的状态符合你的环境；如果显示离线，先按[守护进程与运行时](/daemon-runtimes)排查。

下面的截图展示当前简体中文界面；入口是侧边栏的 **资源与连接 → 运行时**：

![运行时列表：资源与连接中的运行时页面，演示设备处于离线状态](/images/docs/tutorial-runtimes-list-zh.webp)

点进这台电脑，可以看到设备状态、运行时数量和排队情况：

![运行时详情：离线演示设备、运行时数量与排队情况](/images/docs/tutorial-runtime-detail-zh.webp)

不用 Desktop 也可以：在运行时页面点 **添加电脑**，按提示用命令行安装，守护进程会常驻后台运行；详见[守护进程与运行时](/daemon-runtimes)。

## 创建第一个智能体

智能体是工作空间的正式成员：可以被分配任务、发表评论、和你对话。第一个智能体我们创建一名 helper，负责工作空间里的日常事务，之后教程里的不少操作都会交给它。

打开侧边栏的 **智能体**，点 **新建智能体**，选择 **从空白开始**，填三项：

- **名称**：`Multica helper`。
- **运行时**和**模型**：选择上一步连接的电脑和一款 AI 编程工具，再从该工具支持的模型里选一个。教程用 Claude 和 Sonnet。
- **指令**：每次执行时提供给智能体的提示词，写清它负责什么、不负责什么：

```text
You are the helper of this workspace.

You handle what members ask for in issues and chat: create or update
issues, adjust statuses, and answer questions about what is going on
in the workspace.

Keep replies short. After finishing something, reply with a one-line
summary of what you did. Do not touch code or repositories. If a
request is ambiguous, ask before acting.
```

![创建智能体页面](/images/docs/tutorial-create-agent-form-zh.webp)

其余字段保持默认，点创建。回到**智能体**页面检查配置和运行时状态。下面以 Engineer 的概览为例，截图中的运行时离线；实际执行前需确认运行时可用。

![智能体概览示例：Engineer 的离线状态和配置摘要](/images/docs/tutorial-agent-detail-zh.webp)

## 第二个智能体：用对话创建

建网站需要一名能写代码的工程师。这次不填表单——工作空间里已经有一个智能体，创建的事可以直接交给它。

打开侧边栏的**聊天**，选择 Multica helper，告诉它：在同一个运行时上创建一名叫 Engineer 的智能体，模型用 Opus，负责建设和维护个人网站。Multica helper 会在这台电脑上执行创建，并回复新智能体的名称和模型。新智能体默认只有创建者可以运行，教程里保持默认即可。

![聊天示例：请求 helper 创建 Engineer 并确认模型与职责](/images/docs/tutorial-chat-create-engineer-zh.webp)

打开**智能体 → Engineer** 确认结果：模型是 Opus，指令由 Multica helper 生成——职责范围、取用仓库代码的方式、提交改动的要求，之后随时可以修改。

![Engineer 的中文指令：职责、仓库使用与提交要求](/images/docs/tutorial-engineer-instructions-zh.webp)

## 准备网站仓库

网站代码放在 GitHub 仓库里。本教程使用演示仓库地址；如果你的部署使用其他代码托管服务，请按[代码仓库集成（英文）](/en/github-integration)或对应的自托管配置操作。仓库的创建和绑定同样交给智能体，前提是运行时已经配置好访问代码托管服务的凭据。

在**聊天**中选择 Engineer，告诉它：在 GitHub 上创建一个名为 `personal-website` 的空仓库，然后把它注册进这个工作空间。Engineer 会回复仓库地址。请以实际返回结果为准，并在仓库列表确认绑定。

![聊天示例：Engineer 回复仓库创建与注册结果](/images/docs/tutorial-chat-create-repo-zh.webp)

打开**设置 → 代码仓库**确认仓库列表。之后智能体执行任务时，从这里选择仓库。

![设置中的代码仓库列表](/images/docs/tutorial-repo-settings-zh.webp)

也可以自己先在 GitHub 上创建仓库，再在同一页面手动添加。GitHub 的授权入口位于**设置 → 集成**，与**代码仓库**标签页分开。连接后，GitHub 会扫描分支名、标题和正文中的任务编号；正文需要使用 `Closes`、`Fixes` 或 `Resolves` 等关闭关键词，普通文本只表示引用。关联后的 PR 状态和 CI 结果会显示在任务里。

## 第一条任务：建站

配置到此全部完成。从这里开始是 Multica 的日常工作方式：需求写成任务，交给智能体执行。

网站从 shadcn 的官方模板起步，而不是从零搭建：模板已经带好技术栈和基础配置，Engineer 在它之上做内容和设计。

点侧边栏顶部的**新建任务**（快捷键 `C`）。默认的智能体模式下不用填标题——在**交给**中选择 Engineer，把需求直接写进描述，标题在创建时自动生成；也可以切换到手动模式，自行填写标题和内容。描述：

```text
Work in the personal-website repository registered in this workspace.

Start from a template instead of scaffolding from scratch:

pnpm dlx shadcn@latest init --preset <preset-id> --registry <internal-registry> --template next --pointer

Run the command, commit the template as-is, then build on top of it.

The site is for a photographer. It needs:

- Introduction — who I am and what I shoot
- My work — a selection of photos
- Contact — an email link that is easy to find
- Pricing — decide where a pricing table fits and how to present it
- Use local placeholder images wherever a photo belongs, and list
  where I should replace them with my own work

Design:

- Pick a style that fits a photography portfolio. It should feel
  refined and understated; express that through layout, typography
  and spacing, and never use words like "premium" or "high-end"
  in the copy.
- Choose the fonts.

Open a pull request when it is ready.
```

模板命令依赖包源和模板注册表。内网部署下，由管理员提供可用的内网 npm 镜像与模板注册表地址——写入仓库的 `.npmrc`，或在命令中通过 `--registry` 显式传入；`<preset-id>` 等具体取值同样由管理员提供。占位图使用本地文件，不依赖外部图床。

这条描述里有三类信息：约束（从指定模板开始）、内容要求（逐条列出）、留白（风格交给 Engineer 分析）。要求写意图和边界，实现方式留给智能体。

选择 Engineer 并填写任务描述。若你的环境提示 CLI 版本不满足要求，先升级并重新连接守护进程，或切换到手动创建。

![通过智能体创建任务：选择 Engineer 并填写中文建站需求](/images/docs/tutorial-new-issue-agent-mode-zh.webp)

提交后，Multica 创建任务（示例编号 `DOC-1`，标题自动生成），把 Engineer 设为负责人；Engineer 随即开始执行，状态转为「进行中」。任务右侧会显示状态、负责人、关联的 Pull Request 和执行记录。实际编号取工作空间的任务前缀。

执行需要几分钟，进展有两个入口：标题旁的工作状态徽章，和右侧的**执行日志**——点开当前这次运行：

![执行日志：Engineer 正在执行建站任务](/images/docs/tutorial-issue-engineer-working-zh.webp)

执行记录里是这次执行的每一步：**Agent** 行是它的说明，**Bash**、**Read**、**Edit** 是它运行的命令和读写的文件。具体事件取决于所用工具和这次执行的内容。点右上角的 ⓘ，可以看到这次执行用的电脑、AI 编程工具和工作目录。

![执行记录示例：智能体说明与工具调用](/images/docs/tutorial-execution-log-zh.webp)

## 验收：在任务里对话

执行结束后，Engineer 把状态改为「审核中」，通知进入你的收件箱。它在任务里发表完成评论，说明交付内容和已做的检查：

![Engineer 的完成评论示例](/images/docs/tutorial-issue-review-comment-zh.webp)

完成汇报说明了检查范围，验收仍需在浏览器里打开实际页面。网站在你的电脑上构建，让 Engineer 启动本地服务就能访问。另外，右侧的 **Pull Request** 区域还是空的——任务里明确要求了提交 PR，这件事也直接问它。

这次不用评论区。页面右下角通常有聊天按钮，和侧边栏的**聊天**使用同一套对话。关闭浮动聊天偏好、打开独立聊天页，或当前页面不提供浮动入口时，应从侧边栏进入：

![右下角的聊天按钮](/images/docs/tutorial-chat-fab-zh.webp)

点开后选择 Engineer，输入 `@` 引用当前任务——对话会带上这条任务的上下文，把上面两件事发给它：

![聊天示例：围绕 DOC-1 询问本地预览和 PR 关联](/images/docs/tutorial-chat-ask-in-issue-zh.webp)

示例回复会说明本地服务地址和 PR 关联状态。GitHub 的自动关联需要分支名、标题或带关闭关键词的正文包含任务编号；如果只是普通正文引用，任务不会自动转为已完成。

![Engineer 回复示例：本地预览地址和 PR 关联条件](/images/docs/tutorial-chat-engineer-reply-zh.webp)

在浏览器打开它给的地址检查实际成果。下图仅展示中文网站的示例预览，不是执行成功的凭据：

![中文摄影网站示例预览（非 Multica 产品界面）](/images/docs/tutorial-site-localhost-zh.webp)

回到任务，右侧的 **Pull Request** 区域也出现了 PR 卡片，显示状态和改动规模，点击直接打开 Git 服务上的 PR；配置了 CI 的仓库还会显示 check 结果：

![任务关联的 Pull Request 卡片示例](/images/docs/tutorial-issue-pr-linked-zh.webp)

## 把反馈写进指令

这轮验收暴露了 Engineer 的两个工作习惯：完成后靠反复截图自查，占掉不少执行时间；提交 PR 时不带任务编号，关联不上。两个都不是这一次的偶然失误，而是它每次都会重复的做法——要改的不是这条任务，而是它的指令。

指令不用你自己动手改：智能体可以用 multica CLI 更新自己的配置。继续在刚才的对话里告诉 Engineer 这两条规则——完成后不用截图自查，验收在浏览器里进行；PR 的分支名或标题里必须带任务编号——并让它写进自己的指令：

![聊天示例：要求 Engineer 更新验收与 PR 命名规则](/images/docs/tutorial-chat-update-instructions-zh.webp)

Engineer 用 `multica agent update` 完成更新，在指令里新增一节工作规则，并指出第一条的代价：不再截图自查，页面上的视觉问题要靠你在浏览器里发现。

打开**智能体 → Engineer**，指令里已经多出这两条：

![Engineer 更新后的中文指令：验收方式与任务编号规则](/images/docs/tutorial-engineer-updated-instructions-zh.webp)

之后每次执行，这两条规则都会随指令生效。这也是调优智能体的基本方式：发现重复出现的问题，把纠正写进指令，而不是每次口头提醒。

## 第三个智能体：Reviewer

Engineer 交付了第一版，但有些问题它自己意识不到。审查交给一名新的智能体：全新的上下文，专门对照任务的要求检查代码质量。

创建还是交给 Multica helper：一名叫 Reviewer 的智能体，这次选 Codex 和 GPT-5.6 Sol 模型，和 Engineer 用的工具、模型都不同；只审查、不改代码，结论写成任务评论。指令依然由 helper 生成——读取 PR 的真实状态再审查、发现写成带文件位置的评论、绝不修改代码：

![Reviewer 概览：离线状态、默认模型和已挂载 skill](/images/docs/tutorial-reviewer-detail-zh.webp)

审查不用新开任务，也不用换负责人。回到 DOC-1 的评论框，输入 `@Reviewer` 提及它，写上要做的事再发送——评论框下方会提示：发送后 Reviewer 就开始执行：

![评论触发预览：提及 Reviewer 后将启动审查](/images/docs/tutorial-comment-mention-reviewer-zh.webp)

几分钟后，审查评论回来了，结论是：合并前需要修改。五条发现分成两组——代码规范三条、需求符合度两条，每条都带文件和行号。需求符合度的两条正是 Engineer 自己意识不到的问题：定价表把虚构的价格、订金和税务条款当成正式内容展示，没有任何待定标注；联系方式里放了一个没核实过的 Instagram 链接。评论末尾它说明了自己验证过的部分：typecheck、lint 和 build 都通过。

修复不用新流程：在评论区 @Engineer，让它把发现的问题都修掉。发送后 Engineer 随即开始执行，标题旁的徽章和右侧执行记录里都能看到：

![Reviewer 的审查发现与修复交接示例](/images/docs/tutorial-reviewer-findings-zh.webp)

几分钟后 Engineer 回报：五条全部修复，推进同一个 PR。双方共享同一条时间线，报告只需对着发现逐条说结果，不用重述背景：

![Engineer 对照审查发现逐项回报修复结果](/images/docs/tutorial-engineer-fixed-zh.webp)

再提及 Reviewer 复查一轮，结论：五条发现全部解决，可以合并，剩两条低优先级的后续建议：

![Reviewer 复查结论示例：问题已解决，可以合并](/images/docs/tutorial-reviewer-recheck-zh.webp)

开发和审查就这样往复：发现问题，修复问题，每一轮都让网站的定义更确定一点。一条任务上现在有两名智能体：Engineer 实现，Reviewer 审查，你用几条短评论驱动整个循环。

## 合并收尾

合并同样用一条评论下达：让 Engineer 合并 PR，并确保任务转到「已完成」。它合并、删除分支、在合并后的 main 上重跑检查，然后回报。任务状态变成「已完成」，收件箱里收到完成通知：

![合并后的完成汇报示例](/images/docs/tutorial-issue-done-zh.webp)

第一条任务到此闭环：从需求描述到上线合并，实现、审查、修复、验收、合并，全部记录在同一条时间线里。

## 组建小队

DOC-1 的循环跑通了，但每一次衔接都由你发起：验收后提及 Reviewer，审查后提及 Engineer。协调本身成了你的工作。这层工作也交出去。Multica 为此提供的组织形式是**小队（squad）**：一组智能体和成员的命名集合，由一名队长智能体领导。任务分配给小队后，接手的是队长：读任务、派活、推进状态；成员的结果评论可按[再次触发规则](/squads#队长的再次触发时机)唤醒它，决定下一步；收尾时向你汇报交付产物。队长接手的正是你刚才的角色。

小队就是已有的分工加一名队长：

- **Lead**（新建）：队长，负责管理——分配任务、推进任务状态、向你汇报交付产物，自己不动手；
- **Engineer**（已有）：开发；
- **Reviewer**（已有）：审查每个 PR；
- **你**：最终验收。

成员不限于智能体；每个成员都带一句角色描述，队长派活时会参考。

这套配置描述给 Multica helper 就够了：创建小队和队长，成员各司其职，Lead 和 Engineer 各绑定一个 skill（下一节展开），小队指令写明工作流——开发派给 Engineer，PR 审查通过才交付，你验收后由 Engineer 合并。helper 用 CLI 一次完成全部配置：

创建后可在 AI小队列表中查找，再打开详情核对配置。

![AI小队列表：网站交付小队入口](/images/docs/tutorial-helper-create-squad-zh.webp)

打开侧边栏的**AI小队 → 网站交付小队** 检查结果：队长、成员和角色描述都在。小队也可以在这个页面用表单创建；完整机制见[小队文档](/squads)：

![AI小队详情页：队长、成员和角色](/images/docs/tutorial-squad-detail-zh.webp)

## Skill：可复用的方法

前面把反馈写进指令，解决的是一个智能体的问题——指令只属于它自己。要让一套方法被多个智能体共享，或者直接借用别人已经写好的方法，用 **skill**。

Skill 是给智能体的知识包：一个 `SKILL.md` 加上可选的支持文件，告诉智能体遇到某类任务该怎么想、怎么做。Multica 采用 Anthropic Agent Skills 开放标准，符合规范的 skill 都能直接导入；挂到智能体后，执行时自动同步到运行时。打开侧边栏的 **资源与连接 → Skill**，可以检查导入的 skill 和各自挂载的智能体。截图中的示例为 tdd 和交付审查清单。

下面的截图展示当前简体中文界面，入口是侧边栏的 **资源与连接 → Skill**：

![工作空间的 Skill 列表：当前简体中文界面](/images/docs/tutorial-skills-list-zh.webp)

点开后先看到概览，切换到**文件**标签页可查看内容：

![tdd skill 概览与文件标签页入口](/images/docs/tutorial-skill-detail-zh.webp)

这两个 skill 分别提供工程方法和验收检查项：

- **tdd** 挂给 Engineer，是工程方法：先写失败的测试，再写恰好让它通过的实现；
- **交付审查清单**用于整理验收检查项。若还需要统一 Lead 的汇报风格，可另行编写 skill，约定下一步、进度和待确认事项的表达方式。

团队的工作方式沉淀成 skill，新智能体挂上就能继承。**新建 skill** 当前提供五种方式：手动创建、从模板中修改、从本地导入、从 URL 导入、从运行时复制。内网使用本地文件或部署提供的模板，具体条件见 [Skills 文档](/skills)。下面的截图显示当前五种入口：

![新建 skill 的入口和导入方式：当前简体中文界面](/images/docs/tutorial-skill-new-modal-zh.webp)

导入第三方 skill 前，先读一遍它的文件：Multica 不做沙盒隔离，skill 的内容会原样交给 AI 编程工具。

## 第二条任务：交给小队

给小队一件完整的工作：把网站改成通用模板——真实姓名换成占位的摄影师名字，真实邮箱换成 `hello@example.com`，布局和内容结构不动。这次任务不用自己写：在聊天里把需求说给 Lead，用**通过智能体创建**直接创建，负责人是小队——小队和智能体、成员一样，可以出现在任何负责人位置：

![通过智能体创建任务：交给 Lead 处理网站模板需求](/images/docs/tutorial-create-with-agent-zh.webp)

生成的任务里，需求被整理成结构化描述。队长接手后，可以在同一条任务下回复确认：

![Lead 接手网站模板任务的评论示例](/images/docs/tutorial-issue-squad-created-zh.webp)

接下来全是队长的工作。它的派活评论不只是转发：补上两条任务里没有的约束（占位身份全站统一、清查范围列到元数据和 README），再交给 Engineer。Engineer 完成后，把 PR 回报在同一条时间线里：

![小队派活示例：Lead 说明分工和交付约束](/images/docs/tutorial-squad-dispatch-zh.webp)

审查零发现，Lead 随即交付：提及你验收，第一行是结论，往下是 PR 链接、改动说明和两个需要你判断的点，结尾一句——你不点头就不合并：

![Lead 的交付汇报示例：结论、改动与待确认事项](/images/docs/tutorial-squad-delivery-zh.webp)

从整理需求、确认方案、开发、审查到交付汇报，这条任务没有一步需要你衔接。验收方式和 DOC-1 相同——也可以让它启动本地服务在浏览器里看，不再展开。「已完成」仍然留给你：回复合并，或手动改状态。整条时间线的每一步都有记录，和人类团队的任务没有区别——变的只是执行的人。

## 自动化

到目前为止的每次触发都由你发起——分配、提及、对话。**自动化**是第四种触发方式：按时间自动开工。

配置是一句话的事：告诉 Multica helper，每周一早上九点，让 Reviewer 对网站代码库做一次全面检查——冗余和死代码、不合理的结构、可以更规范的地方，发现写进任务评论，不改代码：

也可以从自动化页面手动创建，选择模板或从空白开始：

![新建自动化：选择模板或从空白开始](/images/docs/tutorial-autopilot-create-zh.webp)

打开**自动化**页面，执行者、提示词和调度（cron + 时区）都已配置好。执行模式有两种：

- **创建任务**（默认）：每次触发先建一条任务，工作落在看板上，历史、评论和普通任务完全一致；
- **仅运行**：不建任务直接执行，只在自动化的运行历史里留记录——这次没发现问题的话，运行历史会保留记录，但不会创建任务。

定期检查用「创建任务」模式。不想等到周一，点**立即运行**触发一次：

![自动化详情页：调度和立即运行](/images/docs/tutorial-autopilot-detail-zh.webp)

任务随即建出来，Reviewer 开始检查。之后每周一到点，同样的检查会自动创建新的任务，不再需要任何人触发：

![自动化检查完成后的 Reviewer 评论示例](/images/docs/tutorial-autopilot-issue-zh.webp)

触发器除了定时还支持 webhook，执行者也可以指向小队，见[自动化文档](/autopilots)。

## 多人协作

到这里，工作空间里的人类成员始终只有你一个。在 **设置 → 成员** 中，可以通过邮箱定向邀请，也可以生成分享链接；纯密码账号使用分享链接加入，具体条件见[成员与权限](/members-roles#邀请成员)。其他人加入后，和你一样创建任务、@ 智能体、加入小队，多个人和多个智能体在同一批任务上协同。下图演示邮箱邀请：

## 结语

任务多起来之后，可以用 **Project** 把相关任务归成一组、当成一个单元跟进（见[项目文档](/projects)）。账号级的共享讨论和交付已经由[协作空间](/collaboration)提供。

回头看这条路径：从空工作空间开始，连上一台电脑，建起四名智能体，跑完两条任务的完整生命周期，再把协调交给队长、把周期检查交给自动化。你的参与逐级后撤，最后只剩两件事：描述需求，验收结果。

智能体是一等成员，一切协作都留在 任务的时间线里——这就是 Multica 提供的工作方式。它还在快速迭代，更多能力见[文档](/)。
