에이전트는 [Multica 워크스페이스](/workspaces)의 협업자입니다. 이슈를 할당하거나 댓글에서 @멘션하거나 직접 대화할 수 있습니다. 에이전트는 연결된 런타임을 통해 AI 코딩 도구를 호출하고 진행 상황과 결과를 워크스페이스에 기록합니다.

에이전트 자체는 계속 실행되는 프로세스가 아닙니다. 반복해서 사용할 수 있는 정체성과 설정의 묶음이며, 작업을 받을 때만 구체적인 [실행 태스크](/tasks)가 생성됩니다.

## 에이전트 설정

| 설정 | 역할 |
|---|---|
| **이름, 아바타, 설명** | 팀에 에이전트가 누구이며 어떤 작업에 적합한지 알려 줍니다. 설명은 표시용이며 실행 프롬프트에 포함되지 않습니다. |
| **지시문** | 역할, 작업 방식, 경계, 결과물 요구 사항을 규정합니다. 모든 실행에서 사용됩니다. |
| **대화 시작 예시** | 에이전트별 예시를 최대 3개 제공하며, 새 채팅을 열 때 표시됩니다. 선택하면 전송하지 않고 입력창에 채웁니다. |
| **스킬** | 재사용 가능한 방법, 참고 자료, 지원 파일을 제공합니다. |
| **런타임, 모델, 사고 강도** | 어느 런타임에서 어떤 AI 코딩 도구와 모델을 사용할지 결정합니다. Codex 같은 일부 도구에서는 속도 단계도 선택할 수 있습니다. |
| **Access** | 어떤 멤버가 에이전트를 실행할 수 있는지 결정합니다. |
| **실행 설정** | 동시 실행 상한, 환경 변수, CLI 인수, MCP, 외부 연동을 포함합니다. |

모델을 바꾸거나 지시문을 수정해도 새 에이전트가 만들어지지 않으며 이전 이슈, 댓글, 실행 기록도 사라지지 않습니다.

## 에이전트, 런타임, 실행 태스크

| 개념 | 역할 |
|---|---|
| **에이전트** | 누가 어떤 방식으로 작업할지 결정 |
| **런타임** | 어느 컴퓨터에서 어떤 AI 코딩 도구로 실행할지 결정 |
| **실행 태스크(task)** | 이번 실행의 과정과 결과를 기록 |

하나의 런타임이 여러 에이전트를 지원할 수 있고, 하나의 에이전트도 여러 실행 태스크를 차례로 완료할 수 있습니다. 런타임이 오프라인이어도 에이전트의 정체성과 기록은 남아 있지만 새 태스크는 런타임이 복구될 때까지 기다려야 합니다.

## 작업에 참여하는 방법

- **이슈 담당**: 에이전트를 담당자로 지정하면 태스크가 큐에 들어간 뒤 처리를 시작합니다.
- **댓글 하나 처리**: 댓글에서 에이전트를 @멘션하며 이슈 담당자는 바뀌지 않습니다.
- **논의 이어가기**: 에이전트의 댓글에 답하면 새 정보가 이후 실행에 들어갑니다.
- **직접 대화**: 이슈에 연결되지 않은 대화를 시작합니다.
- **프로젝트와 스쿼드 참여**: 에이전트는 프로젝트 lead가 되거나 스쿼드 리더 또는 멤버가 될 수 있습니다.
- **오토파일럿을 통한 실행**: 일정이나 외부 이벤트로 미리 설정한 작업을 트리거하거나 수동으로 실행합니다.

에이전트는 이슈를 만들고, 댓글을 작성하고, 작업 상태를 변경할 수 있지만 인박스가 없으며 `@all` 알림도 받지 않습니다. 에이전트 @멘션은 알림이 아니라 실행 트리거입니다.

## 권한과 Access

각 에이전트에는 owner 한 명과 Access 설정 하나가 있습니다.

| Access | 실행할 수 있는 사람 |
|---|---|
| **나만**(Only me) | 에이전트 owner만 실행할 수 있습니다. |
| **전체 워크스페이스**(Entire workspace) | 워크스페이스의 모든 멤버가 실행할 수 있습니다. |
| **지정한 멤버**(Specific people) | 에이전트 owner와 지정된 멤버가 실행할 수 있습니다. |

새 에이전트의 기본값은 **나만**입니다.

<Callout type="info">
워크스페이스 `owner`와 `admin`은 모든 에이전트를 보고 관리할 수 있지만 다른 사람의 "나만" 에이전트를 Access를 우회해 실행할 수는 없습니다. 일반 멤버에게는 자신이 소유하거나 실행할 권한이 있는 에이전트만 표시됩니다.
</Callout>

**보기 권한**은 owner 여부, 워크스페이스 관리 역할, Access가 함께 결정합니다. **수정 권한**은 에이전트 owner와 워크스페이스 owner/admin에게 있으며, 이 중 Access는 에이전트 owner만 바꿀 수 있습니다.

환경 변수와 MCP처럼 자격 증명이 포함될 수 있는 설정에는 더 엄격한 읽기 규칙이 적용됩니다. [에이전트 생성 및 설정](/agents-create#환경-변수와-자격-증명)을 참고하세요.

## 자율 수준과 승인 경계

[역할 템플릿](/agents-create#역할-템플릿)으로 만든 에이전트에는 **자율 수준**이 함께 설정됩니다. 사람이 개입해야 하기 전까지 스스로 어디까지 진행할 수 있는지를 뜻하며, 수준은 누적됩니다.

| 수준 | 가능 | 불가능 |
|---|---|---|
| **옵서버** | 읽기, 분석, 코멘트 | 상태·담당자 변경, 이슈 생성, 파일 편집 |
| **컨트리뷰터** | 위 전부 + 격리 브랜치에서 코드와 테스트 작성, 빌드 실행, 맡은 이슈 진행 | 프로덕션 작업, 상시 자동화 생성 |
| **코디네이터** | 위 전부 + 하위 이슈 생성, 멘션으로 배정, 스쿼드와 자동화 관리 | 프로덕션 작업, 자기 스쿼드 결과 수락 |
| **오퍼레이터** | 위 전부 + 사람이 승인한 고위험 작업 실행 | 승인 없이 고위험 작업 수행 |

이는 단순한 라벨이 아닙니다. Multica는 두 곳에서 동시에 적용합니다. 에이전트가 직접 API를 호출할 때 해당 수준이 금지한 요청은 거부되며, 같은 규칙이 실행마다 서버에서 프롬프트에 추가되어 워크스페이스가 지울 수 없습니다.

수준이 선언되지 않은 에이전트, 즉 역할 템플릿 이전에 만든 모든 에이전트는 영향을 받지 않으며 동작이 전혀 바뀌지 않습니다.

에이전트는 템플릿이 지정한 수준을 그대로 유지합니다. 이 수준은 사람만 변경할 수 있고, 에이전트는 소유자 권한으로 API를 호출해도 자기 상한을 올릴 수 없습니다. 또한 에이전트 설정 화면에는 아직 이 조작이 없습니다.

### 고위험 작업에는 사람의 승인이 필요합니다

다음 다섯 가지 작업에는 항상 사람의 명시적 승인이 필요하며, 승인 1건이 작업 1건에 대응합니다: 프로덕션 릴리스, 운영 데이터에 대한 마이그레이션, 자격 증명 접근, 외부 공지, 되돌릴 수 없는 삭제.

오퍼레이터 에이전트가 이런 작업에 도달하면 계획(명령, 예상 결과, 롤백)만 산출하고 승인 요청을 제출한 뒤 멈춥니다. 요청은 **승인** 목록으로 들어가며 에이전트 페이지에서 열 수 있습니다. 사람이 거기서 계획을 읽고 승인하거나 반려합니다. 승인자와 결정, 이후 에이전트가 보고한 내용이 모두 거기에 기록됩니다. 승인은 거기에 기술된 하나의 작업만 대상으로 하며, 인수를 바꾼 재시도나 다음 단계, 이후의 동일 작업은 포함하지 않습니다.

요청을 결정할 수 있는 것은 사람뿐입니다. 에이전트는 자기 요청도, 다른 에이전트의 요청도 승인할 수 없습니다.

<Callout type="warning">
이는 감사 가능한 경계이며 샌드박스가 아닙니다. 태스크는 [데몬](/daemon-runtimes)을 실행하는 사용자의 권한을 물려받으므로, 에이전트의 파일·시스템 접근 범위는 그 사용자의 범위입니다. 자율 수준과 승인은 Multica가 중개하는 부분을 통제합니다. 프로덕션 자격 증명을 실제로 멀리 두는 방법은 개발 런타임에 두지 않는 것입니다.
</Callout>

## 온라인, 오프라인, 작업 상태

에이전트 목록에는 두 종류의 상태가 함께 표시됩니다.

- **가용성**은 런타임에서 오며 온라인, 오프라인, 불안정 등이 있습니다.
- **작업량**은 실행 태스크에서 오며 처리 중, 대기 중, 유휴 등이 있습니다.

"오프라인"은 에이전트가 삭제되었다는 뜻이 아닙니다. 이미 큐에 들어간 태스크는 런타임이 복구될 때까지 기다립니다. "보관됨" 상태에서만 새 작업을 받을 수 없습니다.

## 보관 및 복원

더 이상 사용하지 않는 에이전트는 보관할 수 있습니다. 보관 후에는 선택기에 표시되지 않고 할당하거나 @멘션할 수도 없습니다. 이전 기록은 유지되며 나중에 복원할 수 있습니다.

<Callout type="warning">
보관하면 큐 대기 중이거나 실행 중인 태스크를 포함해 해당 에이전트의 끝나지 않은 모든 실행 태스크가 취소됩니다.
</Callout>

에이전트 owner와 워크스페이스 `owner`, `admin`은 모두 에이전트를 보관하거나 복원할 수 있습니다.
