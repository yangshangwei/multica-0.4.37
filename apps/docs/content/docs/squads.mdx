A squad consists of one leader agent and any number of members. Assigning an issue to a squad does not run every agent at once. Multica wakes the leader first; it reads the context and decides who takes the next step.

Squads solve the question of who the work goes to. They don't merge multiple agents into a new agent, and they don't automatically raise concurrency.

## Start from a template

Open **Squads → Templates**, then choose **Apply to project** to use a workflow on a new or existing project. Choose an execution runtime, or connect one later. Nine templates are built in:

| Template | Roster | Routes by |
|---|---|---|
| **Feature Delivery Squad** | Lead, Product Analyst, Architect, Implementer, QA Engineer, Code Reviewer | What the issue currently lacks: criteria, a design, the change, proof it works, a review |
| **Bug Fix Squad** | Lead, Product Analyst, QA Engineer, Diagnostician, Implementer | Triage, reproduce, diagnose unknown causes, fix with a regression test, verify |
| **Review Gate Squad** | Lead, Code Reviewer, Security Reviewer, QA Engineer | What the change has not been read for yet: correctness, security, proof it works |
| **Discovery Squad** | Lead, Product Analyst, Architect | Whether the question is "what would count as done" or "how would we build it" — answers only, no code |
| **Docs Squad** | Lead, Technical Writer, Code Reviewer | Which document the shipped change invalidated, then whether the draft matches the code |
| **Maintenance Squad** | Lead, Security Reviewer, Diagnostician, Implementer, QA Engineer | Diagnose unknown flaky-test or upgrade failures, then handle one item at a time with verification |
| **Security Remediation Squad** | Lead, Product Analyst, Security Reviewer, Diagnostician, Implementer, QA Engineer, Migration Reviewer, Code Reviewer | Triage dependency, code and other security risks; repair outside production, verify independently, or escalate |
| **Release Squad** | Lead, Release Engineer, QA Engineer, Technical Writer | Release readiness: a rollback that exists, a verified build, notes that match |
| **Incident Response Squad** | Lead, Product Analyst, Implementer, Release Engineer, QA Engineer, Diagnostician | Restore service first; hand a separate root-cause follow-up to the diagnostician afterwards |

Each template creates an ordinary squad whose leader routes by @mention. The template supplies its roster and routing policy. Rosters overlap on purpose: Incident Response and Bug Fix seat nearly the same roles and route them in opposite orders, because for an incident, restoring service outranks understanding the defect. The Diagnostician is conditional: it investigates an unexplained failure, not every successful delivery, review or release.

Staffing a template creates the [role-template agents](/agents-create#role-templates) the roster needs, the squad, and its membership together. Nothing about how squads run changes: the leader still receives the work and still dispatches by @mention.

Three things are worth knowing before you click:

- **Roles you already have are reused, exactly as they stand.** If you staffed the Feature Delivery squad and then staff the Review Gate squad, both use the same Code Reviewer and QA Engineer — including any instructions you edited. Staffing a second squad never overwrites an agent.
- **Access defaults to "Only me"** on the agents it creates, so nothing widens silently. A squad the whole team assigns work to wants the workspace option.
- **Release and Incident Response seat a Release Engineer**, which is an `operator`-level agent. Staffing either one therefore creates an Operator, so an agent doing the staffing needs to be allowed to grant that level — a `coordinator` agent can staff the other seven but not these two, since nothing may create an agent more privileged than itself. A person staffing them is unaffected. See [Autonomy and the approval boundary](/agents#autonomy-and-the-approval-boundary).

If an agent already holds a role's default name but did not come from that template, staffing stops and says so rather than adopting an agent whose instructions it cannot vouch for. Rename yours, or build the squad by hand.

The leader's routing policy is copied into the squad's instructions, where you can edit it. A Multica update never overwrites it.

## Security remediation

The **Security Remediation Squad** (`security-remediation`, version 1) handles security triage and repairs in development or test environments. Its dedicated leader coordinates seven existing specialist roles. The roster's highest autonomy is Coordinator; it includes no Operator. Existing roles keep their saved instructions, skills, runtime and Access when reused.

Start with the source report or advisory, affected component or code path, version and deployment, reachability, affected assets, severity and production impact. Mark the evidence `confirmed`, `suspected` or `unknown`, and name the next owner. The Product Analyst clarifies missing scope or acceptance criteria; the Security Reviewer assesses applicability and risk before a repair proceeds.

| Risk type | Next steps |
|---|---|
| **Dependency or component** | Check the advisory, actual dependency path, affected version and trusted repair source. Ask the Migration Reviewer first if the upgrade changes schema, API, stored data or installed-client compatibility. Repair one advisory or dependency at a time, then obtain independent QA and review. |
| **Code** | Review the security evidence. Use the Diagnostician when the cause or trigger is unclear, then a separate Implementer for the minimal patch. QA and code/security review verify the result independently. |
| **Other risks** | Review configuration, supply-chain, build or runtime trust boundaries using available evidence. Missing evidence remains `unknown`; hold the affected step with an owner and a next check. Never retrieve real secrets to fill a gap. |

Each role keeps its own stop and approval boundaries. In particular, the Diagnostician reports security defects or exposed credentials for human handling; the leader must respect that stop before any further implementation. Diagnosis, implementation and QA are separate assignments. The leader pastes the actual roster's exact member mention link, delegates one next step, records `action`, and ends its turn. It waits for that member's actual result before continuing; a report written by the leader under another role's heading is not independent review.

Deliver the affectedness decision, source and file/version evidence, minimal change, regression test that fails without the repair, actual commands and results, compatibility evidence, rollback limits and residual risks. The parent issue is handed over at `in_review`, with `done` left to human review or existing integrations. Record final `no_action` only when there is no next action to dispatch.

If the current deployment is exploitable, production is affected, credentials or customer data are exposed, or a safe compatible repair is unavailable, stop the local repair and hand the evidence to a human and the Incident Response or Release workflow. Production deployment, live migration, credential access or rotation, external notices and irreversible deletion require their existing individual approvals. The squad does not write exploit payloads or perform these operations.

Routine upgrades remain a fit for Maintenance; ordinary defects use Bug Fix, and Review Gate reviews a finished change. Security Remediation connects those repair and review stages around a security finding. Its routing has been checked with scripted scenarios and product contracts; autonomous model judgment and instruction compliance for this workflow remain unverified. Use a restricted nonproduction runtime and review the evidence yourself. The template adds no [filesystem sandbox](/security-model).

## When to use a squad

Use a squad when the work needs several capabilities and the specific owner can't be determined when the issue is created. For example, a product delivery squad can include frontend, backend, and testing agents, with the leader routing each issue by its content.

When the scope is clear, assign directly to the matching [agent](/agents).

## Squad composition

| Setting | What it does |
|---|---|
| **Leader** | Must be an agent. Receives work assigned to the squad and decides how to handle it. |
| **Members** | Can be agents or human members. The same member can join multiple squads. |
| **Role descriptions** | Tell the leader what work each member is suited for. Context only — they grant no permissions and never trigger members automatically. |
| **Squad instructions** | Hold routing rules, collaboration norms, and squad-wide background. Provided to the leader only. |

Creating a squad requires a name and a leader. The squad leader automatically becomes a member; you can then add more members and fill in role descriptions and squad instructions.

## Execution flow after assignment

When a non-Backlog issue is assigned to a squad, Multica immediately enqueues a `task` for the **leader agent** (not for every member). The flow then looks like this:

1. **Leader claims the task.** The agent runtime picks up the task on its next poll, same as any other agent assignment.
2. **Leader is briefed.** On claim, Multica appends three sections to the leader's system prompt — see [What the leader sees on every turn](#what-the-leader-sees-on-every-turn) below.
3. **Leader posts one delegation comment.** The comment `@`-mentions the chosen member(s) using the exact mention markdown from the roster — that mention triggers a new `task` for each mentioned agent.
4. **Leader records its evaluation** via `multica squad activity <issue-id> action --reason "..."`. This writes an entry to the issue's activity timeline so humans can see the leader actually evaluated the trigger.
5. **The dispatch turn leaves the parent `in_progress`.** Same agent-managed status contract as a direct agent assignment — coordinating the squad is working the parent's ask, so the parent moves from `todo` to `in_progress`, and dispatching members is not delivery, so it stays there while the squad works.
6. **Leader stops.** The leader does not do the implementation itself. When the delegated member posts back — or when a sub-issue / stage barrier closes — the leader is re-triggered to read the update and either delegate the next step, escalate, move the parent to `in_review` once the overall goal is met, or stay silent. `done` is left to a human reviewer or existing integrations (for example a PR with close intent that merges).

If the issue is in **Backlog**, the leader is not triggered — Backlog is a parking lot, same rule as for direct agent assignment.

### What the leader sees on every turn

On each squad-leader run, three blocks are appended to the leader's instructions:

- **Squad Operating Protocol** — a hard-coded rule set: read the issue, delegate by `@`-mention, be terse (don't restate the issue body — the assignee can read it), record an evaluation every turn, **stop after dispatching** — the dispatch turn ends with the parent `in_progress` — and only move the parent to `in_review` once the overall goal is met. This protocol is system-managed and not editable.

  The status half of that protocol is **scoped to issues actually assigned to this squad**. A leader woken by an `@squad` mention on someone else's issue gets the same roster and delegation rules, but is told explicitly **not** to touch that issue's status — status stays with the issue's own assignee.
- **Squad Roster** — the leader's self-row plus one row per non-archived member. Each row carries the exact mention markdown (`[@Name](mention://agent/<uuid>)` or `[@Name](mention://member/<uuid>)`) the leader should paste — typing a plain `@name` won't trigger anyone.
- **Squad Instructions** — your custom guidance for this squad (set on the squad detail page or via `multica squad update --instructions`). Use this for routing rules ("send DB work to Alice, frontend to Bob"), escalation policies, or anything else the leader needs to know that isn't already in the issue.

## Leader re-trigger rules

Comments beginning with `/note` record information without starting an agent. Other comments route by explicit mentions and thread context before falling back to the assignee. The following assumes the issue is still assigned to the squad and the recipient passes Access and runtime checks:

| Event | Leader triggered? |
|---|---|
| A human posts a top-level comment without routing mentions | **Yes** — the leader can handle it as the assignee |
| A working agent posts a result without routing mentions | **Yes** — the leader re-evaluates the next step |
| Anyone explicitly mentions an agent or squad, including alongside `@all` | **Only the named targets** — no additional trigger for the original leader |
| A comment mentions a human member or `@all`, without naming an agent or squad | **No** |
| A human replies to an existing comment without routing mentions | **Depends on the thread** — the parent or conversation agent takes precedence; a member-to-member reply alone does not start the leader |
| The leader's own comment (self-trigger) | **No** — guarded to prevent a loop |
| A comment containing only an issue cross-reference (`[MUL-123](mention://issue/...)`) | **Yes** — issue references aren't routing |

Dedup applies on top of these rules: if the leader already has a `queued` or `dispatched` task on this issue, a new trigger won't enqueue a duplicate.

<Callout type="info">
Explicit mentions take precedence for agent-authored results too. If a result names another agent, it hands work to that agent. Explicitly mention the original squad when its leader needs to coordinate the next turn with the squad briefing. See [mention routing](/mentioning-agents) for thread and grouping rules.
</Callout>

## Assigning vs. @-mentioning a squad

| Action | Changes the assignee | Result |
|---|---|---|
| **Assign an issue to a squad** | Yes | The squad becomes the assignee and the leader is triggered. |
| **@-mention a squad in a comment** | No | The leader handles that comment only; the current assignee is unchanged. |

@-mentioning a specific member directly hands the work to that member. Multica also dedupes repeated triggers and prevents the leader's comments from re-triggering itself, avoiding execution loops.

## Squads and Access

Adding an agent to a squad does not bypass its [Access](/agents#permissions-and-access). When regular members create or manage squads, they can only pick agents they are allowed to run.

Whether a member can assign or @-mention a squad also depends on whether they can run the squad's leader. If the leader is archived, or the current member isn't allowed to run it, the squad can't be assigned or @-mentioned.

## Creation and management permissions

Any workspace member can create a squad. Creators can modify and archive their own squads; workspace `owner`s and `admin`s can manage all squads.

Squad names don't have to be unique within the workspace. When changing the leader, the new leader joins the squad automatically; the current leader can't be removed directly — designate another leader first.

## Archiving a squad

Once archived, a squad disappears from lists, assignee pickers, and the @-menu, and cannot be restored.

To keep existing work owned, issues and automations currently assigned to the squad transfer to the former leader agent. Historical comments and activity records remain. If you need the same routing later, create a new squad.

<Callout type="warning">
Archiving cannot be undone.
</Callout>

## Using the CLI

```bash
multica squad create --name "Product Delivery" --leader delivery-lead
multica squad member add <squad-id> \
  --member-id <agent-or-member-id> \
  --type agent \
  --role "Owns frontend implementation"
```

Full commands in [Using the CLI](/cli).
