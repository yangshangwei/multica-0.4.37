A squad consists of one leader agent and any number of members. Assigning an issue to a squad does not run every agent at once. Multica wakes the leader first; it reads the context and decides who takes the next step.

Squads solve the question of who the work goes to. They don't merge multiple agents into a new agent, and they don't automatically raise concurrency.

When the workspace has no squads, the Squads page shows collaboration examples. Choose **New Squad**, then **Create from template** or **Create custom squad**. **Read the docs** opens this guide inside the app.

## Start from a template

Open **Squads → Templates**, then choose **Apply to project** to use a workflow on a new or existing project. Choose an execution runtime, or connect one later. Nine templates are built in:

| Template | Roster | Routes by |
|---|---|---|
| **Feature Delivery Squad** | Lead, Product Analyst, Architect, Implementer, QA Engineer, Code Reviewer | What the issue currently lacks: criteria, a design, the change, proof it works, a review |
| **Bug Fix Squad** | Lead, Product Analyst, QA Engineer, Diagnostician, Implementer | Triage, reproduce, diagnose unknown causes, fix with a regression test, verify |
| **Review Gate Squad** | Lead, Code Reviewer, Security Reviewer, QA Engineer, Agent Evaluator, Experience Validation Engineer, Migration Reviewer | Which applicable checks remain: code, security, tests, agent behavior, experience or migration; must-fix findings return to the author |
| **Discovery Squad** | Lead, Product Analyst, Architect | Whether the question is "what would count as done" or "how would we build it" — answers only, no code |
| **Docs Squad** | Lead, Technical Writer, Code Reviewer | Which document the shipped change invalidated, then whether the draft matches the code |
| **Maintenance Squad** | Lead, Security Reviewer, Diagnostician, Implementer, QA Engineer | Diagnose unknown flaky-test or upgrade failures, then handle one item at a time with verification |
| **Security Remediation Squad** | Lead, Product Analyst, Security Reviewer, Diagnostician, Implementer, QA Engineer, Migration Reviewer, Code Reviewer | Triage dependency, code and other security risks; reproduce a code vulnerability before repairing it; a security owner decides before reproduction and repair, and again before closing; repair outside production, verify independently, or escalate |
| **Release Squad** | Lead, Release Engineer, QA Engineer, Technical Writer | Release readiness: a rollback that exists, a verified build, notes that match |
| **Incident Response Squad** | Lead, Product Analyst, Implementer, Release Engineer, QA Engineer, Diagnostician | Restore service first; hand a separate root-cause follow-up to the diagnostician afterwards |

Each template creates an ordinary squad whose leader routes by @mention. The template supplies its roster and routing policy. Rosters overlap on purpose: Incident Response and Bug Fix seat nearly the same roles and route them in opposite orders, because for an incident, restoring service outranks understanding the defect. The Diagnostician is conditional: it investigates an unexplained failure, not every successful delivery, review or release.

Staffing a template creates the [role-template agents](/agents-create#role-templates) the roster needs, the squad, and its membership together. Nothing about how squads run changes: the leader still receives the work and still dispatches by @mention.

Three things are worth knowing before you click:

- **Roles you already have are reused, exactly as they stand.** If you staffed the Feature Delivery squad and then staff the Review Gate squad, both use the same Code Reviewer and QA Engineer — including any instructions you edited. Staffing a second squad never overwrites an agent.
- **Access defaults to "Only me"** on the agents it creates, so nothing widens silently. A squad the whole team assigns work to wants the workspace option.
- **Release and Incident Response seat a Release Engineer**, which is an `operator`-level agent. Staffing either one therefore creates an Operator, so an agent doing the staffing needs to be allowed to grant that level — a `coordinator` agent can staff the other seven but not these two, since nothing may create an agent more privileged than itself. A person staffing them is unaffected. See [Autonomy and the approval boundary](/agents#autonomy-and-the-approval-boundary).

If an agent already holds a role's default name but did not come from that template, staffing stops and says so rather than adopting an agent whose instructions it cannot vouch for. Rename yours, or build the squad by hand.

The leader's routing policy is copied into the squad's instructions, where you can edit it. A Multica update never overwrites it.

## Security remediation

The **Security Remediation Squad** (`security-remediation`, version 2) handles security triage and repairs in development or test environments. Its dedicated leader coordinates seven existing specialist roles. The roster's highest autonomy is Coordinator; it includes no Operator. Existing roles keep their saved instructions, skills, runtime and Access when reused.

Version 2 adds three constraints to the triage and routing of version 1: a code vulnerability is reproduced before it is repaired; two gates, one before reproduction and repair and one before closing, wait for a human security owner's decision; and the closing summary reconciles every conclusion with its source and the commit it applies to.

### Before you start

Check the following before the first issue. The workflow stops if any one is missing.

**Name a security owner.** On the squad detail page choose **Add Member**, pick a workspace member, and enter `security owner` as the **Role** ("安全负责人" also works). You can add several; any one of them can decide a gate. Without such a member the issue's creator takes the role. An issue created by an automation or an agent has no human creator, so the leader replies that the squad has no security owner ("小队缺少安全负责人") and stops. After adding one, comment on the issue and mention the squad; only then does the squad continue. Only a workspace owner or admin, or the person who created the squad, can add members and edit a **Role**, so they are the ones who name the security owner. The leader never adds a member or edits a role itself; when a change is needed it asks a person. The leader matches those words anywhere in the **Role**, rather than matching the whole role. Use `security owner` or "安全负责人" directly, and keep them out of other roles, including "not a security owner" or "security owner's assistant".

**Make sure the security owner can run the squad's agents.** Agents created by the template have [Access](/agents#permissions-and-access) set to "Only me": only the owner of the agents (the person who created the squad) can run them, and administrators are no exception. When the security owner is someone else, their decision has no effect:

- A comment that mentions the squad is posted, with a notice that the squad wasn't triggered because "This target can't be found, or you don't have permission to use it".
- A comment without a mention shows no notice and starts no agent.

There are two ways to let other people decide a gate:

- **Open it when you create the squad.** On the Squads page choose **New Squad**, then **Create from template**, and set "Who can assign work to this squad" to "Everyone in the workspace". A squad created with **Apply to project** in the template catalog has no such option; its agents are always "Only me".
- **Open it afterwards.** The owner of the agents opens each agent's detail page, goes to **Settings** > **Access**, and under "Who can run this agent" chooses "Entire workspace", or "Specific people" with the security owner selected, then clicks **Save**; nothing changes until it is saved. To change several at once, select the agents in the agent list and choose **Set access scope**. Change the leader and every member: after a decision, each delegation the leader makes is checked against the permissions of the person who decided. Agents that were reused keep their earlier setting, so check them too.

Opening the agents to the whole workspace also lets other members run them on the owner's runtime. Choose "Specific people" when only one or two owners decide gates.

**Bind the leader and members to available nonproduction runtimes.** If the leader has no runtime, the squad may appear in the `@` list but cannot be selected; permission alone does not make it runnable. Configure the runtime on the agent detail page and check that it is online.

**Raise the instruction size limit if the leader runs on Codex.** Otherwise the leader cannot read the roster or the squad instructions, and its instructions tell it to stop on every turn without delegating. See [Limits](#limits).

### Workflow

The three risk types follow different steps. A code vulnerability has the most:

| Step | What happens | Who moves it forward |
|---|---|---|
| Intake | The leader writes the triage record. If production is exploitable now, or credentials or customer data are exposed, it stops here and hands over to people | Leader |
| G1 | In one comment the leader dispatches the Security Reviewer and lists the open decisions with its own proposals. The Migration Reviewer joins when the change affects schema, API, installed clients or stored data | The security owner decides |
| Reproduction | The reproducer writes a test that fails on the baseline commit | The reproducer returns a result |
| Repair | The Implementer commits a minimal patch and does not modify the reproduction test | The Implementer returns a result |
| Verification | When the squad has a vulnerability verification member, it first reruns the reproduction test on the fix commit; then the QA Engineer verifies the original risk and runs regression checks | Each returns a result |
| G2 | In one comment the leader dispatches the Code Reviewer and the Security Reviewer, plus the Migration Reviewer when a migration is involved | The security owner decides |
| Closing | The leader reconciles the evidence, writes the summary and hands the issue over at `in_review` | A person accepts it and marks it `done` |

When everything goes well a person acts three times: the G1 decision, the G2 decision, and final acceptance. More human steps appear when G1 chooses human reproduction, when a reviewer is needed outside the two gates (for example a migration discovered halfway through the repair), when any member stops, or when the security owner's decision disagrees with a reviewer's result.

The gates need a person because the three reviewer roles are [restricted role templates](/agents-create#role-templates): their comments never start an agent and never wake the leader (see [Leader re-trigger rules](#leader-re-trigger-rules); reviewers reused from older versions are the exception, see [Existing squads](#existing-squads)). Once the review results are in, the workflow stays where it is until the security owner has read them and decided. After the Product Analyst, Diagnostician, Implementer or QA Engineer returns a result, the leader continues on its own.

All of this assumes the issue is assigned to this squad. When the squad was mentioned into someone else's issue, a member's result does not wake the leader, and the leader neither subscribes the security owner nor changes the issue's status: after every returned result a person has to mention the squad before the workflow continues. Assign the issue to the squad to get the full workflow.

The other two risk types differ from the table as follows:

| Risk type | Differences |
|---|---|
| **Dependency or component** | No reproduction test. At G1 the Security Reviewer supplies reachability evidence: the version actually resolved, the dependency path in the lockfile, and whether the affected function is called. Repair one advisory or dependency at a time and keep the lockfile and source evidence. When no safe, compatible version exists, hold and hand over to the security owner. |
| **Other risks** | Configuration, supply chain, build artifacts, agents, skills and MCP, and runtime boundaries. At G1 the Security Reviewer states the source, the trust boundary and the evidence gaps, and the security owner decides whether a reproduction test is needed. Missing evidence remains `unknown` with an owner and a next check. Never retrieve real secrets to fill a gap. |

When the cause or trigger of a code vulnerability is unclear, the Diagnostician investigates after G1 and before the repair; diagnosis and implementation go to different members. When scope or acceptance criteria are unclear, the leader asks the Product Analyst first.

Each role keeps its own stop and approval boundaries. In particular, the Diagnostician reports security defects or exposed credentials for human handling; the leader must respect that stop before any further implementation. The leader pastes the actual roster's exact member mention link and delegates one next step per turn; the batch of reviewers before a gate counts as one next step. A report written by the leader under another role's heading is not independent review.

### Deciding a gate

The leader's gate comment states which reviewers were dispatched, the open decisions with the leader's proposal for each, the conclusions available for each, who decides, and how.

| Gate | Open decisions | Available conclusions |
|---|---|---|
| G1: before reproduction and repair | Severity, disposition, route, deadline, who reproduces, who needs to know | Disposition: repair, not affected (with a reason and evidence), won't fix, risk accepted. Reproduction: the vulnerability verification member, independent human reproduction, self-proof by the patch author, not applicable |
| G2: before closing | Review conclusions, variant list, backport range | Accept, return (naming the gap), risk accepted |

The security owner reads the reviewers' results first, then writes the decision in either of two ways:

1. Comment on the issue, type `@` and pick the squad from the list that opens. A top-level comment and a reply both work. A name that was not picked from the list, or a pasted "@squad name", is plain text and not a mention; the squad name in the leader's gate comment is plain text too, so copying it does not work.
2. Post a top-level comment that mentions nobody.

For example, G1 decided the first way:

> @Security Remediation Squad G1: severity high; disposition: repair; route as proposed; due December 18; the patch author proves it; disclosure normal.

G2 decided the second way:

> G2: review conclusions accepted. Variant list confirmed, two places. No backport needed.

The most common mistake is to reply in the thread that holds the leader's comment without mentioning the squad. Such a reply may not reach the squad. When the thread starts with an agent's comment, the reply goes to that agent alone, on a turn where the leader has neither the roster nor the squad instructions; the version 2 instructions tell the leader to answer only with the correct way to decide, and the workflow does not advance. Only when the thread starts with a person's comment that itself went to this squad does the reply reach the leader with the squad's context. Use one of the two ways above rather than relying on a reply.

Keep these rules in mind:

- The second way works only when the issue is assigned to this squad. When the squad was mentioned into someone else's issue, use the first.
- The leader continues only after confirming three things: the decision comes from the security owner in person; every reviewer has returned a result after the comment that most recently dispatched that reviewer; and every open decision has a conclusion, written item by item or as acceptance of the proposals. An old G1 result, a result from before a returned G2, a failure notice or a progress comment cannot stand in for the current result. Won't fix, risk accepted and any deferral also need a reason and a review date. If anything is missing, the leader replies with what is missing.
- Post the release after every reviewer's result, and keep it unchanged until the leader explicitly confirms that this release passed its checks. An edit, adding or removing a reaction, resolving it or setting it as the conclusion, and adding or removing attachments increase the comment's `revision`, whoever does it. At validation time, a `revision` above 1 always invalidates the release, even if the text and author are unchanged. If the comment was too early or changed, the security owner must read the results and post a new comment; editing the old one cannot repair it. A normal reply, a waiting notice or a rejection is not confirmation that the release passed. The leader can reference and confirm this release in its next delegation, closing or handover comment; it does not need a separate acknowledgment comment.
- If nothing happens after the decision, check the permissions described in [Before you start](#before-you-start).
- If a reviewer never returns a result, or the thread shows a failure notice posted under its name, mention the squad as usual and say so. The leader checks the run history: if the run is still going, it says whom it is waiting for; if it ended without a result or no run exists, it dispatches that reviewer once more. Each reviewer has one retry per gate and one per temporary review point; returning G2 for another review does not reset that allowance. Another failure goes to the security owner to repair the cause, with no further automatic dispatch. The owner cannot waive a required review to release the gate. A reviewer's failure does not notify the leader on its own, and the failure notice does not count as a review result.
- A temporary review point outside G1 and G2 requires the same three checks, including the current review results. Other decisions handed to the security owner, such as whether to proceed on static evidence when safe reproduction is impossible, also require that owner's own unchanged comment.

Before posting the first gate comment, the leader subscribes the security owners on the roster to the issue, so they are notified when reviewers return results. People who turned notifications off are not notified and need to come back and look.

### Reproduction

A code vulnerability needs a "minimal security reproduction" before it is repaired: one automated test in the repository's test layer that fails on the recorded baseline commit because the security property is broken. It has four boundaries:

- Local test fixtures and synthetic data only. No outbound traffic; no real credentials, production or third-party systems.
- Stop once the flaw is shown to be reachable and triggerable. No payload chaining, data extraction or persistence. Memory-corruption and remote-execution flaws stop at evidence of the trigger.
- No attack script that can be used outside the test framework.
- The patch author must not modify the reproduction test.

It is a failing test, not an exploit. The squad still does not write exploits, attack payloads or data-extraction steps.

The security owner decides at G1 who reproduces:

| Reproducer | Condition | Recorded as |
|---|---|---|
| Vulnerability verification member | The squad has an agent whose role contains `vulnerability verification`, and it is neither the patch author nor a reviewer of the same vulnerability | Independent reproduction |
| Independent human reproduction | The squad has no vulnerability verification member; done by the security owner or someone they name, and the security owner posts the result as a comment in one of the two ways described in [Deciding a gate](#deciding-a-gate) | Independent reproduction |
| Self-proof by the patch author | The squad has no vulnerability verification member and the security owner accepts self-proof; the Implementer commits the failing test first and the patch second, as two separate commits | Marked "not independently reproduced" |
| Proceed on static evidence | Safe reproduction is impossible and the security owner decides to continue | The closing summary states this limit |

Only an independent reproduction lets exploitability be recorded as confirmed. The Diagnostician and the QA Engineer do not reproduce before the repair: their role rules tell them to stop and report when they meet a security defect. The QA Engineer must also stop if verification shows that a security defect remains; the leader cannot assign someone else to bypass that rule.

### The vulnerability verification seat

The vulnerability verification seat is a pilot. The template does not include it, and the roster still has seven working roles. Without the seat, G1 chooses between independent human reproduction and self-proof by the patch author.

If you need independent reproduction without a person doing it every time, add the seat yourself:

1. [Create an agent](/agents-create) with the instructions below. A hand-built agent has no autonomy level and the product currently has no control to set one, so the limits in the sample are instructions to the agent, not something the platform enforces.
2. On the squad detail page choose **Add Member**, select the agent, and enter `vulnerability verification` as the **Role** ("漏洞验证" also works).
3. Make sure the security owner can run it, as described in [Before you start](#before-you-start).

```text
# Vulnerability verification

You write the minimal security reproduction for the Security Remediation Squad and rerun it on the fix commit. You show that a security property is broken; you do not exploit the flaw, write the patch or review the patch.

## Responsibilities

- Write one minimal security reproduction: an automated test in the repository's test layer that fails on the baseline commit named in the delegation comment because the security property is broken.
- List places with the same pattern: how you searched, where it matched, and whether each match is reachable in the same way.
- When asked, rerun the same test on the fix commit and report the real result. Do not modify the test.

## Not your job

- Writing the patch or changing the code under test. If the patch has a problem, put it in your result; the Implementer handles it.
- Reviewing the patch. A vulnerability you reproduced is reviewed by someone else.
- Going past the stop point. Stop once the flaw is shown to be reachable and triggerable. No payload chaining, data extraction or persistence. Memory-corruption and remote-execution flaws stop at evidence of the trigger. No attack script that can be reused outside the test framework.
- Touching real environments. Use local test fixtures and synthetic data only. No outbound traffic. Do not read real credentials, production data or third-party systems.
- Any production operation. Commit only on isolated branches in development and test environments.

## Input

Read the triage record, baseline commit and stop boundaries in the delegation comment first, then the affected code path and the existing tests near it. When the delegation comment says to refer only to the `finding_id`, keep details that locate the vulnerability out of branch names, commit messages and test names.

## Deliverable

Post one comment that mentions no member or agent, stating in order:

- Reproduction: test file path and test name, baseline commit, the real command, exit code and failing output.
- Same-pattern list: the search pattern and directories, each match and whether it is reachable in the same way.
- Rerun after the fix (when asked): the fix commit, the real command and exit code.
- Not done: what you did not run, read or verify, and why.

## Done when

The reproduction test fails on the baseline commit, and it fails because the reported security property is broken. The commands, exit codes and output in your result come from runs you actually executed. The list states how you searched. The rerun targets the fix commit named in the delegation comment.

## When a person must step in

- Reproduction needs real credentials, production data, a production environment or a third-party system.
- The problem can be shown only by going past the stop point.
- Safe reproduction is impossible. State why and what you tried, then stop.
- You find signs that production is exploitable now, or that credentials or customer data are exposed. Report and stop.
```

This template exists only in the documentation. It is not a built-in role, and upgrades do not update it. Whether it becomes a built-in role depends on evidence from real use.

### Triage record and deadlines

The leader keeps a triage record in the issue's comments. Each update is a new comment that preserves the older record; it never edits an earlier delegation comment and risks cancelling or retriggering its runs. The version 1 fields are unchanged: risk type, source, affected surface and versions, reachability, affected assets, severity, exploitability, evidence state, production impact, route, blocked actions and next owner. Version 2 adds twelve fields:

| Field | What it records |
|---|---|
| `finding_id` | The finding's identifier: the issue number plus `-F` and a sequence number. A duplicate names the original finding |
| `cwe` | The CWE identifier |
| `severity_basis` | Why this severity: scoring vector, reachability, affected assets |
| `exploit_maturity` | Whether exploitation exists in the wild: `none-known`, `poc-public`, `exploited-in-wild`, `unknown` |
| `disposition` | `under_investigation`, `affected`, `not_affected`, `fixed`, `risk_accepted`, `wont_fix` |
| `not_affected_reason` | One of five fixed reasons, for example `vulnerable_code_not_in_execute_path` |
| `reproduction` | `independent`, `author-only`, `static-only`, `not-reproducible`, `pending`, `not-applicable` |
| `reproduction_ref` | The reproduction test's path and the baseline commit |
| `fix_ref` | The fix commit |
| `backport_range` | Versions or branches that need the fix |
| `due` | A date, `next-regular-release` or `unset` |
| `disclosure` | `need-to-know` or `normal` |

These fields are evidence recorded in comments. They add no issue status, approval type or permission. Four rules apply:

- `unknown` is never rewritten as not affected. `not_affected` comes only from the security owner's decision at G1, with a reason and evidence.
- `fixed` is entered only after G2 is accepted, with the fix commit.
- `risk_accepted` and `wont_fix` need a reason and a review date written by the security owner.
- `exploitability` records whether exploitability is confirmed in this project; `exploit_maturity` records whether exploitation exists in the wild. They are filled in separately and neither is derived from the other.

Default deadlines count from the moment the severity is confirmed at G1:

| Severity | Default deadline |
|---|---|
| critical | 7 days |
| high | 30 days |
| medium | 90 days |
| low | Next regular release |

The leader proposes a deadline from the table and the security owner confirms or changes it at G1. An unknown severity has no default; the security owner sets it. A flaw that is exploitable in production now does not use this table and goes straight to people and incident response. The deadline is one line in the triage record; it is not written to the issue's due date.

These numbers follow common practice. They do not come from any single standard and are not compliance advice. To use different deadlines, edit the table in the squad instructions on the **Instructions** tab of the squad detail page. The leader's own instructions carry a copy; when the two differ, the squad instructions decide.

### Evidence, variants and confidentiality

- **Conclusions are bound to commits.** Every conclusion names the commit it applies to. If the fix commit changes after verification or review, the earlier conclusions are void and the affected steps are redone on the new commit.
- **Closing reconciliation.** The leader's closing summary lists the source comment, author and commit for every conclusion: reproduction, repair, verification after the fix, regression, each reviewer's conclusion, and the security owner's decisions at G1 and G2. A conclusion that cannot be tied to a definite commit, or that was voided and not redone, does not pass. When a member's statement disagrees with the raw command output, the leader marks the difference and the raw output decides.
- **Variants.** The reproducer lists places with the same pattern, and the G2 reviewers check that the list is complete. After the security owner confirms it at G2, the leader creates one unassigned issue per variant in `backlog`, titled with only the finding identifier and a sequence number. Variants are not folded into the current patch. When the squad was mentioned into someone else's issue, it lists the variants and creates no issues.
- **Confidentiality.** With `need-to-know`, until the fix is released, the branch names, commit messages, PR titles and descriptions, and the titles and descriptions of derived issues the squad writes refer only to the `finding_id` and carry no detail that locates the vulnerability. Evidence in issue comments is always redacted. External disclosure (advisories, identifier requests, notices to upstream or customers) is drafted only; a person publishes it.

Deliver the affectedness decision, source and file/version evidence, minimal change, regression test that fails without the repair, actual commands and results, compatibility evidence, rollback limits and residual risks. The parent issue is handed over at `in_review`, with `done` left to human review or existing integrations. Record final `no_action` only when there is no next action to dispatch.

If the current deployment is exploitable, production is affected, credentials or customer data are exposed, or a safe compatible repair is unavailable, stop the local repair and hand the evidence to a human and the Incident Response or Release workflow. Production deployment, live migration, credential access or rotation, external notices and irreversible deletion require their existing individual approvals. The squad does not write exploit payloads or perform these operations.

After a recoverable blocker is resolved, the security owner posts a new, unchanged comment explaining how it was resolved, the evidence and the allowed nonproduction next step, using one of the [gate release methods](#deciding-a-gate). The leader checks the safety boundaries and required gates again; any remaining stop condition keeps the workflow stopped. That comment cannot override a member's own stop rules or bring incident-response work, real-credential access or third-party testing back into local execution.

### Limits

- **The gates depend on a person.** Once the review results are in, nothing moves without the security owner's comment. While the security owner is away the issue waits at the gate and stays `in_progress`.
- **There is no issue-level visibility control.** Anyone who can read the issue can read its comments. The confidentiality rules bind only what the squad itself writes; when a narrower audience is needed, the security owner decides whether to keep details outside the issue.
- **Confidentiality does not cover pushes.** `need-to-know` binds names and wording only. The reproduction test and the patch are commits on branches of the repository; once they are pushed, the repository's permissions decide who can read them. When people outside the need-to-know group can read the repository, `need-to-know` does not keep the reproduction test from being read before the fix is released; prepare a repository or fork that only that group can read first.
- **Isolation comes from the deployment.** "No outbound traffic" and "no real credentials" are instructions to the agents, not network or filesystem limits. The template adds no [filesystem sandbox](/security-model); put the squad's agents on a restricted nonproduction runtime.
- **Notifications may be off.** If subscribing the security owner fails, the gate is not blocked, and people who turned notifications off are not reminded.
- **Naming the security owner is bound by instructions.** The platform lets a leader manage squad members and edit the squad instructions. The instructions tell this leader not to, but that is not a platform restriction. The member list on the squad detail page shows who the security owners are now.

<Callout type="warning">
When the leader runs on Codex, raise Codex's instruction size limit first. Otherwise the leader cannot read the roster or the squad instructions.
</Callout>

With the default roster and minimal task context, the generated instruction file for a version 2 leader and squad measures 79,766 bytes (about 80 KB): the leader's own instructions, the Squad Operating Protocol, the roster and the squad instructions, followed by the platform's general guidance. Actual task and workspace configuration can make it longer. By default Codex reads only the first 32 KiB, so the roster and the squad instructions fall in the part that is dropped. Add one line to the Codex configuration file on the machine that runs the daemon. The file is `~/.codex/config.toml` by default; when `CODEX_HOME` is set in the daemon's environment, it is `config.toml` in that directory. The line must come before every `[...]` table in the file:

```toml
project_doc_max_bytes = 131072
```

- This is a temporary configuration step for tasks started afterwards; the daemon does not need a restart and does not currently raise this value to match the injected text. Edit an existing root-level key instead of adding a duplicate, and keep an existing larger value.
- `131072` is an example budget of 128 KiB, not a fixed value that fits every squad. Allow enough UTF-8 bytes for the actual generated `AGENTS.md`, including additional instruction files from the repository or its parent directories in the total reading budget.
- Before starting work, check that the new task's `CODEX_HOME/config.toml` retains the root-level `project_doc_max_bytes`, and check whether the installed Codex version reports instruction truncation. Do not copy or publish credentials when checking configuration.
- Without a sufficient limit, the version 2 instructions tell the leader to reply that this turn's instructions are incomplete ("本轮指令不完整") and stop, instead of delegating from a partial brief. This is a rule the model must follow, not a runtime guarantee that incomplete instructions will be rejected.
- That check decides whether the brief is complete by looking for the last section of the squad instructions, "最终证据" (final evidence). When you edit the squad instructions, keep that section and keep it last.
- This rests on Codex's public source code and on a manual measurement of the composed brief. Multica's automated tests cover only the copying of the configuration file and the presence of this stop rule in the instructions. It has not been verified with a real Codex run, and the instruction size limits of other runtimes have not been checked.

### Existing squads

Upgrading Multica does not change squads and agents that already exist. Their instructions are copies made when they were created.

| What the workspace has | Result |
|---|---|
| A Security Remediation Squad created before the upgrade | Keeps running as version 1 |
| No such leader, and a squad created after the upgrade | Leader instructions and squad instructions are both version 2 |
| A version 1 leader, and another squad created after the upgrade | The new squad reuses that leader: squad instructions are version 2, leader instructions are still version 1 |

In the third case the gates and the reproduction rules take effect through the squad instructions, but the older leader instructions say only "one next step per turn" and do not count a gate's reviewer batch as one step, so reviewers may be dispatched one at a time and more decisions are needed. The older leader instructions also lack the rule that a plain reply is not a decision: a reply without the squad mention, in a thread that starts with the leader's comment, reaches the leader without the squad instructions, so on that turn it acts on its version 1 instructions alone and the gate rules do not apply. If this combination runs on Codex without the higher limit, the squad instructions are cut in the middle of the gate section and the leader reads neither the conditions for a decision nor the reproduction boundaries; a check at the top of the squad instructions tells the leader to reply that the instructions are incomplete and stop. Raise the limit first, as described in [Limits](#limits).

Reused reviewers from older versions (Code Reviewer v1, Security Reviewer v1, Migration Reviewer v1 or v2) are not [restricted role templates](/agents-create#role-templates), so their comments still wake the leader. The instructions tell the leader not to treat an agent's comment as a decision, so the gate still waits for the security owner.

To move an existing squad fully to version 2, replace both instruction bodies by hand:

- **Squad instructions.** On the Squads page choose **New Squad**, then **Create from template**, and create a new Security Remediation Squad. Copy the full text from its **Instructions** tab, paste it into the **Instructions** tab of the original squad, and save. You can also switch to the new squad: it shares its leader with the original squad, so the leader step below is still required. Give it a different name when you create it, so that a decision does not mention the wrong squad.
- **Leader instructions.** The product currently has no place to view the leader template's text. Create a squad from the template in a workspace that does not have this leader yet and has an online runtime you can use, open the new leader's detail page, copy the full **System prompt** under **Capabilities** > **Instructions**, then paste it into the same place on the original leader and save.

Edited instructions are not merged automatically. Save your own changes first, then carry them into the new version one by one.

Routine upgrades remain a fit for Maintenance; ordinary defects use Bug Fix, and Review Gate reviews a finished change. Security Remediation connects those repair and review stages around a security finding. The version 2 workflow has been checked with instruction contract tests and scripted scenarios, in which test code plays every role; they show that the platform hands control to the party the instructions expect at each step. Whether a real model follows the instructions remains unverified, and this workflow is not a compliance statement. Use a restricted nonproduction runtime and review the evidence yourself.

## When to use a squad

Use a squad when the work needs several capabilities and the specific owner can't be determined when the issue is created. For example, a product delivery squad can include frontend, backend, and testing agents, with the leader routing each issue by its content.

When the scope is clear, assign directly to the matching [agent](/agents).

## Squad composition

| Setting | What it does |
|---|---|
| **Leader** | Must be an agent. Receives work assigned to the squad and decides how to handle it. |
| **Members** | Can be agents or human members. The same member can join multiple squads. |
| **Role descriptions** | Tell the leader what work each member is suited for. Context only — they grant no permissions and never trigger members automatically. |
| **Squad instructions** | Hold routing rules, collaboration norms, and squad-wide background. Provided to the leader only. |

Creating a squad requires a name and a leader. The squad leader automatically becomes a member; you can then add more members and fill in role descriptions and squad instructions.

## Execution flow after assignment

When a non-Backlog issue is assigned to a squad, Multica immediately enqueues a `task` for the **leader agent** (not for every member). The flow then looks like this:

1. **Leader claims the task.** The agent runtime picks up the task on its next poll, same as any other agent assignment.
2. **Leader is briefed.** On claim, Multica appends three sections to the leader's system prompt — see [What the leader sees on every turn](#what-the-leader-sees-on-every-turn) below.
3. **Leader posts one delegation comment.** The comment `@`-mentions the chosen member(s) using the exact mention markdown from the roster — that mention triggers a new `task` for each mentioned agent.
4. **Leader records its evaluation** via `multica squad activity <issue-id> action --reason "..."`. This writes an entry to the issue's activity timeline so humans can see the leader actually evaluated the trigger.
5. **The dispatch turn leaves the parent `in_progress`.** Same agent-managed status contract as a direct agent assignment — coordinating the squad is working the parent's ask, so the parent moves from `todo` to `in_progress`, and dispatching members is not delivery, so it stays there while the squad works.
6. **Leader stops.** The leader does not do the implementation itself. A delegated member's result comment on the same issue can wake the leader under the [comment-routing rules](#leader-re-trigger-rules). The leader then reads the update and either delegates the next step, escalates, moves the parent to `in_review` once the overall goal is met, or stays silent. `done` is left to a human reviewer or existing integrations (for example a PR with close intent that merges).

Work split into sub-issues uses a separate stage barrier. A child at `in_review` has delivered its work and still awaits acceptance; that status does not close a stage. When every child in the lowest unfinished stage reaches a `done` or `cancelled` category, an eligible parent agent or squad leader can be woken under the existing routing rules. Parents in Backlog, already closed, or assigned to a person do not wake an agent. Without explicit stages, all children form one group. Finishing an agent execution does not change these issue states.

If the issue is in **Backlog**, the leader is not triggered — Backlog is a parking lot, same rule as for direct agent assignment.

### What the leader sees on every turn

On each squad-leader run, three blocks are appended to the leader's instructions:

- **Squad Operating Protocol** — a hard-coded rule set: read the issue, delegate by `@`-mention, be terse (don't restate the issue body — the assignee can read it), record an evaluation every turn, **stop after dispatching** — the dispatch turn ends with the parent `in_progress` — and only move the parent to `in_review` once the overall goal is met. This protocol is system-managed and not editable.

  The status half of that protocol is **scoped to issues actually assigned to this squad**. A leader woken by an `@squad` mention on someone else's issue gets the same roster and delegation rules, but is told explicitly **not** to touch that issue's status — status stays with the issue's own assignee.
- **Squad Roster** — the leader's self-row plus one row per non-archived member. Each row carries the exact mention markdown (`[@Name](mention://agent/<uuid>)` or `[@Name](mention://member/<uuid>)`) the leader should paste — typing a plain `@name` won't trigger anyone.
- **Squad Instructions** — your custom guidance for this squad (set on the squad detail page or via `multica squad update --instructions`). Use this for routing rules ("send DB work to Alice, frontend to Bob"), escalation policies, or anything else the leader needs to know that isn't already in the issue.

## Leader re-trigger rules

Comments beginning with `/note` record information without starting an agent. Other comments route by explicit mentions and thread context before falling back to the assignee. The following assumes the issue is still assigned to the squad and the recipient passes Access and runtime checks:

| Event | Leader triggered? |
|---|---|
| A human posts a top-level comment without routing mentions | **Yes** — the leader can handle it as the assignee |
| A working agent posts a result without routing mentions | **Yes** — the leader re-evaluates the next step |
| Anyone explicitly mentions an agent or squad, including alongside `@all` | **Only the named targets** — no additional trigger for the original leader |
| A comment mentions a human member or `@all`, without naming an agent or squad | **No** |
| A human replies to an existing comment without routing mentions | **Depends on the thread** — the parent or conversation agent takes precedence; a member-to-member reply alone does not start the leader |
| The leader's own comment (self-trigger) | **No** — guarded to prevent a loop |
| A comment containing only an issue cross-reference (`[MUL-123](mention://issue/...)`) | **Yes** — issue references aren't routing |

Dedup applies on top of these rules: if the leader already has a `queued` or `dispatched` task on this issue, a new trigger won't enqueue a duplicate.

<Callout type="info">
Explicit mentions take precedence for agent-authored results too. If a result names another agent, it hands work to that agent. Explicitly mention the original squad when its leader needs to coordinate the next turn with the squad briefing. See [mention routing](/mentioning-agents) for thread and grouping rules.
</Callout>

## Assigning vs. @-mentioning a squad

| Action | Changes the assignee | Result |
|---|---|---|
| **Assign an issue to a squad** | Yes | The squad becomes the assignee and the leader is triggered. |
| **@-mention a squad in a comment** | No | The leader handles that comment only; the current assignee is unchanged. |

@-mentioning a specific member directly hands the work to that member. Multica also dedupes repeated triggers and prevents the leader's comments from re-triggering itself, avoiding execution loops.

## Squads and Access

Adding an agent to a squad does not bypass its [Access](/agents#permissions-and-access). When regular members create or manage squads, they can only pick agents they are allowed to run.

Whether a member can assign or @-mention a squad also depends on whether they can run the squad's leader. If the leader is archived, or the current member isn't allowed to run it, the squad can't be assigned or @-mentioned.

## Creation and management permissions

Any workspace member can create a squad. Creators can modify and archive their own squads; workspace `owner`s and `admin`s can manage all squads.

Squad names don't have to be unique within the workspace. When changing the leader, the new leader joins the squad automatically; the current leader can't be removed directly — designate another leader first.

## Archiving a squad

Once archived, a squad disappears from lists, assignee pickers, and the @-menu, and cannot be restored.

To keep existing work owned, issues and automations currently assigned to the squad transfer to the former leader agent. Historical comments and activity records remain. If you need the same routing later, create a new squad.

<Callout type="warning">
Archiving cannot be undone.
</Callout>
