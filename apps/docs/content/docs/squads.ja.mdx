---

スクワッドは、1 体のリーダーエージェントと複数のメンバーで構成されます。イシューをスクワッドに割り当てても、すべてのエージェントが一斉に動くわけではありません。Multica はまずリーダーを起こし、リーダーがコンテキストを読んで、次のステップを誰に任せるかを決めます。

スクワッドが解決するのは「仕事を誰に渡すか」という問題です。複数のエージェントを 1 つの新しいエージェントに統合することも、同時実行数を自動的に増やすこともありません。

## テンプレートから作成

**スクワッド**ページの **Use a template** で、スクワッドを一度に構成できます。組み込みは 8 つです。

| テンプレート | メンバー構成 | ルーティングの基準 |
|---|---|---|
| **Feature Delivery Squad** | リード、Product Analyst、Architect、Implementer、QA Engineer、Code Reviewer | 課題に今足りないもの：受け入れ基準、設計、変更、動作の証明、レビュー |
| **Bug Fix Squad** | リード、Product Analyst、QA Engineer、Diagnostician、Implementer | トリアージ、再現、原因不明なら診断、回帰テスト付き修正、検証 |
| **Review Gate Squad** | リード、Code Reviewer、Security Reviewer、QA Engineer | その差分にまだ足りない観点：正しさ、セキュリティ、動作の証明 |
| **Discovery Squad** | リード、Product Analyst、Architect | 問いが「何をもって完了とするか」なのか「どう作るか」なのか。結論のみで、コードは書きません |
| **Docs Squad** | リード、Technical Writer、Code Reviewer | 出荷済みの変更がどの文書を古くしたか、そして草稿がコードと一致しているか |
| **Maintenance Squad** | リード、Security Reviewer、Diagnostician、Implementer、QA Engineer | 原因不明の flaky テストやアップグレード失敗を診断し、検証付きで一度に 1 件ずつ |
| **Release Squad** | リード、Release Engineer、QA Engineer、Technical Writer | リリースの準備状況：ロールバックが存在するか、ビルドが検証済みか、記載が一致しているか |
| **Incident Response Squad** | リード、Product Analyst、Implementer、Release Engineer、QA Engineer、Diagnostician | まず復旧し、その後に別の根因調査を Diagnostician へ渡す |

8 つは 8 通りの実行モデルではありません。どれもリーダーが @メンションで割り当てる普通のスクワッドです。テンプレートが与えるのはメンバー構成とルーティング方針で、複数のエージェントを初めて組み合わせるときに間違えるのはそこです。構成の重複は意図的です。Incident Response と Bug Fix はほぼ同じロールを、逆の順序でルーティングします。障害対応では、不具合の理解よりも復旧が優先されるからです。Diagnostician は原因不明の失敗に限って使い、成功した配達・レビュー・リリースには追加しません。

テンプレートからの作成は、必要な[ロールテンプレートのエージェント](/agents-create#ロールテンプレート)、スクワッド本体、メンバー関係をまとめて作ります。スクワッドの動作自体は変わりません。リーダーが作業を受け取り、@メンションで割り当てます。

実行前に知っておくべき点が 3 つあります。

- **既にあるロールはそのまま再利用されます。** Feature Delivery を作ったあとに Review Gate を作ると、両方が同じ Code Reviewer と QA Engineer を使います。編集した指示もそのままです。2 つ目のスクワッド作成がエージェントを上書きすることはありません。
- **作成されるエージェントの Access の既定は「自分のみ」** です。暗黙に広がることはありません。チーム全員が割り当てるスクワッドではワークスペースを選んでください。
- **Release と Incident Response には Release Engineer が入ります。** これは `operator` レベルのエージェントです。したがってこの 2 つの作成は Operator を生成するため、エージェントが代行する場合はそのレベルを付与できる権限が必要です。`coordinator` のエージェントは他の 6 つを作成できますが、この 2 つはできません。自分より権限の高いエージェントは作れないためです。人が作成する場合は影響を受けません。[自律レベルと承認の境界](/agents#自律レベルと承認の境界)を参照してください。

ロールの既定名を既に別のエージェントが使っており、それがそのテンプレート由来でない場合、作成は中止して理由を表示します。指示の内容を保証できないエージェントをスクワッドに取り込まないためです。名前を変更するか、手動で作成してください。

リーダーのルーティング方針はスクワッドの指示にコピーされ、編集できます。Multica の更新が上書きすることはありません。

## 適した場面

仕事に複数の能力が必要で、イシュー作成の時点では具体的な担当者を決められない場合に、スクワッドを使います。たとえば、プロダクト提供のスクワッドにフロントエンド、バックエンド、テストのエージェントを入れておき、リーダーが各イシューの内容に応じて割り振る、といった形です。

仕事の範囲が明確なら、対応する[エージェント](/agents)に直接割り当ててください。

## スクワッドの構成

| 設定 | 役割 |
|---|---|
| **リーダー** | 必ずエージェントです。スクワッドに割り当てられた仕事を受け取り、どう処理するかを決めます。 |
| **メンバー** | エージェントでも人間のメンバーでもかまいません。同じメンバーが複数のスクワッドに参加できます。 |
| **ロールの説明** | 各メンバーがどんな仕事に向いているかをリーダーに伝えます。あくまでコンテキストであり、権限を付与したりメンバーを自動的にトリガーしたりはしません。 |
| **スクワッドの指示** | ルーティングのルール、協働の進め方、スクワッド全体で共有すべき背景を保存します。リーダーにだけ提供されます。 |

スクワッドの作成には、名前の入力とリーダーの選択が必要です。スクワッドのリーダーは自動的にメンバーになります。その後、メンバーの追加、ロールの説明、スクワッドの指示を続けて設定できます。

## 割り当て後の実行フロー

1. イシューが `backlog` 以外のステータスでスクワッドに割り当てられると、Multica はリーダーのためにタスクを作成します。
2. リーダーは、イシューのコンテキスト、スクワッドの指示、そしてメンバーのロールとスキルを含む名簿を見ます。
3. リーダーがコメントで適切なメンバーを @メンションします。エージェントへの @メンションは新しい実行をトリガーし、人間のメンバーへの @メンションはその人に通知を送ります。
4. メンバーの進捗と結果は元のイシューに書き戻され、リーダーは後続の情報に応じて再び調整できます。

イシューがまだ `backlog` にある間は、割り当てだけではリーダーはトリガーされません。`backlog` を出た時点で実行が始まります。

<Callout type="info">
リーダーの職責は調整であり、実装を自分で仕上げることではありません。振り分けを終えると今回の実行を停止し、メンバーが進捗を更新してから改めて判断します。適切なメンバーがいない場合、リーダーは自分で引き受けず、イシューにギャップを書き残します。
</Callout>

## スクワッドへの割り当てと @メンション

| 操作 | 担当者が変わるか | 結果 |
|---|---|---|
| **イシューをスクワッドに割り当てる** | はい | スクワッドが担当者になり、リーダーがトリガーされます。 |
| **コメントでスクワッドを @メンションする** | いいえ | リーダーがそのコメントだけを処理し、元の担当者は変わりません。 |

特定のメンバーを直接 @メンションすると、仕事はそのメンバーに渡ります。Multica は重複したトリガーをまとめ、リーダーのコメントがリーダー自身を再びトリガーすることも防いで、実行ループを回避します。

## スクワッドと Access

エージェントをスクワッドに入れても、その [Access](/agents#権限と-access) はバイパスされません。一般メンバーがスクワッドを作成・管理するときに選べるのは、自分が実行を許可されたエージェントだけです。

メンバーがあるスクワッドを割り当てたり @メンションしたりできるかどうかも、そのスクワッドのリーダーを実行できるかで決まります。リーダーがアーカイブ済みの場合や、現在のメンバーに実行権限がない場合、そのスクワッドは割り当ても @メンションもできません。

## 作成と管理の権限

どのワークスペースメンバーでもスクワッドを作成できます。作成者は自分が作ったスクワッドの変更とアーカイブができ、ワークスペースの `owner` と `admin` はすべてのスクワッドを管理できます。

スクワッドの名前は、ワークスペース内で一意である必要はありません。リーダーを交代すると、新しいリーダーは自動的にスクワッドに参加します。現在のリーダーを直接外すことはできず、先に別のリーダーを指定する必要があります。

## スクワッドのアーカイブ

アーカイブすると、スクワッドは一覧、担当者ピッカー、@メニューから消え、復元もできません。

既存の仕事が担当者を失わないよう、現在スクワッドに割り当てられているイシューとオートパイロットは、元のリーダーエージェントに引き継がれます。過去のコメントとアクティビティ記録は残ります。同じルーティングが後で必要になったら、スクワッドを作り直してください。

<Callout type="warning">
アーカイブは取り消せません。
</Callout>

## CLI の利用

```bash
multica squad create --name "Product Delivery" --leader delivery-lead
multica squad member add <squad-id> \
  --member-id <agent-or-member-id> \
  --type agent \
  --role "フロントエンド実装を担当"
```

完全なコマンドは [CLI コマンドリファレンス](/cli)を参照してください。
