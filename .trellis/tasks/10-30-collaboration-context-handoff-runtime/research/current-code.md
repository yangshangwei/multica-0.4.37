### Corrections to make before activating the runtime child

1. Scope the missing paging claim to **runtime** context/CLI. Human comments already page. Choose whether additional human byte/total metadata is part of this child; it is additive, not a new pager.
2. Distinguish `included_in_prompt` / potential reader IDs, command lifecycle state, and a model's reported processing. Do not label existing readers as actual comprehension or derive `completed_input_ids` from them.
3. Replace the example handoff `comment_id`/`version` with truthful `handoff_id`, correlated event ID/sequence, actor and timestamp. Initial assignment may have no handoff row; expose that absence. Decimal event sequences/revisions stay strings on the wire.
4. Define which snapshot is immutable. Current issue/context reads change over time; claim replay must not silently rebuild a different envelope. Keep a frozen handoff snapshot/reference and a separately labelled refreshed projection, following the memory base/latest distinction.
5. Decisions/reasons/verification are currently unstructured memory/comment text. The server can expose source pointers and quoted facts, but cannot invent a normalized confirmed decision or verification status without a writer contract. First increment should expose `not_structured`/source references rather than infer decisions with an LLM.
6. A `can_submit_command:true` author label does not turn all comments by that author into instructions. Only admitted frozen input/delegation is executable. Current metadata and immutable admission provenance must be separate fields; all general comments/memory/handoff quotations remain evidence data.
7. The parent permission question concerns knowledge promotion. It should not block deterministic runtime provenance research, but no candidate confirmation authority should be invented in this child.
8. Feature negotiation must not advance resource configuration epochs or revoke consent merely because a daemon upgraded. Parent's four independent feature flags are not current code; only add gates justified by deployment behavior, using existing host admission/claim negotiation patterns.

### Storage and migration decisions

- H1 can initially project existing rows; no new broad knowledge table is necessary. A durable H2 snapshot can use `collaboration_run_event`, with a deterministic producer key and a small claim support marker only if required to distinguish old runs. Any marker is additive and nullable for historical runs.
- H3 cannot recover a precise historical cause set from the last `wake_parent_run_id`. Recommend one narrow group wake-cause relation (group, monotonic order, cause kind/source ID, source run/input, nullable assigned continuation). Allocate order under the existing group lock. An event-backed implementation is acceptable only if it can persist pre-continuation causes and atomically freeze/consume their assignment without rewriting source facts. Mark older runs' cause coverage unknown.
- H4 can reuse existing event identity/sequence indexes. If a separate checkpoint receipt index or H3 unique/order index is justified, every new index uses its own `CREATE [UNIQUE] INDEX CONCURRENTLY` migration. No foreign keys/cascades. Application cleanup must include any new relation.
- Before adding any new event kind, update `ListCollaborationRunRecordEvents` and `collaborationRecordEventItems` together. Internal metadata events should be filtered explicitly, as preparation events already are. Checkpoints should map to the existing public message/tool discriminants where possible. Do not emit an unknown record item to installed v1 clients.
- Checkpoint and final-outcome messages need stable identity/coverage rules. Current item IDs are `event:<event-id>:<within-event-index>`; separate final and checkpoint events otherwise produce duplicates. Define a single canonical message sequence and final-covered-through marker before coding ingestion.
- Fresh/upgrade/reapply and rollback/old-client reads must preserve history. Turning off new writes cannot make already persisted new events unreadable.

## Caveats / Not Found

- No durable checkpoint stream, versioned handoff snapshot or complete wake-cause set was found in the inspected paths. This report does not claim full repository absence beyond these owners.
- Existing provider final outcome body is recorded but may be absent, partial or rejected; it is not interchangeable with completion proof. No server-owned structured decision/verification catalogue exists in these paths.
- A byte budget smaller than a single encoded comment requires an explicit policy: reject with a required minimum, or offer a separately paged item body. Silently skipping the item or returning the same cursor would violate the parent's complete-recall acceptance. Select this policy in the child design.
- The host currently aggregates model usage only at final result; checkpoints cannot truthfully invent intermediate token/cost totals.
- Checkpoint redaction reduces exposure but is not a guarantee of secret removal. Preserve the existing source-private read boundaries and explicitly document that server memory purge does not purge provider/local copies.
- E0 upstream 502 and E1–E6 gates belong to the closure owner. No real-account or model evidence was produced here. Deterministic fake-provider acceptance is necessary but cannot establish model compliance with provenance guidance.
