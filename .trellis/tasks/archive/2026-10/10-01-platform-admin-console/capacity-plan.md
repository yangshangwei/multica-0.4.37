# 容量与性能设计

用户已确认 100–1000 台终端。以下是待验证的工程基线，不是当前系统实测数据或容量承诺。

## 1. 负载假设

| 变量 | 基线 / 压力场景 |
| --- | --- |
| 管理安装实例 | 100 / 1000 |
| runtime 数 | 平均每实例 3 个，峰值 5 个；实际 workspace/provider/profile 分布需记录 |
| 并发后台观察者 | 10；压力测试 30 |
| 历史执行 | 100 万条测试夹具，分布含重试、失败、取消、缺失用量 |
| 并发执行 | 暂按 100 正在运行，峰值 300；非用户确认值，仅压测场景 |
| 参考环境 | 记录实际 CPU/内存/磁盘/网络与 API/DB 拓扑；起始可用 API 4 vCPU/8 GiB、DB 4 vCPU/16 GiB SSD 做对照，不作为安装最低要求 |

## 2. 频率与速率

新客户端状态每 60 秒上报一次、±20% 抖动，1000 个实例约 16.7 次/秒；活跃窗口 180 秒。状态只更新当前快照，不能每次另写完整历史资产事件。

现有 daemon 默认心跳 15 秒（server/internal/daemon/config.go:24），心跳写库节流与 sweeper 窗口按原实现保持。3000 runtime 按每个 15 秒逻辑更新估算约 200 个 runtime 更新/秒；HTTP/WS 批处理请求数应按实测计数，不能把逻辑条目数当 HTTP QPS。峰值 5000 runtime 约 333 个逻辑更新/秒，单列在压测结果中。

10 名管理员的前台总览/列表 15 秒、详情 5 秒轮询，假设每人同时 3 个查询，查询量约 2–6 QPS。后台 tab 不轮询；mutation 成功精确失效相关 Query，不全量刷新所有页面。

断线重连采用指数退避加全抖动，建议上限 60 秒；保留原协议安全性。模拟 1000 个实例同时重连，报告连接恢复曲线、429/503 比例、认证延迟与 DB 连接池峰值。

## 3. 查询和存储策略

- 默认 50、最大 100 的复合游标分页；避免深 OFFSET。筛选 SQL 使用具体字段、范围和组合索引，不在前端拉取全量再过滤。
- 每个现有 task 状态和安装快照保持事实来源；管理查询只做受限关联，不写另一套任务状态。
- 当前健康保持快照；历史分析优先复用既有按日用量，P2 才增加必要汇总。机器 ID/task ID 不做无限基数 Prometheus label。
- 单次读查询窗口与 timeout 有界；解释计划验证 common filters 与排序。根据实测确定并发/statement timeout，不能用截断未告知用户来假装快速。
- 不集中上传全部本地 daemon 文件日志；首期使用既有执行反馈及受权限控制的诊断内容。后续全文检索和对象存储另立容量课题。

## 4. 数据保留工程初值

| 数据 | 建议保留 | 执行约束 |
| --- | --- | --- |
| 安装当前快照/绑定 | 活跃期间持续；退役保留关联历史 | 不随客户端离线删除 |
| 未确认管理操作 | 至确认/人工处置完成 | 不按简单 TTL 丢掉仍需协调的操作 |
| 已确认操作与告警 | 90 天可检索，关联摘要留审计 | 首次上线先只显示策略，不立即启动破坏性清理 |
| 管理审计 | 365 天 | 脱敏、追加；删除策略独立评审 |
| enroll/binding challenge | 分钟级有效；消费结果短期留作幂等校验 | 不存明文秘密；过期清理不破坏完成接入 |
| 既有任务/用量/日志 | 沿用既有保留策略 | 本项目不擅自清理历史业务数据 |

上线时需由部署配置明确实际保留天数，页面展示真实值。工程初值不等于已批准的数据删除动作。

## 5. 性能验收

目标：1000 安装、100 万历史执行、10 个观察者时，关键分页 API P95 ≤800 ms，Web 首屏 ≤2 s；采样窗口至少 10 分钟，报告 P50/P95/P99、错误率和样本数。

分别测：热/冷查询、最常见过滤、空过滤、大时间窗、首次登录、角色撤销风暴、集中重连、DB 慢查询、缺失用量和故障恢复。使用 fake agent/protocol fixtures，不启动真实个人 agent CLI 或消耗模型配额。

鉴权正确性优先于缓存速度。达不到目标时记录瓶颈与修订建议；不得通过绕过权限、返回旧角色或取消审计来达标。
