### P1-01: keep the composer alive while removing hidden interaction

Files found:

- `packages/views/chat/components/chat-window.tsx` — retained floating chat, dialog visibility and header/popup ownership.
- `packages/views/chat/components/use-chat-input-focus.ts` — opening focus nonce, opener tracking and closing focus return.
- `packages/views/chat/components/chat-fab.tsx` — launcher, dialog relationship and close-time fallback target.
- `packages/views/chat/components/chat-input.tsx` — retained composer with visibility-gated portalled actions.
- `packages/views/chat/components/chat-queue.tsx` — retained queue with visibility-gated action menu.
- Corresponding tests beside these files — lifecycle, preserved draft identity and popup dismissal cases.

Code patterns:

1. The retained root uses `isVisible = isOpen && (isExpanded || boundsReady)` at `chat-window.tsx:100`, then sets `aria-hidden={!isVisible}` and `inert={!isVisible}` at lines 828–829. Pointer events also use `isVisible` at line 789. This covers the closed window and the open-but-unmeasured interval.
2. `useChatInputFocus` uses a layout effect, not a mount-time autofocus. It records the actual opener on a closed-to-open transition (`use-chat-input-focus.ts:47`), waits for visibility before requesting editor focus (`:71`), and returns focus only when focus still belongs to chat (`:54`). It avoids stealing focus when chat is persisted as open during initial page load.
3. Closing can blur an inert descendant before the effect runs. `lastFocusedRef` and the body check at `use-chat-input-focus.ts:57` cover that case; React focus capture also records portalled descendants. Detached/hidden/disabled openers fall back to `[data-chat-launcher]` at line 65.
4. The FAB unmounts while open (`chat-fab.tsx:44`) and remounts on close. It now supplies `data-chat-launcher`, `aria-haspopup`, `aria-controls`, and `aria-expanded` at lines 65–70.
5. An inert DOM ancestor does not cover a popup physically rendered elsewhere by a portal. Current code conditionally mounts the header at `chat-window.tsx:849`, project/actions at `chat-input.tsx:657/722/738`, and queue menus at `chat-queue.tsx:163`. The editor and drafts remain mounted.

Existing regression tests found:

- `chat-window.test.tsx` checks hidden accessibility roles, retained editor identity, opening focus, closing focus return, unsent draft persistence, history popup dismissal, add-menu dismissal, and project-picker dismissal without losing context.
- `use-chat-input-focus.test.ts` is the canonical transition matrix: no focus on initial mount, every explicit reopening, bounds readiness, unchanged rerenders, shortcut opener, unrelated focus, and a removed opener.
- `chat-queue.test.tsx` checks dismissal of the portalled action menu while retaining queued messages and avoiding business mutations.

Remaining acceptance checks:

- In actual Chromium/Electron, focus the visible launcher and press Shift+Tab repeatedly while closed. No descendant of `#floating-chat-window` or its former portals may receive focus. Capture the accessibility tree as well as DOM attributes; jsdom cannot prove browser inert behavior.
- Open with launcher and keyboard shortcut, close from the composer/header and from an open history/add/project/queue popup. Check focus return and reopening with the same editor draft. Include a disabled composer, where the named window is the current fallback.
- Do not add a modal focus trap merely to fix hidden focus. The current dialog is a floating nonmodal workspace tool; its visibility contract should remain distinct from modal page blocking.

### P1-03: one labelled primitive per selection, with parent-cell isolation

Files found:

- `packages/views/issues/components/list-row.tsx` — per-issue selection over the existing priority icon.
- `packages/views/issues/components/list-view.tsx` — group selection and mixed state.
- `packages/views/agents/components/agents-page.tsx` — agent row/header checkbox cells and row navigation.
- `packages/views/projects/components/projects-page.tsx` — project row/header checkboxes, compact table.
- `packages/views/skills/components/skills-page.tsx` — established directly-labelled checkbox pattern.
- `packages/ui/components/ui/checkbox.tsx` — Base UI wrapper with built-in focus ring and checked/mixed semantics.
- `packages/views/locales/{en,zh-Hans}/{issues,agents,projects}.json` — translated object/range names.

Code patterns:

- Task row selection now uses `Checkbox` with `Select {{identifier}}` at `list-row.tsx:100`. It remains in keyboard order, reveals on row focus-within, and switches the priority icon with opacity instead of display-none. Task group controls use `Select all loaded issues in {{status}}` at `list-view.tsx:558`, which accurately names the loaded scope and retains indeterminate state.
- Agent row controls now receive `Select {{name}}` at `agents-page.tsx:402/1310`; header selection is directly labelled at line 692. `focus-visible:opacity-100` makes keyboard-focused controls visible. The current all-selection copy is "Select all agents" even though the associated test describes filtered selection; consider making range copy explicit only after confirming the precise filtered/all contract.
- Project row and header controls already use the skill-library pattern: `projects-page.tsx:352/500` names each target, preserves mixed state and uses a visible non-text border plus focus ring.
- Put `rowLinkInteractiveProps` on the containing cell, not only the Checkbox root (`agents-page.tsx:401`, `projects-page.tsx:351`). Base UI may emit another click from a sibling hidden input; stopping only the root click would allow selection to navigate the entire row. The existing skill-presentation spec explicitly documents this at `.trellis/spec/views/frontend/skill-presentation.md:33`.
- `packages/ui/components/ui/checkbox.tsx:10` supplies focus-visible border/ring treatment. Preserve the primitive rather than nesting it inside another button with separate `aria-pressed` state.

Existing regression tests found:

- `list-view.test.tsx:287` uses actual Tab/Shift+Tab and Space to move from group control through the accordion trigger to a row checkbox, asserts mixed/full/off group state, and ensures selection does not collapse the group.
- `agents-page.test.tsx:322` covers row/all selection, mixed state, maintained focus and no navigation on ordinary/modifier/middle interactions. It asserts focus CSS classes, but its `.focus()` calls and jsdom rendering do not prove real opacity or responsive reachability.
- `projects-page.test.tsx:408` covers exactly one named control per selection, keyboard mixed state and no navigation. It directly focuses the control instead of proving the full page Tab path.

Remaining acceptance checks:

- Use real keyboard traversal without any mouse hover in the 1440px desktop. Record focused checkbox opacity and visible ring in light and dark themes for all three lists.
- Inspect an active filter/group and confirm the select-all name matches the entities actually selected; preserve server/client state ownership and existing selection behavior.
- At 900px and enlarged UI, agent checkbox cells remain conditionally hidden below the existing `@2xl` container breakpoint. This predates the current fix; verify the intended compact selection alternative before claiming narrow-layout batch selection is covered. This research did not establish that alternative.
- Checkbox Space/click/middle/modifier operations must not open issue/agent/project details or start row drag. Preserve the existing sortable row event guards and group collapse behavior.

### P1-04: project identity is an anchor; the rest of the row remains a pointer shortcut

Files found:

- `packages/views/projects/components/projects-page.tsx` — `ProjectTableRow` renders a focusable title anchor.
- `packages/views/navigation/app-link.tsx` — canonical shared adapter link, browser/desktop modifier behavior and prefetch-on-focus.
- `packages/views/navigation/use-row-link.ts` — row pointer fallback and click/auxclick isolation.
- `packages/views/projects/components/projects-page.test.tsx` — component wiring and title/row interaction regressions.
- `packages/views/navigation/app-link.test.tsx` — canonical generic link behavior, including focus prefetch.

Code patterns:

- The project table title at `projects-page.tsx:394` uses `href={rowHref}`, `newTabTitle={project.title}`, and `rowLinkInteractiveProps`. Its visible focus ring lives at line 398.
- `AppLink` calls consumer handlers before adapter navigation (`app-link.tsx:43/51`). Propagation is stopped without preventing the link's native/adapter behavior. Desktop middle clicks explicitly open the destination tab; web leaves native anchor behavior intact (`:100`).
- Keep whole-row navigation as a convenience on the plain `ListGridRow`. Do not make the entire interactive row another anchor or button; it contains checkboxes, menus and inline editors.
- `use-row-link.ts:14` still says the name should stay plain text and avoid a second entry point. That comment conflicts with `CLAUDE.md`, `.trellis/spec/views/frontend/component-guidelines.md:118`, `.trellis/spec/views/frontend/skill-presentation.md:32`, and the existing agent/skill/project identity link pattern. A focused comment correction is useful if the implementation owner touches that file; no behavior rewrite is necessary.

Existing regression tests found:

- `projects-page.test.tsx:277` proves that Tab from the row checkbox reaches the title and Enter navigates exactly once.
- Cases at lines 291 and 310 assert one navigation for title click, desktop modifier/middle clicks, and native web modifier behavior. Cases at lines 325 and 336 retain row pointer navigation and isolate inline controls.

Remaining acceptance check: on the real desktop table, Tab to a long project title, observe a visible focus indicator, press Enter, and verify the exact detail URL/tab title. Confirm that its menu and inline fields retain their own focus/activation paths.

### P2-08: reuse Base UI tab behavior while preserving drafts and URL contracts

Files found:

- `packages/views/agents/components/agent-overview-pane.tsx` — top-level and nested detail navigation with dirty-editor confirmation.
- `packages/views/skills/components/skill-detail-page.tsx` — top-level Overview/Files tabs, file panels and preserved drafts.
- `packages/views/skills/components/file-tree.tsx` — file triggers inside the Files tab list.
- `packages/ui/components/ui/tabs.tsx` — shared Base UI wrapper forwarding root orientation.
- `apps/desktop/src/renderer/src/components/tab-bar.tsx` — desktop destination buttons and context actions.
- `packages/views/settings/components/settings-page.tsx` — established shared Tabs navigation pattern.
- Tests adjacent to the above consumers — keyboard behavior, URL parameters, panel associations and draft continuity.

Code patterns:

1. Agent top tabs use `Tabs` at `agent-overview-pane.tsx:346`, named `TabsList` at line 357, triggers at line 364 and matching panels at line 379. Both top and nested lists set `activateOnFocus={false}` so arrows move focus without immediately replacing a dirty editor. Nested orientation follows the mobile breakpoint at line 414.
2. Skill top navigation uses `Tabs` at `skill-detail-page.tsx:1245`, the named manual-activation list at line 1356 and matching panels at line 1393. The Files rail uses another named, vertical Tabs root/list at lines 642–649; file rows use `TabsTrigger value={node.path}` at `file-tree.tsx:208`.
3. Existing tests assert one tabIndex 0, Arrow/Home/End movement, Enter/Space activation, `aria-controls` panel association, preserved query/hash, and unsaved editor drafts. Preserve these semantics during visual verification; automatic activation would bypass or repeatedly trigger dirty-navigation confirmation.
4. The shared wrapper must forward `orientation` to the Base UI root (`packages/ui/components/ui/tabs.tsx:16`). Local `data-orientation` selectors prevent an outer vertical list from restyling an inner horizontal list; the UI spec already requires browser geometry validation for this.
5. Desktop tabs are workspace navigation destinations, currently represented by buttons. `tab-bar.tsx:320` now exposes only the active destination with `aria-current="page"`. There is no reason to claim a full ARIA tablist contract unless the shell is deliberately redesigned around that contract.
6. The existing desktop changes also cover P1-06: Alt+Shift+Arrow key commands at `tab-bar.tsx:305`, pointer context commands at line 449, focus restoration after movement at line 634, and pinned-segment boundaries at line 688. Coordinate with the desktop lane rather than editing the same file independently.

Existing regression tests found:

- `agent-overview-pane.test.tsx:252` covers top-level manual activation and URL query/hash preservation. The case at line 279 covers secondary vertical roving, editor identity, cancel/discard and destination confirmation.
- `skill-detail-page.test.tsx:180` keeps navigation keystrokes in an add-file input; cases at lines 193 and 226 cover manual top/file tab activation, panels and both description/file draft continuity.
- `tab-bar.accessibility.test.tsx` covers active destination semantics, keyboard movement, pointer movement, focus retention, storage rehydration, segment boundaries and Chinese command labels. Store clamp matrices remain canonical in the existing tab-store tests.

Remaining acceptance checks:

- Verify actual tab focus rings and visible panel geometry on the desktop at 1440px and 900px. For agent nested navigation, verify horizontal ArrowLeft/Right when narrow and vertical ArrowUp/Down when wide. Capture inactive panels in the accessibility tree and ensure retained panels do not expose hidden controls.
- Focus the agent Instructions tab with a dirty editor. Arrows must only move focus; Enter/Space must use the existing confirmation. Cancel preserves the editor; discard opens the requested destination. Check skill description and file drafts across top-level/file navigation.
- Inspect current desktop destination semantics and available keyboard/context reorder commands together. Do not divide P1-06/P2-08 changes to `tab-bar.tsx` between independent editors.
