# 设计安全漏洞修复 AI 小队

## Goal

**第二阶段授权（2026-10-27）**：用户在了解模拟结果及真实模型未验证的限制后明确要求“推进第二阶段”。本次按 `phase2-plan.md` 在现有任务中固化内置模板，准入依据调整为已完成的模拟、产品契约与阶段二检查；不把原真实模型门槛改记为通过，继续禁止真实运行时调用。

让团队可以把组件依赖漏洞、程序代码漏洞和其他安全风险送入一条可追踪、可分流、有人审查的修复流程。小队应帮助人判断“是否受影响、风险有多大、怎样修、怎样证明已经闭合”，但不能把未批准的生产操作或攻击性验证交给 AI 自行执行。

本次采用两阶段交付：先在当前工作区用现有角色组装并运行试点，收集真实证据和缺口；试点通过后，再把稳定的路由和边界固化为产品内置模板/角色。

### 当前续跑范围：用户授权的模拟验证（2026-10-27）

用户明确要求“不调用真实的运行时，模拟一下是否可行”。本轮改用脚本化 provider double 验证既有产品的排队、身份、精确派活、成员回传、leader 收口，以及合成补丁的独立测试；不再调用 Codex/OpenCode 或模型服务。输出必须明确标注模拟，不能把预设路由与补丁当成模型的自主决策。具体边界与验收见 `pilot/simulation-plan-20261027.md`。原阶段一的真实模型验收与阶段二准入仍单独保留，不自动勾选通过。

本轮模拟已完成：四个案例最终 `in_review`，29 次成功角色执行，24 项后端契约与 14 项模拟工具测试通过，并完成独立复核与临时环境清理。详见 `pilot/simulation-results-20261027.md`。本轮无需继续提供模型服务配置。

## 已确认的仓库事实

- 当前有 8 个内置小队模板：特性交付、缺陷修复、合并门禁、需求预研、文档同步、例行维护、发布、事故响应（`server/internal/service/builtin_squad_templates.go:102-396`；产品文档同步列出这 8 个模板）。
- 例行维护小队已经覆盖 CVE/安全公告的基本路径：先由安全审查员确认公告是否适用，再由实现工程师逐项修改，由测试工程师独立验证；涉及 schema/API/已安装客户端时加入迁移审查员（`server/internal/service/builtin_squad_templates/maintenance/INSTRUCTIONS.md:5-29`）。
- 安全审查员当前是 observer，只做基于代码和配置的报告，检查授权、输入注入、凭据、数据暴露、依赖和资源耗尽，不写漏洞利用、不修代码、不访问生产（`server/internal/service/builtin_agent_templates/security-reviewer/INSTRUCTIONS.md:5-27`）。其配套 `multica-security-review` skill 还要求威胁建模、信任边界、供应链和 SBOM 证据，缺证据时只能标记 `hold`/`unknown`（`server/internal/service/builtin_role_skills/multica-security-review/SKILL.md:20-44`）。
- 合并门禁小队已有安全审查员，但职责是审查已完成的 diff，不负责修复（`server/internal/service/builtin_squad_templates/review-gate/INSTRUCTIONS.md:1-31`）。
- 事故响应小队处理正在发生的生产影响，先止血、回滚或缓解，再做独立根因调查；生产动作由发布工程师在人工审批后执行（`server/internal/service/builtin_squad_templates/incident/INSTRUCTIONS.md:5-40`）。
- Agent 自治等级从 observer、contributor、coordinator 到 operator 逐级开放能力；生产发布、线上迁移、凭据访问、外部公告和不可逆删除必须逐项人工审批（`apps/docs/content/docs/agents.mdx:55-105`）。
- Multica 默认以守护进程操作系统用户的权限运行任务，不提供通用文件系统安全边界；隔离应由专用用户、容器或虚拟机提供（`apps/docs/content/docs/security-model.mdx:8-32`）。
- 小队由 leader 接收 issue，再通过精确的 @mention 按阶段派给成员；成员角色说明只是路由上下文，不会授予额外权限。新建角色默认 Access 为“仅自己”，创建小队不会隐式放宽权限（`apps/docs/content/docs/squads.mdx`、`apps/docs/content/docs/agents.mdx:30-55`）。

## Requirements

### R1. 统一分诊和分流

对每个安全事项记录来源、受影响组件/代码路径、受影响版本或部署、可达性、影响资产、严重程度、是否正在产生生产影响，以及证据状态（`confirmed` / `suspected` / `unknown`）。至少分为：

1. 组件/依赖漏洞（CVE、安全公告、锁文件或镜像中的受影响版本）；
2. 程序代码漏洞（授权、注入、凭据、数据暴露、资源耗尽等）；
3. 其他安全风险（配置、密钥暴露、运行时边界、供应链、部署或监控缺口）。

### R2. 区分例行修复和正在发生的事故

- 没有当前生产影响时，按“安全审查 → 最小修复 → 独立验证 → 门禁审查”推进；一次只处理一个 CVE、一个依赖或一个明确漏洞。
- 已确认可被当前部署利用、存在凭据泄露、客户数据暴露或正在发生影响时，立即转入事故响应路径，先请求人工介入和安排止血，再创建独立的根因与永久修复任务。
- 小队不得把生产发布、线上迁移、密钥读取/轮换或外部通知当作普通修复步骤。

### R3. 角色职责必须可审计且不自审

方案应明确 leader、分诊/风险评估、安全审查、诊断、实现、验证、迁移/兼容性审查和发布/事故升级的职责边界。修改代码的成员不能验证自己的修改；安全审查员不写攻击载荷、不直接修复；最终结论必须保留文件/版本/命令/测试/残余风险等证据。

### R4. 复用现有能力，避免权限膨胀

首选复用现有角色模板和小队机制；只有现有角色无法覆盖的职责才建议新增角色。安全审查和诊断默认为 observer/contributor 的既有等级，代码与测试为 contributor，路由为 coordinator，任何 operator 能力只用于已获人工批准的高风险动作。

### R5. 修复闭环必须可验证和可回退

每项修复至少提供：受影响性判断、最小变更、无修复时失败的回归/安全测试、修复后测试结果、依赖或 API 兼容证据、回滚限制、未解决风险和下一步 owner。仅编译通过或只跑静态检查不能视为闭环。

### R6. 先试点再固化

阶段一必须能在当前工作区用现有角色完成三类安全事项的非生产演练，并记录路由、证据、阻塞和误分流。阶段二只固化试点中重复出现且边界清楚的职责；不把未验证的假设写进内置模板。

## Out of Scope

- 本阶段不实现漏洞扫描器、CVE feed、SBOM 平台、SIEM 或自动生产补丁系统。
- 不设计或生成可直接使用的漏洞利用、数据提取路径或针对真实系统的攻击验证。
- 不绕过现有人工审批、自治等级、Access 或守护进程边界。
- 阶段一不修改产品代码；阶段二的代码改动必须在阶段一验收后另行启动。

## Key Decisions

- 两阶段落地：先工作区试点，再内置模板；阶段一的结果是阶段二的输入和准入门槛。
- 组件漏洞与普通依赖升级优先复用例行维护路径；代码漏洞可复用缺陷修复的诊断/实现/验证顺序；最终安全审查和合并门禁保持独立。
- 正在发生的生产安全事件转交事故响应/发布路径，安全修复小队只负责准备证据和非生产修复方案。
- 不新增“攻击验证”角色；安全证据以静态审查、威胁模型、可控测试和脱敏运行信号为主。
