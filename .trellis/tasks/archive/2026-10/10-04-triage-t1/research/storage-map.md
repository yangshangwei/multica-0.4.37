## Recommended concrete model

Prefer explicit server-owned admission state and candidate fields. In particular, keep candidate project/assignee separate from actual issue project/assignee: this prevents pre-admission project counts, inherited squads and assignment consumers from treating review intention as committed work. Merely reusing the actual columns makes correctness depend on patching every current and future projection.

1. Add `issue.admission_status text NOT NULL DEFAULT 'not_required'` with allowed values `not_required/pending/accepted/rejected/duplicate`. Ordinary existing/new issue creators inherit the default. This is not a new execution status. No public generic patch setter.
2. `workspace_triage_settings`: workspace UUID, enabled=false, target_status_key (default todo), require_priority=false, responsibility_mode (`none/notify/assign`), reviewer_user_id nullable, revision, updated_at/by. Lazily initialize with insert-on-conflict. Keep generic workspace settings independent.
3. `issue_triage`: issue/workspace UUID, round>=1, first_entered_at, entered_at, reviewer_user_id, snoozed_until, candidate_project_id, candidate_assignee_type/id, source_type (`manual/csv`), source_url, import_batch_id/row_number nullable, duplicate_target_id nullable and target reference snapshot. No title/description/comments/attachments copy. Priority, dates and labels remain ordinary issue attributes; project/assignee are candidates until acceptance. If reducing table count matters, these server-owned columns can live directly on `issue` rather than introducing this table; the authority separation still matters.
4. `triage_action`: UUID, workspace/issue UUID, round, actor_user_id, action, request_key UUID, payload_hash, old/new admission result, reason, before/after JSON snapshots, created_at, execution_state (`not_requested/pending/queued/failed`), execution_task_id, execution_error_code, notification delivery state. Unique `(workspace_id, actor_user_id, request_key)`; reject same key/different digest. Immutable decision/snapshots; execution and delivery progress are separate mutable columns. This one table serves history and durable action operation identity; another generic operation table is unnecessary.
5. `triage_import_batch`: UUID, workspace/creator UUID, file_name, content_digest, column_mapping, preview revision, totals/status, created_at, stable notification identity. Do not save raw file bytes unless needed for remapping; parsed cells suffice for 1,000 rows/5 MiB.
6. `triage_import_row`: batch/workspace UUID, physical row_number, original cells, normalized payload, errors/warnings, external_id, confirmed override/include flags, state (`valid/warning/error/skipped/imported/failed`), issue_id, last_error, attempted_at. Unique `(batch_id,row_number)`. Successful rows and provenance remain after issue deletion so retries cannot recreate a deleted imported issue.

Suggested indexes: admission workspace/status; queue `(workspace_id,entered_at,issue_id)` and snooze `(workspace_id,snoozed_until)`; history `(workspace_id,issue_id,created_at,id)`; import row uniqueness; nonunique `(workspace_id,external_id)` for successfully imported rows. External-ID uniqueness must NOT be an unconditional DB unique constraint because the product permits explicit import-anyway overrides.

## Transaction and idempotency contracts

### Enabled fence and action serialization

- Every operation producing pending work (manual create, import row, reopen) and disable uses the same locked settings row. Acquire workspace KEY SHARE first, settings lock next, then existing catalog/owner/issue locks in their established order. Disable counts `admission_status='pending'`, including snoozed rows, while holding the fence. A request queued behind disable rechecks enabled before writing.
- Every review request carries `request_key` plus `expected_revision`. Look up prior successful action by scoped key first; matching payload returns the original result even if current issue revision changed. Otherwise recheck human actor, workspace membership and item state inside the transaction, lock current issue, compare revision, validate ALL attributes/targets, write properties/admission/history and commit once. Conflicting second reviewer gets 409 plus current safe result; no new history or notification.
- Use `RequireHumanActor` router gate AND a handler/service actor check for approve/reject/duplicate/snooze/reopen/settings/import. Explicit manual input can retain existing permitted agent submission semantics without granting approval rights.
- Validated project, status, labels, assignee/reviewer and duplicate target must remain valid through commit. Use current same-workspace reads/locks, not preview data as authority. Snapshot duplicate target identifier/title in history; later reads resolve live target only within caller access.
- Reopen only rejected/duplicate; increment round and entered_at; retain first_entered_at and old history. Clear duplicate/snooze; apply current responsibility settings. Accepted/not_required cannot reopen in T1.
- Snooze is a timestamp predicate (`NULL OR <= now()`), not a required scheduled state-transition worker. Consequently a service restart cannot strand expired work. Optional reminder delivery uses a once-per-snooze-action event identity; it must recheck current pending state and snooze version before notifying.

### Accept and accept-and-execute

- Acceptance atomically moves candidate project/assignee to formal issue columns, applies explicit validated payload, admission status and execution target status, clears snooze, and records one action. Ordinary acceptance never calls generic UpdateIssue post-write dispatch or `IssueService.Create` enqueue behavior. A dedicated triage event can invalidate issue/project caches without an automation interpreting acceptance as assignment.
- Accept-and-execute validates actor invocation rights and current prerequisites, commits acceptance with a durable `triage_action.execution_state='pending'`, then attempts dispatch. A dispatch failure updates execution state/reason while preserving acceptance. Return accepted state and retry affordance rather than a generic failed-accept response.
- Execution attempt prepares external overlay before locks. A second transaction locks the operation/item, rechecks current accepted state, persisted assignee and current invocation authority, calls `EnqueuePreparedIssueTaskInTx`, and stores returned task ID/state in the SAME transaction. Commit precedes finalize/wakeup. If task ID already exists, return it without enqueue, even after it has completed/cancelled/failed. This closes the long-after-success duplicate window not covered by queue pending uniqueness.
- Retry endpoint refers to the original action ID, never repeats acceptance. Changed assignee/context must produce a clear conflict requiring an explicit fresh execution decision. A lost commit response is reconciled by reading that action; never blindly replay an uncertain commit. No external calls while row locks are held.
- Follow lifecycle transaction's NOWAIT/sorted owner lock approach where locks overlap runtime/agent/issue order; retry only clearly rolled-back lock failures. Do not introduce unbounded loops for uncertain commit results.

### CSV preview/commit

- Native Go `encoding/csv`, strict valid UTF-8 with optional BOM, maximum 5 MiB and 1,000 data rows; reject file-level failures before preview writes. Reject NUL and existing field length violations. Date-only strict parse `2006-01-02` with actual calendar validity. Mapping is explicit and persisted; state/iteration/attachments map only to warnings/unadopted fields.
- Preview can persist batch/row plan (no issues, tasks or inbox rows). Resolve candidate project/label by unique name, human by email and agent by unique name only within caller workspace/authority; missing/ambiguous/foreign candidates become empty with warnings. Store IDs as proposal, not authority. Similar titles produce candidates only.
- Commit accepts preview revision and explicitly selected/override rows. Recheck enabled and membership, then each row has its own transaction. Lock batch/row, return existing result for imported row; validate current referenced resources and current field input; create pending issue and history and mark row imported with issue ID atomically. `AllowDuplicate=true` bypasses ordinary title dedup only.
- For default external-ID skip across racing batches, take a transaction advisory lock on canonical `(workspace UUID, external ID)` before existence check and creation. Imported rows provide durable external identity, including after issue deletion. Override rows deliberately bypass skip, never row idempotency.
- Keep succeeded/skipped rows terminal for same batch; only failed/not-attempted rows retry. User edits to failed content create a new preview revision or new batch, never mutate payload under a successful row identity. File digest itself is not an idempotency key because intentionally repeated imports are allowed.
- Batch summary uses one durable identity per batch/recipient and updates totals on retries rather than creating another inbox row. Row-level entering-review notifications are suppressed for CSV; summaries go to importer and configured recipient (dedupe when same person).
- Failed-row CSV export must preserve quote/newline encoding and neutralize spreadsheet-formula cells; include human-readable row failures. Export only accessible batch rows, not hidden candidate data.

### Durable notification delivery without another generic service/table

Existing `CreateInboxItem` does not dedup; dispatching normal events again is insufficient. Small implementation: persist per-recipient generated inbox IDs with action/batch notification state in the decision transaction, then retry a separate delivery transaction that rechecks membership, inserts with `ON CONFLICT (id) DO NOTHING`, and marks delivery complete. Those stable row IDs must be generated once and stored, not regenerated on retry. Use a bounded action/batch pending scan after restart. Delivery failures never roll back admission. The self-event exception is the explicit batch summary to its initiating operator/importer.

Do not put title/description snapshots into broadcast event fields addressed to nonmembers. Inbox `details` remains `map[string]string` (IDs, counts and URL strings). Existing inbox archive/snooze must never mutate `issue_triage.snoozed_until`.

## Proposed HTTP boundaries

Workspace context continues to use current middleware/header conventions; exact route naming is owned by final design.

- `GET/PUT /api/triage/settings` — all members read, human owner/admin write, revision conflict and pending count on refused disable.
- `GET /api/triage` — items, total_pending/actionable/snoozed independent of filters, cursor/page metadata, typed source/reviewer/candidate filters, stable entered_at+ID ordering.
- `POST /api/triage/issues` — trusted manual-source pending creation, request key for uncertain response.
- `GET /api/issues/{id}/triage/history` and `GET /api/triage/history` — rounds/actions and CSV batch summary, readable with feature disabled.
- `POST /api/issues/{id}/triage/actions` — action enum, request key, expected revision, action-specific fields; returns typed item/action/optional execution outcome. `POST .../actions/{actionId}/execute` retries original execution only.
- `POST /api/triage/batch/preview`, `POST /api/triage/batch` — selected IDs/revisions only, accept/reject/snooze/reviewer only, per-item stable request key, preflight then per-row results.
- `POST /api/triage/imports/preview`, `PATCH /api/triage/imports/{id}/preview`, `POST /api/triage/imports/{id}/commit`, `GET /api/triage/imports/{id}`, `GET .../failed.csv` — batch ownership/workspace access checked each time.

## Verification owners and non-obvious gaps

- New canonical tests use `dbfx.Issue`, `dbfx.Insert/InsertNoID` and `testutil.Call`; avoid copying older open-coded fixture/recorder quartets. Reference rollback/fault injection and channel-based lock barriers in `handler/issue_revision_test.go` and `handler/lifecycle_handoff_atomic_test.go`.
- `handler/handler_test.go:44` exits **0** if DB unreachable. An unconfigured `go test` success is not evidence. Use the checkout's explicit isolated reachable DATABASE_URL, migrate it, and inspect named non-skipped test output. No ambient authenticated agent CLI is needed; fake runtimes and queue-row counts prove dispatch.
- Test disabled/default unchanged behavior, member-v-admin and machine actor denial, create-disable/reopen-disable races, candidate resource deletion/permission loss at commit, accept-reject conflicts, payload-key mismatch, fault at each transaction write, same-key replay after success and after task completion, dispatch failure/retry, import row double-submit/partial retry/external ID racing override, exactly one batch notification, expired snooze after restart, reviewer departure, duplicate-target deletion and issue/workspace teardown.
- Cover formal lists/counts/grouped/table/facets/children/project summaries separately from explicit all-status search. Keeping candidates separate reduces projection leakage but does not replace admission filters.
- Strict reason length is a new 1–2,000-rune T1 contract; current comment code's `commentHardCap=2000` is a COUNT of comments, not a content limit, so do not mistake that constant for text validation.
- Performance numbers in PRD remain targets until measured against 10,000 formal/2,000 pending issues and 1,000-row CSV, including preview/commit timing. This research did not run performance tests.
