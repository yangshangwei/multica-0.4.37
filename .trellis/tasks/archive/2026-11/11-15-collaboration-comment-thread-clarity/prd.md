# 协作任务详情评论区降噪与未解决讨论突出

## Goal

协作任务详情页的评论区现在操作按钮比正文更抢眼，状态没有视觉信号。重排后，用户打开页面应一眼看到**未解决的讨论**，正文是每条评论里最重的元素，低频操作和审计信息退到需要时才出现。

纯前端改动（`packages/views/collaboration` 加一个 `packages/core/collaboration` 纯函数），不改接口、不改权限判定、不改写入语义。

## Background

### 现状问题

- 每条评论纵向叠 6 行：作者行、「当前权限」、正文、回复/编辑/删除、解决讨论/表情、评论历史。三组操作分属三个容器，所以各占一行：`comment-list.tsx:134`、`discussion-actions.tsx:38`、`comment-history.tsx:18`。
- 操作按钮是 ghost + 前景色 + 中等字重，正文是常规字重，按钮在视觉上压过正文。
- 「当前权限」`<details>` 每条都有，位置在作者与正文之间（`comment-list.tsx:118`）。
- 已删除评论与正常评论占同样版面（`comment-list.tsx:127`）。
- 已解决只是作者行里一段灰字（`comment-list.tsx:116`）；回复关系只是「查看被回复评论」链接（`comment-list.tsx:126`），没有串结构。
- 「已加载 x / y 条评论」在全部加载完时仍显示（`collaboration-detail.tsx:128`）。
- 时间为 `toLocaleString` 的完整时间，精确到秒（`comment-list.tsx:115`）。

### 解决语义（服务端，不改）

- 一个讨论串 = 根评论 + 任意层级的所有后代（`collaboration_discussion.sql` 的递归 CTE）。
- 一个串同一时刻最多只有一条评论带 `resolved_at`：解决任意一条会清掉同串其它评论的解决标记（`ClearOtherCollaborationThreadResolutions`）。因此「串已解决」⇔ 串内存在一条 `resolved_at != null` 的评论。
- 每个串创建时都是未解决状态。
- `can_resolve` = 有评论能力 且（未删除 或 已解决）（`collaboration_comments_view.go:193`）。已删除且未解决的评论不能被解决。
- 只有编辑和删除会改 `updated_at`（`collaboration_comments.sql:30,39`）；解决与表情不改。

### 分页约束

- 评论列表按 `created_at DESC` 分页（`collaboration_comments.sql:26`），页面再按时间升序显示（`collaboration-detail.tsx:79`）。更早的评论可能尚未加载。
- 所以一个串的根或带解决标记的那条可能不在已加载页里：未全部加载时不能给出准确的未解决总数。规范禁止把已加载页的数量说成总数（`.trellis/spec/views/frontend/collaboration-detail.md` §3）。

### 必须保留的既有契约

- 恢复与重试：未知回执的 recover / retryOriginal、编辑冲突、内容省略后按需加载（`comment-list.tsx:128-131,153-159`、`discussion-actions.tsx:52-58`）。规范 §5 禁止把未解决的意图藏进折叠的祖先里。
- 单独恢复的评论并入已加载页时组件身份不变，未发送的编辑内容不丢（`comment-list.tsx:42`）。
- 锚点导航：`#comment-<id>` 聚焦、`target:bg-accent`、重复导航键（`collaboration-detail.tsx:49-68`）。
- 评论行按 ID 去重；Agent 徽标、外部协作者标记、长名字换行。
- 触屏下可点击目标 `pointer-coarse:min-h-11`。
- 「引用为结果」只在显式点击时准备结果草稿。
- 时间用 `useLocale()`。
- 文案只有 en 与 zh-Hans（`packages/views/locales`），需同步并通过 parity 测试；用词遵循 `apps/docs/content/docs/developers/conventions.zh.mdx`。

## Requirements

### R1 单条评论降噪

- R1.1 操作合并为一行。常显：回复、已有表情与表情选择。收进「更多操作」菜单：编辑、删除、评论历史、引用为结果、当前权限。
- R1.2 正文是评论中视觉最重的元素；常显操作为弱化样式。
- R1.3 「当前权限」不再每条常显，完整信息在菜单内。作者行保留现有的外部协作者与 Agent 标记，不新增其它权限标签。
- R1.4 已删除评论压成一行：作者、「评论已删除」、时间、更多操作菜单（回复、评论历史、当前权限）。已有表情仍可见，以便移除自己的表情。
- R1.5 七天内显示相对时间，更早显示本地化日期；完整时间可通过悬停获得，`<time dateTime>` 保留 ISO 值。
- R1.6 编辑过且未删除的评论显示「已编辑」，点击打开评论历史。
- R1.7 评论区（标题、列表、输入框）宽度统一到 75ch，与描述区一致。

### R2 讨论串与解决状态

- R2.1 回复挂在所属讨论下缩进显示，左侧竖线串成一个讨论；串内按回复关系深度优先、同级按时间升序；缩进最多 3 级。
- R2.2 父评论未加载的回复，按其最上层可知祖先归组，并保留「查看被回复评论」链接。父评论已加载时不再显示该链接。
- R2.3 「未解决讨论」定义：串内没有任何已加载评论带解决标记，**且**串内至少有一条未删除的评论。（根评论已删除且无回复的串不算。）
- R2.4 未解决的串展开显示，竖线使用更强的中性语义色（不用警示色）；串上只有一个常显的「解决讨论」按钮，位于根评论；根评论不可解决时位于串内第一条可解决的评论。其它评论的「解决讨论」在各自的更多操作菜单里。
- R2.5 首次显示时已解决的串折叠成一行：已解决标记、解决人、可展开；评论已全部加载时附带评论条数。展开后可看到全部内容并取消解决。
- R2.6 页面打开期间变为已解决的串保持展开，直到用户手动收起或重新进入页面；确保操作反馈与「取消解决」不会从用户眼前消失。
- R2.7 折叠只隐藏不卸载：串内正在编辑的内容不丢。
- R2.8 带未完成恢复操作的串（未知回执的评论修改或讨论操作）不得处于折叠状态。
- R2.9 锚点导航命中折叠串内的评论时，先展开再滚动聚焦。

### R3 评论区头部

- R3.1 标题旁显示评论总数（服务器未提供总数时不显示数字，保留现有的「未提供评论总数」说明）。
- R3.2 存在未解决讨论时，标题旁显示其数量，点击跳到第一个未解决讨论并聚焦。数量为 0 时不显示。
- R3.3 评论未全部加载时，未解决数量的文案明确是「已加载评论中」的数量。
- R3.4 「已加载 x / y」仅在未全部加载时出现，位于「加载更多」按钮旁。

## Acceptance Criteria

- [ ] AC1（R1.1, R1.2）一条本人撰写的普通评论，正文下方只有一行操作；编辑、删除、评论历史、引用为结果只能从「更多操作」菜单触达，功能与改动前一致。
- [ ] AC2（R1.1）从菜单打开编辑或删除后，焦点进入表单；关闭后焦点回到该评论的菜单触发按钮。
- [ ] AC3（R1.3）评论不再常显「当前权限」；打开菜单可读到角色与 AI 指令提交权限。外部协作者与 Agent 标记不变。
- [ ] AC4（R1.4）已删除评论只占一行，仍显示「评论已删除」，菜单内可回复与查看历史。
- [ ] AC5（R1.5）en 与 zh-Hans 下时间均为相对时间或本地化日期，`datetime` 属性为 ISO 原值，悬停可见完整本地化时间。
- [ ] AC6（R1.6）编辑过的评论显示「已编辑」，点击展开该评论的历史；未编辑的不显示。
- [ ] AC7（R2.1, R2.2）根评论与其回复渲染为一个缩进的讨论；父评论已加载时没有「查看被回复评论」链接，未加载时有且可跳转。
- [ ] AC8（R2.3, R3.2）标题旁的未解决数量符合定义：无回复的未解决评论计入；根已删除且无回复的不计入；全部成员已删除的不计入；已解决的不计入。
- [ ] AC9（R2.4）未解决的串只有一个常显「解决讨论」按钮；点击后请求与改动前相同（`POST …/comments/<id>/resolve`）。
- [ ] AC10（R2.5, R2.6）进入页面时已解决的串是一行折叠条，展开后可取消解决；在页面内刚解决的串不自动折叠，「讨论已更新」反馈与「取消解决」可见。
- [ ] AC11（R2.7, R2.8）串内有未知回执待恢复时该串保持展开，恢复按钮可见；手动收起一个正在编辑的串再展开，输入内容仍在。
- [ ] AC12（R2.9）通过链接定位到折叠串内的评论时，该串展开，目标评论获得焦点并滚入视口；重复导航仍然生效。
- [ ] AC13（R3.3, R3.4）还有下一页时显示「已加载 x / y」且未解决数量带「已加载评论中」的限定；全部加载后两者的限定都消失。
- [ ] AC14 单独恢复的评论并入已加载页后，其未发送的编辑内容仍在（现有回归用例继续通过）。
- [ ] AC15 窄宽度与长文案（长名字、长英文按钮）下无横向溢出；触屏下所有可点击目标不小于 44px。
- [ ] AC16 `pnpm typecheck`、`pnpm lint`、views 与 core 的相关 Vitest 通过；locale parity 测试通过。
- [ ] AC17 受影响的协作 E2E 选择器已同步更新；实际跑过哪些、哪些未跑，在交付说明中如实列出。

## Out of Scope

- 高亮「@我的」与「上次查看后的新评论」：评论数据没有逐条的提及或未读字段（`content-schema.ts:34`），需要接口支持，另立任务。
- 任何服务端、接口、权限判定、解决语义的改动。
- 评论输入框的发送、预览、AI 确认流程及其内部布局（`comment-composer.tsx` 不改）。
- 「加载更多」按钮的位置与文案（仍在列表下方）。
- 按解决状态重新排序讨论：保持时间顺序。
- 工作区任务详情页（`packages/views/issues`）的评论区；移动端。

## Risks

- 协作 E2E 默认不在 `make check` 里跑（需要专门的门控环境）。本任务会改动 5 个 E2E fixture 与 4 个 spec 里的选择器；如果门控环境起不来，这部分只能做到「已改未跑」。
- 「已编辑」用 `updated_at` 晚于 `created_at` 判定。协作侧只有编辑会在不删除的情况下改它；若其它路径改了 `updated_at`，会多显示一个「已编辑」，点开历史可核实。
- 本任务要改的文件里，`collaboration-detail.tsx`、两个 `collaboration.json`、`core/collaboration/index.ts` 上已有 11-14 的未提交改动（非本任务）。实施会叠加在其上，提交时只能提交本任务的改动。
