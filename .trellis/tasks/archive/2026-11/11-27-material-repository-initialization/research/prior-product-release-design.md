# 产品版本、物料归属与运行时接入建议

日期：2026-11-26。状态：规划补充，未实现、未执行真实仓库操作。本文集中记录本轮版本管理与接入讨论，其他规划文档引用本文；具体 schema、权限及实现接口仍待最终评审。

## 1. 本轮事实与建议的边界

| 内容 | 确定程度 |
| --- | --- |
| 按 V1.8.0、V1.8.1 等产品版本管理需求与 issue，各版本有自己的交付范围 | 用户明确提出，记为 D11 |
| 增加 `releases/<version>/`，正文仍按稳定物料 ID 存放 | 助手提出的设计建议，未获得独立的最终方案确认 |
| 自动初始化基础文件、后续目录与文档按需产生 | 本轮对“不用手工提前建目录”的建议；已有仓兼容和初始化审核规则待定 |
| 提供仓库地址，复用已配置运行时完成 Git 操作 | 用户追问的接入方向；“只填地址”以已有默认环境、认证和完整操作能力为条件，不承诺任意地址开箱可用 |

D1–D10 继续有效。补充版本管理不授权产品实现、真实仓库接入、代码自动合并或 QA 自动修复，也不表示本轮建议均已成为已确认决策。

## 2. 产品版本与物料修订

产品版本表达交付范围，例如 V1.8.1；Git commit 与文件摘要表达某份文档/代码的具体修订。同一产品版本可以经历多次需求评审，一个问题也可能关联多个产品版本。版本归属不能由默认分支名、最新 Git tag 或 Agent 的自然语言猜测决定。

建议版本具有系统内稳定身份与显示名称，并关联物料项目。需求、问题仍保持全局物料身份和固定路径；在 Multica 从版本入口管理和查看它们。

```text
system-materials/
├── requirements/
│   ├── REQ-0042/prd.md
│   └── REQ-0043/prd.md
├── issues/
│   └── ISS-0186/
│       ├── issue.md
│       └── resolution.md
└── releases/
    ├── v1.8.0/
    │   ├── release.yaml
    │   ├── test-plan.md
    │   ├── acceptance.md
    │   └── baseline.yaml
    └── v1.8.1/
        └── release.yaml
```

这里是各阶段可能形成的布局，不一次性生成所有文件：建立版本时可创建 `release.yaml`，测试计划、验收和发布基线在实际阶段产生。

| 文档 | 建议职责 |
| --- | --- |
| `release.yaml` | 版本定义、本次计划交付的需求和计划修复的问题引用；不复制正文，不保存每次运行状态 |
| `test-plan.md` | 本版本测试范围、验收项与跨模块场景 |
| `acceptance.md` | 对具体被测版本组合的验收结论与证据引用，不能仅写“已完成” |
| `baseline.yaml` | 发布时实际交付的物料修订、需求/修复结果、代码仓 SHA、构建标识及验收引用；与计划范围分别核对 |

正式版本范围以审核合并后的 Git 物料为准。Multica 保存候选排期、审批决定、实时状态和运行记录，并生成版本视图；调整正式范围需送审，不能在数据库和 Git 中各维护一份可独立生效的清单。讨论、指派和执行状态变动仍不产生 Git 提交。

当前范围引用应定位稳定物料 ID、路径及具体内容修订。新 PRD 与版本清单可在同一次提交中建立关联，合并后由系统记录实际提交和内容摘要；不把尚未生成的本次 commit SHA 写回其自身文件。发布基线在后续步骤引用已存在的物料提交与构建结果，保留不可变的发布凭据。

## 3. 产品 Agent 提交需求

建议入口为“物料项目 → V1.8.1 → 新建需求”。从版本入口创建时带入明确的目标版本；直接发起的需求由用户指定或在排期时选择。没有目标版本的需求可先保留待规划草稿，是否允许正式入库到未排期池尚待决定。

1. Multica 固定系统/项目、目标版本身份、物料仓、允许路径和候选正文修订，分配稳定需求 ID。
2. 产品 Agent 探索工程、澄清并生成 PRD；正文中声明版本不能自行覆盖可信任务配置。
3. 达到可评审条件后，受控提交在同一个 PR/MR 中创建 `requirements/REQ-0043/prd.md`，并修改 `releases/v1.8.1/release.yaml` 的需求范围引用。
4. 产品审核完整变更，包含需求内容及版本归属。产品批准后继续按 D7 检查权限、当前修订及 Git 门禁，合并并核对两个关联部分；半成功不得显示为已纳入版本。
5. 按 D8 创建或启动方案阶段，交接固定 PRD、产品版本及本次范围修订。增加关联或重放通知不重复创建阶段运行。

运行前再次核对版本是否允许变更。版本名称相似、版本不存在、属于另一系统、排期已改变或冻结后仍使用旧意图时，应显示原因；不能自动改投“最新版本”或静默新建版本。建议冻结后仅通过明确的变更审核调整，已发布交付基线保持不变。冻结/解冻和版本创建权限仍待定。

物料评审分支按配置创建，不强制每个产品版本维护长期 Git 分支。需求从 V1.8.0 延期到 V1.8.1 时，评审同一次排期变更中的移出/移入关联，保留原需求、讨论和证据；若来源版本已发布，保留其当时事实，在后续版本记录新增交付安排。

## 4. issue 的版本关系与提交

| 关系 | 示例与约束 |
| --- | --- |
| 发现版本 | V1.8.0 的具体测试构建；记录实际环境，版本未知时不猜测 |
| 影响版本 | 已确认 V1.8.0 受影响，其他版本可为待核实；发现于某版本不证明只有该版本受影响 |
| 计划修复版本 | 决定在 V1.8.1 处理；这是排期，不是修复事实 |
| 已验证修复版本 | V1.8.1 某构建通过复测，关联代码及证据；需要多个维护版本修复时分别记录 |

建议流程：

1. 测试人员或获授权的测试 Agent 从 V1.8.0 的问题入口报告，带入发现版本并记录实际被测构建、复现、预期/实际及原始证据。
2. 系统分配 ISS-0186 并准备 `issues/ISS-0186/issue.md` 候选变更，报告保存发现和已核实影响版本。问题审核、分流角色与入库生效规则沿用待定项，不因 D7 的需求审核规则而自动批准问题。
3. 分流后若决定在 V1.8.1 修复，提出该版本 `release.yaml` 的问题修复范围变更。修复启动仍需另行确定的 QA 权限和门槛，不能因建立关联即派发。
4. 修复后在 `resolution.md` 保留代码/构建版本与实际复测证据，再形成已验证修复关联。多个修复目标分别验收；一个版本通过不自动证明其他目标通过，整体关闭规则待明确。

同一 ISS-0186 可出现在 V1.8.0 的“发现的问题”和 V1.8.1 的“计划修复”列表，始终引用同一原始报告。发现/影响版本来自问题报告，计划修复范围来自版本清单，验证结果来自证据记录，避免维护同一关系的两份权威字段。

已发布版本仍允许登记后续发现的问题：更新问题报告及其版本关联，由 Multica 索引生成视图；不为了增加“发现的问题”去重写冻结的发布范围或当时验收结果。历史补充采用可追溯的新记录，不掩盖原结论。

## 5. 仓库接入与按需初始化

建议在已有默认运行环境和授权配置齐备时，用户只需填写物料仓地址。没有可用环境、平台工具或权限时，系统明确列出缺失能力，不把仓库地址当作认证或写入授权。

| 分工 | 职责 |
| --- | --- |
| Multica | 可信项目/版本绑定、物料编号与路径、冻结的提交意图、人工审核、阶段启动和结果核对 |
| 产品/测试 Agent | 在既有角色边界内产出正文、分析与证据建议，不自行批准或改变权限 |
| 获授权运行时/执行工具 | 读取、初始化、写文档、commit、push、创建/更新 PR/MR，以及接到有效合并意图后的受控合并 |

复用运行主机已有认证是候选执行方式，仍需选定并记录实际执行身份。Git clone/push 能力不等于 PR/MR 创建、状态读取或合并能力；后者需可用的平台 API/CLI 或已有连接器。具体执行适配方式待技术验证，不预先承诺免配置或完全无需平台接口。

建议分别检查读取、推送、PR/MR 管理与合并所需工具/权限。配置或只读检查无法证明的权限标记为未验证，在首个已授权操作时记录结果；接入探测不偷偷推测试分支或合并文件。凭据保留在授权环境，不放入文档、任务正文或仓库。

首次初始化通过独立、明确授权的仓库准备操作补齐说明、格式配置、模板与规则，保留可审查的差异。初始化规则文件需要工程维护权限，不沿用产品 PRD 的自动合并权限。空仓无默认分支时如何建立首个提交、初始化由谁审核仍待定，不承诺此时已能创建 PR/MR。已有仓检查兼容性后补齐必要内容，不覆盖或强迁移现有文件。

建立产品版本时生成版本定义；需求/问题第一次送审时创建其目录；设计、测试、修复和验收文件随真实产出增加。无需预建空目录或占位文档。旧项目未启用版本物料流程时保持原有行为；已启用流程但存在无版本旧物料时保留“未关联版本”，不得自动分配到最新版本。

Observer 的只读边界继续有效。若运行时承担 Git 写入，应使用系统独立授权的操作身份与窄合同，不能让只读产品 Agent 借别的凭据间接逃逸。若选择可写产品 Agent，需要重新设计角色与权限；当前讨论没有作出该选择。

## 6. 候选验证与待定事项

候选验证需覆盖以下结果，当前均未执行：

- 同时存在 V1.8.0/V1.8.1 时，需求正文与目标版本引用在同一评审中生效；错版本、缺版本、旧排期、冻结和重复提交不能静默成功。
- 同一 issue 发现于 V1.8.0、计划修复于 V1.8.1，两个版本视图可回查同一报告；多版本影响与修复分别表达，不能把排期或一次通过当作全部修复。
- 需求延期不移动正文或丢失关联；已发布版本仍能登记新发现问题，旧基线与实际交付证据不变，后续修改 PRD 不改变历史读取结果。
- 初始化重试、创建版本重试和 PR/MR 回执丢失不重复写物料或派发；已有文件不被覆盖，未授权的规则路径修改被拒绝。
- 只有读权限、只能推送但无 PR/MR 工具、可创建 PR/MR 但无合并权限等情况分别显示真实能力；无法确定时不伪报通过。
- 默认测试使用 fake provider、临时 Git 仓与隔离项目；真实平台验证另行授权，不使用用户环境认证作隐式探测。

仍需定案：首期是否包含完整版本闭环；版本创建/范围审核/冻结权限；未排期需求是否可正式入库；需求分批交付及多维护版本 issue 关闭规则；QA 入库与修复启动；初始化审核和空仓首提交；运行时 Git 与平台 API/CLI/连接器的具体适配。最终方案批准前不进入实现。
