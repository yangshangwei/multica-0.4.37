# Research: Editor interaction risks and test plan

- Query: Review mention suggestions, popup lifecycle, extension wiring and tests for the opt-in issue mention picker.
- Scope: internal; planning only. Excludes preference-store reuse and composer call-site investigation.
- Date: 2026-11-25
- Evidence: inspected current source and the leader's latest `prd.md`, `design.md`, and `implement.md`. No tests executed; the reported 51-test baseline is supplied evidence, not new verification.

## Findings

### Corrections needed in the proposed plan

1. **Blocking UX specification gap: keyboard entry into auxiliary controls.** `prd.md:31` requires plain-Tab acceptance and keyboard-operable filters; `design.md:63` describes already-focused controls but does not define how focus reaches them. Today plain Tab is consumed even with zero candidates (`packages/views/editor/extensions/mention-suggestion.tsx:425`); Shift/modifier+Tab falls through (`packages/views/common/picker-keys.ts:27`). The popup is appended to document body (`packages/views/editor/extensions/suggestion-popup.tsx:172`), so native reverse tab order is not a reliable toolbar-entry contract. Specify and communicate a deterministic keyboard route into the toolbar/footer and back to editing without inserting a mention. Do not simply add tabIndex or disable pointer focus and call the controls keyboard accessible. Add that route to AC6 and the real-editor checks in `implement.md:32` and `implement.md:62`. This is a missing interaction decision, not a reproduced runtime failure.

2. **Selection restoration must not disarm the active trigger.** `design.md:62` and `design.md:64` promise selection preservation/restoration. Explicit selection-only transactions disarm the trigger outside composition (`packages/views/editor/extensions/suggestion-trigger-arming.ts:108`). Therefore, retain the existing ProseMirror selection during filter/page/retry actions and avoid an unconditional `setTextSelection(savedRange)` or caret move on refocus. Restoration of an actually changed selection needs an explicit tested lifecycle; on Escape, dismissal may intentionally disarm it. Test pointer filter -> type another character -> accept at the original range. Merely asserting that focus returned is insufficient.

3. **Focused-control Escape needs plugin exit as well as visual cleanup.** The shared controller's Escape callback calls cleanup, relying on Tiptap's editor key handler to dispatch the exit (`packages/views/editor/extensions/suggestion-popup.tsx:192`; installed dependency `packages/views/node_modules/@tiptap/suggestion/src/plugin/props.ts:51`). A DOM handler on the new toolbar must explicitly exit the correct PluginKey and contain the event; invoking only the renderer callback can leave active suggestion state/decorations behind. `design.md:64` correctly identifies the control-focus path; add this implementation constraint and verify reopening after dismissal.

4. **Make the IME guarantee concrete, including Escape.** MentionList guards composition before navigation/acceptance (`packages/views/editor/extensions/mention-suggestion.tsx:401`), but the shared popup handles Escape before reaching that guard (`packages/views/editor/extensions/suggestion-popup.tsx:194`). Upstream also always exits on Escape when its handler runs (`packages/views/node_modules/@tiptap/suggestion/src/plugin/props.ts:51`). This establishes a handler-level gap; browser ProseMirror composition handling may prevent delivery, so it is not proof of a native-browser defect. Specify that IME-owned events cannot select, submit, page, switch category or dismiss; cover `isComposing`, Safari keyCode 229, and the editor's composing state in real-editor/new-control tests. Avoid treating a guard added only to MentionList as protection for every path. Native Chinese composition verification remains necessary.

5. **Existing async cancellation is query-scoped, not identity-scoped.** `design.md:77` may reuse the request guard for query changes, but `design.md:58`/`:78` must be implemented separately: the existing effect depends only on query and project-search mode (`packages/views/editor/extensions/mention-suggestion.tsx:351`), reads workspace once (`:289`), and selection records against the current workspace (`:394`). Supply captured workspace/account ownership to the categorized popup, close on scope changes, and reject acceptance if current identity differs even before asynchronous cleanup runs. Test a scope change with identical query and a late response; query-change tests alone do not prove this requirement.

## Caveats / Not Found

- No product code, tests, task activation, preferences, call sites, or Git operations were changed or executed. Only this report was written.
- No native interaction was reproduced; focus/IME findings distinguish concrete handler behavior from browser behavior requiring verification.
- The keyboard route into auxiliary controls is the remaining blocking UX specification issue. Other items above are concrete implementation/test clarifications for the otherwise compatible opt-in design.
- Existing caches may be incomplete while loading; this review does not independently prove the directory endpoints' full-workspace completeness. The leader owns data/preference/call-site integration.

## Planning disposition

The leader incorporated all five findings into the proposed plan on 2026-11-25. The keyboard route is now explicit: Alt/Option+ArrowDown enters categories, auxiliary controls have their own navigation sequence, and an explicit Return to typing action restores DOM focus without a selection transaction. PRD R5/AC6 and the design/implementation checks cover it. The plan also specifies correct plugin exit, IME-owned Escape/Safari guards, context-mode precedence, and identical-query scope-change coverage. These are proposed behaviors awaiting the user's final planning approval, not verified implementation results.
