### Lane/environment prerequisites and evidence limits

1. **Standard legacy lane:** `scripts/check.sh:67–94` appends task-only URLs, legacy auth, high synthetic email limits; it sets managed installations, knowledge, admin and device auth false. It builds production Web and uses one Playwright worker/zero retries. It does not establish password/admin/managed/knowledge/device acceptance.
2. **Full check is not automatically a suitable mixed-lane suite:** `collaboration-knowledge.spec.ts` has no configuration skip before the seven Web tests; the native test (`:284`) throws if `COLLABORATION_ELECTRON_RENDERER_URL`/`COLLABORATION_ELECTRON_SOURCE_ROOT` is absent. `collaboration-runtime-handoff-web.spec.ts` also has no skip. Select explicit spec groups with `--list`, record omissions, and run the correct lane rather than treating all skips as passed.
3. **Password/managed lane:** control readiness requires `E2E_PASSWORD_AUTH=1`, owned DB, matching API URL/production build, and deployment ID (`e2e/fixtures/collaboration-control-journey.ts:29`). Managed fixtures enroll task-generated keys and scoped credentials; two independently isolated runtime profiles must be proven in executed evidence.
4. **Host lane:** `collaboration-host-runtime`, `collaboration-host-squad`, `collaboration-memory-runtime`, and `collaboration-host-switch` require explicit task-owned host daemon, Provider, and CLI paths. `hostRuntimeConfigured()` skips before absent opt-in; a selected-but-incomplete environment fails. This is suitable deterministic process acceptance without real vendor accounts.
5. **Control protocol fixture limit:** `e2e/fixtures/collaboration-control-journey.ts:38` explicitly describes a synthetic offline Linux resource. It may obtain a real permit but starts no process and supplies no proof. A Web control scenario using it does not demonstrate Linux Provider execution or native termination.
6. **Retained-history fixture limit:** `e2e/fixtures/collaboration-runtime-handoff.ts:16–18` directly seeds completed run history after public human setup. It proves authorized HTTP/UI projection, older comment recall and revocation; not checkpoint ingestion, Provider execution, or termination proof. `collaboration-records` and recorded-run knowledge source tests have the same seeded-history distinction.
7. **Native renderer limit:** knowledge native flow runs actual Electron compositor, platform routing and IPC using the existing harness. It asserts `daemonStarts=0` (`e2e/collaboration-knowledge.spec.ts:338`); it does not establish full production Main daemon management or packaged installer behavior.
8. **Full Main/package/installer lanes:** `collaboration-host-installed` requires explicit native executable or cached image and pinned hashes; `collaboration-installed-main` requires a selected packaged Linux image; `.deb` real install is separate from directory package. OS/arch of client and runtime must both be recorded.
9. **Real Provider lane:** strict explicit gate and current authorization needed. Do not reuse prior model/account/budget approvals, begin RK1, or resume old experiment processes based on repository ledgers. `agentintegration` build tag does not by itself authorize account access.
10. **Dedicated databases:** `scripts/test-go.sh:12` allows 40m; regular packages execute `-p 1 -parallel 2` (`:45`) because fixtures share singleton rows. Agent packages use bounded `-p 2 -parallel 2`. Script guards prevent ambient installed CLI execution. Redis integration needs a separate task-only Redis because fixtures flush logical DBs.

### Gaps to retain explicitly in the acceptance matrix

- Actual new/old server pair matrix and migration/upgrade behavior need selected old bytes and owned before/after databases; parser unit tests alone are insufficient.
- Native Windows/Linux, Mobile/iOS/Android, installation/signatures/notarization and real Provider execution cannot be inferred from Chromium, macOS Electron, a Linux protocol fixture, or historical reports.
- Source/browser knowledge tests do not prove model use or every launch fence. Tagged deterministic composites cover server/daemon/physical fake processes; current authorized real models remain separate.
- Whole-machine disconnect/daemon kill/API restart need task-only processes and retained run/ledger evidence. Route fault injection alone does not prove recovery after a real process restart.
- Every P0/P1 row should name exact actual case IDs, planned count, PASS/FAIL/BLOCKED/SKIPPED, first-run artifact and final persistent fact. All rows above remain **NOT EXECUTED BY RESEARCHER** until root execution joins evidence.
