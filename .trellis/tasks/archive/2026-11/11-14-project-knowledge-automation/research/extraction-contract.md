# 服务端自动整理与采纳检查契约（规划建议）

日期：2026-11-14。用户已选择统一服务端 `pkg/llm`、项目策略默认开启且可配置、无项目跳过、重开立即暂停自动知识直至重新验收并检查。本文件补足实现可行性；未调用模型、测试或外部服务。

> 最终设计复核补充：本研究中的“每份验收0–3条/一组生成与检查”适用于新增知识。重验必须完整处理已有暂停自动贡献，最终 `design.md` §5–6 将其分为最多6个复查批次加1个新增批次，每批≤3条及独立时限/结果；新增预算不截断复查。最终设计另区分create/revalidate/revise、自身前驱比较例外、全来源理由授权及原子批次结果。本文保留原始研究建议，冲突处以最终设计为准。

## 1. 可复用 API 与用量事实

- `Client.GenerateJSON(ctx, model, system, user, temperature, maxCompletionTokens)` 返回**未解析 string**；请求 JSON object 不保证业务结构。调用者必须拒绝额外字段、重复键、未知引用、无效 UTF-8 和多余尾随值（`server/pkg/llm/client.go:375`）。
- 默认模型来自现有部署配置；无 API key/base URL 时 `Enabled()` 为 false，零网络请求。`temperature=0` 表示不设置参数，不能将其报告成温度被强制设为零；GPT-5.6 家族有既有 reasoning 参数规则（`:393`、`:446`）。
- `GenerateJSON` 当前丢弃 completion usage；`Client.Chat` 返回完整 SDK completion，但不得在领域服务另引 SDK（`:20`、`:313`、`:435`）。建议在 `pkg/llm` 内提取共享私有生成逻辑，增加返回自有 `JSONResult{Text, Model, Usage}` 的薄方法，保留旧方法及参数协商行为，不添依赖。
- 自有 Usage 记录模型实际返回的输入/输出/总 token、可用的缓存/推理细分，以及 `known/partial/unknown`；在 `pkg/llm` 内依据原始响应字段是否存在区分真实0与字段缺失。上游没有提供、超时或连接中断时不能写零消耗；不据 token 单价猜账单。仅保存规范化模型名、用量及调用身份，原始 provider 响应和错误不进入通用日志。
- SDK 请求重试沿用 `MULTICA_LLM_MAX_RETRIES`（默认2）；JSON helper 还可能做最多2次参数兼容协商，共享 deadline。不能把“两阶段”说成严格只有两次 HTTP 请求（`:393`）。

## 2. 首期固定预算（建议常量，不扩张配置表单）

| 项目 | 建议预算 |
| --- | --- |
| 候选 | 每个已验收版本 0–3 条；每条正文≤2 KiB、摘要≤256 B、引用≤4 个 |
| 整理来源 | 最终验收材料及其明确关联的来源，共≤8份完整材料、解码后≤128 KiB |
| 历史对照 | 当前目标全部有效贡献，沿用≤16条 / 完整材料≤128 KiB |
| 模型输入 | 每阶段含固定说明、来源、候选和必要对照，解码材料≤288 KiB；完整 JSON wire≤2 MiB |
| 模型输出 | 生成≤6,000 completion tokens、解码文本≤24 KiB；检查≤3,000 tokens、解码文本≤16 KiB |
| 执行 | 每API实例最多2个整理工作；每阶段60秒、整次工作120秒；租约至少180秒 |
| 自动重试 | 短暂数据库/抢占失败最多3次退避；模型阶段交给既有SDK传输重试，终态失败不再循环重新生成 |

副本数会影响总模型并发，部署文档需记录；不谎称上述是跨副本全局配额。需要全局账单上限时另列能力。

超过任何预算均保留明确待处理原因，**不截取正文前缀、不只看前几条知识、不自动删除旧知识腾空间**。来源选择是确定范围，不宣称检查全部任务历史；附件只用已授权的文字事实/引用，不抓取 URL 或运行引用中的命令。当前默认上下文可能接近128 KiB，加上交付结果超限是合法待处理情况。

## 3. 两阶段整理，权限检查贯穿

1. 从正式 accepted 的交付身份取得快照，冻结 source workspace/project、验收事件/生命周期、项目策略版本和明确材料版本。无项目、manual、策略关闭、来源不匹配立即跳过模型。
2. 以专用内部“项目知识整理”用途解析读取权限，不能伪造项目负责人或系统管理员的人类 principal；项目策略配置权不授予其他来源的正文访问权。默认策略的系统来源、实际启用/修改者与本次系统执行分别记录。
3. 资料只发给部署管理员已配置的服务端模型入口；不发给项目候选小队、最后执行者或策略修改者。无模型配置则 `waiting_configuration`，不借个人CLI凭据、不自行补默认外部账号。
4. 第一次模型调用仅生成 0–3 条有引用的候选；第二次使用独立请求/系统提示检查候选与完整允许来源、目标知识的关系，不带第一次模型的推理过程。两次可用同一配置模型，不能称为统计独立或多模型证明。
5. 返回结果后在短事务内重新检查验收、项目归属、策略版本、来源访问/版本、目标知识 revision、到期/暂停状态及预算；变化则不沿用旧检查结论。

源资料的对照读取借用现有可用性检查的实现，但 `KnowledgeSourceAvailability` 自身不授予权限（`server/internal/service/collaboration_knowledge_sources.go:17`）。项目知识中可能有其他来源或已失权材料；不能因为拥有目标项目配置权就向模型发送那些正文。

## 4. 生成输出与精确来源

建议生成形状（所有 ref 由服务端临时分配，模型不输出真实数据库身份）：

```json
{"candidates":[{"ref":"k1","summary":"金额展示单位约定","statements":[{"text":"订单接口金额以分为单位。","source_ref":"s1","quote":"订单接口金额以分为单位。"}]}]}
```

- 服务端以 ref 映射回同一协作任务的准确材料身份、版本和完整正文 SHA256，校验 quote 非空且是该版本正文的精确连续子串，不做模糊匹配。
- 每条 statement 都要有来源。首期自动采纳正文优先由已引用的陈述及固定格式组成；超出来源的新推断、扩展适用范围或模型自创“必须/始终”规则进入待审，不靠润色变成事实。
- 精确引文只能证明“这些字在来源里”，不能证明事实正确或未断章取义。完整来源及必要上下文交给第二阶段检查；检查结论仍是模型意见。
- 服务端固定目标为冻结的来源项目、自动采纳类型和适用场景，不接受模型指定空间/项目、用户、权限、状态或调用工具。
- 现有知识源仅允许 `memory/comment/run_record`（`server/pkg/protocol/collaboration_knowledge.go:193`、`:219`）；若候选直接引用正式交付文本，必须明确新增不可变 `delivery` 来源契约及权限检查，不能伪装成评论，也不能只存一个显示链接。

## 5. 检查输出与确定性采纳门

检查请求一次覆盖本批最多3条及全部允许的目标对照，结果对每个候选返回唯一 ref：

```json
{"checks":[{"ref":"k1","support":"supported","reuse":"reusable","relation":"novel","related_refs":[],"reason":"来源明确陈述该约定"}]}
```

`support` 为 supported/unsupported/uncertain；`reuse` 为 reusable/transient/uncertain；`relation` 为 novel/duplicate/conflict/uncertain。related_refs 只能引用输入中已有知识或本批候选。不得输出数值置信度作为决策依据。

| 确定性门 | 要求 |
| --- | --- |
| 验收与来源 | 精确 accepted 身份仍有效、没有重开；所有引用版本及SHA256可读且匹配 |
| 策略与范围 | 当前项目存在且归属未变；项目策略启用，规则版本一致；manual不运行 |
| 结构与引文 | 严格schema、候选/引用数量和文本预算通过，引用均由服务端解析 |
| 检查完整性 | 每个候选恰好一个完整检查结果，无未知ref或缺失字段；整批与完整目标revision一致 |
| 候选意见 | supported + reusable + novel 才可继续；这是规则接受模型意见，不是客观正确性证明 |
| 发布预算 | 在目标锁下验证新增后全部有效贡献≤16条/128 KiB，含元数据，不能仅计正文 |

现有预算使用 `CollaborationKnowledgeSizes` 和 `ValidateCollaborationKnowledgeTargetBudget`，须复用，见 `server/pkg/protocol/collaboration_knowledge.go:587`。证据中的“测试通过”只能来自已保存的可核对测试事实；模型说通过、引用里自称通过及已验收本身都不能改写成服务器验证通过（同文件`:59`）。

## 6. 重复、冲突、并发及不确定性

- 先对目标与批内按规范化结构做精确重复检查，文本仅统一换行，不删除内部空格或改变大小写、数量、否定词；命中不新增。语义重复由检查阶段标记并保留关联依据，不自动修改原贡献。
- 对照必须完整覆盖目标有效集合。任何应对照条目正文对整理用途不可读，或集合超预算/读取失败，整批转 `review_pending`，不得悄悄跳过该条后认定 novel。项目权限不扩大来源权限。
- 自动采纳按验收身份 + 规则版本 + 候选规范化内容摘要建立幂等键；提交时CAS目标知识revision。并发批次改变目标则既有“无冲突”意见失效，转待处理；显式重试可以重新检查，不能自动循环耗费模型请求。
- duplicate→跳过；conflict/uncertain/unsupported→待审；transient→无复用价值跳过；schema无效/模型超时/预算超限→工作待处理。失败原因代码可见，源正文仍按访问权限过滤。
- 已保存的成功阶段结果只在所有绑定未变时复用。进程崩溃导致模型是否完成未知时记录 `generation_uncertain`，不能无界自动重放，也不能报零费用；人工重试沿用工作身份并记录新attempt。
- 重开事务立即暂停该来源自动贡献；旧任务/旧租约不能重新激活。重新验收需新的验收身份及完整重校验；人工历史保留。规则采纳身份、检查摘要及证据事实分开显示。

默认上限与状态名为本规划的建议，不是现有公开协议。除 `pkg/llm` 的结构化用量返回外无需新增模型SDK或第三方依赖；知识生成、采纳与消费开关及权限仍各自独立。
