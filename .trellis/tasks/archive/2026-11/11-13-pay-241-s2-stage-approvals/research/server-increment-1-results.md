## 6. Deviations and decisions for review

1. Proposal children carry title, description and priority only. They are created unassigned, `todo`, in the root's project; assignment goes through ordinary entry points afterwards. F04 names "责任/项目" as following ordinary issue bounds; carrying an assignee would need the handler-level invocation permission checks inside the acceptance transaction. This is a scoped simplification, not a confirmed rule.
2. The machine gates cover **direct** children of a managed root. A machine creating a sub-issue under an ordinary child is unchanged. An agent-created issue that a human later attaches to a managed root is execution-gated until the product approver confirms it.
3. Modify-accept is two requests (revise by the approver, accept that exact version); the decision view derives `accepted_with_modification`.
4. Policy refusals are never stored; only committed revisions carry the original key.
5. Scope confirmation is invalidated by lifecycle change, a disable/re-enable, a moved product-approver role, or a changed participant/account generation of the signer. Credential identity and expiry are not stored (only `credential_kind`).
6. A task queued before the gate applied is still claimable and is refused at start; it stays unstarted until confirmation. Nothing surfaces this to a user yet.
7. Stage events use the existing ledger and create reference notifications of new kinds; the activity API shows them as `other` with no details (asserted). Whether the current client tolerates the new notification kinds was not checked; no deployment can produce them while enabling is gated.
8. Reads expose a SHA-256 of each child's title+description to every reader, including external participants who cannot open the child; the external product approver needs it to confirm scope.
