# Linux installed Main enrollment diagnosis

The Linux `final-r3-02` failure is now confirmed as an acceptance-container prerequisite failure. The packaged Main reaches the password login and API configuration, but managed installation registration cannot start because the container lacks `/etc/machine-id`. `apps/desktop/src/main/managed-process.ts` reads `/etc/machine-id`, `/proc/sys/kernel/random/boot_id`, and `/proc/self/ns/pid` on Linux. `loadManagedInstallation` takes the management file lock before enrollment; the lock calls `managementProcessIdentity`, so missing machine-id aborts registration before the installation record, deployment-bound credential, daemon PID/profile or health server can exist. This matches the observed `operation_failed` at registration, absent installation metadata, absent profile pid/log files, and `managed_setup_failed`/`ENOENT` codes.

A task-owned Docker probe used the exact cached `multica-gap-full-main@sha256:db164dd...` image, the current candidate source and Linux directory payload, `--network none`, `--read-only`, and read-only mounts. It directly imported the frozen `managementProcessIdentity` and executed the exact bundled CLI version command. Results: machine-id `ENOENT`/open; boot ID readable; PID namespace readable; actual identity function failed with `ENOENT` path `/etc/machine-id`; bundled CLI exited0 and reported candidate `0.6.7-476-g1a32ca36c`. Raw output is safe (byte counts, error code/syscall/path, version only) and retained under `evidence/linux-enrollment-diagnosis/`.

Recovery for a new Linux packaged acceptance run: create a fresh task-owned 32-hex machine-id file with mode0444/0644, bind it read-only to `/etc/machine-id` in the fixture container, and retain the existing `/proc` identity reads. The value must be generated for this acceptance container and never copied from the host, reported as a credential, or reused as product state. A clean container is required so previous installation/profile/daemon records cannot mask the prerequisite. This is a fixture/container launch change, not a product change and does not prove Linux installation if the bind is omitted. Re-run only after a read-only preflight proves the exact file is visible, then preserve all existing source/DB/PID/installation/daemon/Stop/Resume assertions.

## Reproduction with the minimal fixture fix

The same exact cached image and bundle were run read-only with a freshly generated task-owned machine-id file mounted `:ro` at `/etc/machine-id`; no host identity was read or mounted. The frozen `managementProcessIdentity` then passed, reporting only hash-valid host/boot IDs, and the exact bundled CLI version exited zero. The container exited and the generated identity directory was removed. Evidence: `evidence/linux-enrollment-diagnosis/machine-id-green.json` and `machine-id-green.stdout`.

The fixture change in `runtime/detail-proposal/machine-id-fixture.patch` generates a unique 32 hex byte value plus newline in a `0700` task-private directory, mounts it read-only, and cleans it after an owned container is confirmed stopped. On Docker disconnect/unknown state it retains the file for root cleanup rather than deleting evidence or risking a live bind.
