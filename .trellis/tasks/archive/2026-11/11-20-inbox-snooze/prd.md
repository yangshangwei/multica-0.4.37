# 收件箱通知延后：持久化提醒与共享交互

## Goal

让用户把暂时不处理的通知移出当前收件箱，在指定时间重新看到它；在此期间仍能收到需要立即处理的重要提醒。Web 和 Desktop 使用同一套交互，刷新、服务端重启和跨设备使用都不会丢失延后计划。

## Requirements

### R1 — 用户自己的通知组

- 延后范围为当前用户、工作空间、通知组。有任务的通知按整组操作；没有任务关联的通知按单条操作。
- 延后不改变其他成员的提醒、任务状态、截止日期、订阅关系或智能体运行。
- 同一任务延后期间的后续普通通知归入同组，沿用既有提醒时间。
- 收件箱、已延后、已归档互斥；已读状态是独立维度。延后本身保留原有已读状态。

### R2 — 快捷时间和自定义时间

- 通知行提供时钟入口，右键、触屏菜单和详情操作提供相同的“延后...”操作。操作入口不触发通知选择或自动已读。
- 快捷项为 1 小时后、3 小时后、明天、3 天后、1 周后；每项右侧显示实际提醒时间。
- 小时项按时长计算；日级选项按用户本地日历计算，在对应日期 09:00 提醒，保存绝对时间。
- 自定义时间显示日期、时间和当前实际时区；只接受未来时间。首次默认明天 09:00，改时间时带入已保存的值。
- 跨年时间显示年份；菜单停留后提交重新检查时间有效性。不存在的夏令时本地时间应提示重新选择，重复时段必须展示解析后的时区偏移，避免静默使用与展示不同的时间。
- 不沿用待分诊任务的 90 天业务限制；本功能没有另设最大延后天数。

### R3 — 已延后列表和失败恢复

- 列表底部在已归档入口之前提供“已延后”及通知组数量；零条时也可进入。
- 已延后按提醒时间从近到远排列，展示提醒时间，并允许查看详情、改时间、现在提醒和归档。
- 查看详情不取消延后；“现在提醒”回到主收件箱并标为未读，不自动打开详情。
- 当前选中组延后成功后再移走选择，优先续接下一项、再上一项；没有剩余项时清空详情。
- 保存失败保留原通知、选中项、未读数和输入时间，并提供可重试的错误反馈。
- 空列表与读取失败分别展示，读取失败保留重试入口。

### R4 — 到期和重要事件

- 到期后通知组回到主收件箱靠前位置并标为未读，展示“延后提醒”来源，保留原事件时间、通知身份和评论落点。
- 普通评论、表情及普通状态变化不提前结束延后，不弹出该组的普通系统提醒。
- 对当前用户本来就应投递的有效新通知中，直接 @ 本人、任务分配给本人、智能体执行失败会提前结束延后并重新标为未读。
- 群体提及不自动视为直接 @ 本人；重复投递同一已保存事件不能反复唤回。提前提醒不绕过已有通知偏好或接收人检查。
- 每次有效延后只发生一次到期或提前唤回；不能通过创建重复通知来伪造提醒。
- 一次重要事件唤回后重新延后，重放原重要源事件仍保持延后；第一次延后与新通知同时发生时也遵循提交顺序。

### R5 — 撤销与后续变更

- 单组延后、改时间和现在提醒成功后提供撤销，还原该次操作前的提醒时间、列表及其修改的已读状态。
- 撤销只针对自己那次成功操作。如果另一设备已修改提醒、归档或改变同组相关状态，拒绝旧撤销并刷新当前状态，不能覆盖较新的操作。
- 归档清除相应延后计划，不会在原定时间复活通知。既有已解决执行失败通知的自动归档行为继续有效。
- 全部已读、批量归档、归档已读和归档已完成默认作用于主收件箱，不隐式处理已延后项。
- 已到期但后台尚未处理的通知视为重新未读；“全部已读”可正常确认它，“归档已读”不能按到期前的旧已读值将其归档。
- 任务删除或失去访问权限后移除不可访问的项，不投递失效提醒。

### R6 — 计数、同步和兼容

- 主收件箱未读数和跨工作空间提示使用同一规则：排除已归档、有效已延后的组，然后按界面展示的每组最新通知判断未读。
- 已延后入口数量按组计算，与该列表的行数一致，不与原始通知条数混用。
- 延后状态由服务端持久化，不能由单设备计时器决定。在线各设备接收当前工作空间或其他工作空间的变更；刷新、重新聚焦、断线重连和服务端重启后可恢复。
- 新接口响应经过运行时 schema 校验。已有列表响应使用可选的附加字段，保留已安装客户端的兼容能力；原生移动端沿用服务端的过滤和计数语义。

### R7 — 可访问性与共享实现

- Web 和 Desktop 的 UI、时间逻辑、请求与缓存逻辑在共享包实现；Desktop 的三类收件箱标签身份可区分。
- Tab 可到达时钟入口，菜单方向键、Enter 和 Escape 行为正确；关闭浮层后焦点回到触发控件，菜单键盘操作不切换背后的通知。
- 窄屏没有横向溢出，触屏操作区满足至少 44px；浅色和深色使用现有语义 token、字体层级及 Base UI 组件。
- 成功、错误与撤销结果有可访问反馈。产品文案遵循中英文术语规范。

## Out of Scope

- 批量延后、重复提醒、工作日历、个人默认时间偏好。
- 原生移动端的延后菜单和已延后页面；服务端状态语义仍须保持一致。
- 改造待分诊任务的延后流程、协作通知的数据模型或任务执行调度。
- 新 UI 依赖、独立于共享页面的新 Web/Desktop 收件箱实现。
- 生产部署、安装包发布和现有无关改动的整理。

## Acceptance Criteria

- [x] AC1 / R1：同一任务的多条通知整体延后，其他任务、工作空间和用户不受影响；无任务通知单独延后。
- [x] AC2 / R2：五个快捷时间、跨日/跨年、本地时区和夏令时校验正确；过去时间和提交时已过期时间被拒绝。
- [x] AC3 / R3：行内、右键、触屏与详情入口执行相同操作；已延后列表、数量、排序、改时间、空状态及重试可用。
- [x] AC4 / R3、R7：成功后选择正确续接，失败保留通知、输入和详情；键盘、触屏、浅深主题和窄屏交互可用。
- [x] AC5 / R4：延后期间普通通知继续合并且不弹普通提醒；直接提及、分配和执行失败只对实际接收人提前唤回一次。唤回后重新延后，再重放原事件仍保持延后；首次延后与通知插入的两种竞争顺序都有验证。
- [x] AC6 / R4、R6：到期在服务端恢复到靠前位置并标为未读，不复制通知；服务端重启、离线后恢复不漏提醒、不重复。
- [x] AC7 / R5：撤销还原成功操作前的状态；另一设备后续修改、归档或读状态变更后旧撤销被拒绝。
- [x] AC8 / R5：已归档及已解决失败通知不在到期时复活；主列表批量操作不影响已延后项。已到期但原始行已读的组执行“全部已读”后刷新仍为已读，“归档已读”保留其重新未读提醒；删除和撤权后不产生失效提醒。
- [x] AC9 / R6：列表行数、主未读数、已延后数量和跨工作空间未读提示保持一致；操作发生在另一工作空间时仍更新。
- [x] AC10 / R6、R7：旧响应缺少附加字段时正常展示；新响应缺失身份或格式错误时不能显示成功；Desktop 三类标签和深链接恢复正确。
