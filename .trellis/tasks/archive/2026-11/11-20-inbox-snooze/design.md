# 收件箱延后技术设计

## Decision and boundaries

沿用已确认的行内时钟、快捷菜单和底部已延后入口。服务端保存用户级通知组计划，共享 Core 管理请求与 React Query，Views 管理浮层及交互，Web/Desktop 只沿用现有页面接线。

不把待分诊任务的 `issue_triage.snoozed_until` 用于本功能：它属于任务审核流程，不能代表个人的通知选择。也不只给当前通知行附加本地时间：那无法覆盖后续同任务通知及服务端重启。

代码证据见 `research/inbox-evidence.md`。现有计数语义是“每组最新通知是否未读”，不是“任一历史通知未读”；本次统一不同查询的计数实现，不另改这一产品语义。

## Storage and identity

新增 `inbox_snooze` 表，逻辑身份为 `workspace_id + recipient_type + recipient_id + group_kind + group_id`。`group_kind` 为 `issue` 或 `item`，`group_id` 分别为任务 UUID 或无任务通知 UUID。所有输入身份由当前用户拥有的真实通知解析，不能由请求自由指定其他接收人。

表保存当前 `snoozed_until`、最近 `reminded_at`/来源、状态版本及最近一次可撤销操作的服务端快照，还记录本次延后的任务 revision 水位，并在关键来源回执中消费当时已提交可见的相关来源 ID。数据库时间用于时间处理，不作为来源已提交的证明。取消后保留必要的版本记录，防止“取消后再延后”的旧撤销或旧到期任务匹配到新计划。快照只记录此次操作实际修改的状态，避免用客户端旧缓存恢复数据库。

关键通知另用最小的 `inbox_critical_source` 回执表保存来源/接收人/通知组的首次消费事实。该表仅用于确认直接提及、本人分配和执行失败是否是新来源，避免扩大到其他通知的去重。它可以关联已有通知 ID；被延后基线判定为历史来源时，记录消费而不伪造新通知。回执与通知写入、延后状态转换在同一事务提交，通知原有 ID 保持不变。

- 有效隐藏计划：`snoozed_until > now()`。已过期计划不能因为后台扫描暂停而继续隐藏。
- 手动、到期或重要事件唤回：清除计划、推进版本，将当前非归档通知组重新标为未读并记录新的提醒排序时间。
- 归档：清除计划和撤销资格，不恢复已归档通知。
- 原始 `created_at`、通知 ID 和 `details.comment_id` 保持原始事件身份；`reminded_at` 只是新的显示排序依据。
- 关系验证和删除清理由应用层完成，不加外键或级联行为。
- 两张表的身份唯一索引与有效到期扫描索引均使用 `CREATE [UNIQUE] INDEX CONCURRENTLY`，各占一个单语句迁移；不能通过表定义中的唯一约束或主键隐式创建不符合规范的索引。
- 每条新增迁移提供对应 `.down.sql`，最后使用现有 sqlc 流程生成查询代码。

## State transitions and concurrency

延后、改时间、现在提醒、撤销、归档和到期处理在服务端事务中操作。对同一组使用同一并发控制边界，重新检查实际拥有者、访问权和当前版本后提交；不能分别提交计划和通知状态。

该边界也覆盖第一次计划尚无状态行的情形：在现有权限/撤权 fence 之后，用固定组身份取得事务级 `pg_advisory_xact_lock`，再建立或锁定组状态行。通知生产者也在相同 fence 内判断真实新源、写入通知、决定唤回/抑制并推进版本，提交后才广播。不能在独立事务中先插入通知、再异步判断其是否应结束新计划。一个事务操作多个组时按相同身份排序取得组 fence，沿用现有成员撤权锁顺序。

首次延后之前已提交的通知属于被延后内容；延后之后提交的有效新重要通知可以唤回。通过控制两个事务到达共同 fence 的次序，分别验证这两种结果。

| 操作 | 当前状态 | 结果 |
| --- | --- | --- |
| 延后 / 改时间 | 非归档的个人通知组 | 保存未来绝对时间、推进版本、保存本次撤销快照；保持既有已读值 |
| 现在提醒 | 有效延后计划 | 清除计划、标为未读、更新提醒排序时间；提供本次撤销回执 |
| 到期 | 时间已到且版本仍匹配 | 原子清除计划并标未读；无活动通知或访问失效时仅清除计划 |
| 新重要通知 | 投递成功且存在有效计划 | 在同组并发边界内结束当前计划并标未读；重复投递不能重复转换 |
| 普通通知 | 存在有效计划 | 仍保存通知并进入同组，沿用提醒时间，禁止普通系统提醒 |
| 归档 | 收件箱或已延后 | 归档活动通知并清除相应计划，推进版本以失效旧撤销 |
| 撤销 | 原操作仍是该组最新可撤销版本 | 恢复服务器快照，推进版本并使该 token 单次消费 |
| 旧撤销 | 后续操作或相关状态已变化 | 返回冲突，保留较新状态，客户端刷新并提示 |

需要阻止的竞争包括：两台设备同时改时间、现在提醒与到期、归档与到期、延后与重要通知、重要事件重放及旧撤销覆盖较新的读状态。普通读/未读操作也必须使会覆盖其结果的旧撤销失效。新通知的保存身份与既有重放去重行为保留。

## API contract

沿用现有工作空间收件箱命名及当前用户认证，新增按通知锚点操作的三个接口；实施时与真实 router 的既有后缀约定保持一致：

- `POST /api/inbox/{id}/snooze`：`{ snoozed_until: RFC3339 timestamp, expected_revision }`，用于延后和改时间。
- `POST /api/inbox/{id}/unsnooze`：`{ expected_revision }`，用于现在提醒。
- `POST /api/inbox/{id}/snooze/undo`：消费上次响应返回的 `undo_token`。

输入 `{id}` 只用于查找当前用户拥有且可访问的通知，然后推导通知组及实际工作空间。请求不接受可任意指定的 `recipient_id` 或未验证任务身份。已归档、找不到或不可访问的目标不能安排新计划。

成功响应包含实际工作空间、通知组身份、当前状态版本、`snoozed_until`、`reminded_at`，用户操作另返回可撤销回执。列表投影提供可选的 `snooze_revision`，没有历史计划时为 0；改时间、现在提醒和撤销按观察到的版本提交，避免静默覆盖其他设备修改。快照保留在服务器；客户端只持有与用户、组和版本绑定的 token。时间无效或不在未来返回 400；目标不可访问按现有资源隐藏约定拒绝；版本冲突或已被后续状态取代的撤销返回 409。

新增 `GET /api/inbox/snoozed`，保留既有 `GET /api/inbox` 和 `GET /api/inbox/archived`。共享页面 URL 增加已延后视图参数，既有 URL 不改变。投影增加可选的 `snoozed_until`、`snooze_revision`、`reminded_at` 和 `reminder_reason`，旧响应缺少它们时 Core 默认无延后状态。新 mutation receipt 的资源身份、版本和时间必须严格校验，schema 失败不能进入成功或撤销分支。

列表的归档过滤、延后过滤、排序和分组使用相同的身份与时间规则。主列表先排除有效延后/归档，再取最新组投影；已延后按提醒时间排序，数量按组统计。主未读与跨工作空间未读共用同一组投影语义。尚未物化的已到期计划在读取时投影为未读，并以到期时间作为提醒排序依据；用户标读或归档必须在同一事务里消费/清除该过期标记，不能在下一次刷新重新变成未读。

全部已读与归档已读也使用这个有效投影：即使原始 `read=true`，到期未消费的组仍是有效未读。全部已读必须消费该标记，不能因为原始行已读而跳过；归档已读不能归档这个重新未读的组。所有主列表批量操作继续排除未来的有效延后计划。

## Notification delivery and expiry

复用既有定时扫描的生命周期和持久化到期模式，新增独立的个人收件箱到期处理。启动时扫描，之后按现有 15 秒扫描周期处理有界批次；同组更新使用版本和条件消费，多实例并发不能重复唤回。提醒承诺是保存时间到达后的下一次成功扫描，不声称精确到秒。

到期查询和处理都检查当前工作空间成员资格、任务存在性及实际活动通知。删除或撤权后清理计划并停止广播；处理错误保留可重试计划，不先把状态标为完成。

所有真正写入 `inbox_item` 的生产路径需要覆盖统一的延后投递判断，包括普通订阅评论、提及、分配、执行失败、快速创建结果、自动化、待分诊提醒、项目更新和迭代提醒。只改普通评论监听器不能满足首期范围；独立的 collaboration notification 表/API 不迁入此模型。

普通通知在有效延后时仍持久化，但不发送可触发系统提醒的普通 `inbox:new`。可以发送仅用于缓存失效的个人组状态事件。重要通知只在已有偏好、成员和静音检查允许真实投递，且该源事件/接收人尚未持久投递时唤回。当前 generic `CreateInboxItem` 的随机 ID 不能证明源事件是新事件，因此关键允许集合需要独立于进程的持久化来源身份。

关键来源回执通过 `INSERT ... ON CONFLICT DO NOTHING` 单次消费，唯一键包含工作空间、接收人类型/ID、目标通知组、通知类型、来源 kind、来源 UUID 及需要时的原 revision：

| 关键来源 | 原始身份 |
| --- | --- |
| 评论中的直接提及 | 原评论 UUID |
| 任务描述中新增的直接提及 | 任务 UUID + 已提交的任务 revision |
| 分配给该接收人 | 任务 UUID + 已提交的任务 revision |
| 本次智能体执行失败 | 本次失败的真实 `task_id` |
| 委派恢复耗尽产生的失败说明 | 已保存的耗尽说明评论 UUID，来源 kind 与原执行失败区分 |

在已有通知详情中保留相应来源元数据。这个消费边界也在未延后时生效，回执跨已读、归档和再次延后保留，只有拥有者/工作空间/源组清理时删除。若能够用已有来源元数据匹配旧随机 ID 通知，接纳原通知而不重写其 ID、已读或归档状态。

不得用分配前后值、通知入库时间、消息文本或新生成的随机事件 ID 代替原始来源。更新/重试必须传递事件中已经持久化的 revision/task/comment 身份，不读取任务现在的 revision 或最新执行来改变旧事件的 key。缺失身份的历史通知或合成事件不获得“新重要事件”唤回资格；真正的新业务生产路径必须补齐元数据，不能用缺省路径放弃首期唤回。消费重复的来源不触发通知插入、唤回、状态转换或广播；普通评论现有 v1 UUIDv5 identity 和 `pgx.ErrNoRows` 处理不改变。

历史分配通知没有原 revision，历史普通失败通知可能存储 `{}`，不能猜测其来源。首次延后时在共同组 fence 内保存当前已提交任务 revision 水位，并将当时已提交可见的相关评论、失败执行和耗尽说明来源 ID 消费到现有关键来源回执；只读取相关组/来源关系，避免扫描整个工作空间。水位以内的分配/描述来源以及已经消费的可见来源属于已有内容，不提前唤回。使用确切来源行/事件，不以附近时间推断关联，也不使用重放时的新入库时间。收到可验证的历史来源时写入消费回执而不创建新提醒；无法验证的历史来源保持普通抑制。

PostgreSQL `now()` 表示事务开始时间，即使改成更新时 `clock_timestamp()`，也不能证明该来源已提交。来源事务在延后之前开始、在延后之后提交时，延后基线不能把它误判为旧来源。测试通过真实事务屏障覆盖这一顺序，以及可见旧来源重放、有元数据通知接纳和首次延后/新来源的两种并发次序。

目前 `mentioned` 同时包含直接提及、`@all` 和 `@squad`。创建通知时从已解析、已验证的提及来源增加 `mention_scope` 标记，仅明确的个人提及标记为 `member`；不能仅凭 `type=mentioned` 把全部群体提及当作直接提及。提前唤回的允许集合为新投递的直接 `mentioned`、分配给该接收人的 `issue_assigned`、`task_failed`；不因任意 `action_required`、`autopilot_paused` 或未知通知类型而唤回。旧通知不通过事件重放取得新的唤回资格。

已解决 `task_failed` 的自动归档继续执行；到期只操作非归档行，不复活失败历史。若该组没有活动通知，计划取消。工作空间删除清单、任务删除、成员撤权/退出及账号删除增加显式计划与相应来源回执清理，使用现有撤权事务和锁顺序。重要提醒的变更与普通投递抑制共用服务端状态判断，避免客户端猜测通知优先级。

## Realtime and cache recovery

使用内容最小化的个人通知组状态事件，携带 `workspace_id`、当前接收人、组身份和版本。通知组状态事件、现有 `inbox:unread` 必须同时注册到个人事件集合与接收人路由；只定义 event 常量不会完成跨设备投递。

Core 在事件所属工作空间失效以下查询，而不是只使用当前活动工作空间：主收件箱、已延后、已归档、相应数量及账户级跨工作空间未读摘要。新通知、任务投影更新、删除和断线恢复也覆盖已延后查询。

客户端不保存服务端延后状态到 Zustand 或 localStorage。查询使用焦点/重连刷新与有界的 30 秒恢复刷新，修复漏事件或重启窗口；服务端仍拥有标未读、排序和一次性唤回。系统提醒仅使用服务端确认可提醒的投递。

## Shared UI

- 扩展 `InboxView` 为三种状态，保持既有 inbox/archived URL 可用；已延后具有独立深链接和 Desktop tab subject，不能与主收件箱标签合并。
- 在 `InboxRowActions` / `useInboxItemActions` 增加统一动作；行内时钟、右键、紧凑行菜单和详情都打开同一个共享时间选择器。
- 复用 Base UI 浮层、日期/时间组件及 Sonner 可撤销反馈。不要把带待分诊文案的 `SnoozeInput` 直接耦合进收件箱。
- 时间计算作为 Core 纯函数拥有唯一测试矩阵：打开菜单生成时间，提交再校验；本地日历计算和绝对时长分开。Views 负责本地化显示和时区说明。
- 入口、成功反馈与失败状态沿用 `inbox` 中英资源。中文产品标签用“延后”“已延后”“现在提醒”“更改时间”“撤销”。
- 对会移走当前行的操作等待服务器成功再续接选择；现在提醒与到期唤回不自动打开详情或被旧选择立即标读。查看已延后详情不取消计划。
- Footer 节点保持稳定，沿用虚拟列表现有焦点与滚动结构。浮层按容器宽度收缩，触屏与键盘无需依赖鼠标悬停。

## Verification and rollback

执行计划中的测试分别证明纯时间契约、API 边界、服务端事务/重放、Core 缓存与计数、共享组件交互和真实 Web/Desktop 用户链路，不把预览验证当作后端证明。

上线顺序为服务端迁移与兼容投影，然后新客户端。应用回滚前先停止新增延后并恢复仍有效的计划到主收件箱，再撤除表与字段消费，避免用户通知永久隐藏。数据迁移的回滚必须保留原通知 ID、已归档状态和评论落点；没有本轮生产发布操作。
