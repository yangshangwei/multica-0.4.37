## New canonical protocol evidence

`TestIterationCanonicalReadSemanticsDiagnostic` captures the exact SQL and typed parameter values issued by generated `ListActiveTasksByIssue` and `LockIssueIterationParticipation` methods. The task adapter then queues those exact separate statements through pgx `SendBatch` and feeds their results back into the same generated methods/scanners, rather than substituting generic `Rows.Values` digests or hand-maintained column lists. Each result and `Rows.Err`/`BatchResults.Close` path is consumed.

1. **Nonempty, empty and missing results.** The population contains queued, dispatched, running and waiting-local-directory tasks, plus a completed task that the canonical query excludes. Serial and pipelined results match as complete typed structs, in canonical created-time order; a second issue has an empty task slice. Source participation is current, target participation exists but is left, and another target has no row. Missing participation returns `pgx.ErrNoRows`; the following existing-target and empty-task results are still consumed successfully. The serial transaction is rolled back before the pipeline transaction begins, so those locks are acquired afresh. Raw typed results and exact SQL/parameters: `typed-result-parity.json`, `canonical-reads.json`.
2. **Actual first acquisition and new RC statement snapshots.** A separate holder locks source participation. The pipeline executes the active-task read, then blocks on the canonical source participation query. The diagnostic confirms the exact waiter/holder PIDs and PostgreSQL lock wait via `pg_blocking_pids`; this is not a sleep-only scheduling assumption. The holder changes the source's started flag, makes the target current, and completes the running task, then commits. The source lock read returns the updated source; the later target query sees its newly current row; the later active-task read returns three rows instead of the earlier four. The absent target still yields typed `ErrNoRows`, and batch close succeeds. This proves that these separate canonical statements in a READ COMMITTED pgx batch can observe the holder's post-wait commit. It does not establish a safe place to queue them in the full lifecycle algorithm. Raw proof: `first-lock-fresh-snapshot.json`.
3. **Server error and rollback.** A task-only title marker is written in a new transaction, followed by the canonical active-task read and an explicit division-by-zero statement. The query result reports SQLSTATE `22012`, batch close reports the error, rollback succeeds and the original title is recovered. This is a raw protocol error/rollback proof, not an injected failure in the current production lifecycle implementation. Raw proof: `batch-error-rollback.json`.

The raw concurrency proof deliberately permits a direct holder to change target participation while the writer waits on its source. It demonstrates snapshot visibility; a lifecycle implementation must separately preserve the workspace/iteration/issue/reference authorization fences that constrain such writers in the real product.

## Root-cause evidence and smallest possible future scope

Existing source still performs one active-task query for each issue (`server/internal/service/iteration_lifecycle_preview.go:290`) and source then target participation locks for each move (`server/internal/iteration/membership.go:53`). The prior 3,000-read ABBA result supports a transport cost direction. The new evidence removes the earlier experiment's empty-only/generic-scan/already-held-lock limitations for a small canonical protocol population and validates several existing full-owner regressions. It does not time that population or explain the original tail samples.

If a product change is separately authorized, the smallest plausible boundary remains complete-set active-task/participation preparation with canonical generated result handling. A pipeline must retain separate ordered SQL statements, current authorization fences, sorted complete-set issue/iteration/reference locks, source-before-target validation, exact task rows/running counts, and each error/close check. Missing target is permitted; missing source and already-current target must still fail according to `membership.go:53–69`; active-target reentry also depends on `HasIterationActiveJoin` at `membership.go:71`. Do not move task/reference checks ahead of the fences, fold reads into a single SQL snapshot, drop canonical reads or change the transaction's isolation/retry owner.

The write path already batches phases. CAS typed `ErrNoRows` mapping, every batch result/close, and owner rollback are in `server/internal/iteration/membership_batch.go:97–146`. Current authorization and durable replay ordering remain in `server/internal/iteration/operation_execute.go:40–85`.
