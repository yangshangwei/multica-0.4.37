## Source-grounded authority, reader and storage contracts

These portions fit existing code and do not need a new protocol or recovery mechanism:

1. **Caller identity.** `lockRuntimeBusiness` (`collaboration_squad.go:88`) resolves the run through current mcb hash and verifies capability sequence equals `AuthorizedAttemptSeq`. It calls the current source/group/grant checks and retained reservation checks. The uploader Agent is `r.run.AgentID`; issue/source come from `r.access`; the attempt is from the authorized capability/run and actual attempt row. Multipart fields must not accept uploader/run/attempt/source authority, human drafts, attachment IDs, encryption keys, storage keys or caller-provided hashes/type. UUID zero and malformed inputs refuse at the boundary. Existing actor/workspace headers grant no authority here.
2. **Preflight versus final write.** Before external storage, resolve current runtime admission and the original event when available. Release DB locks before ciphertext upload. After storage, acquire the same current source/run transaction again, verify the original attempt still matches, check current mcb/source/participants/grant/reservation, recheck replay/capacity and the outcome fence, then write all required effects. The existing lock order and authority-set retry remain intact (`collaboration_runtime.go:116`, `:227`, `:336`). A revoked token, target/resource/source authority or changed attempt during slow storage must prevent inserts and private receipt replay.
3. **Runtime reader.** `RuntimeAttachment` (`collaboration_runtime_preparation.go:517`) currently allows only exact frozen manifest IDs/versions, under `lockRuntimeBusiness`. Extend it with an exact own-output branch requiring matching issue/source, Agent, run and current authorized attempt, permanent delivery, valid row and exact version. Otherwise keep the existing frozen-input branch; do not grant any whole-issue list fallback. Another run's/earlier attempt's file is unreadable unless it was independently frozen into this run's authorized input manifest. Unknown/foreign file identities stay indistinguishable. Do not make own-output reads depend on locating that output in the old input manifest.
4. **After slow reads.** The real runtime content handler already calls the same service again after decryption and compares the complete row (`handler/collaboration_runtime_preparation.go:89`). Keep that check and its exact run/file/version response headers. Shared `serveCollaborationAttachmentBytes` performs reauthorization before the first byte (`handler/collaboration_attachments.go:295`). Current authorized humans read delivered output through existing issue authorization/native capabilities, without receiving machine or storage credentials. Public/ordinary private-prefix rejection remains unchanged.
5. **Physical objects and commit uncertainty.** Existing draft upload supplies the correct model: independent random object/key, existing `secretbox`, ciphertext under `private/collaboration/`, exact digest/size on read, and deletion of only the attempt's own known loser (`collaboration_attachments.go:111`, `:174`, `:419`). Runtime mutations already return `*collaborationRuntimeCommitError` for uncertain commits and do not internally replay them (`collaboration_runtime.go:440`). Reuse that marker. Reset “inserted this object” state on each internal callback attempt, since a rolled-back insertion followed by a replay does not own the winner. Keep a possible inserted object on an unknown business commit; release a known loser. A failed preflight read-only commit does not justify creating an object or a new intent. Never classify a retained encrypted orphan as a confirmed business refusal.
6. **Single outcome fence.** Current admission does not itself reject `BusinessOutcome.Valid`; the new-output guard belongs in the locked writer after matching prior-event handling. `RuntimeSquadActivity` can already set business outcome before stdout's original recording (`collaboration_squad.go:419`; `runtime_capabilities.go:489`). Honor both paths: no new output after business outcome is recorded, while original matching output replay remains subject to current authority. Serialize output insertion and outcome freeze through the same run lock; output-first includes the file, outcome-first refuses the new file and cleans its prepared loser. Original outcome ACK remains content-free after withdrawal/settlement and must never return these refs or private content.
7. **History.** Freeze only committed outputs of the original outcome's current attempt. Later files, comment edits/deletes, new attempts or explicit new runs cannot change that frozen result. Result records project stored IDs; current attachment metadata resolves bytes under present authority. Absence of an old outcome extension remains an absent fact, not an empty list inferred from current attachments.
