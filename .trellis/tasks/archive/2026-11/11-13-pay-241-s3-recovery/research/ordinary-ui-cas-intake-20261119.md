## What already exists

`Issue.revision` is an **optional number**, explicitly absent for older backends (`packages/core/types/issue.ts:215`). `IssueSchema` accepts an optional positive integer (`packages/core/api/schemas.ts:1352`). It is not the collaboration decimal `collaboration_revision` or source write-context authority. Do not cast a collaboration version into this field or fabricate a missing ordinary revision.

`UpdateIssueRequest.expected_revision?: number` is already the aggregate CAS token (`packages/core/types/api.ts:118`). `useUpdateIssue` forwards caller-supplied data unchanged to `api.updateIssue` for ordinary writes (`packages/core/issues/mutations.ts:127`), and `ApiClient.updateIssue` serializes that data to the existing `PUT /api/issues/{id}` (`packages/core/api/client.ts:3484`). No Core/Go protocol addition is necessary for a single-issue field picker.

Core already removes `expected_revision` from optimistic Issue patches (`mutations.ts:162`; batch equivalent `:481`). On ordinary mutation failure it rolls back through the existing coordinator and invalidates detail/list/table owners (`:240`); success reconciles the authoritative revision. Keep the synchronous `onMutate` cancellation/patch sequence. The batch path has its own conditional optimistic ownership and partial-outcome semantics; it must not be replaced with uncontrolled single-item fan-out.

The server validates a supplied positive revision and reports the exact issue conflict (`server/internal/handler/issue.go:4232`, `:4435`). SQL rechecks the precondition on the row version actually locked by UPDATE (`server/pkg/db/queries/issue.sql:204`, `:253`). A meaningful changed field increments revision once; a no-op need not increment (`:239`). When `expected_revision` is absent, the optional API contract remains available. Choose different field values in the test so the winner advances R to R+1.

### Current cache authority is not the rendered observation

`findSourceIssue` scans detail, table, bucket, flat and array caches and explicitly selects the highest revision, preferring collaboration-marked projections (`packages/core/issues/source-collaboration.ts:25`). The source relationship cannot disappear in a partial projection. Keep that behavior for collaboration classification and existing guards.

It is wrong to auto-fill ordinary `expected_revision` from this finder in `useIssueSurfaceActions`, or from `prevDetail` read by Core `onMutate`. A user can be acting on a captured context-menu Issue at R while another cache already contains R+1. Such a lookup would silently grant the old intent a newer token. The request must retain the supplied UI observation. The observed Issue can still be followed by current server authorization and the existing collaboration redirect/guard; these are different inputs.

## Common-revision batch and compatibility

The wire remains `{issue_ids, updates, completion_bindings?}`. `BatchUpdateIssuesOptions` contains only completion bindings (`packages/core/types/api.ts:62`), and per-result `revision` is an **outcome**, not an observation (`:68`). `ApiClient.batchUpdateIssues` freezes ids and validates ordered outcomes (`client.ts:3677`). Go `BatchUpdateIssuesRequest` has no generic per-issue revision observations (`handler/issue.go:5091`). The loop passes the same `req.Updates.ExpectedRevision` to each item (`:5640`).

- **One selected row or several equal positive observations:** prove the nonempty `selectedIssues` set all carries the same positive revision R, then use existing `updates.expected_revision: R`. Obtain that set from the rendered-universe intersection, never raw selection IDs or a maximum/minimum cached revision. Carry the same R through the toolbar's Agent/squad modal branch, which runs before `handleBatchUpdate`.
- **Missing or heterogeneous observations:** leave the token absent as today; do not guess a common value. The current wire cannot express distinct per-item observations. No per-item map, backend addition or single-item fan-out is proposed. This is a separate compatibility boundary, not an additional universal S3 mandate.
- Preserve partial/unknown outcomes and selection retention, `updated` success count, mixed-collaboration refusal, status behavior, all-backlog assignment bypass and existing confirmation branches. A per-result revision remains an outcome, not permission to resubmit an older intent.
