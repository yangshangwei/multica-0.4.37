## Required linearization boundary

Design §3/§10 requires every issue facts writer to acquire the workspace iteration transaction fence **before any issue/attachment lock**, capture before/after, and record the event plus scope_revision in that business transaction. A WS listener cannot supply this invariant. Unknown status categories must not silently inherit todo in I1 snapshot/start/end calculations. Ordinary unassociated issue writes also acquire the fence, otherwise simultaneous join can miss the transition.

Use the existing workspace **FOR KEY SHARE** fence (LockWorkspaceForChatSessionCreate or LockLifecycleWorkspace), which conflicts with workspace deletion while allowing the non-key issue_counter update. Do not turn this into FOR SHARE: two creates can each hold SHARE, one own the iteration advisory lock, then its counter UPDATE waits on the other's SHARE while the other waits on the advisory lock. Existing issue creation increments workspace.issue_counter inside the transaction.

The current handoff overrides the older abstract order: preserve T1 `beginTriageWrite` workspace KEY SHARE → T1 settings INSERT/UPDATE lock → subscriber advisory/member lock → status catalog → I1 fence. Do not reorder member before T1 settings. Source-context and lifecycle creation still take issue locks before a later custom-status catalog lock; fix at the owning entry before adding I1, rather than acquiring I1 inside a callee after those locks.

### P1 transaction and lock contract (current code)

- W01 `updateIssueAtomically` delegates each complete attempt to `updateIssueAtomicallyOnce`. Its `Begin` does **not** set isolation; preserve the existing transaction starter/default. Do not incorrectly apply P1 project RR to W01. Current order: workspace KEY SHARE → custom-status catalog shared (built-ins skip) → attachments FOR UPDATE → issue FOR UPDATE → project FOR SHARE NOWAIT → issue UPDATE/CAS → attachment bind/reload → commit. Add authorization/catalog/I1 fence before attachments; preserve the rest. Field-base title/description checks, expected revision, and refresh of omitted nullable fields all happen against the locked current row.
- `service.RetryProjectAssociationTransaction` owns W01/Create/T1 acceptance retry: **4 total attempts**, only PostgreSQL `55P03`, waits 10/20/30 ms. Every failed attempt rolls back completely. Do not wrap it in `iteration.RunTransaction` or widen the error contract accidentally. Project lookup `ErrNoRows` remains project-not-found, not a retryable lock error.
- P1 project writes `runProjectTransaction`: SET isolation **REPEATABLE READ before all queries** → workspace KEY SHARE → subscriber advisory → current member lock → callback/project lock. Project delete deliberately uses **READ COMMITTED** through `runProjectDeleteTransaction` so a writer that committed while deletion waited is visible to its child sweep. Both have 3 total attempts for `40001`/`40P01`/`55P03` and their own final 503 contract.
- W14 deletion callback: administrator check → project FOR UPDATE → autopilots ordered by ID FOR UPDATE → disable triggers → detach autopilots → `DetachProjectIssues` → chat/views/resources/progress cleanup → delete project → commit. Add catalog/I1 fence **before project FOR UPDATE**, not at `DetachProjectIssues`. Detachment is explicit, tenant-scoped, and increments each issue revision; the earlier inventory's FK-only description is obsolete. Legacy FK DDL still exists, so do not mistake the absence of new FKs for removal of old constraints.
- Project references in W01 and W06 use NOWAIT deliberately because deletion takes project before issue. Replacing NOWAIT with a blocking wait while holding issue locks creates a cycle. W07 already takes workspace KEY SHARE → project SHARE → autopilot UPDATE before duplicate guard/counter; I1 must precede that project lock too.
- `iteration.LockWorkspace` only acquires the advisory fence. It does not authorize, set isolation, retry, or lock issue/reference rows. A recorder must borrow `pgx.Tx`; transaction ownership and post-commit publication remain with the caller. Ordinary unassociated issue writes also fence, so a concurrent join cannot miss their transition.

These do not update issue columns, but can change a preview's project/assignee/identifier summary or authorization. An issue-only hook is not sufficient protection for their live reference values.

## Minimum practical integration surface

1. A small reusable tx-level `LockIssueFactsWrite(ctx, tx, workspaceID, actor...)` / `RecordIssueChange(tx,before,after,...)` in the I1 service, with an explicit caller-held-lock contract. Call lock at transaction entry, never inside record-after-write.
2. A service-owned transactional status/content mutation function for autocommit W02/W03/W04; main HTTP W01 already has the correct tx shell to integrate. Runtime fallback W05 must stop bypassing it.
3. Capture deletion W12 and project/squad batches W13/W14 in their own existing/new transactions. Preserve frozen histories, do not FK them to mutable entities.
4. StartTask gets one transaction containing real task start + execution-start fact; side effects and broadcasts stay after commit. Do not conflate enqueue or first completion with start.
5. Creation W06/W07/W08 plus owning T1/lifecycle txs get ordering fixes and explicit-field confirmation. W06 alone is insufficient.
6. Workspace delete and revoke get explicit cleanup; status immutability and unsupported cross-workspace behavior receive contract tests rather than invented product flows.
