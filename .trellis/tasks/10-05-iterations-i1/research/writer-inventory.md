# I1 writer inventory — read-only implementation map

Date: 2026-10-06. Scope: repository as read before I1 implementation. This is code evidence, not executed I1 regression evidence. Paths/lines below are baseline locations and may shift during implementation. Captured for the implementation task; writer integration has not yet been implemented or verified.

## Required linearization boundary

Design §3/§10 requires every issue facts writer to acquire the workspace iteration transaction fence **before any issue/attachment lock**, capture before/after, and record the event plus scope_revision in that business transaction. A WS listener cannot supply this invariant. Unknown status categories must not silently inherit todo in I1 snapshot/start/end calculations. Ordinary unassociated issue writes also acquire the fence, otherwise simultaneous join can miss the transition.

Use the existing workspace **FOR KEY SHARE** fence (LockWorkspaceForChatSessionCreate or LockLifecycleWorkspace), which conflicts with workspace deletion while allowing the non-key issue_counter update. Do not turn this into FOR SHARE: two creates can each hold SHARE, one own the iteration advisory lock, then its counter UPDATE waits on the other's SHARE while the other waits on the advisory lock. Existing issue creation increments workspace.issue_counter inside the transaction.

Document the intended ordering explicitly and correct callers before adding a later-stage hook. Current T1 beginTriageWrite does workspace KEY SHARE -> triage settings UPDATE -> LockSubscriberWrites/LockActiveMember, while design says member -> T1 settings. Source-context and lifecycle creation have issue-before-catalog lock inversions today. Retrying a deadlock is not a substitute for correcting the ordering.

## Status catalog, cross-workspace moves, parent-child automation: actual behavior

1. `issue_status.go:80` request deliberately has no Key or Category. `queries/issue_status.sql:89 UpdateIssueStatusEntry` cannot modify either. Archive (`issue_status.go:356`, SQL :108) takes catalog exclusive, sets archived_at, **does not migrate existing issue status**. `issuestatus.Effective` still uses archived categories. There is currently no legitimate status reclassification writer to hook; preserve immutable-category rejection and test it. A future reclassification path must fence and record every affected issue; direct SQL operational changes are outside current app contract and must not be silently supported.
2. Existing status create owns tx + catalog exclusive (`createIssueStatusEntry:226`); reorder owns tx + catalog shared; presentation update is autocommit. Archived status affected issue counts do not mean membership changes. Existing tests: TestBuiltInStatusesAreImmutable, TestArchiveRetiresStatusWithoutTouchingExistingIssues, TestArchiveCommitsInsideTheWriteRaceWindow, TestExplicitKeyCreateAlsoTakesTheCatalogLock.
3. `handler/issue_move.go` is **relative rank/status movement within the same workspace**, not cross-workspace transfer. No production UPDATE issue.workspace_id or cross-workspace move handler/query found. Do not describe an existing supported path. Ensure new I1 SQL/transport refuses workspace mutation for any participation history (`iteration_history_move_unsupported`) and add guard if such an endpoint is introduced.
4. `issue_child_done.go:70 notifyParentOfChildDone` / batch variant post system comments and explicitly wake parent assignee; **do not update parent or sibling status**. Parent advancement is agent-driven through ordinary issue update. Tests squad_parent_status_contract_test.go, issue_child_done_test.go, issue_child_done_stage_test.go, issue_status_test.go TestBatchCustomTerminalStatusEntersStageBarrier. Do not invent server auto-completion or duplicate count propagation for I1.
5. `CompleteTask` does not change issue status; worker agent manages it via CLI. Failure settlement W04 is the exceptional server state writer. `MarkTaskWaitingLocalDirectory` is parked, not started; claim/dispatched is not running. Only successful StartAgentTask is actual start.

## Snapshot reference and authorization writers

These do not update issue columns, but can change a preview's project/assignee/identifier summary or authorization. An issue-only hook is not sufficient protection for their live reference values.

- `handler/project.go:529 UpdateProject` -> h.Queries.UpdateProject :650 (autocommit) can rename project; `DeleteProject` W14 erases current reference via legacy FK. Start/end must lock project FOR SHARE NOWAIT before reading a summary, and preview hash must include the actual fields used. Frozen snapshots cannot join live project for names.
- `handler/agent.go:1869 UpdateAgent` -> :2235 autocommit name update; `handler/squad.go:371 UpdateSquad` uses own transaction and qtx.UpdateSquad :501; `handler/auth.go:653/:810`, auth_password.go:323 `UpdateUser` name changes. Agent/squad/user display values are live references, including user shared across workspaces. Lock relevant referenced rows and freeze the display under closure transaction; if scope_revision promises these names too, introduce explicit reference invalidation/fence protocol instead of pretending issue_revision covers them.
- `handler/workspace.go:382 UpdateWorkspace` can change issue prefix, which affects identifier formatting. Snapshot identifier must be materialized, not reconstructed later from current workspace prefix.
- `workspace_revoke.go:43 revokeAndRemoveMember` (DeleteMember / LeaveWorkspace) opens tx, **first** LockSubscriberWrites :58 -> archives owned agents / cancels tasks / removes grants & subscriptions -> DeleteMember :217. It does not unassign issue.assignee_id. I1 must use current membership authorization for reads/replay and clean notification outbox/protected inbox here; recipient fence must prevent regeneration after revoke. Add workspace KEY SHARE first consistently to avoid delete/member-order cycles. Existing T1 TestTriageAcceptanceRevokedMemberCannotOpenNotificationTargetsOrAttachments and TestTriageAcceptanceResultNotifiesOnlyActiveCurrentRecipientsOnce are reusable patterns, not I1 proof.

## Direct SQL bypass summary

Confirmed application raw SQL issue writes: triage_actions.go :215/:399/:429/:438, triage.go :590. Confirmed implicit writer: legacy project FK nullification (migration 034). Autopilot/onboarding/status reset are generated SQL but bypass main IssueService create/update paths. `lock_issue_execution` is a PL/pgSQL lock-bearing function invoked inside task statements; any new fence must precede invocation. The repository has task usage dirty-rollup triggers on issue DELETE/project update (migrations 102,243); these do not record I1 facts and must not be mistaken for coverage.

## Minimum practical integration surface

1. A small reusable tx-level `LockIssueFactsWrite(ctx, tx, workspaceID, actor...)` / `RecordIssueChange(tx,before,after,...)` in the I1 service, with an explicit caller-held-lock contract. Call lock at transaction entry, never inside record-after-write.
2. A service-owned transactional status/content mutation function for autocommit W02/W03/W04; main HTTP W01 already has the correct tx shell to integrate. Runtime fallback W05 must stop bypassing it.
3. Capture deletion W12 and project/squad batches W13/W14 in their own existing/new transactions. Preserve frozen histories, do not FK them to mutable entities.
4. StartTask gets one transaction containing real task start + execution-start fact; side effects and broadcasts stay after commit. Do not conflate enqueue or first completion with start.
5. Creation W06/W07/W08 plus owning T1/lifecycle txs get ordering fixes and explicit-field confirmation. W06 alone is insufficient.
6. Workspace delete and revoke get explicit cleanup; status immutability and unsupported cross-workspace behavior receive contract tests rather than invented product flows.
