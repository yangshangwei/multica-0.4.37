# 跨账号协作验收标准

本附表是 [PRD](prd.md) 的验收部分，编号连续保留；实施归属见 [implement.md](implement.md)。

2026-10-17 修订：按[本轮需求设计调整](mention-redesign-2026-10-17.md)更新 @触发和多目标条目，追加 AC90–AC97。用户已确认 M01：资源允许时跨目标可并行，同目标有序；M02 已确认两级控制，M03 已确认本单授权目标清单。产品选择已收敛，技术契约须复审。原单目标轨迹保留为同一目标回归，不再代表不同目标必须全局串行；各用例仍待产品实现与实际验证。

以下是完整交付需要验证的可观察结果，目前尚无整条端到端验收通过。已有基础实现与回归证据见 [progress.md](progress.md) 和 [本轮实现验证](verification-2026-10-13.md)；基础测试不等于整条 AC 完成。

- [ ] AC01（R01、R02、R21）：同一套 Multica Server 部署中，两个使用不同工作空间的账号之间完成授权派单，接收人无需成为整个来源空间的普通成员，也能在个人工作台访问获共享的本单；来源空间的其他资源仍受各自权限保护。
- [ ] AC02（R02）：接收人离线时仍能收到持久待办；重新登录查询可见。读取或归档通知不会代替业务处理完成。
- [ ] AC03（R03、R04）：任务可转给产品、测试或开发账号，交接说明和交接目的可查，任务身份及此前历史保留。
- [ ] AC04（R04）：提交阶段结果给测试或另一位开发后，接收人能够接续处理，整单不会仅因转交自动完成。
- [ ] AC05（R05、R36）：获授权协作者能读取并跟踪本单专属讨论、已记录的 AI 执行消息及结果，来源工作空间普通成员保留既有基础访问；不具备有效协作授权或来源空间访问权限的账号不能读取。
- [ ] AC06（R06、R07）：产品、当前处理人以及保留权限的原处理人都能在本单授权范围内发指令、停止及恢复；普通转交不会自动移除原协作者权限。
- [ ] AC07（R08）：同一 AI 会话已有执行时，后续指令进入队列，不将新指令伪装为已经实时送达运行中的 AI。
- [ ] AC08（R09）：指令 1 运行、2 和 3 排队时，停止操作使 1 停止并挂起 2、3；停止过程不能因为竞态自动启动下一条。
- [ ] AC09（R09、R10）：挂起期间新增指令继续等待；刷新、网络重连和 daemon 重连不会自动解除挂起。
- [ ] AC10（R10）：明确恢复后 2、3（及暂停期间加入的指令）合为一批执行一次（M07），1 不自动重试；如无后续指令则保持空闲。
- [ ] AC11（R11）：运行中转交不停止当前执行；挂起中转交不恢复队列；原协作者的权限保持。
- [ ] AC12（R06、R09、R10）：参与者能分辨控制请求的操作者、受理状态和实际执行结果；重复请求和过期操作不会造成重复执行或错误恢复。
- [ ] AC13（R12）：发起人和当前处理人可以通过邀请或转交新增协作者；不具备这两种身份的已有协作者，即使保留本单 AI 控制权限，也不能通过任一入口让新账号加入本单。
- [ ] AC14（R07、R11、R12）：转交后，新的当前处理人取得新增协作者权限；并非发起人的原处理人不再拥有这项权限，仍保留本单查看、评论、指挥、停止和恢复权限。发起人的新增协作者权限不随转交变化，执行与队列状态仍遵守 R11。
- [ ] AC15（R06、R12、R13）：仅 creator/handler 能组织新增目标，已合法加入本单的实际资源 owner 才能确认其组合，未参与者先走原邀请流程；组织者不能替其他 owner 授权，普通参与者不能新增目标。授权齐备后参与者可使用目标，@owner 或阅读通知不生成授权。
- [ ] AC16（R12、R13）：现有及以后合法加入的参与者可使用本单已有有效目标授权，无需逐人确认；授权不扩展到其他任务/资源。小队所有实际成员资源须授权，但这不使其成员自动成为独立 @agent 目标，也不邀请人类 owner/成员。
- [ ] AC17（R14）：发起人可以执行移除协作者操作；并非发起人的当前处理人及其他已有协作者均不能执行该操作。普通转交不会自动移除原协作者。
- [ ] AC18（R13、R14）：协作者被移除后，不能继续凭原协作身份读取本单、发表评论或发起 AI 控制请求，也不能凭此前的按单运行资源授权绕过移除结果；直接链接、实时订阅和附件请求应使用一致的协作权限判断。
- [ ] AC19（R14、R15）：队列中存在多个协作者提交的未执行指令时，移除其中一位协作者会自动取消其在本单提交的未执行指令，保留内容、提交人及取消原因；其他协作者的指令不因这项规则被取消。
- [ ] AC20（R09、R10、R15）：挂起队列中的未执行指令同样适用移除后的自动取消；明确恢复队列、重新连接或重新加入协作不会自动恢复已取消指令。有权限的协作者需要执行相同内容时，须另行提交新指令。
- [ ] AC21（R14、R15、R16）：协作者 A 的指令正在执行，A 和 B 均有后续排队指令时，移除 A 会请求停止 A 的当前执行并挂起所属通道；A 的未执行指令自动取消，B 的排队指令保留但不能因停止过程自动启动。界面区分停止已受理与执行端已确认结束。
- [ ] AC22（R09、R10、R14、R16）：没有有效的明确恢复操作时，收到停止回执、刷新页面或重新连接都不能解除该通道挂起。被移除者无权恢复；仍有权限的协作者恢复后，从下一条有效排队指令继续，不自动重做已停止或已取消的指令。无关会话不因本次移除被停止或挂起。
- [ ] AC23（R09、R17）：停止请求已受理但执行端断线、旧执行尚未确认结束时，恢复请求被拒绝并告知等待原因；通道继续挂起，不启动下一条指令，也不保存待确认后自动生效的恢复请求。
- [ ] AC24（R10、R17）：旧执行随后确认结束时，即使此前有人请求过恢复，会话仍保持挂起；重放此前被拒绝的请求不能自动恢复。只有仍有权限的协作者重新发起明确恢复操作，才可从下一条有效指令继续。
- [ ] AC25（R02、R03、R04、R18）：任务由产品 P 发起，开发 D 将任务转给 P 补充信息；P 执行"补充完成并交回"后，当前处理人回到提出本次补充请求的 D，P 和 D 的当前待办随责任转移而更新，任务身份及协作历史保留。
- [ ] AC26（R04、R11、R18）：补充信息期间仅发表评论不会自动交回；明确执行交回动作不会把整单标记为完成，也不会停止、恢复或重启本单 AI。普通转交已有的协作权限保留规则继续适用。
- [ ] AC27（R19、R36）：普通协作入口下，当前处理人或其他协作者不是发起人时，不能将整单标记为完成，即使已完成测试验证；发起人的完成权限不因普通转交转移。发起人退出来源空间后，账号及本单协作身份仍有效时，仍可明确完成整单；R38 的代管条件须单独验证。
- [ ] AC28（R04、R18、R19、R38）：提交阶段结果、执行"补充完成并交回"、记录测试通过或 AI 执行成功都不会自动完成整单；整单完成必须来自发起人的明确操作，或符合 R38 的明确代管操作。
- [ ] AC29（R02、R19、R20）：非发起人的当前处理人提交最终结果并执行"提交验收并转交"后，当前处理责任和待办一起转给发起人；原处理人不再承担当前处理责任，发起人能从个人工作台找到本单并进行验收。
- [ ] AC30（R07、R11、R19、R20、R38）：提交验收后整单仍未完成，须经 R19 或 R38 允许的明确完成操作；原处理人保留协作权限，运行中的 AI 继续运行，已挂起的队列仍挂起，不因提交验收自动停止、恢复或重启。
- [ ] AC31（R22）：首版用户流程在 Web 和 Desktop 均可完成；跨端接续处理时，当前处理人、协作权限、任务历史和队列状态保持一致，不因切换客户端产生另一份协作任务或不同的操作权限。
- [ ] AC32（R09、R14–R17、R22）：CLI/daemon 配套适配本单执行和控制规则；既有接口请求、旧客户端调用或 daemon 重连不能绕过队列挂起、停止未确认时拒绝恢复及协作者被移除后的指令处置规则。
- [ ] AC33（R08、R23）：不同协作者跨 Web/Desktop 向同一单指定 A/B 两个目标，在双方授权有效、资源容量充足且无暂停时，B 无须等待 A 完成即可执行；A 忙碌期间连续的多条 @A 并入一个待执行批次，A 结束后作为一次后续处理执行，单条取消只移出该条。分别保存目标、真实提交人和执行关系，结果归同一单；不能把 B 的指令交给 A，也不能按客户端重复执行。
- [ ] AC34（R09、R10、R17、R23）：停止目标 A 时，A 及其适用派生执行/队列暂停，同 lane 目标（A 任队长的小队）一起暂停/恢复并同时列出，其他 lane 的目标 B 保持状态；B 自身条件满足且无整单暂停时可独立恢复。整单暂停后，新增 @目标、切客户端或只恢复某个目标均不能绕过；其他单据不受影响，控制范围和结果明确可见。
- [ ] AC35（R06、R24）：有权参与者新发评论并明确 @已获授权的智能体或小队时，发送即提交对应执行，不额外要求“发给 AI”；小队由队长接入组织工作。普通无 @评论、仅回复 AI、纯文本名字及未解析为具体对象的 `@AI` 不自动执行，发送前可预览并取消本次目标。
- [ ] AC36（R08、R09、R23、R24）：每个有效 @执行目标保留输入快照、实际提交者及入队结果；通道忙碌时并入待执行批次，适用范围挂起时继续等待明确恢复。新 @不解除挂起，回执不能把等待/暂停写成已经开始；跨目标调度按 M01 验证。
- [ ] AC37（R13、R17、R25）：撤回某资源时阻止所有依赖该 grant 的新执行，停止相关组/派生并挂起目标，保留输入和历史；无关有效目标不变。失效目标移出候选，旧选择在服务端被拒；不能把撤权生效显示成进程已结束。
- [ ] AC38（R10、R17、R25）：旧执行确认结束但授权仍无效时不能恢复；重新取得有效授权后，队列仍等待有权限的协作者明确恢复，不自动重做已停止指令。本次资源授权撤回不取消其他任务的授权，也不自动移除本单协作者。
- [ ] AC39（R13、R17、R26）：仅发起人和当前处理人可执行运行环境切换；旧执行未确认结束、队列未挂起或新环境未取得拥有者的本单授权时，均不能完成切换，不得借切换绕过停止确认或资源授权。
- [ ] AC40（R10、R11、R23、R26）：明确范围的环境切换保留同单历史、指令原目标及状态，继续挂起；明确恢复后才在合法新环境接续，不重做停止/取消条目，不把 @A 改成 @B。新增目标与环境替换分别处理，普通转交不隐式切换；小队换队长时等待输入转入新队长通道末尾，恢复该小队前不执行、可单条取消，不阻塞新通道其他目标；切换控制遵守已确认 M02，替换资源须由对应拥有者按单授权，不改变指令原目标。
- [ ] AC41（R26、R27）：新环境可以基于已提交的 Git 代码或明确交付的附件准备本单所需文件；准备文件或完成环境切换本身不启动执行，仍须满足 R26 的授权、停止确认和明确恢复条件。
- [ ] AC42（R27）：仅切换运行环境不会自动搬运原环境的工作目录或未提交修改；未被明确交付的本地文件不会因切换而自动上传或出现在新环境中。
- [ ] AC43（R13、R28）：多个目标/小队成员使用不同环境时，各自沿用实际环境的供应商账号和额度，记录真实人类发起者、实际执行者及授权来源；同环境多人提交和普通转交不切换为新处理人的供应商账号。
- [ ] AC44（R28）：使用环境中配置的 AI 服务账号不意味着调用者获得环境拥有者的个人 Multica 登录权限；执行访问 Multica 仍使用任务级凭据及真实指令发起人约束，不能借共享供应商账号绕过本单授权或扩大工作空间访问范围。
- [ ] AC45（R21、R29）：可以使用同一 Server 内接收人的完整用户名、邮箱或账号 ID 精确定位并确认目标；姓名片段、空查询或模糊条件不能通过本功能列出账号目录。
- [ ] AC46（R12、R29）：精确查找成功本身不会新增协作者或转交任务；只有具备相应权限的人明确确认操作后才变更协作关系或处理责任，无匹配账号时不产生这些变更。
- [ ] AC47（R14、R30）：非发起人且不再承担当前处理责任的协作者可以主动退出，无需发起人代为移除；当前处理人未转交责任前不能退出，发起人不能退出或移除自己。
- [ ] AC48（R14–R17、R30）：主动退出后，原协作权限失效，本人未执行指令自动取消；若本人指令正在运行，则请求停止并挂起所属通道，其他协作者的排队指令保留。退出者不能再发起控制或恢复，停止未确认时仍拒绝恢复。
- [ ] AC49（R15、R25、R30、R31）：owner D 提供多个目标及小队成员资源，离开本单时全部相关 grants 撤回，相关执行请求停止、目标挂起、失效候选移除；D 的等待输入取消，其他作者输入保留。其他 owner 的无关目标及全体历史保留。
- [ ] AC50（R10、R17、R25、R31）：资源拥有者重新加入本单不会自动恢复原授权或队列；须在旧执行确认结束并重新取得有效授权后，由有权限的协作者明确恢复。该离开事件不撤回其对其他任务提供的授权。
- [ ] AC51（R02、R14、R32）：发起人 P 移除当前处理人 D 后，D 的协作权限撤销，当前处理人变为 P，待办进入 P 的个人工作台；任务身份保留，不留下没有接手人的中间结果。
- [ ] AC52（R32）：移除非当前处理人的协作者不改变当前处理责任；移除与自动回交失败时不能仅完成移除。重复或过期的移除请求不能把后来接手者的责任再次改回发起人。
- [ ] AC53（R03、R12、R33）：发起人和当前处理人可向已有协作者发起普通转交；其他已有协作者即使拥有 AI 控制权限，也不能通过普通转交修改当前处理人。接收人为新账号时仍验证 R12。
- [ ] AC54（R07、R33）：普通转交完成后，并非发起人的原处理人不再拥有普通转交权限，新处理人取得该权限；原处理人的讨论和 AI 控制权限继续保留，不能利用转交前的角色或旧请求覆盖新的处理责任。
- [ ] AC55（R34、R36）：普通协作入口下，发起人可以取消整单或重开已完成、已取消的任务；非发起人的当前处理人及其他协作者均不能执行这些操作，普通转交不会转移该权限。发起人退出来源空间后，账号及本单协作身份仍有效时，仍可执行取消、重开；R38 例外须单独验证。
- [ ] AC56（R06、R19、R34、R38）：整单取消或重开须验证发起人权限或 R38 的完整代管条件，不能借 AI 控制能力、运行环境拥有者身份或其他入口绕过；本条不撤销协作者已有的 AI 停止及队列控制权限。
- [ ] AC57（R19、R34、R35）：发起人完成或取消整单时，当前 AI 执行收到停止请求，所有协作者的剩余未执行指令均取消，保留历史和取消原因；业务任务已结束不等于进程已确认退出，界面仍须表达真实停止状态。
- [ ] AC58（R17、R34、R35）：已完成或已取消的任务不能通过 @智能体/小队、旧“发给 AI”入口或恢复继续执行，也不能新增派生工作。重开不复活停止/取消条目，旧执行及其应收尾派生工作未确认结束时遵守恢复屏障；相同结束类别的自定义状态也适用。
- [ ] AC59（R02、R05、R07）：原处理人转出任务、归档通知并重新打开客户端后，仍能从个人工作台找到自己有协作权限的本单并查看记录，无需加入整个来源工作空间；该单不再计入其当前处理待办。已退出或被移除的账号不能继续凭旧协作身份使用这一入口。
- [ ] AC60（R24、R36）：来源空间普通成员未加入本单时保留查看/普通评论，但即使 @真实智能体/小队也不能触发执行；直接请求同样拒绝，不能伪装已入队。该成员不凭来源身份取得 AI 控制、转交、移除或整单管理权限。
- [ ] AC61（R14、R30、R36）：账号退出或被移出本单协作后，若来源空间成员身份仍有效，可以继续凭该身份查看和普通评论，但旧协作控制权限失效；若两种访问依据都已失效，详情、历史、附件和实时访问均应拒绝。
