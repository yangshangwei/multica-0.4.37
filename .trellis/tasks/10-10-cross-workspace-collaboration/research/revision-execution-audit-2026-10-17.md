# Research: Revised multi-target execution audit

- Query: Compare the revised M01–M03 / R08–R17 / R23–R26 / R31 / R35 / R53 contracts with backend schema, queue/control, authority invalidation and ordinary execution writers; identify implementable follow-up slices.
- Scope: internal; current source inspection, no production mutations or test execution.
- Date: 2026-10-17
- Active task: `.trellis/tasks/10-10-cross-workspace-collaboration`; the parent reports current implementation authorization and task activation. Older planning-only wording in task documents is historical for this dispatch.

## Findings

### Conclusion

The human workflow foundation is reusable, but the execution foundation requires structural adjustment. It currently has one session queue, one active grant, one run per command and one unsettled run per session. The revised design requires an issue controller, typed targets, one root FIFO/group per target, and multiple separately proven runs per group. There is no production target/group implementation or positive shared execution path to preserve.

These are confirmed incompatibilities with new requirements, **not evidence that the latest requirement edit caused a runtime regression**. The existing foundation spec accurately describes the same limitations. Public creation is still unregistered (`server/cmd/server/router.go:1607`); `ResumeQueue` deliberately refuses every positive admission (`server/internal/service/collaboration_queue.go:243`). Neither should be enabled by the model migration alone.

### B. Existing gaps that remain prerequisites (not newly broken by M01–M03)

1. **Resource consent/admission and runtime proof are not implemented.** A search of non-test source under `server/internal`, `server/pkg/db/queries` and `server/pkg/protocol` found no target/group/delegation model, `CanAdmitCollaborationRun`, `AuthorizeCollaborationBusinessCapability`, grant-creation service, runtime-enrollment consumer or proof-ingestion path. Only gate reads (`collaboration.sql:77`) and termination stop-intent update (`:238`) use those scaffold tables. Migrations and seeded tests do not constitute a working grant, permit, supervisor or proof protocol.

2. **Ordinary execution fencing does not reject collaboration sources.** `server/internal/service/issue_admission.go:11` checks triage admission and comment dispatch eligibility only. `server/migrations/535_triage_execution_fence.up.sql:48` checks admission under KEY SHARE and returns true at `:57`; it never checks issue_collaboration. `TaskService.enqueueMentionTaskWithCommentPlan` (`server/internal/service/task.go:1392`) then permits an explicit agent, creates ordinary issue-linked work at `:1426`, and applies ordinary attribution fallback/MCP overlays at `:1417`/`:1423`. This is a service/SQL boundary gap despite the current HTTP guards. A direct internal caller could insert or claim ordinary work for an otherwise paused collaboration issue. This audit establishes the code path, not a reproduced publicly reachable exploit.

3. **Task purpose routing is absent.** `server/pkg/db/generated/models.go:232` AgentTaskQueue has context plus ordinary issue/chat/autopilot links, no purpose. Generic claim at `server/pkg/db/queries/agent.sql:840` uses only the ordinary execution fence. Its null-source serialization (`:891`) treats all issue/chat/autopilot-less tasks alike. `server/internal/handler/daemon.go:3071` parses quick-create only by context/type after generic claim assembly; `:2147` already assembles general plugin and connected-app capabilities. `server/internal/service/task.go:3767` finalization rechecks only the ordinary issue fence then mints an ordinary task token at `:3777`. Future collaboration engine rows need explicit purpose, dedicated source admission, capability allowlisting, and rejection by generic claim/start/retry/finalize selectors before any broad payload/token assembly.

4. **Resource cleanup / bulk operational cancellation lacks collaboration fanout.** `server/internal/service/runtime_teardown.go:62` locks runtime before touching tasks, then `:80` bulk-cancels engine rows and `:117` detaches runtime history; no source grant/group stop is recorded. `server/internal/handler/workspace_revoke.go:93` archives runtime agents and `:111` bulk-cancels tasks. `server/internal/handler/agent.go:2635` delegates “Cancel all” to ordinary task cancellation. `server/internal/service/task_cancellation.go:103` locks a chat/task path and updates task status directly. These paths must discover every affected source target/group and record durable stop/fences before cleanup, obeying E02 source/resource NOWAIT intersections. Engine terminal status must never settle collaboration runs. Source membership loss must not revoke participation or advance a global collaboration account epoch.

5. **Old comment/event machinery is incompatible if reused.** Ordinary trigger computation deduplicates by agent UUID and upgrades a direct agent to squad leader (`server/internal/handler/comment.go:3024`), contrary to distinct typed agent/squad targets. Ordinary edit/delete retriggers surviving input (`comment.go:3414`, `:3446`, `:3570`), contrary to immutable collaboration commands and no execution from edits. Existing loaders currently refuse collaboration writes (`server/internal/handler/collaboration_boundary.go:61`), so retaining these guards is correct. New comment/input routes must not publish unsanitized ordinary events: `server/cmd/server/notification_listeners.go:897` sends source inbox notifications and `:903` parses ordinary mentions; `server/internal/service/plugin_event_bridge.go:45` forwards full payload unless a caller supplied suppress_execution. A boolean producer convention is not a substitute for a source/purpose boundary.

6. **Smallest machine capacity needs real handoff, not queue bookkeeping.** `server/internal/daemon/daemon.go:4856` takes machine slots before claim and `:4905` returns a slot only after handleTask finishes. `server/pkg/db/queries/agent.sql:1879` counts dispatched/running/waiting_local_directory against agent capacity. A living squad leader that waits for a member cannot be made non-blocking by setting DB state to waiting or splitting target FIFO alone. Implement durable member intents + sealed leader phase + slot release + fresh continuation run as E03 prescribes, and verify MaxConcurrentTasks=1 with fake executables.

### C. Existing behavior worth preserving

- `server/internal/handler/collaboration_boundary.go:61`/`:100` reject ordinary writes and batches before effects; current source-space access and separate participant control should remain.
- `server/internal/service/collaboration_queue.go:302`–`:454` already preserves human identity, locked reauthorization before receipt recovery, exact immutable epochs, bounded transaction retry, and no automatic mutation replay after uncertain commit.
- `collaboration_queue.go:194`–`:225` preserves first forced disposition and requires original permit/progress/outcome evidence for server-proven never-launched settlement. Reuse the **per-run** invariant, not its root-command completion side effect.
- `server/internal/auth/password_revoke.go:27` persists collaboration epoch invalidation within the security transaction and before its no-runtime early return at `:47`. Preserve the separation from source-object fanout and historical termination credentials.
- `server/pkg/db/queries/collaboration_reconciliation.sql:7` prevents later account epochs overtaking earlier ones; `:96` commits cursor movement with source effects. Multi-target adaptation belongs inside that issue transaction, not a second untracked loop after cursor advance.
- Transfer/handoff is human responsibility only (`server/internal/service/collaboration_workflow.go:97`, `:197`); no new target/group state changes should be added there.
- Workspace deletion checks retained collaboration records before cleanup (`server/internal/handler/workspace.go:1131`), including terminal issues. Keep this fence.

### D. Small coherent implementation slices and ownership

**S0 — Close the ordinary execution bypass while public collaboration stays disabled.** Independently actionable before the new runtime. Own `server/internal/service/issue_admission.go`, the relevant ordinary enqueue/start/finalize boundaries in `task.go`/`task_start.go`, and a new forward migration that replaces `lock_issue_execution` with collaboration-source rejection. Use dedicated regression tests for direct service enqueue, direct SQL insert/claim/finalize, queued legacy source rows, and ordinary issue/chat/quick-create controls. Do not broaden “parent is collaboration” into denial of R51 ordinary child work; explicit R56 captured-source denial already has its own boundary. When purpose arrives, generic issue-less selectors need an additional explicit purpose exclusion.

**S1 — New persistent target/group model with safe historical mapping.** One owner for new migrations, all collaboration SQL, sqlc regeneration, and migration tests. Add target/config/roster/group/delegation identity and new indexes; migrate only proven historical associations. Preserve UUIDs, old seq, run fence/claim/launch nonce, forced root, unsettled proof and termination snapshot. A waiting legacy command has no immutable target: do not infer it from mutable active_grant_id. Retain it inaccessible to promotion and keep execution gate closed until an explicit safe migration policy is satisfied. Additive DDL/backfill may land before executable writers, but do not drop single-run guards as a standalone “parallelism” change.

**S2 — Integrate scoped stop/invalidation/lifecycle with the new model.** A single owner should change `collaboration_queue.go`, `collaboration_workflow.go`, `collaboration_lifecycle.go`, `collaboration_account_reconciliation.go`, and their query files together. Introduce transaction-borrowing group stop/settle primitives; acquire sorted target locks before participant/grant/command/group/run as E02 requires. Route target Stop, issue Stop, author departure, grant invalidation, account fanout and close through the same scoped primitives. Initially retain Resume refusal until real admission/proof exists. This provides a coherent verified model without claiming runtime support.

**S3 — Target organization/consent + typed comment submission.** Depends on S1/S2 contracts. Add issue-authorized target management, per-resource owner consent/config epochs, mention-target projection and input transaction with per-target accepted/blocked outcomes. Root input is created only by a new human comment; preview has no effects; edits never dispatch. R45 cancellation remains one waiting root command. Coordinate a single router/DTO integrator with core/client work rather than parallel edits to `router.go` or `collaboration.go`.

**S4 — Purpose, enrollment/supervisor, then scheduler/positive Resume.** P4 owns purpose middleware, credentials, daemon/protocol/native supervisor; P5 owns scheduling, target FIFO, group delegation/continuation and resource teardown integration. Share one owner for `task.go`, `agent.sql`, claim finalization, `daemon.go` and generated DB files. Positive Resume requires full current authorization + historical proof + gate validation in one transaction; no temporary “set active” endpoint. P4/P5 must finish before opening public creation or new execution controls.

### E. Migration and verification details

- Latest observed migration is 619; reallocate the next numbers immediately before writing because other agents share the workspace.
- Do not rewrite 571 or index migrations 591–595. Every new index is a separate single-statement CREATE [UNIQUE] INDEX CONCURRENTLY file, with no new FK/REFERENCES/cascade/inline PK or UNIQUE index construction.
- Required new identity constraints include target(session,kind,resource), command(target,seq), command(input_event,target), group(command), one unsettled group per target, run(group,step_key), and delegation(parent_run,request_key). Keep run/task and termination identities. Remove old session-sequence/run-command/session-unsettled constraints only with validated backfill and compatible writers.
- `server/internal/migrations/collaboration_schema_test.go:52` intentionally rehearses migrations 571–612 and `:111` verifies their historical single-run constraint. Keep that dated fixture; add a new full-upgrade suite proving old data preservation plus new group uniqueness/concurrency instead of rewriting the old evidence into a claim of new support.
- Regressions to run when S1/S2 land: collaboration queue/workflow/lifecycle/account reconciliation suites plus existing fairness/review tests. Add deterministic DB barriers for two concurrent target promotions, same-target FIFO, stop vs member expansion, cancel vs promote, revoke/disable vs permit, and close/reopen with unknown member proof. All source effects and cursor progress must roll back together on an injected required-write error.
- Multi-target controls: target A stop leaves B unchanged; issue stop catches newly added targets and late children; one invalid grant or unknown member makes Resume All change zero states; target resume under global pause rejects; old rejected request stays rejected after proofs/consent improve; never-launched member does not settle live siblings; root author identity survives every delegation.
- Ordinary boundary tests must assert zero tasks/tokens/provider invocations on rejected collaboration paths and preserve normal task semantics. Native tests use task-owned fake executables only: capacity=1 handoff, fork/burn/reap/seal crashes, restart/replay, detached descendants, revoked business credentials with valid termination-only proof, and unavailable/unsupported containment.
- Use isolated task-owned PostgreSQL/private schemas for migration and concurrency tests; do not rely on suites that silently skip without DATABASE_URL. No tests were run by this research-only audit.
