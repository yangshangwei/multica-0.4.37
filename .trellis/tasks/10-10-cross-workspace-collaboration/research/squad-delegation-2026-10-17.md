# 协作单小队派发：保持现状

日期：2026-10-17。状态：用户确认 M08 保持现有小队工作方式，不新增 `multica squad delegate`（讨论 §65）。本文取代同日的结构化派发建议稿。

## 保持不变

普通任务的小队流程原样用于协作单：

- 队长按小队说明挑成员，发一条 @成员 的评论写明要做什么，然后结束本轮（`server/internal/handler/squad_briefing.go:39`、`:67`）。队长不在运行中等待成员，不占运行位。
- 每个成员是一次独立执行，使用自己的环境和额度；执行记录照常保留派发来源（`delegated_from_task_id`，`server/internal/attribution/attribution.go:239`）。
- 成员回帖、提问或完成时队长被再次唤醒，读新进展后决定继续派发、向人类求助或收尾；无需处理时记 no_action 退出（`squad_briefing.go:69-80`）。成员也可以像现在一样 @其他成员。
- 小队说明、CLI 和 SKILL.md 不改。

## 协作单的适配

协作单不允许机器评论启动新的执行，负责人也始终是人类，所以以下两点由协作入口实现，普通任务不受影响。

1. **评论里的 @成员 作为组内派发。** 只有同时满足以下条件，才把该评论里的 @成员 记为本组派发：作者是本组仍在运行的队长或成员 run；被 @ 的智能体在本组 promote 时冻结的名册内，且对本单的授权仍有效。以 comment_id 加成员去重，重试或重复事件不会派出两次；编辑评论不追加派发。本组 run 评论 @本单当前参与者时按 R52 通知（如队长 @发起人求助）；其他机器评论里的 @ 不启动执行、不发通知，派发也不会把人类成员加入本单或通知他们。
2. **唤醒队长不再依赖“负责人是小队”。** 组内成员回帖、提问或 run 结束时，在同组生成一次队长续作 run。队长已有排队中的续作时合并为一次，与现有合并规则一致。
3. **人类再 @队长或 @小队并入本组续作（M11，讨论 §66）。** 满足执行契约 E01“M11 并入”时（小队组尚有存活或排队 run、派发未封闭也未结算、目标无 hold 且授权有效、lane 无更早未并入的合格 waiting），人类新的 @S 或直接 @队长 A 归入本组，冻结其作者代次与目标授权，与成员回帖合并为下一次队长续作，回执显示“并入当前小队执行”。条件不满足时照常 waiting 进下一批。另一支同队长小队仍进下一批（M06）。续作 run 被领取时把输入写入其提示快照，即为已读取；只有该 run 证明从未启动才算未读取。组停止或结算时，未读取的并入输入回到 waiting（作者已移除或单据关闭则取消）；只为它追加的授权失效时，该条回到 waiting 并置目标 hold；该作者被移除时，已读取则按 R16 整组停止，未读取只取消该条；两种情况都移出只为它追加的授权。

现有说明里协作单不支持的路径（如用 `--status todo` 子任务指派智能体）明确拒绝并返回 `collaboration_subtask_unsupported`，队长按说明记 `failed`。

队长和成员的协作业务 token 须放行现有说明用到的调用：读本单上下文、发本组评论、`multica squad activity`（E07）。

## 停止与结算

- 停止小队或整单时封闭本组派发：迟到的 @成员 评论不再派发，活着的成员 run 收到停止请求，尚未启动的派发撤销，不再生成队长续作。
- 组在没有活着或排队的 run，且每个 run 都有合法终结证据时结算。成员失败照常唤醒队长，由队长决定，服务端不隐式重试。
- 容量：队长发完评论就结束本轮，所以容量为 1 的机器上不会出现“队长等成员、成员等队长的运行位”。成员与同单同 agent 的其他运行仍按现有 (issue, agent) 规则排队；同一机器独占目录仍由容量检查保证。

## 与已撤回建议稿的差别

不新增结构化派发命令和系统派发记录；不要求队长取得终结证明后成员才开始；不按“整阶段结束才唤醒一次”，也不设续作上限或派发层数限制，均沿用现状。
