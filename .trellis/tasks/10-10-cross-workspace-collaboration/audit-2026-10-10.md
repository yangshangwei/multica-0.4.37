# 需求审计：跨账号任务流转与共享 AI 协作工作台

## 结论

当前 PRD 能准确保留本轮讨论的核心选择，适合作为需求草案；尚未达到可直接实现、排期和最终验收的程度。

本次识别 7 项需要补充的契约：4 项 P1、3 项 P2。这里的优先级表示实现前的需求收敛优先级，不表示现有产品已经发生对应漏洞或故障。PRD 已将部分事项诚实地列为 O01–O07；审计进一步说明其影响、具体反例和缺少的验收结果，不将"尚未写 design.md"本身当作需求缺陷。

主要结论是：跨空间共同控制需要明确授权来源；用户指令队列不能直接等同于现有 task 队列；停止并挂起与当前取消 task 是不同契约；业务流转尚缺少阶段结束和待办归属的完整规则。

## 已核对一致的核心规则

以下选择与用户最后的答复一致，不应在下一轮重新询问或回退：

1. 不强制共用工作空间，可以跨不同账号流转。
2. 转交对象不限于产品，可以是测试、其他开发等账号。
3. 转交用途包括补充信息与提交阶段结果。
4. 本单采用共享协作过程方向；产品已明确从仅评论改为可以指挥、停止 AI。
5. AI 正忙时新指令排队，不要求实时插话。
6. 停止当前执行时同时挂起后续队列，等待明确恢复。
7. 恢复从下一条开始，不自动重做被停止的指令。
8. 转交后已有协作者保留 AI 控制权限。
9. 转交保持运行及队列的原有状态。

文档也正确地把同一 Server 作为分析前提，并标明跨空间执行关联仍是候选设计；早期 20%～40% 的粗估未被当作最终排期。

## F01 · P1：共同控制的授权规则不闭合

**位置：** [PRD 第 39 行](prd.md#L39)、[第 74 行](prd.md#L74)、[第 94 行](prd.md#L94)。

R06 将"获授权协作者"定义为可以控制本单 AI 的人，但没有说明谁能让一个新账号获得这种资格，以及单据授权怎样与个人运行资源授权衔接。R07 确定保留权限，却没有决定旧协作者是否还能继续邀请、转交和向新人授予控制权。

**具体反例：** 产品 P 将任务交给开发 D，D 使用自己的私有智能体执行；D 再交给测试 T。按最终需求，P、D、T 都可以控制本单 AI。若实现只在任务表增加参与者：

- 保持现有智能体调用门禁，P、T 仍可能被拒绝，无法满足 AC06。
- 把所有控制请求伪装成 D 或使用 D 的完整凭据，实际操作人与外部工具权限归属就会失真。
- 如果任意旧参与者还能加入新人，任务参与关系会隐式扩大 D 的运行资源授权，而 PRD 没有规定授予者。

**代码依据：** [invokeAgentDecision](../../../server/internal/handler/agent_access.go#L73) 区分实际调用人和任务来源人，私有智能体默认只允许拥有者；[任务 token 的空间绑定](../../../server/internal/middleware/workspace.go#L69) 不能通过切换请求头扩大；[评论调用目标](../../../server/internal/handler/comment.go#L3164) 仍限定同一空间。现有[执行订阅授权](../../../server/cmd/server/scope_authorizer.go#L65)还允许任务所在空间的成员查看，这与"哪些人算本单协作者"需要形成明确关系。

**最小补充：**

- 定义发起人、当前处理人、原协作者、来源空间的非协作成员、运行资源拥有者各自能查看、评论、转交、邀请、撤权和控制什么。
- 明确本单执行授权由谁授予，以及绑定智能体或运行时后，后加入的协作者是否自动覆盖在该授权内。
- 指令、执行、费用展示和外部工具调用应保留真实操作人与对应授权依据；具体凭据结构交给设计，不让前端传入的身份成为授权来源。
- 添加无权账号、仅有源空间成员身份者、权限已撤销者、旧协作者和新协作者的正反例。

这不会改变已经确定的"协作者保留本单控制权"，只是补齐谁可以成为协作者、控制哪些资源及何时失效。

## F02 · P1：用户指令不能直接视为一条现有 task

**位置：** [PRD 第 27 行](prd.md#L27)、[第 42 行](prd.md#L42)、[第 75 行](prd.md#L75)。

PRD 的例子明确要求"1 停止、2 和 3 保留，恢复后先 2 再 3"，但只定义了任务、AI 执行和会话，没有说明指令本身是否独立可追踪、可排序、可标记停止。其实现风险不是是否使用某张表，而是现有队列语义不同。

**具体反例：** 指令 1 正在执行，开发提交指令 2，产品紧接着提交指令 3。现有评论路径可把 2、3 合并为一个待执行 task，并以新评论更新触发内容和归因。UI 可以显示"已排队"，但后端没有分别处理 2、3 的确定边界。此时无法证明 AC10 要求的顺序，也难以说明停止的是哪条指令。

**代码依据：** [MergeCommentIntoPendingTask](../../../server/pkg/db/queries/agent.sql#L1947)明确合并待执行评论，并重写运行归因；[处理器中的合并路径](../../../server/internal/handler/comment.go#L2375)沿用这一行为；[现有 claim](../../../server/pkg/db/queries/agent.sql#L808)按 issue/agent 或 chat session 串行化，而非任意新定义的共享协作会话；[任务排序](../../../server/pkg/db/queries/agent.sql#L900)也不能替代用户指令的顺序契约。

**最小补充：**

- 在需求中定义一条已受理指令的作者、目标、可追踪身份、顺序与结果，不预先指定数据库实现。
- 既然用户选择从下一条开始，就必须能识别被停止的那条与尚未执行的后续条目；若底层仍批量执行，必须证明不会破坏这一可观察语义。
- 明确队列作用于哪个 AI 会话；首版支持多少个并行会话可作为范围决策，不能自动把"本单""某个智能体""整台 daemon"当作同一个队列。
- 验收增加多账号连续提交、领取前合并竞争、重发相同指令和中途转交，验证作者、顺序与单条状态保持。

已确定的排队策略无需重问；需要补的是保证该策略成立的契约。

## F03 · P1：停止与恢复缺少未确认状态的结果定义

**位置：** [PRD 第 43 行](prd.md#L43)、[第 50 行](prd.md#L50)、[第 76 行](prd.md#L76)、[第 98 行](prd.md#L98)。

AC08–AC12 已有正确方向，但"停止成功""防止错误恢复"等表达还不足以区分数据库终态、进程停止回执和允许下一条领取的时点。

**具体反例：** Server 受理停止并把当前 task 标为取消，daemon 此时断网、旧进程仍在运行。另一位协作者立即点击恢复。如果只检查数据库 task 已终态，就可能启动下一条，与尚未退出的旧进程同时操作相同工作目录。反过来，如果执行已自然完成而停止请求稍晚到达，也不能把实际完成结果无条件覆盖成已停止。

**代码依据：** [CancelTaskInTx](../../../server/internal/service/task_cancellation.go#L67)处理单次取消；[取消后的副作用](../../../server/internal/service/task_cancellation.go#L137)会通知任务结束并唤醒等待者；[daemon 取消观察](../../../server/internal/daemon/daemon.go#L5040)与 Server 请求不是同一时刻；[停止回执](../../../server/internal/daemon/cancel_receipts.go#L276)有执行代次和进程确认要求；[RerunIssue](../../../server/internal/service/task.go#L5653)还会清理待执行槽并新建执行，不能直接充当"恢复后续原队列"。

**最小补充：**

- 分别定义队列开放/挂起状态和当前执行运行/停止请求中/已停止/已完成/失败的可观察结果，不把业务任务状态充当队列状态。
- 明确停止未确认时恢复请求是拒绝、等待还是记录恢复意图；无论采用哪种交互，都不能无证据地宣称旧执行已经停止。
- 挂起必须覆盖所有可产生或领取该队列执行的入口，包括正常完成跟进、重试、重新运行、旧客户端请求和自动触发；无需把无关队列一起停掉。
- 增加停止与领取、停止与完成、停止与恢复同时发生，daemon 断线、回执重放和过期控制请求的验收结果。
- "跳过被停止指令"不承诺撤销它已经产生的文件修改或外部操作；恢复后应能识别已保留的结果，避免用户误以为已经回滚。

这些是 R09–R10 成立所需的结果约束，具体锁、版本和幂等机制应留给设计。

## F04 · P1：交接目的尚未构成业务闭环

**位置：** [PRD 第 36 行](prd.md#L36)、[第 38 行](prd.md#L38)、[第 53 行](prd.md#L53)、[第 95 行](prd.md#L95)。

"补充信息"和"提交阶段结果"已经确认，但现在的验收只证明能选择接收人并继续处理，没有明确补充完成或阶段验收后由谁承担下一步，也没有明确谁能关闭整单。

**具体反例：** 开发交给产品补充信息，产品发表补充评论后，系统可以继续把任务留在产品待办，也可以自动交回开发。两种实现都可能满足现有 AC03–AC04，却产生不同的真实业务流程。测试验证通过后，如果没有整单完成权限及动作定义，任务也可能永久停留在"可接续处理"。

**最小补充：**

- 定义每类交接的当前处理责任、期待动作、完成该动作后的可选下一步与待办变化。
- 明确当前处理人是否唯一、谁可以修改当前处理人以及并发转交冲突时展示什么结果。
- 定义补充信息完成后的返回方式，以及整单完成、取消或重开的权限；不改变已经确定的转交对象和两类交接目的。
- 用"产品 → 开发 → 补充人 → 开发 → 测试 → 修复人 → 完成"验收整个责任与待办链条，而不只验收单次负责人字段变化。

这里确实需要产品决策；不能仅根据现有状态枚举猜测。

## F05 · P2：保留权限没有对应的长期访问入口

**位置：** [PRD 第 24 行](prd.md#L24)、[第 36 行](prd.md#L36)、[第 41 行](prd.md#L41)、[第 74 行](prd.md#L74)。

个人工作台目前被定义为汇总需要我处理的任务，但保留权限的原处理人已经不再承担当前处理责任。AC06 可通过直接链接测试，却没有要求用户离开详情页后还能找到自己参与的任务。

**具体反例：** 开发不是创建人，也没有拥有该任务使用的智能体；转给测试之后，"分配给我"不再包含此单，"我创建的"和"我的智能体"也找不到。即使仍有控制权限，关闭页面并归档通知后，实际入口可能丢失。

**代码依据：** [现有我的任务范围](../../../packages/core/issues/stores/my-issues-view-store.ts#L13)与[列表参与关系](../../../server/pkg/db/queries/issue.sql#L1)不等同于新的共享协作者集合；[通知深链接](../../../packages/core/realtime/use-realtime-sync.ts#L542)还依赖用户所属空间列表，跨空间非成员不能直接照搬。

**最小补充：** 明确区分"当前待办"和"我参与的/我转出的"访问能力，具体名称和页面位置后定；验收转交、通知归档、重启客户端后仍能找到本单，且打开时不要求加入整个来源空间，也不跳错空间。

## F06 · P2：普通评论和执行指令的分界不明确

**位置：** [PRD 第 40 行](prd.md#L40)、[第 42 行](prd.md#L42)、[第 74 行](prd.md#L74)。

产品和其他协作者可以直接指挥 AI 已经确定，但"可以指挥"不直接说明每一条普通评论都是执行请求。PRD 没有定义评论、回复 AI、提及 AI 及显式执行指令之间的关系。

**具体反例：** 测试在 AI 回复下写"收到，稍后验证"。沿用当前回复路由可能触发一次执行；另一个实现若一律只当普通评论，则用户明确要求 AI 修复的内容也可能不执行。仅测试"可以发表评论"和"可以发指令"无法捕获这种差异。

**代码依据：** [评论触发器](../../../server/internal/handler/comment.go#L2632)同时有显式提及、回复作者和隐式路由；[回复 AI](../../../server/internal/handler/comment.go#L2702)可以进入执行；当前[评论输入](../../../packages/views/issues/components/comment-input.tsx#L164)还有触发预览与抑制机制。

**最小补充：** 选择并说明用户怎样表达执行意图，以及如何在发送前知道会进入哪条 AI 队列。建议保留清楚的讨论与执行意图区别，但不在本次审计中擅自决定必须是两个按钮、`@` 语法或某个新入口。补充普通评论、明确指令、回复、提及、编辑已排队输入和挂起期间发送的结果验收。

## F07 · P2：共享任务的生命周期仍依赖未定政策

**位置：** [PRD 第 37 行](prd.md#L37)、[第 41 行](prd.md#L41)、[第 94 行](prd.md#L94)、[第 99 行](prd.md#L99)。

保留协作权限是明确的，但任务源空间被删除、资源拥有者退出、某位协作者被明确撤权后，保留哪些记录、哪些控制请求还有效，没有验收策略。普通转交保留权限不能被扩张为退出、账号禁用或空间删除后仍无条件保留全部权限。

**具体反例：** 产品的源空间 A 被删除，开发和测试仍在其他空间跟进任务。如果沿用源空间清理路径，单据与评论会被删除；如果只保留新增参与关系，又可能留下打不开的待办和失效的执行引用。另一种情况是排队期间撤销某人的执行权限，稍后恢复时该指令是否仍可执行也尚未定义。

**代码依据：** [源空间评论清理](../../../server/pkg/db/queries/workspace_delete.sql#L533)与[任务清理](../../../server/pkg/db/queries/workspace_delete.sql#L555)会删除相应业务记录；来源空间保留任务的方案因此必须选定清理政策，而不只是新增一张授权关系。

**最小补充：** 首版选择并写明空间删除时阻止删除、保留归档或转移归属等其中一种策略；分别定义退出、撤权、禁用、资源不可用时的读取、控制、排队和通知结果。加入已撤权用户的旧链接、旧 WebSocket、附件访问及待执行指令的负向验收。

## 建议补充的验收场景

这些是新增验收建议，不表示测试已实现，也不替用户选择尚未确定的政策。

| 场景 | 需要验证的结果 | 对应发现 |
| --- | --- | --- |
| 任务协作者不是目标私有智能体拥有者 | 按明确的本单资源授权成功或拒绝，真实操作者与执行凭据不混用 | F01 |
| 原协作者继续添加第三人 | 只有被授权的角色能扩大协作范围；不因保留 AI 控制权自动获得授权管理权 | F01 |
| 源空间普通成员不在本单协作者列表 | 按已选政策确定其读取与控制能力，HTTP、实时流和附件保持一致 | F01 |
| 两个账号在领取前连续提交指令 2、3 | 可追踪两条指令的作者、顺序与结果，不能只显示一个无法解释的合并执行 | F02 |
| 两个 AI 会话中只停止一个 | 精确作用于所选队列，另一个会话保持原状态 | F02、F03 |
| Server 受理停止后 daemon 断线，另一人恢复 | 界面表达未确认状态，不把数据库取消直接当作进程已经退出 | F03 |
| 停止与自然完成同时到达 | 已发生的结果如实保留，后续队列按确定的控制顺序执行 | F03 |
| 挂起期间出现自动跟进、重试或旧 CLI 请求 | 不能绕过该会话的挂起门禁或自动重做已停止指令 | F03 |
| 补充信息完成并交回开发 | 当前处理责任、待办计数和交接记录按确定规则一致变化 | F04 |
| 阶段结果通过验证，申请整单完成 | 有明确可执行的完成动作和权限，而非只停留在能继续转交 | F04 |
| 原处理人转出、归档通知并重启客户端 | 仍能通过参与记录或等价入口找到任务；不被算作当前待办 | F05 |
| 评论确认与明确执行请求使用相同编辑器 | 发送前后都能分辨是否触发 AI、触发哪条队列 | F06 |
| 源空间删除、参与者撤权、运行资源退出 | 按选定政策保留或终止对象，不留下未定义的读取和执行权限 | F07 |

## 其他范围与文档结论

- O07 的同一 Server 前提、各客户端首版范围应在排期前确认，不需要先假设新增跨 Server 联邦协议。
- 已安装 Desktop、CLI 和 daemon 的版本组合应进入 `design.md` 与 `implement.md` 的兼容验证，尤其旧取消、重新运行入口不能绕过新的队列门禁。根项目 [API 兼容规则](../../../CLAUDE.md#L132)已有要求。
- `design.md`、`implement.md` 尚未创建符合当前任务阶段；真正的问题是上述业务决策和可观察契约还没有收敛，不能把空缺全部推给实施人员临场决定。
- 初始上下文清单通过 Trellis 路径与结构校验，只证明文件可用，不证明这些需求已经完成评审。
- 本次不提供新的工时百分比；特别是现有评论合并与新指令队列之间的差异，应先定契约再估算。

## 建议处理顺序

1. 先确定协作者加入与权限管理角色，以及本单执行资源的授权来源（F01）。
2. 明确业务交接的责任与结束方式，并保证保留协作者的访问入口（F04、F05）。
3. 将已经决定的排队、停止、恢复语义写成指令及执行状态契约，补齐异常验收（F02、F03）。
4. 明确评论触发与任务生命周期政策，再形成完整技术设计及实施计划（F06、F07）。

下一项最高价值的产品决策：谁可以通过转交或邀请让新账号加入本单，从而获得本单 AI 控制权限？建议由发起人和当前处理人管理；允许所有协作者扩展参与范围会更灵活，但会扩大多人共享运行资源的授权面。这是审计建议，尚未成为已确认需求。
