## 目标与用户价值

让使用不同个人账号、不同工作空间的人围绕同一张任务持续协作。接收人在个人工作台看到派给自己的待办，可以评论、调用 AI，并将任务转给其他账号补充信息或接续处理。

任务的当前处理责任可以流转，已有协作者继续查看过程并共同控制本单 AI。任务身份和协作历史持续保留，避免参与人反复复制需求和整理上下文。

## 术语

| 术语 | 本任务中的含义 |
| --- | --- |
| 任务（`issue`） | 用户所说的单子，承载需求、处理责任、公开讨论和交接历史 |
| AI 执行（`task`） | 智能体的一次执行；一个任务可以关联多次执行 |
| 工作空间 | 任务、智能体和运行时的资源及权限范围，不等同于个人账号或本机工作目录 |
| 个人工作台 | 按登录账号汇总需要处理的任务，包括跨空间任务 |
| 当前处理人 | 这一阶段接手处理责任的账号 |
| 协作者 | 对本单拥有相应查看、评论与 AI 控制权限的参与账号 |
| AI 会话及指令队列 | 本轮以同一 AI 会话内的指令顺序讨论排队、停止和恢复；多智能体时的准确分组规则待设计 |

原始讨论出现的 `Aiden` 没有被确认为项目中的专有实体或固定智能体。本任务统一使用 AI 智能体，不据此创建名为 Aiden 的功能。

## 已确认需求

| ID | 需求 | 规则 |
| --- | --- | --- |
| R01 | 独立账号与工作空间 | 不强制参与者共用一个工作空间。需要支持各人拥有个人工作空间的情况，也兼容同空间协作。 |
| R02 | 账号级待办 | 接收人在自己的个人工作台看到分配给自己的跨空间任务。待办由实际处理责任和业务状态决定，不依赖通知是否未读。 |
| R03 | 通用账号转交 | 可以转给产品、测试、其他开发等具体账号，不把流程限制为返回产品岗位。转交保留同一任务的身份及历史。 |
| R04 | 两类交接目的 | 支持请对方补充信息，以及提交本阶段处理结果供对方继续处理。提交给测试或其他开发不自动等于整单完成。 |
| R05 | 本单全过程共享 | 本单专属讨论、尝试、系统已记录的 AI 执行过程和结果向获授权协作者共享。当前方向为讨论中的 B。 |
| R06 | 共同控制 AI | 获授权协作者可以发表评论、发出 AI 执行指令、停止当前执行以及恢复队列。产品不再局限于查看和评论。 |
| R07 | 转交后保留协作权限 | 转交改变当前处理责任，已有协作者保留本单查看、评论、指挥、停止和恢复权限。显式撤权、退出规则另行设计。 |
| R08 | 新指令排队 | AI 正忙时，新指令排队，当前一轮结束后执行。本轮选择排队策略，不要求运行中实时插话改变当前执行方向。 |
| R09 | 停止并挂起队列 | 停止当前执行，同时挂起该 AI 会话的后续指令。排队内容保留，挂起期间新加入的指令也等待明确恢复。 |
| R10 | 明确恢复并跳过已停止指令 | 有权限的协作者明确恢复后，从下一条排队指令开始。被停止的指令不自动重试；队列为空时保持空闲。刷新、重连不构成恢复操作。 |
| R11 | 转交不改变执行状态 | 转交时保持执行和队列的原有状态：运行中的继续运行，挂起的仍挂起；不因换处理人自动停止、恢复或重启。 |

### 交互结果的必要约束

- 当前处理人、协作者权限和 AI 执行状态分别表达，避免把交接、撤权、停止混为一个动作。
- 控制操作应显示操作者及实际生效状态；停止请求已受理与执行端确认停止需要可区分。
- 单据共享范围与个人工作空间的其他任务、资源范围分别处理。共享本单不自动意味着共享整个空间。
- 转交本身不能隐式创建重复的 AI 执行；多个协作者的指令必须有可解释的顺序。
- 人类转交和停止 AI 不自动把业务任务标记为已完成；具体业务状态及完成权限待明确。

## 典型用户流程

1. 产品在自己的工作空间创建任务，写明需求并派给开发账号。
2. 开发在个人工作台收到待办，打开本单，查看背景并评论。
3. 开发调用 AI；产品与开发可以共同查看本单记录的过程、发指令和停止执行。
4. 信息不足时，开发把任务转给某个账号补充信息；已有协作者继续跟踪。
5. 阶段处理完成后，任务可以交给测试验证，再交给其他开发修复。
6. 每次转交只改变处理责任，保持当时的 AI 运行和队列状态。
7. 某位协作者停止 AI 后，当前执行停止，后续指令挂起；明确恢复后从下一条开始。

## 验收标准草案

以下是未来实现需要验证的可观察结果，当前均未实施或验收。

- [ ] AC01（R01、R02）：两个使用不同工作空间的账号之间完成授权派单，接收人无需成为整个来源空间的普通成员，也能在个人工作台访问获共享的本单；来源空间的其他资源仍受各自权限保护。
- [ ] AC02（R02）：接收人离线时仍能收到持久待办；重新登录查询可见。读取或归档通知不会代替业务处理完成。
- [ ] AC03（R03、R04）：任务可转给产品、测试或开发账号，交接说明和交接目的可查，任务身份及此前历史保留。
- [ ] AC04（R04）：提交阶段结果给测试或另一位开发后，接收人能够接续处理，整单不会仅因转交自动完成。
- [ ] AC05（R05）：获授权协作者能读取并跟踪本单专属讨论、已记录的 AI 执行消息及结果；无授权账号不能读取。
- [ ] AC06（R06、R07）：产品、当前处理人以及保留权限的原处理人都能在本单授权范围内发指令、停止及恢复；普通转交不会自动移除原协作者权限。
- [ ] AC07（R08）：同一 AI 会话已有执行时，后续指令进入队列，不将新指令伪装为已经实时送达运行中的 AI。
- [ ] AC08（R09）：指令 1 运行、2 和 3 排队时，停止操作使 1 停止并挂起 2、3；停止过程不能因为竞态自动启动下一条。
- [ ] AC09（R09、R10）：挂起期间新增指令继续等待；刷新、网络重连和 daemon 重连不会自动解除挂起。
- [ ] AC10（R10）：明确恢复后执行 2，再执行 3，1 不自动重试；如无后续指令则保持空闲。
- [ ] AC11（R11）：运行中转交不停止当前执行；挂起中转交不恢复队列；原协作者的权限保持。
- [ ] AC12（R06、R09、R10）：参与者能分辨控制请求的操作者、受理状态和实际执行结果；重复请求和过期操作不会造成重复执行或错误恢复。

## 当前分析前提与未纳入的范围

- 当前架构分析以参与者连接同一套 Multica Server 为前提。用户确认了可以使用不同工作空间，尚未单独确认跨独立 Server 部署的需求；不能据此宣称已经支持服务间互通。
- 用户明确选择排队处理新指令，不把运行中实时追加指令列为首版必需能力。
- 本单共享不包含把所有已有私人聊天、无关任务、整个电脑文件系统默认开放给协作者。
- 讨论涉及 Desktop、Multica CLI、daemon 和 Server 的交互；Web/Mobile 的具体交付范围和版本顺序尚未确认。
- 没有确认引入新依赖、新登录类型或重写整个系统的需求。
