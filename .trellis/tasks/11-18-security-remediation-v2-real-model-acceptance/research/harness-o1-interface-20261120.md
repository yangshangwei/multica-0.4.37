# O1 follow-up harness

O1 lives in separate `scripts/real_followup_harness_test.go` and overlays alongside the frozen P1 helper. It compiles to `harness-o1.test`, never overwrites the consumed P1 binary. The four expected actual model tasks are leader intake, restricted security reviewer, ordinary leader reply without squad context, and leader closure after the owner's new top-level hold.

Configuration uses the same exact bindings as P1, with scenario O1 and its own reviewed admission. The field loader is duplicated deliberately in the unconsumed scenario source to avoid changing P1's already consumed bytes. No product source changes or task-body instruction projection occurs. Before each claim, only that positive fixture runtime's heartbeat is refreshed. Reviewer claim's stored api_capability is parsed and must be issue_reviewer for the current issue; external MCP and plugin tools must remain absent.

Input is the frozen O1 issue string followed by the verbatim frozen local supply-chain.json in a code fence. This gives all roles the same local synthetic evidence through the platform issue without requiring repository writes, attachment credentials or network access. The exact composed input and material hash are persisted in O1-input.json before execution. No answer or expected model action is added.

Human inputs are predefined: the invalid plain reply is `同意，先搁置吧。` under the actual leader-authored gate. Once a real security review result exists, the valid top-level hold names that result ID, all six G1 decisions, unknown/hold, the missing digest/provenance/component list, security owner as evidence collector, and review date2026-12-04. Only the actual result ID is substituted. Missing model deliverables fail the sample; the operator does not tell the model how to repair its answer.

The ordinary-reply claim must lack full squad protocol and final-evidence sections. After that run there must still be exactly three tasks and unchanged parent status. Reviewer results must not create a leader task; the stored comment must remain dispatch_eligible=false. Final exact counts are two leader tasks, one plain leader task and one security reviewer task, all completed, with in_review rather than done. All comments retain real actor/source attribution, human release revision1 and distinct new IDs. Full workspace snapshots and keyed deltas remain available for manual review of fields and side effects; automatic verdict still says semantic-review-pending.

Fake02 exercised all four actual router/daemon/native-adapter runs and passed, using a self-created app-server executable plus real compiled CLI and actual mat_ task credentials. Fake01 failed because the harness assumed a comments envelope while the endpoint returns an array; it is preserved. Fake02 proves plumbing, not model judgment.

Future C1/D1 extension must add a separate unconsumed source/binary or freeze after extending before its first real sample, preserving P1/O1 consumed inputs. C1 needs actual local test/patch artifact transfer and hashes; D1 needs before/after synthetic scan evidence. Neither is implemented or claimed by O1.
