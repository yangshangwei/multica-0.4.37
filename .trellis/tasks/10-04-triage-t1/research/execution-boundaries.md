# T1 execution and formal-scope boundary research

Research date: 2026-10-04. Read-only code audit against the new `codex/triage-t1` worktree. This document proposes integration points; it does not claim implementation or tests have passed.

Sources read: root `CLAUDE.md`, `.trellis/spec/server/security-boundaries.md`, `.trellis/spec/server/project-execution-squad.md`, and the complete T1 requirements in `docs/plans/2026-10-04-work-management-prds/triage-prd.md` (especially TRI-FR-08, 09, 14, 19, 26).

## Required invariant

Admission and execution status are separate. Only `not_required`/equivalent legacy default and `accepted` are formal work and eligible for issue execution. Pending, rejected, and duplicate issues never execute, regardless of backlog/todo/custom status, assignee, caller, or transport. Pending creation is explicit in T1; ordinary human, CLI, automation, and channel creation remain formal by default. Admission cannot be supplied or overwritten through ordinary issue metadata or fields.

Ordinary acceptance changes admission and validated fields together but is not an execution trigger. The acceptance endpoint must not call generic update code that interprets backlog → todo, assignment, or changed project defaults as dispatch. Accept-and-execute needs a durable action/idempotency record: queue uniqueness only prevents simultaneous pending rows, not replay after a prior run finishes.

## Smallest robust shared guards

1. **One pure admission predicate and one typed error/reason.** Put the status vocabulary in a small server-owned domain module (or the new triage service). Formal eligibility is an allowlist, not “not pending”: rejected and duplicate are equally blocked. Add the reason to `server/internal/dispatch/reason.go` and the handler dispatch response mapping. HTTP responses should include the affected stable issue reference/link without leaking foreign targets. Unknown/corrupt admission values fail closed.
2. **One persisted-write fence used by task SQL.** `server/migrations/284_task_owner_row_fence.up.sql:lock_task_owner_rows` already guards `CreateAgentTask`, `CreateDeferredChannelIssueTask`, `CreateDeferredAgentTask`, and `CreateRetryTask` in `server/pkg/db/queries/agent.sql`. Its purpose is workspace teardown; do not casually mix all policy into it. Add a specific admission fence, using the caller's transaction connection and issue row lock, to the issue-linked statements. This covers transactional lifecycle and delegated-recovery inserts as well as wrappers. Preserve issue-less chat/quick-create/autopilot behavior.
3. **Claim and mutation backstops.** Add the same formal predicate to `ClaimAgentTask`, `ListQueuedClaimCandidatesByRuntime`, `ListQueuedClaimCandidatesByRuntimes`, `ReclaimStaleDispatchedTaskForRuntime`, `ReclaimStaleDispatchedTasksForRuntimes`, and `StartAgentTask`. Check SQL deferred promotion (`PromoteDeferredChannelIssueTask`, `PromoteDueDeferredTasksForRuntime`, `PromoteDueDeferredTasksForRuntimes`), `LinkTaskToIssue`, and merge/planned-input writers. Candidate filters avoid repeated unusable work; claim/start still enforce independently.
4. **One guarded ordinary issue mutation policy.** Protect generic status/assignment/project/hierarchy writes server-side; admission fields are absent from ordinary request DTOs. Backstop `UpdateIssue` and `UpdateIssueStatus` SQL for nonformal issues, while preserving content-only updates. This covers GitHub auto transitions (`handler/github.go`), failed-task recovery and runtime sweeper updates that call `UpdateIssueStatus` directly. A triage decision owns its own transaction-bound SQL update after checking current admission and revision.
5. **Ordinary accept event discipline.** `service/plugin_event_bridge.go:SubscribePluginEvents` forwards every issue update and derives `issue.status_changed` from `status_changed=true`. Publish a distinct triage decision event (or an explicit suppression flag understood by execution-capable listeners); do not cause ordinary accept to be interpreted as a status/assignment trigger. Keep realtime invalidation and history notifications. `cmd/server/autopilot_listeners.go` currently syncs linked runs on terminal changes; it is not a general start-on-status engine, but plugin forwarding is a real downstream automation surface.

A database trigger on issue-linked queue admission/start can give the strongest future-call-site protection, but it changes all direct writers and can cause generic SQL errors or rollback failed-task settlement. Prefer the explicit shared SQL fence plus narrow service error mapping unless the implementation demonstrates trigger error and retry semantics. Do not introduce foreign keys or cascading actions. Every new index must be its own `CREATE INDEX CONCURRENTLY` migration.

## Authenticated actor distinction

- `handler/actor_guards.go:isMachineCredentialActor` rejects server-stamped `X-Actor-Source: task_token` and `cloud_pat`. `middleware/auth.go` strips user-supplied actor-source before stamping. JWT/cookie and human `mul_` PAT retain member behavior.
- `handler/handler.go:resolveActor` handles task-token agent identity and validates legacy `X-Agent-ID` + `X-Task-ID` pairs. A valid legacy agent pair must also be denied human-only triage decisions even when it uses a human PAT; therefore `RequireHumanActor` alone is insufficient for the product rule “agents cannot approve”. Use the machine credential gate **and** resolved actor type for decisions, batch, CSV import and settings.
- A token carrying its runtime owner's `X-User-ID` is not a human approval. Workspace membership or owner/admin status of that user does not override the actor gate.
- Accept-and-execute must preserve `invokeOriginatorFromRequest`, `canInvokeAgent`, `validateAssigneePair` and squad-leader invocation semantics. Admin configuration rights do not grant private-agent invocation. The review decision being human-only does not make every agent reference invocable.
- Public Plugin API is a separate auth surface: `handler/plugin_action.go` resolves installation/invocation actors. Its current v1 issue PATCH calls `IssueService.UpdateContent` and only exposes title/description; it does not provide status/assignment or a triage decision. `CreatePluginComment` intentionally omits mention dispatch already. Preserve that behavior. Do not route plugin credentials into new human-only endpoints through owner/member attribution.

## Races and failure semantics to test

1. **Fresh creation leak:** `IssueService.Create` commits and broadcasts before ordinary enqueue. Creating a formal row and adding triage state afterward leaves a real dispatch window. Persist intake admission in the original transaction.
2. **Lock strength:** existing `lock_task_owner_rows` locks issues `FOR KEY SHARE`; this does not conflict with ordinary non-key admission/status updates. A new serialized fence must use an appropriate row lock and compatible order. Existing owner order is workspace → agent → issue → runtime; lifecycle locks source/child sorted with `NO KEY UPDATE NOWAIT`. Avoid holding an issue lock while waiting on an agent lock held by a writer waiting on that issue. Use the established NOWAIT/retry discipline, never uncertain-commit replay.
3. **Stale structs:** an enqueue receives `db.Issue` read before a decision. Re-read with the transaction-bound query, not the global pool while holding a lock. Generic content PATCH also carries nullable assignee/project fields from a snapshot (`IssueService.UpdateContent`); a delayed content edit must not restore stale candidate fields after acceptance.
4. **Pending unique index is not idempotency:** `CreateAgentTask` uniqueness only covers queued/dispatched issue-agent pairs and can vary by head SHA. A retry after task start or completion can create another task. Persist accepted action ID + execution attempt/result; retries reuse it and never reaccept.
5. **Delayed comment trigger across acceptance:** a comment written while pending may be enqueued after acceptance by a delayed handler/reconciliation job if the only check reads current admission. Block it based on captured/current decision boundary; do not retain planned obligations from pending comments to execute merely because acceptance happened later. New explicit post-accept actions remain allowed.
6. **Ordinary accept + generic listener:** publishing backlog→todo as ordinary status change can trigger downstream execution after the admission gate is already open. Prevent that at the event/intent boundary.
7. **Disable vs intake/reopen/import:** lock workspace triage settings and pending count in the same transaction used for intake/reopen. A separate pending-count preflight followed by disable can race a new pending row. Snoozed rows count as pending.
8. **Accept-and-execute failure:** commit valid admission first, then independently persist the execution outcome. Runtime offline/invoke revoked after review cannot roll back accepted work or produce a vague 500 that invites reacceptance. Resolve retry by action record.
9. **Replay/claim:** test physically seeded queued, deferred, dispatched-unstarted, waiting-local-directory tasks against pending/rejected/duplicate issues, including batch claim and stale replay. No daemon payload should be returned and no running state should be committed.
10. **Priority rule race:** read current settings under the review transaction, validate priority once, update admission+attributes+history once. A generic status update or batch must never perform implicit acceptance.

## Scope caveats

This is a code audit, not an execution experiment. No backend/frontend code was changed, no DB was mutated, and no tests were run in this lane. Iteration membership is not currently implemented in this branch's baseline; the triage domain invariant must be required by a future iteration writer, but T1 should not create a fake iteration selector or new iteration subsystem. Chat connectors remain ordinary source behavior in T1 as the PRD explicitly directs.
