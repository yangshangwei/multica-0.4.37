# 多账号多 Agent 跨空间协作业务场景闭环测试

## Goal

用户原话：“请模拟多个账号和agent，根据业务场景做一下完整的跨空间协闭环作测试，给我个测试报告。”

在一套新建的、只归本任务使用的隔离环境里，用多个合成账号和确定性的模拟 Agent 跑通三个业务场景的跨空间协作闭环。环境里的 API、数据库、调度器、CLI 和 Provider 子进程都是真实运行的，只有 Agent 的输出是预设的。三个场景都是 Codex 主线没有覆盖的。另外在同一环境原样复跑 Codex 主线，做独立复现。最后交付一份按业务场景组织的中文测试报告。

## User Decisions（2026-11-09）

- D1 测试方式：补新的业务场景。①外包交付，②客服工单，③异常治理，外加复跑 Codex 主线。只新增测试文件，不改产品代码。
- D2 流程：新建独立 Trellis 任务（本任务），先审计划再执行。不修改 Codex 已归档的 `11-09-collaboration-multi-account-qa` 任务，也不修改它的 3 个测试文件。

  - 主线：产品、研发、测试三个拥有者，单个 Agent，5 次实际执行，补充信息、转交、退回、验收，已结束运行的撤权与重新授权。
  - 补充：同一拥有者的小队、配置切换、共享上下文接续。
  - 它自列的未覆盖项：跨拥有者小队、运行中撤权、离线恢复、Desktop 等。
- 产品语义来源：`apps/docs/content/docs/collaboration.zh.mdx`、`collaboration-knowledge.zh.mdx`。机制核实与代码出处见 `research/scenario-feasibility.md`。

## Requirements

- R1 隔离环境：只有本任务使用的私有目录、新数据库、端口 59765–59767、服务进程和构建产物，写入前核实归属。结束时只停止本任务的进程，保留数据库和日志。不触碰 Codex 环境、`multica-closed-loop-*` 容器和其他会话的环境。
- R2 场景① 外包交付（乙方小队 + 知识沉淀）：
  - 甲方 A 在甲方空间发起 AI 辅助任务，处理人是乙方经理 B。B 把乙方工程师 C（没有任何工作空间的外包账号）加入任务，并转交给 C。
  - B 拥有的乙方小队（Leader 加成员，运行在 B 的运行环境）由 B 提供、处理方采纳，B 逐个资源授权后显式恢复。
  - C 提及小队后，真实依次执行：Leader 派活 → 成员回写 → Leader 续跑总结。
  - C 提交结果，A 退回一次，C 再次驱动小队修改，A 验收完成。
  - C 提出知识候选（目标为甲方空间）。B 无权确认，A 确认。
  - 在知识开关打开的部署下，甲方的二期任务里乙方 Agent 的真实运行收到这条知识。
  - 竞争乙方账号 Y 无法访问任何相关任务。
- R3 场景② 客服工单（手动 → AI 辅助 → 重开返工）：
  - 客服 S 以手动处理方式发起任务给研发 D，附客户日志。D 请求补充信息，S 返回说明，并用评论共享样例文件。
  - 手动模式下 AI 资源操作被拒绝。S 切到 AI 辅助后仍需授权和显式恢复。
  - D 的 Agent 真实运行，收到两份文件且哈希一致。D 提交，S 验收完成。
  - 客户回报复现后，S 重开任务，目标被暂停，需显式恢复后 Agent 才再次执行。D 再次提交，S 再次验收。
- R4 场景③ 异常治理（运行中撤权、移除参与者、取消与重开）：
  - 负责人 L 发起任务，合作方 O1、O2 各自提供 Agent 并授权。
  - O1 的 Agent 真实运行期间，O1 撤回授权：在途工作停止，进程真实终止并留下证明；排队指令保留；O2 不受影响。重新授权后仍需显式恢复，恢复后排队指令真实执行。
  - L 移除 O2：O2 在途运行停止，等待指令被取消，O2 失去访问，只收到不含内容的移除通知。
  - L 取消任务：AI 指令和恢复都被拒绝。L 重开，显式恢复后继续执行，最终由 O1 提交、L 验收完成。
- R5 独立复现：在本任务环境原样运行 HEAD 中 Codex 的 4 个用例（主线 closure，补充 squad、switch、memory-runtime），与 Codex 的结果逐项对照。
- R6 报告：中文 `report.md` 加机器可读 `results.json`，放在 `artifacts/qa/collaboration-business-scenarios-20261109/`。内容包括：
  - 总体结论、环境与源码身份、每个场景的业务叙述和拓扑；
  - 逐步的预期与实际、证据链接、问题清单与复现步骤；
  - 覆盖矩阵（对照 Codex），未覆盖项与证据边界。
- R7 约束：
  - 只新增测试文件（新 spec、本任务 fixture，必要时加本任务专用 Provider），不改产品代码和已有测试。
  - 不使用真实 AI 账号，不对外发消息，凭据不进报告和 Git。
  - 发现缺陷时记录原始证据、继续执行不依赖它的部分，不为全绿修改产品。
  - 首轮失败保留，修正测试后用新的 run ID 重跑。

## Acceptance Criteria

- [ ] AC1 环境：报告写明快照提交、数据库名、端口、进程、二进制哈希和配置（含每批运行时知识开关的状态），并提供“快照与候选提交零漂移”的前后核对，以及测试结束后的端口释放和闸门恢复证据。
- [ ] AC2 场景①：
  - 3 个协作账号、1 个无关账号和 2 个工作空间各有明确 ID；C 的工作空间数为 0。
  - 同一条任务实际观察到小队三段运行（leader、member、continuation），运行环境和资源拥有者都属于 B，指令作者是 C。
  - 一次退回、一次验收，最终 `done`。
  - B 的知识确认被拒绝，A 的确认成功。
  - 二期运行的 `knowledge_observation.contributions` 包含该候选；如果实际不包含，如实记录为发现，不改判为通过。
  - Y 访问被拒绝，且响应里不含任务标题。
- [ ] AC3 场景②：
  - 手动模式下的 AI 资源操作返回 `task_manual`。
  - 切换后在显式恢复之前没有运行。
  - Agent 收到的两个附件哈希与上传内容一致。
  - 首次验收后状态为 `done`；重开后显式恢复前没有新运行；第二次提交并验收后为 `done`。
  - 交付历史里两次提交及其决定都可追溯。
- [ ] AC4 场景③：
  - 撤权回执为 `grant_revoked`，目标 hold 为 `grant_required`。
  - 在途运行最终 `host_exit_observed`，Provider 没有被放行就终止；对应指令为 stopped。
  - 排队指令在显式恢复后真实执行成功；O2 期间正常执行。
  - 移除后 O2 读取任务返回 404、等待指令被取消、在途运行停止，并收到 `removed` 通知。
  - 取消后 `submit_command=false`、恢复被拒绝；重开并恢复后可以继续，最终 `done`。
- [ ] AC5 每个场景都分别断言“Agent 运行成功”和“业务完成”，入队或回执不算执行。每个场景都保留截图、证据 JSON 和 daemon 退出账本，结束时清理无错误，`pageerror` 为空或逐条列出。
- [ ] AC6 复现：Codex 的 4 个用例在本环境的结果（通过、失败、跳过）如实记录，并与 Codex 报告逐项对照；有差异时给出原始证据。
- [ ] AC7 报告：中文，有总体结论、覆盖矩阵、问题列表（区分产品缺陷、测试设施问题和环境问题）、未覆盖项和执行命令。未测项不标为通过，凭据扫描为 0 命中。

## Out of Scope

- 真实或付费模型推理质量，真实支付、客服、外包系统的业务正确性。
- 跨拥有者 AI 小队（一个小队混合不同账号的 Agent）。现有资料无法确认能否构造，列为未覆盖项。
- 真实 Electron/Desktop 窗口、移动端、安装包、跨服务器、多台物理机、操作系统沙箱、离线恢复。
- 性能压测，全站视觉与无障碍审计，修复发现的产品缺陷，部署上线。
