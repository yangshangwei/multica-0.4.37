## Protocol and policy

`pkg/protocol/collaboration_knowledge.go` exports proposal, target, required source, evidence, applicability, approval/decision request, receipt, contribution and exact three-field target hint types. It reuses the existing strict decoder and canonical UUID/version helpers. Unknown, duplicate, case-alias, omitted/null required and cross-kind fields are refused. Budgets distinguish decoded UTF-8 materials from escaped wire bytes; original invalid UTF-8 is rejected before JSON can repair it.

Sources are `memory`, `comment`, or `run_record`, all anchored to one issue. Commit/test evidence is inert text with an exact required source anchor; run-record evidence must also appear in required sources. No external reference is dereferenced. `verification` is an attributed proposer claim, never a server-verified statement. Record IDs are capped at 256 bytes, commit/test references at 2,048 bytes.

Proposal JSON requires explicit nullable expiry/correction/derivation fields. Strict decoding checks UTC timestamp shape without rejecting an elapsed original request; new writes call `ValidateCollaborationKnowledgeProposalAt` with post-lock time **after** original-key recovery. Missing/null reviewed revision/version/hash returns `ErrCollaborationKnowledgeRevisionRequired` for HTTP 428. Shape errors remain `invalid_knowledge_request`.

Receipt actions are `propose|approve|reject|withdraw`. The recommended success codes shared with the Core owner are `knowledge_proposed|knowledge_approved|knowledge_rejected|knowledge_withdrawn`; the future service owns actual emission. Go validates receipt shape but does not interpret an unknown code as success. The existing scope/actor/request namespace remains untouched; cross-kind idempotency and candidate-only actor-owned recovery still belong to batch 2.

`internal/collaboration/knowledge.go` evaluates trusted, current facts with `Principal.Human()` and existing source-read semantics. Proposal/source withdrawal requires current source Read plus creator/current handler; it does not add a participant-row or open-issue requirement. Target confirmation requires membership plus human project lead or workspace owner/admin. Target-only withdrawal remains content-free. Rejection is a reduction of pending state: it requires the same human source Read and target role as approval, but does not require available/unexpired material and never restores hidden body access.
