# 自动初始化专用管理员：技术设计

状态：规划草案，等待最终方案审阅；本文件不代表已实现。

## 1. 目标与边界

在用户已启用密码模式和管理后台的离线部署中，升级脚本自动完成专用账号创建与平台授权。用户在服务器读取初始密码后登录、改密，即可使用后台。

自动入口放在离线升级完成迁移和健康检查之后、报告升级成功之前。提供同一个独立维护脚本，供升级后才开启后台的部署补做初始化。普通 API 重启不创建账号；不接入公共注册接口，不修改原认证方式或注册策略。

产品范围与验收标准以 `prd.md` 为准。相关代码证据见 `research/auth-contracts.md` 和 `research/upgrade-integration.md`。

## 2. 方案选择

| 方案 | 结论 |
| --- | --- |
| 镜像/SQL 种子中放固定用户名和通用密码 | 不采用：部署之间共用凭据，且难以保持既有账号和强制改密边界 |
| 每个 API 进程启动时初始化并保存密码 | 不采用：把部署维护与 API 可用性绑定，多副本的文件归属及宿主交付更复杂 |
| 升级脚本调用部署侧 CLI，先持久化密码文件，再原子创建账号和记录 | 采用：复用现有离线维护边界，独立于开放注册，异常结果可核对且不重置已有密码 |

不把明文或可逆初始密码保存在数据库，也不增加单独的 `prepared` 数据库阶段。事务回滚后遗留的合法文件可以作为同一初始化意图继续使用。

## 3. 对外操作契约

### 3.1 升级与维护脚本

拟新增：

```text
initialize-platform-admin.sh --deployment-dir DIR [--compose-file OVERLAY ...]
```

`offline-upgrade.sh` 在 `/healthz` 成功后自动调用。脚本沿用最终版本的主 Compose、所有有序覆盖文件和已加载镜像。独立执行同一个脚本可安全重试，不需要账号 UUID 或初始密码参数。

有效配置由 Compose 解析，并在 CLI 内再次核对：

| 条件 | 行为 |
| --- | --- |
| 非密码模式，或后台关闭 | 成功跳过；不生成凭据文件、不创建账号 |
| 密码模式且后台开启，部署 UUID 无效/缺失 | 明确失败，沿用现有文档修复配置；不自行生成 UUID |
| 已有管理员或永久初始化记录 | 保留现状，输出不含密码的结果 |
| 符合首次初始化条件 | 创建 `platform_admin`，密码文件默认 `DIR/admin-initial-password.txt` |

`ALLOW_SIGNUP` 不参与部署侧初始化授权，也不被修改。`MULTICA_MANAGED_INSTALLATIONS_ENABLED` 保持现有取值；完整总览的配置要求仍由升级文档说明。

### 3.2 服务端维护命令

拟新增并与现有命令并存：

```text
server platform-admin initialize --credentials-file ABS_PATH --reason TEXT
```

- 固定创建新的 `platform_admin`；不接受角色、用户 UUID 或明文密码参数，不支持覆盖现有账号。
- 复用现有密码配置校验、内部组织/索引检查和数据库连接方式；在监听器及后台工作启动前完成并退出。
- `reason` 沿用 1–1000 字节非空约束。
- stdout 只输出一条有版本号的非秘密 JSON 回执，例如 `status`、`organization_id`、`user_id`、`initialization_id` 和凭据文件路径。错误只包含受控代码，不打印文件内容、密码、数据库连接串或原始请求结构。
- 结果区分 `initialized`、`already_initialized`、`preserved_existing_admin`、`skipped_mode_disabled`、`skipped_admin_disabled`。冲突、文件错误、数据库不可用和不确定结果返回非零退出码。
- 现有 `platform-admin bootstrap --user ...` 保持“指定完整密码账号授权”的契约；不得放宽它对强制改密账号的要求。

## 4. 持久化模型与首次资格

新增 `platform_admin_initialization`，在当前单内部组织模型下作为数据库级的一次性记录，每个内部组织最多一条终态。不能仅用可配置的部署 UUID 作为唯一键；也不能因组织 ID 意外改变而忽略该数据库里已存在的其他初始化记录，出现不同组织/部署的记录应报告身份冲突。拟定字段：

| 字段 | 用途 |
| --- | --- |
| `organization_id` | 永久唯一的初始化范围 |
| `deployment_id` | `created` 状态必填，用于文件与部署的一致性校验；人工授权写入的保留记录可为空 |
| `initialization_id` | 本次意图的随机 UUID，与凭据文件对应 |
| `state` | `created` 或 `preserved_existing_admin` |
| `user_id` | `created` 对应的新账号；保留已有管理员时可为空 |
| `initial_credential_version` | 核对尚待改密的初始凭据；保留状态为空 |
| `created_at` | 审计与诊断时间 |

数据库不保存明文密码、密码的快速摘要或整个凭据文件。密码仅进入现有 `user_password_credential.password_hash`，使用现有密码 KDF。

新增表不加外键或级联操作。组织唯一索引采用单条 `CREATE UNIQUE INDEX CONCURRENTLY` 独立迁移。实施时根据最新仓库分配迁移编号，不能占用并行工作的编号。非空标记的 down 迁移必须拒绝删除；工作空间/账号清理和保留清单不得移除该记录。

“有效超级管理员数量为零”不能作为首次资格：待改密、停用或被临时禁止的管理员都可能不在该数量内。资格在平台全局锁内按以下顺序判断：

1. 已有终态记录：不得再次创建或恢复权限。
2. 已有任何平台角色（包括只读观察者）或历史成功超级管理员授予记录：写入 `preserved_existing_admin` 终态并保留账号；不产生新凭据。保留已有平台角色是对“已有管理员保持不变”的保守落实，不能把观察者配置误认成一套从未管理过的部署。成功记录的具体查询条件使用 `research/auth-contracts.md` 中的全库谓词，覆盖 bootstrap 操作和 before/after 含 `super_admin` 的 applied 审计，排除失败尝试，不通过当前 user/credential JOIN 过滤掉历史。
3. `platform_admin` 已被普通账号占用：返回 `username_conflict`，不提权、不改密、不改名。
4. 否则才允许创建专用账号。

未来人工 bootstrap 或超级管理员授予路径在同一事务内补写“已有初始化”标记，避免角色随后被撤销、账号被删除或审计保留策略变化后重新触发自动初始化。旧部署的既有角色/成功审计按上面的首次检查处理，不把已有账号转为待改密。

现有人工 bootstrap 只要求密码模式，不要求后台开关或部署 UUID；补写保留标记不能给它增加这些前置条件。人工路径可以写 `deployment_id=NULL` 的 `preserved_existing_admin` 记录，无凭据文件可复用。自动创建路径仍必须有有效且一致的部署 UUID，`created` 行由数据库 CHECK 约束必填字段。

旧部署若曾人工删除全部平台角色及成功授予历史，现有数据无法区分“从未初始化”和“初始化证据已被清除”。自动流程不承诺恢复被销毁的历史；这类已知异常数据库应先人工核查并保留初始化状态，再接入自动升级。此限制不影响保留正常角色、审计或新永久记录的部署。

## 5. 文件与事务顺序

### 5.1 凭据文件

- 使用 `crypto/rand` 生成至少 24 字节随机数，再编码为符合现有密码规则的 32 字符初始密码；不用环境变量、用户名或时间推导密码。
- 文件格式为可直接阅读的有版本 JSON，扩展名按产品约定保留 `.txt`。内容包括用户名、初始密码、部署 UUID、组织 UUID、初始化意图 UUID 和生成时间；不宣称尚未提交的账号已可登录。
- 目录必须是明确指定、受信任的业务部署目录。新文件权限 `0600`，归启动维护脚本的操作系统用户所有；只允许常规文件，拒绝符号链接、未知内容、错误归属或不安全权限，不替换已有文件来“修复”冲突。
- 文件先在同目录以独占临时文件写入并同步，再以不可覆盖的原子发布方式放到最终路径，同步父目录。实现必须验证所用文件系统支持所选发布方式；失败发生在数据库账号提交之前。
- 复用已有合法意图文件时也必须重新同步该文件和父目录，成功后才能提交账号；文件存在不代表此前的父目录同步已成功。同步失败仍须中止数据库提交，并保留文件供同一意图重试。
- 临时文件名采用明确前缀，只清理本命令创建且可确认归属的临时文件。最终凭据文件不能放进通用失败清理 trap。

### 5.2 创建事务

部署 CLI 是文件与数据库的协调者，拥有事务的提交/回滚责任；service 使用类似现有 `RecoverPasswordForDeploymentInTx` 的借用事务接口，处理锁、资格和数据库写入，不接收明文密码或负责文件 I/O。CLI 在锁内完成资格检查、文件持久化、借用事务写入的顺序，不通过“先提交账号再写文件”拼接两个结果。

1. 在事务外准备随机密码或读取、校验同一意图的合法现存文件，并计算现有 KDF 哈希。
2. 开启事务并调用现有 `LockPlatformAdminMutation`；对既有账号操作保持“平台 advisory lock → 按 UUID 排序的用户锁”的顺序。
3. 锁内重新检查初始化记录、既有管理员/历史、用户名冲突、组织状态、部署标识，以及事务外读取的文件/凭据快照。快照变化时回滚后重新准备，不能在不确定提交后盲目重试。
4. 首次创建时，确认初始密码文件已按 5.1 节持久保存；此时文件可以先于数据库账号存在。
5. 同一事务写入新 `user`、`must_change_password=true` 的密码凭据、`super_admin` 角色、初始化记录、部署操作者的 `admin_operation` 和 `admin_audit_event`。
6. 提交后才报告 `initialized`。该专用路径允许暂时没有“已完成改密的有效管理员”；不能据此改变普通管理写的最后管理员保护。

正常初始化不需要临时开放注册，也不签发人类登录凭据。账号只能通过真实用户名/密码登录。

### 5.3 重试与并发

| 可观察状态 | 处理 |
| --- | --- |
| 没有标记、文件不存在 | 准备新的意图；锁内仍需重新检查资格 |
| 没有标记、同一部署的合法待提交文件存在 | 复用原密码/意图并重新执行事务，不生成另一密码 |
| `created` 标记，账号仍处初始改密阶段，文件与版本/密码哈希吻合 | 返回已初始化，复用原文件；不更新密码或角色 |
| `created` 标记，账号已改密、停用、恢复过密码、删除或角色已变更 | 返回已初始化/维护提示，不复活初始权限；旧文件不再被宣称为当前密码 |
| 待改密账号已提交，但对应文件缺失、损坏或不匹配 | 显式恢复错误，走已有部署维护流程；不自动重置密码 |
| 同名普通账号、未知文件、不同部署/意图 | 明确冲突；不覆盖任何一方 |
| 提交结果不确定 | 重新连接，在同一平台锁下按组织/意图查终态；核对后返回结果，无法确认则报告未确认并保留文件 |
| 同一数据库、不同维护主机并发 | 只有一个创建者；若另一主机看见已提交的待改密账号但没有匹配的本地凭据文件，返回非成功的 `credentials_unavailable`，与文件被外部删除的场景一致；不声称密码已交付，不生成新密码 |

永久标记独立于账号可用性和初始文件。用户改密后可删除失效的初始密码文件；删除文件、停用账号或再次升级都不会触发重新创建。外部误删尚未使用的密码文件和恢复旧数据库属于明确的运维恢复边界。

不依靠不可信的宿主路径猜测“密码在另一台机器上”，标记也不存储可自动回取的秘密地址。`credentials_unavailable` 回执只给出非秘密意图/账号标识，提示部署维护者核对原初始化主机上的文件；若确已丢失才走显式恢复。数据库初始化已完成与本次密码可交付是两种状态，不能合并为同一个成功结果。

## 6. Docker 与升级脚本接入

- `initialize-platform-admin.sh` 复用现有 Compose 解析和镜像选择模式，解析实际服务配置后才决定跳过或调用。
- 为一次性维护容器生成临时的结构化 Compose 覆盖文件：只为该次调用增加业务部署目录的挂载和维护者 UID/GID；正确转义 Compose 的 `$`，保留路径中的空格、引号、逗号和冒号。拒绝覆盖文件在保留目标路径设置的冲突挂载。
- 使用同一后端服务的网络/数据库配置以及选中的镜像，运行 `/app/server platform-admin initialize`；设置 `--no-deps`、`--pull never`、`--rm`、`-T`，不启用 `--service-ports`，不走镜像默认迁移入口。
- 用已加载前端镜像中的 Node 生成/校验非秘密覆盖 JSON；不要求目标机安装 Node/Go，不把已有含秘密的 Compose JSON 原样写入日志或临时文件。
- 凭据文件由维护容器直接写入宿主部署目录，API 常驻容器不新增凭据挂载；不存在 stdout 导出秘密后再落盘的窗口。
- 初始化失败时升级脚本报告“服务已升级、管理员初始化未完成”，保留原有备份和新镜像状态，不报告整次升级成功、不回滚数据库或重设密码。重试独立维护脚本即可，无需重新导入镜像。
- `.gitignore`、`.dockerignore`、打包检查排除初始密码和私有暂存文件。原始包只包含代码、脚本与说明，不包含任何实例生成的账号记录或凭据。

## 7. 强制改密与客户端

复用现有 `must_change_password`、受限 `change` JWT、`/api/me/password/change`、会话版本提升和凭据撤销流程。改密前继续拒绝业务、后台、PAT/CLI token、任务/守护进程等凭据绕过路径，不把受限账号算作有效管理员。

现有改密处理还需补齐：强制改密期间，服务端拒绝与当前密码完全相同的新密码。该检查必须与当前凭据及 `must_change_password` 状态的事务复核一致；普通非强制改密行为保持原契约。采用明确错误码并在共享密码表单的错误映射中提供中英文提示，不为本功能新建登录页。

首次改密成功后返回当前账号的新正常会话，初始密码和此前受限会话均失效，`/admin` 目标导航继续保留。验证 Web/桌面共用密码流程，不扩展到独立移动端功能。

## 8. 验证与交付

详细顺序与案例见 `implement.md`。核心证明是：一次创建、持久可取的独立密码、严格改密门禁、成功改密后可用的管理员、重复/失败/并发不改既有凭据，以及包内不存在明文秘密。

文档同步：升级指南及其两份包内副本、桌面交付清单、平台管理中英文说明、生成的内置文档、`.env.example` 的管理开关说明和离线交付/认证规范。人工 bootstrap 保留为已有完整账号的显式维护工具。

当前共享工作区存在其他任务的未提交修改，包括迭代/分拣和新迁移；实施前重新核对文件归属和迁移序号，仅提交本任务的变化。此规划不启动真实升级、不修改当前已登录的本机管理员。
