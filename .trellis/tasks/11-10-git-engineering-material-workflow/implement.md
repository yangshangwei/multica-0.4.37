# 实施与验证顺序草案

日期：2026-11-26 更新。状态：planning；这是可供审阅的草案，不是实施授权。保留完整产品/设计/研发/测试愿景，候选首期链路为“探索工程 → PRD 自动送审 → 产品审核 → 系统受控自动合并 → 按项目开关启动方案阶段或进入待办”，实际首期边界仍待定案。产品版本管理、目录按需生成和运行时接入为本轮补充，具体合同见 [版本与接入建议](research/product-release-workflow.md)。

## 1. 固定数据与权限合同

覆盖 R3/R8/R9/R12/R16/R17/R18/R19/R20/R21、PAC1/PAC4/PAC6/PAC7/PAC12/PAC13/PAC14/PAC15/PAC16/PAC17/PAC18/PAC19。

- 版本合同定案后定义产品版本身份、物料修订和范围引用；正式范围以获批 Git 为准，数据库保存候选和工作流事实。新物料与范围引用同一评审生效，合并回执记录实际修订，避免文件自引用尚未生成的 SHA。
- 明确 issue 发现/影响/计划修复/验证结果的各自来源；延期只改关联，冻结发布基线保留实际交付。发布后新问题不修改旧范围；各维护版本复测分别记录。

- 从既有项目资源扩展明确的输入工程与输出物料配置；验证工作空间、项目、仓库及当前操作者权限。
- 定义稳定物料身份、候选修订、Git 基线关联与提交意图；保留业务事项/Agent run 现有身份。
- 按 D10/PAC15 验证完成、关闭、重开与归档不移动物料或产生纯状态 Git 提交，归档仍可搜索和追溯；物料合并不代替需求验收，修复产出不代替复测通过。具体状态转换与归档行为在映射和权限定案后实现，不默认添加自动归档。
- 若目录方案纳入本期，按稳定物料身份实现跨工作空间的授权关联，编号不能仅使用空间内显示号；从类型模板生成允许路径，校验 ID、元数据、引用与版本，索引从已核对 Git 内容重建。业务状态变化不搬文件，普通需求不能修改 Agent 指南/schema 等规则文件；路径配置不充当访问授权。QA 入库/执行在其角色与门槛确定后独立验证。
- 系统拓扑定案后，复用项目多仓资源，区分逻辑系统/模块 ID、Multica 工作空间/项目 ID、代码仓 ID 与权限。验证一条需求只保留一份正式 PRD、多个模块任务共享其固定版本、同一模块阶段不会被多个项目重复派发；覆盖模块开关关闭、仓库访问撤销、部分代码仓合并及联调失败，不能把目录中的 URL 或跨项目关系直接视为执行授权。
- 在项目设置持久化自动启动配置，默认开启且保留显式关闭，不设需求级覆盖。核实创建/指派自动派发与已有执行控制：关闭路径在 `todo` 中保留待办并等待明确手动启动，不能借用 `backlog` 改变用户要求的状态，也不能只靠前端或一次性的“不启动”参数保证后续恢复不派发。
- 若研发交接纳入首期，按 design.md 第 2 节固定需求版本、验收条件与工程来源引用，给后续阶段保留上游依赖关系；按固定引用加载并校验完整 PRD，以正文或可读的只读文件连同来源信息交付。交接引用现有权威内容，不复制另一份正式需求，不实现通用工作流引擎。
- 定案草稿何时持久化、如何接收 Observer 分析结果、由谁拥有发布权限；禁止借用宽权限绕开角色合同。
- 拟改范围：服务端项目资源、物料服务/查询/迁移；共享 core 的类型、API/schema。复用点以研究文件为起点，最终文件清单在实施前复核。
- 验证：跨工作空间、过期修订、目标配置变化、重命名稳定身份、恢复不重复建任务；拒绝分析结果覆盖目标仓/路径或附带执行命令。数据库清理遵循项目隔离规则。
- 若研发交接纳入首期，使用不派发真实 Agent 的消费样例验证固定基线可读取、交付正文与 Git 内容一致、大文档全文可读取、来源链接固定版本、验收条件可追溯、重复通知不产生新基线；未获批、版本或摘要不匹配、读取失败或无权访问时不就绪。该验证不能代替后续自动开发的产品验收。

## 2. 实现可恢复的 Git 提交

覆盖 R8/R10/R19/R21、PAC2/PAC4/PAC16/PAC19。

- 候选执行方式为复用已授权运行时，Multica 持久化可信仓库/路径/版本/修订和操作意图；具体适配经验证后选定。分别检查读取、推送、PR/MR 管理、门禁读取和合并，不以 clone 或 Agent 完成证明全链路能力。
- 初始化使用独立维护授权，普通需求发布不可改写模板/schema/Agent 规则。覆盖兼容已有内容、空仓、部分初始化与重试；默认测试不读取用户凭据，不隐式创建远端探测分支。

- 面向 GitLab/GitHub 定义本流程需要的窄操作合同，复用现有读取和鉴权能力，不重构当前 VCS/GitHub 两条路径。建议先完成 GitLab 的完整闭环，再用同一行为矩阵适配 GitHub；顺序与首期范围待确认，不增加其他平台。
- 持久化发布意图，再写允许路径、提交分支、推送、创建/更新关联 PR/MR；回填真实结果。
- 增加查询恢复、重试去重、人工并发冲突与权限撤销处理。
- 拟改范围：服务端受控发布/持久化层，必要的 provider 和 daemon 明确操作；不依赖 Agent 退出收尾证明发布成功。
- 验证：push 成功后断网、MR/PR 创建成功但回执丢失、重复执行、目标分支变化、非文档路径/链接逃逸；只读凭据不得被当成写入授权。自建 GitLab 验证实际 API/执行器连通与信任配置，各平台分别验证审批对版本的适用性；无需真实 Git 凭据的测试先通过。

## 3. 接上自动触发与评审事实

覆盖 R7/R10/R11/R14/R15/R16/R17、PAC2/PAC3/PAC5/PAC9/PAC10/PAC11/PAC12/PAC13/PAC14。

- 将冻结的可评审修订转为一次发布意图，持续讨论不逐条触发；结构检查与内容判断分开。
- 有效产品批准创建一次持久化合并意图；合并执行器核对当前批准、完整 PR/MR 变更、预期 HEAD、目标仓/分支/允许路径及系统合并权限与原生门禁。条件满足后调用带版本条件的合并能力；等待检查或队列时恢复原意图，变化或撤回后不沿用旧批准。系统同步本身不能凭空创建批准或合并授权。
- 记录实际系统合并身份、真实产品审核人、时间和结果提交；远端合并事实及获批内容核对通过后更新物料基线。请求接受、入队或超时不算成功，重试先读事实，已合并则回填，不重复创建操作。
- 实现 Multica 人类审核决定的版本绑定、项目权限检查、重复意图恢复与远端回执关联；按 D6 使用系统集成身份同步审核摘要和原始记录引用，不要求审核人绑定 Git 账号，不以机器人 review 冒充人类批准。
- 物料 PR 不能通过普通 closing intent 误关闭开发事项；通知丢失可由后台对账恢复。
- 同步更新相关角色/技能/注入说明与源码映射，保持 Observer 边界一致。
- 若 D8 纳入本期，基线核对后创建或恢复同一方案阶段任务；按项目开关建立启动意图或保留待办。自动与手动启动共用基线读取、执行授权与去重检查；关闭时创建、预分派、恢复和领取均不得自动运行。现有需求预研角色禁止创建实现任务，方案与任务拆解的角色合同需单独核对，不能直接假定该角色已支持此阶段。
- 为方案产出记录所用 PRD 版本及待审核状态；当前方案未经审核不得触发编码。验证 PAC12–PAC14：默认值、显式关闭持久化、项目隔离、待办手动启动、重复通知/点击、创建与派发间中断、回执丢失及输入变化。真实 Agent 验证与默认测试分开。
- 验证：阻塞问题不提交、旧草稿/旧审批不生效、合并内容与批准内容对应、文档基线更新不自动派发实现；无 Git 账号的有权人类可审核、无项目审核权限时拒绝、机器身份/自报审核人拒绝、系统署名与回链、审核时内容变化、重复批准、退回后修订、远端写回失败与原生门禁未满足。当前产品批准且条件满足时系统自动合并，无额外人工按钮；合并权限不足、冲突、HEAD 改变、夹带越权文件、批准撤回时不执行。检查/队列等待、合并成功但响应丢失及通知重投可恢复；未经当前版本审核的外部合并不更新正式获批基线。

## 4. 接入 Multica 交互与插件

覆盖 R7/R8/R10/R12/R14/R15/R16/R17/R19/R20/R21、PAC1/PAC2/PAC4/PAC6/PAC9/PAC10/PAC11/PAC12/PAC13/PAC14/PAC16/PAC17/PAC18/PAC19。

- 用插件呈现需求正文、来源、修订差异、发布阶段和恢复入口，宿主提供必要的窄 API 与可靠记录。
- 若版本管理纳入首期，提供明确的版本选择与需求/问题入口，显示候选与正式范围、发现/影响/计划修复/已验证修复关系；已有未关联物料不得自动归入最新版本。已发布版本允许后续报告问题，界面不得因此改写旧交付基线。
- 接入界面在已有默认环境时允许从仓库地址开始，缺失环境或权限则显示具体能力与未验证状态；目录由系统按实际操作创建，不要求人手工预建模板和空文件。
- 实现 Multica 内完整阅读、差异、评论、批准与退回，以及可追溯的业务审批同步状态；不设置个人 Git 账号绑定前置步骤。批准前明确其将触发系统合并当前需求版本；分别展示业务审核、原生门禁、正在合并/等待/受阻与实际合并结果，无需另一个人工提交合并步骤。
- 增加项目自动启动开关及说明；展示方案任务的待办、排队、运行和待审核状态。关闭后可从原待办手动启动，不要求打开整个项目开关；配置使用服务器权威状态，失败不得把未保存的值当作已生效。
- 插件通过 SDK/窄 API 工作，不依赖宿主内部包；宿主新增的共享客户端逻辑和业务组件遵循 core/views 边界。检查 web/desktop，移动端范围另行确认。
- 验证：来源缺失、加载失败、权限丢失、草稿过期、半成功提交、返回刷新与长文档；API 异常响应按 schema 契约降级。

## 5. 集成检查与试点

- PAC16–PAC19 按新增研究的验证清单执行：两个产品版本并行送审、错版本/过期排期、冻结、延期、多维护版本修复、发布后新增问题、历史基线固定、初始化和能力缺失。目录与运行时方案定案前仅保留候选测试要求，不创建真实接入资源。
- 针对以上行为先形成必要的失败用例，再实现；不新增仅镜像实现的测试。
- 后端使用隔离测试数据库和实际鉴权入口，普通测试不得访问真实 Agent/Git 账号。
- 测试代码自行构造物料项目、模块项目及仓库资源，使用 fake provider 或临时本地 Git 仓检验版本/目录行为；覆盖尚未配置运行时绑定的状态。后续真实平台集成验收单独准备授权测试环境，不阻塞前期功能实现，也不声称离线测试证明了真实接入。
- 依据实际改动运行定向 Go/Vitest 检查，再按仓库要求执行 `pnpm lint`、`pnpm typecheck`、`pnpm test`、`make test` 及适用静态分析；命令与环境以实施时的 Makefile/package.json/spec 为准。
- 关键用户路径使用生产构建的 Web 和 Desktop 做验证；不能用模拟 provider 结果宣称真实集成已经通过。
- 在授权测试仓完成完整链路及一次需求修改，留下原始提交、PR/MR、审批、最终内容和恢复证据。
- 比较产品人员澄清、审阅、返工时间与验收质量，记录失败与人工接管；阈值由试点规划确定。

## 依赖与回退

步骤 1 → 2 → 3 为主链；步骤 4 在数据/接口冻结后可与服务端独立推进，最后统一执行步骤 5。暂不新建子任务，待范围定案后再按独立验收边界拆分，避免把未决草案当作执行计划。

回退先停新发布与新合并执行，保留历史基线、候选文档、远端分支/PR 与操作回执，继续核对已在途的合并；不删除用户已经审阅的记录，不回写覆盖 Git 正式内容。任何部分失败都应能够解释哪些副作用已经发生，以及如何核对恢复。
