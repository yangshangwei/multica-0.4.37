## 2. 一个业务系统一个逻辑物料根，模块保留独立项目与代码仓

用户语境中的项目是模块，物料边界应上提到业务系统。建议同一协作与保密范围内，一个业务系统共用一个物料仓；既有模块项目和多个代码仓保持各自职责，一条业务需求只在系统物料根中定义一次。不同工作空间按授权关联同一份物料，不按部门、项目或代码 Git 地址复制 PRD。

| 概念 | 建议含义 |
| --- | --- |
| 业务系统 | 产品需求、模块间契约与联调验收的整体边界，例如交易系统；这是领域概念，不声称当前已有同名 Multica 实体 |
| Multica 项目 | 现有模块的任务、Agent/小队、执行资源和 D8 配置，例如订单、支付、门户 |
| 模块代码仓 | 一个模块可关联一个或多个代码仓；共享库也可被多个模块引用，不能用 Git URL 数量推断项目数量 |
| 系统物料仓 | 全局需求、测试问题、总体方案、模块方案引用与联调依据 |

按 D9，未来产品/测试使用的物料仓本身就是系统物料根，其普通 Multica 项目兼任协调入口，不另外建立协调仓库。以下是待实现的目录约定：运行时可初始化空仓，或对已含内容的仓库做兼容读取；并不假定当前已经存在某个目录供扫描。多系统共仓时可评审 `systems/<stable-system-id>/`，目录不改变 Git 的读取边界。原先的“一项目一物料仓”建议不适用于模块型项目划分。

```text
system-materials/                   # 一个业务系统的逻辑物料根
├── README.md                       # 给人的目录说明、使用方法
├── AGENTS.md                       # 给 Agent 的短入口和读取规则
├── material.yaml                   # 格式版本、稳定系统 ID、目录约定
├── .material/
│   ├── schemas/                    # 元数据、引用和各物料类型的校验规则
│   └── templates/                  # PRD、问题报告、方案、测试计划模板
├── modules/
│   ├── order/
│   │   └── module.yaml             # 模块职责、逻辑代码仓标识与依赖
│   ├── payment/
│   │   └── module.yaml
│   └── portal/
│       └── module.yaml
├── requirements/
│   └── REQ-0042/
│       ├── prd.md                  # 唯一正式需求定义，首次入库的必需文档
│       ├── design.md               # 跨模块总体方案、接口和数据流
│       ├── plan.md                 # 模块分工、依赖和总体验收映射
│       ├── test-plan.md            # 系统联调场景与预期结果
│       └── modules/                # 有需要时添加模块细化，不复制 PRD
│           ├── order/plan.md
│           └── payment/plan.md
├── issues/
│   └── ISS-0186/
│       ├── issue.md                # 现象、复现、预期/实际、被测版本及证据
│       └── resolution.md           # 可选：核实后的根因、修复与回归证据引用
├── contracts/                      # 跨模块交互契约，或指向既有契约源的引用
├── specs/                          # 跨需求适用的领域规则与长期工程契约
├── decisions/                      # 重要取舍、替代项和适用范围
└── knowledge/                      # 已核实的复盘、操作方法与可复用知识
```

目录按需建立，初期只需入口、模板/规则、`requirements/` 和 `issues/`。不预先生成空方案、空测试计划或大批占位文档。独立图片、录屏、详细日志和构建制品放制品/附件存储，物料保存稳定版本的引用与必要摘要；少量适合 Git 的文本样例可以放在对应物料目录。

需求关联的方案、计划与测试计划放在同一个目录，接手 Agent 可局部读取。测试问题独立建档，因为一个问题可能影响多条需求，也可能来自旧功能或环境，不能强制塞进某条新需求目录。`issues/` 表示问题定义文件，不是 GitLab/GitHub 原生 Issues 数据库的文件副本。

`modules/<id>/module.yaml` 是长期模块目录，不是该模块的需求清单；`requirements/<id>/modules/<module-id>/` 则保存这一次需求的模块细化。若 OpenAPI、protobuf 或事件 schema 已以代码仓为权威源，`contracts/` 保留其固定版本引用，不再复制一份可独立修改的正式契约。

### 模块、项目与多个 Git 地址的映射

下面以订单模块为例展示目录内容草案，逻辑标识由系统物料统一维护，真实 URL、项目与资源绑定在接入时显式配置：

```yaml
module_id: order
name: 订单模块
repositories:
  - repository_id: order-service
    purpose: backend
  - repository_id: order-contracts
    purpose: api-contracts
dependencies: [payment]
```

Multica 配置将 `order` 绑定到明确的工作空间/模块项目及相应项目资源，将逻辑仓库 ID 绑定到具体托管实例、仓库和权限。模块目录的变更可提出绑定建议，但不能仅靠 Git 文件中的 URL 自动新增访问或写入授权。现有 [项目资源类型](../../../../packages/core/types/project.ts#L97) 和 [项目资源进入任务上下文](../../../../server/internal/handler/project_resource.go#L945) 已有多仓基础；系统/模块语义、物料绑定和跨项目编排仍需实现，不能将多仓资源等同于完整闭环已存在。

### 跨模块需求与项目开关（D9 归属已确定，编排待评审）

按 D9，功能使用时产品/测试物料仓对应的普通项目就是系统需求入口，统一形成总体方案并承接整体验收，再把带稳定物料引用的模块任务关联到订单、支付等项目。名称可为“系统需求与测试”，并非新增项目类型；这个项目与模块项目承担不同工作，无需再加一层独立的协调项目。创建/选择项目、填写仓库地址和配置访问属于未来的使用步骤；当前开发通过隔离测试数据验证这些行为，不要求用户事先准备真实资源。

产品在该项目提出完整需求和审核 PRD，测试在此记录系统问题与验收结果；研发在原模块项目处理关联任务。共享 Git 保存正式内容，项目保存讨论、分派、状态与运行。配置关系本身不复制需求、移动代码仓或自动实现跨项目编排，也不将共享 Git 的读取权限等同于所有工作空间项目权限。

D8 仍按项目配置。候选规则是：协调项目的开关控制总体方案阶段，各模块项目的开关控制归属于该项目的方案细化/任务拆解；关闭的模块任务进入待办，不由协调者绕过开关派发。独立模块可先推进方案，有依赖的任务保留等待，全部必要模块和系统验收未满足前不报告整体交付完成。涉及两个层级的阶段归属和开关判定尚待评审，不能据此改写已确认的 D8 为全局开关；编码仍需通过对应方案审核。

同一需求在多个项目中保留可追溯的关联任务，不复制正式 PRD；同一“需求版本 + 模块 + 阶段”只允许一个有效派发归属。跨工作空间关联必须走授权与交接合同，不能用未经验证的跨空间父子关系替代访问控制。

### 多仓版本与系统验收

每次运行和联调记录一份输入/被测版本清单：物料仓 commit、涉及模块、各代码仓完整 SHA、实际构建/镜像标识和环境。多个仓库没有共享的 Git 提交号，也不具备原子合并；已合并的模块、未合并的模块、契约兼容性和部署顺序分别跟踪。必要模块的代码结果与当前版本组合的联调证据齐备，才判断需求交付完成。

版本清单保存在权威运行/测试记录中，Git 可保存某次验收的不可变引用或证据索引，不维护每次部署都改写的全局“当前版本”。Agent 按任务读取所需模块的已授权仓库和相关契约，不要求所有 Agent 每次克隆全部 Git 地址。

## 3. 稳定 ID、结构化元数据与版本

建议“Markdown 正文 + 小型 YAML frontmatter”，一个物料只有一份元数据，不再维护同义 `metadata.json` 或中央登记表。以下字段是协议草案，名称和 schema 尚未实施。

```yaml
---
schema_version: 1
id: REQ-0042
type: requirement
title: 支持订单退款
affected_modules: [order, payment]
---
```

```yaml
---
schema_version: 1
id: ISS-0186
type: issue
category: bug
title: 退款成功后订单仍显示已支付
affected_modules: [order, payment]
requirement_refs:
  - id: REQ-0042
    material_commit: <物料仓的完整提交 SHA>
    acceptance_ids: [AC-03]
tested_repositories:
  - repository_id: order-service
    commit: <订单服务被测代码的完整提交 SHA>
  - repository_id: payment-service
    commit: <支付服务被测代码的完整提交 SHA>
build_ref: <可追溯的测试构建或制品版本>
---
```

- 示例 `REQ-0042` / `ISS-0186` 由物料系统在同一物料根中唯一分配，不能由 Agent 扫描最大数字后自行加一。并发创建使用唯一分配及重复校验；目录名中的稳定 ID 不随标题改变。
- 规范物料身份是“托管实例与仓库稳定 ID + 稳定系统/根标识 + 物料 ID”。Multica 的工作空间/模块项目/事项是这份物料的本地关联，不是另一份物料定义。[现有事项编号按工作空间分配](../../../../server/internal/service/issue.go#L499)，不能只用界面编号把跨空间事项当成全局同一对象。
- 任务拆解的 `plan.md` 保存任务 ID、目标、依赖和验收条件；执行状态、负责人、重试和运行记录留在 Multica。任务规模增长到需要独立评审时，再把具体定义拆为 `tasks/<task-id>.md`，保留原身份。
- `category: bug` 是问题类型，不是当前执行状态。未经确认的问题可以保留其他分类或待分类事实，不把每个测试反馈直接当作已确认软件缺陷；关联需求可为零到多条。
- `affected_modules` 表达需求影响或观察到的问题范围，不自动认定根因/修复负责人。测试无法判断模块时先留待分流，确认归属后再关联相应项目任务，不为每个可能模块复制一个缺陷。跨模块问题保留一份现场与版本组合。
- Git 中不维护 `status: in_progress`、`assignee`、Agent 会话或随每次执行变化的计数。正式批准来自真实审核记录与合并核对，文件自报 `approved: true` 不构成批准。
- 当前文件版本由外部读取清单记录仓库、完整 commit、路径和内容摘要；不要在文件中填写“本次提交自身 SHA”，避免循环引用。问题对需求/代码的引用使用已经存在的具体版本。
- 一份旧版本问题报告继续保留首次报告依据；修复结果与复测另关联被测新版本。不能把所有引用自动改为最新分支，以免丢失“当时测的是什么”。

## 4. 模板的最低内容

| 物料 | 必要正文 |
| --- | --- |
| `prd.md` | 用户与问题、目标、范围、不做什么、主要流程、边界条件、带稳定 ID 的验收条件、工程依据和未决事项 |
| `issue.md` | 问题分类、影响范围、复现前置条件与步骤、预期/实际、被测环境与代码/构建版本、原始证据、关联需求与验收项（如有） |
| `design.md` | 采用的需求版本、边界、数据流、方案取舍、兼容与回退、待审核事项 |
| `plan.md` | 采用的需求/方案版本、稳定任务 ID、任务目标、依赖、所覆盖验收项和验证方法；不作为实时看板 |
| `test-plan.md` | 验收项到测试场景的映射、输入、独立预期、环境需求与证据收集方式 |
| `resolution.md` | 已核实的根因、代码变更引用、回归用例及实际复测证据；待验证项必须标明 |

测试人员提交的现场描述应原样保留可追溯版本。AI 可以补充结构、分析与建议，不能把未实际执行的复现、推测的根因或口头“已修复”改写成已验证事实。

### 完成、修复与归档（D10 已确认）

用户在本轮说明后确认接受当前设计：Git 中的 `requirements/<id>/` 与 `issues/<id>/` 保持固定路径，完成、修复、关闭、重新打开或归档均不搬文件，不建立 `requirements/done/`、`issues/fixed/` 或业务 `archive/` 目录。Git 保存定义、修订与证据引用，单看目录名无法判断当前进度，实时状态以 Multica 为准。

Multica 分别表达以下业务维度。表中是产品阶段语义，不直接声明新的 API/数据库枚举；与现有任务状态的映射和具体转换权限在实现设计中确定。

| 维度 | 业务阶段与规则 |
| --- | --- |
| 物料审核 | 草稿 → 待审核 → 已批准并合并；修改产生新的待审版本，保留旧基线 |
| 需求交付 | 待规划 → 方案审核 → 开发中 → 待验收 → 已完成；整体完成须有对应版本的验收证据 |
| 问题处理 | 待确认 → 待修复 → 修复中 → 待复测 → 已关闭；复测失败可重新打开，保留处理历史 |
| 归档 | 独立于上述状态，从日常列表收起但仍可搜索、查看关联和追溯证据；不替代完成或关闭 |

问题修复后可在同一目录的 `resolution.md` 中补充已核实根因、修复代码版本与实际复测证据，原 `issue.md` 保留最初报告及被测版本。纯状态与归档操作不生成 Git 提交，正式证据内容更新仍按物料修订规则处理。完成/关闭是否自动归档、归档权限和触发时机尚未决定；D10 不改变 QA 入库审核、分流及修复启动尚待确认的边界。

## 5. 谁管理目录

1. **系统接入时配置。** 有权限的管理者绑定系统物料仓/根、模块到 Multica 项目和各代码仓的关系、发布身份与审核规则。Git 中的 `material.yaml` 只描述内容格式/系统身份，模块目录描述工程关系；连接凭据、权限与 D8 自动启动开关仍以 Multica 项目配置为准。
2. **产品与测试只操作业务表单。** 产品提交需求、测试提交问题；系统分配物料 ID、从模板生成候选文件并创建/更新对应分支和 PR/MR。日常讨论和不完整草稿留在 Multica，送审条件按物料类型定义。
3. **受控发布器管理路径。** Agent 提出内容，宿主根据可信项目配置构造允许写入的路径，不执行正文中的目录/权限指令。人工也可通过受审查的 Git 变更编辑，必须经过相同格式、版本和身份检查。
4. **按物料类型决定审核与生效。** 需求按 D7 在产品批准当前版本后受控自动合并。测试问题的入库审核/分流角色与修复启动条件尚待规划；不能因为已有需求自动合并规则，就推定测试问题可直接派发修复或关闭缺陷。
5. **同一物料串行提交，并发物料各自变更。** 发布/重试保留意图与预期版本；人工并发修改产生明确冲突，不覆盖文件或重建另一份同名物料。Git PR/MR 成功只是阶段事实，合并内容核对后才更新正式版本。
6. **Multica 生成目录索引和关联。** 读取 frontmatter 建立可重建的查询索引，按稳定身份定位需求、问题和关联；Webhook 加速更新，对账恢复漏事件。索引不是第二份可独立编辑的正式正文；无需所有提交都修改同一个 `index.json`/`INDEX.md`。
7. **状态变化不搬文件。** 待办、进行中、已关闭、归档显示留在 Multica，不把文件在 `todo/doing/done` 之间移动。标题修改不重命名 ID 目录，内容更新通过 Git 历史表达，不增加 `prd-v2-final.md`。废弃或重复物料保留来源与替代/重复关系；删除和目录迁移需显式审查，不借业务归档删除证据。
8. **规则与知识单独治理。** `AGENTS.md`、schema、模板和流程规范的变更需要工程维护者评审，不能沿用普通需求发布路径自动修改。知识与 skill 候选需核实、审核后发布；不是把全部对话复制成 Agent 指令，也不因目录中出现 `SKILL.md` 就自动加载执行。

目录不是 Git 的读取权限隔离。能直接读取整个 Git 仓库的账号通常也能读取其中其他模块目录；保密范围不同应分仓，并用显式授权的固定版本引用连接系统需求。多个工作空间共同绑定物料时，服务端仍需检查根与引用的访问权限，并为同一物料阶段确定唯一的派发归属，防止多个空间各启动一次 Agent。具体跨空间绑定与阶段归属是后续接口设计的一部分。

## 6. 最低校验与验收建议

物料 PR/MR 校验建议覆盖：

- 必需字段、类型与格式版本；ID 唯一且与路径一致；不以标题判断同一物料。
- 允许目录/文件类型；拒绝路径越界、符号链接逃逸及未获授权的规则文件改写。
- 必需章节与验收项 ID；引用物料、验收项和固定版本存在且可读；外部仓引用按显式绑定解释，不猜目标仓。
- 问题的复现、预期/实际与测试版本齐备；“缺陷已修复”需要实际代码与复测证据，不由 schema 通过代替业务验收。
- 变更是否仍被当前审核覆盖；schema/模板升级对旧物料的兼容性；未知版本不得默默误读或整库改写。

试点应覆盖一条跨两个模块/代码仓的需求、两份跨空间问题记录（其中一份无对应新需求），完成一次需求修改与多仓版本组合复测，验证同一 ID/固定路径、旧依据可追溯、不同物料并发不争抢中央索引、重复事件不重建事项或重复派发。需要覆盖某模块开关关闭、共享仓引用、一个仓已合并另一个未合并、以及单模块测试通过但联调失败时不能报告系统交付完成。D8 只规定需求合并后的方案阶段开关；不能以本目录建议扩展缺陷修复的自动化授权。
