# 需求深化：Git 工程物料与 Multica

初稿日期：2026-11-10；决策更新：2026-11-12。状态：研究与题目重写；D1–D8 已记录到 [PRD](../prd.md)，其他研究建议仍待方案评审。

## 证据范围

- [本地 Multica 能力核查](multica-existing-capabilities.md)：项目资源、Issue/运行、Git 集成、插件 API、事件队列和审批/证据边界；覆盖当前工作树已有修改，不代表部署状态。
- [官方一手资料](primary-sources.md)：Git 文件与平台元数据区别、Webhook 交付和补偿、审批失效及来源证明的适用范围。
- 本文的方法和试点均为研究建议。当前插件事件可能丢弃，已有 PR 合并转完成未检查全面验收证据；不能把这两条现有路径当作已经可靠的自动交付闭环。

## 本轮的核心判断

需要研究的核心是：一条需求经过澄清、设计、拆解、编码、测试和审核后，如何证明实现对应的是被批准的那个版本，以及变化发生后哪些工作需要重新做。接入系统数量、角色数量、生成文档数量不能回答这个问题。

“工程物料放在 Git”有两个需要区分的含义：

- 仓库文件随提交版本化：需求正文、设计、任务定义、缺陷复现、验收用例和证据索引。
- Git 托管平台数据库中的对象：Issue、PR/MR、评论、审批和 CI 记录。这些对象不因代码 clone 而自动进入本地仓库。

用户已确认（D3）：Git 保存物料定义及获批版本，Multica 保存讨论、分派、进度和运行记录。实时业务状态不要求逐次写入 Git。

## 1. 专家还会做什么

| 动作 | 具体问题 | 应产出的证据 |
| --- | --- | --- |
| 跟踪一条真实交付 | 人在何处查资料、等待、纠错、重新确认？ | 带时间的现状过程、返工原因和人类投入基线 |
| 验证自动化的前提 | 提问能否从现有代码与资料回答？哪些决策必须由业务负责人承担？ | 未知项清单、决策责任与提问理由 |
| 明确每个字段的权威来源 | 需求内容、负责人、任务状态、运行状态、审批和验收分别由谁写？ | 对象/字段所有权矩阵，冲突和恢复规则 |
| 设计变更传播 | 需求 v2 是否使 v1 的设计、任务、实现或测试失效？ | 依赖关系及受影响结果的重新验证规则 |
| 把审批绑定到实际对象 | 审的是哪一版需求、设计、代码、产物，批准什么动作？ | 能拒绝过期或越界使用的审批合同 |
| 先试图推翻方案 | 重复事件、漏事件、乱序、网络中断、并发编辑和撤销权限会怎样？ | 失败用例、恢复策略和无法证明时的待确认状态 |
| 测量人的总负担 | 自动生成更多内容是否增加了审阅和纠错？ | 回答问题、审核、返工、交付质量与总耗时的对照 |

产品、设计、技术和验收责任需要有人承担，同一个人可以兼任多个角色；不能默认程序员有权替所有业务方决定。人类审核方案不等于验收实际交付。

## 2. 从哪些原始素材入手

| 原始素材 | 要还原的事实 |
| --- | --- |
| 原始需求聊天、会议录音/逐字稿、工单首条描述及追问 | 用户真正想完成的工作、歧义的来源、决策是何时作出的 |
| 实际操作录屏、设计源文件版本、原型、评审批注 | 交互状态、异常路径、设计修改理由及用户能否完成任务 |
| 原始 Issue/评论/状态历史、指派记录、PR 讨论、提交与 diff | 从需求到代码的真实关联、等待、遗漏和返工 |
| 缺陷首报、复现数据、环境版本、失败日志、事故记录 | 必须保留的行为与已知失败模式 |
| CI 配置、原始运行日志、测试数据、制品、发布记录 | 是否确实执行过所需检查，检查的到底是哪一个版本 |
| Multica 当前源码、权限检查、API、数据库模型、任务消息与运行回执 | 可直接复用的能力、边界与尚未验证的能力 |

优先选择同一条真实工作事项的完整材料链，包含成功交付和至少一次返工。外部系统数据只在已获授权的范围读取，敏感内容不因“统一物料”而自动复制入 Git；本轮没有读取用户外部办公数据。

## 3. 方法、工具与产出

| 方法 | 具体工具 | 产出 |
| --- | --- | --- |
| 情境访谈、直接观察、价值流分析 | 原始录屏、带时间戳的事件表 | 真实流程和人工时间基线 |
| 领域建模与字段所有权设计 | 对象/动作矩阵、状态转移表、Mermaid | 区分需求、设计、业务任务、运行、缺陷、审批和证据 |
| 代码考古与能力核查 | `rg`、`git log -p`、`git show`、源码与已有测试 | “现有能力—证据—复用点—缺口”清单 |
| 可执行契约与依赖追踪 | Markdown + 结构化元数据、JSON Schema 或现有校验器、Git diff | 稳定物料 ID、修订、依赖、责任人与可观察验收条件 |
| 版本与事件一致性推演 | Git 分支/PR、托管平台 API、Webhook 记录、故障注入脚本 | 去重、版本校验、对账、冲突展示与恢复规则 |
| 行为示例与独立验收 | Given/When/Then、现有 Go/Vitest/Playwright、设计体验检查 | 与需求绑定的预期样本和原始测试结果 |
| 历史回放与前瞻试点 | 冻结历史输入、隔离环境、现有 CI、人工工时记录 | 正确性、失败恢复与人类总投入的对照证据 |

这些是研究方法与可选工具，不代表本轮已经运行了故障注入、真实 Agent 或用户试点。

## 4. 什么可以证明结果正确

正确性需要分层证明：

1. **需求成立**：真实使用者能在固定样例和原型中完成目标；业务负责人确认可观察的验收条件。
2. **交付一致**：每个验收结论可追到物料 ID/修订、被测代码版本、制品、测试环境、实际运行记录和批准者；摘要只能证明材料一致性，不能证明语义正确。
3. **流程可靠**：重复事件不重复创建/派发；乱序不回退较新状态；漏事件可以发现并对账；权限撤销、旧审批或旧 CI 不能批准新版本。
4. **实现符合预期**：既有回归测试、独立编写且未提供给实现 Agent 的验收样例、原始缺陷复现、目标用户体验检查共同构成判据；另一个 AI 同意不是充分证据。
5. **确实减少负担**：比较相似工作的人工总分钟数、审阅/纠错/返工时间、等待、首次验收通过率、逃逸缺陷、每项验收交付的成本；计入失败和人工接管。小样本只能形成试点证据。

历史回放仅向 Agent 提供当时可知的输入，将最终修复与后续讨论隔离。公开或模型可能已经见过的样本只能用于检验流程，能力结论需要新的真实试点或充分隔离的样本。

## 职责划分（D3 已确认，审批接入细节待定）

| 信息 | 推荐权威来源 | 另一侧如何使用 |
| --- | --- | --- |
| 已评审的需求、设计、任务/缺陷定义、验收条件 | Git 仓库文件及修订 | Multica 导入为可检索、可操作的投影 |
| 排队、指派、Agent 运行、重试、等待人工答复 | Multica | Git 可按需保存交接/里程碑快照 |
| PR/MR 审批、提交、托管平台 CI 结果 | Git 托管平台/CI | Multica 保留来源与版本，执行动作前核查其有效性 |
| 阶段验收决定 | 明确指定的有权审批者及其审批系统 | Git 留可追溯引用；不能从模糊文字或运行 completed 推断 |

每个字段只有一个权威写入路径。支持两个界面操作，不意味着两个存储可以任意互相覆盖：从 Multica 修改 Git 权威字段时，应产生可评审的物料变更，生效后再更新投影。已不采用“所有业务状态都由 Git 维护”的候选方向，避免把频繁协作更新变成文件写入与合并冲突。Agent 租约、进程、重试等运行事实由执行系统持久化。

不将整个仓库 HEAD 的任何变化都等同于需求失效：需求版本应绑定实际受控文件/对象的摘要或冻结版本清单，审批绑定其具体范围。受影响材料变化才触发依赖失效；代码测试则绑定被测提交/合并结果。分仓时需记录需求仓与代码仓各自的版本，不能用一个模糊“当前版本”代替。

设计大文件、录屏与制品可存于适当存储，在 Git 中保留受控版本的引用和摘要；可移动链接本身不能冻结设计或证据。

当前 Multica 本地 worktree 路径会回放未提交文件，因此代码提交 SHA 可能不足以标识实际执行输入。试点必须绑定实际输入快照/清单，或明确采用干净且冻结的源码模式；不能只记录分支名就声称可复现。

## 一条贯通示例（说明候选机制，非已有真实试点）

输入：“把筛选后的任务导出 CSV”。

| 阶段 | Git 中的工程定义或证据索引 | Multica 中的协作与执行 |
| --- | --- | --- |
| 澄清 | `REQ-DEMO-001`：导出范围、字段、权限、验收样例；未决项明确保留 | AI 先核查现有行为，再向有权决策的人询问尚未消解的歧义 |
| 设计 | 与该需求修订关联的交互稿，覆盖按钮、加载、空结果、失败与权限状态 | 收集设计审阅决定，冻结通过的设计版本 |
| 拆解 | 稳定任务 ID、依赖与对应验收条件；不以文件名或标题作为身份 | 通过受控 API 按仓库身份/物料 ID 建立或更新业务任务投影；重复通知不能重复建任务 |
| 执行 | 代码分支与提交，以及被采用的需求/设计版本清单 | 一次运行冻结输入版本，在隔离工作树中执行并保留运行回执 |
| 验证 | PR 与测试证据索引，绑定被测提交、需求修订、环境与实际结果 | 独立 QA 核对预期行集、权限、异常和体验；Agent 完成后进入待审核 |
| 验收 | 保留针对具体版本的决定和来源引用 | 有权审批者基于当前有效证据验收，服务端检查决定适用于当前对象 |

若中途将“导出当前页”改成“导出全部筛选结果”，系统应标出受影响的交互、接口、实现和测试。正在执行的旧版本任务必须显式报告基线过期；旧测试通过不允许直接把新需求标为完成。受影响项需要更新或重新确认，无关材料不应因仓库的另一处提交而全部重做。

物料同步和执行派发必须区分：保存草稿或同步评论不应自动启动 Agent。同步事件应带可去重的来源身份与版本，回写产生的事件也不能形成反复派发的循环。这些规则需要服务端和故障测试证明，不能只写进 Agent 提示词。

## 重写后的题目

**以 Git 为工程物料版本依据，设计与 Multica 协作的 AI 开发流程：验证一条需求从原始输入到可验收交付的闭环。**

请研究一套覆盖需求澄清、产品与设计决策、任务拆解、实现、测试和审核的 AI 开发流程。工程物料采用 Git 管理，并与 Multica 现有项目、任务、智能体、小队和执行能力衔接。首轮选择一条真实需求及其关联返工或缺陷，以机制深度和可验证性为目标，不扩展办公系统数量。

请先从原始需求对话、用户操作、设计源文件和评审批注、Issue/PR/提交历史、缺陷复现、CI 日志，以及 Multica 当前源码和测试还原工作流；标明资料缺失、冲突、已核实事实和假设，不把整理后的 PRD 当作全部事实。

研究必须回答：

1. 哪些决定必须由人承担，AI 何时可以从现有证据自行完成工作，何时必须提出什么问题；估计并测量人的回答、审核与纠错成本。
2. 按已确认的分工，Git 保存需求、设计、任务、缺陷的定义及获批版本，Multica 保存讨论、分派、进度和运行记录；区分 Git 文件与托管平台元数据，设计版本映射、变更和恢复，说明为何不采用全部业务状态都写 Git。
3. 定义需求、设计、任务、缺陷、审批、代码与证据的稳定标识、修订和依赖，展示一条贯通实例。每个阶段明确输入、产物、责任人、准入和退出条件。
4. 基于当前源码指出可复用的 API、项目资源、Agent/小队、Git 集成和插件扩展点；说明哪些需要服务端强制执行，哪些可由插件承载。不得将提示词约定或观察性接口当作已生效的交付门禁。
5. 给出需求变更、人工否决、重复/乱序/漏事件、并发编辑、运行失败和权限撤销时的行为；规定旧设计、旧审批和旧测试结果何时失效，并展示恢复过程。
6. 用独立预期样例、既有回归测试、原始运行证据、真实用户体验检查和历史回放验证机制；再通过相似任务试点比较人工总投入、返工、逃逸缺陷和每项验收交付成本。说明什么观察会推翻方案。

请输出当前事实与缺口、职责与数据归属、一个完整案例、最小试点及其外部验收证据。未验证的能力明确标为待验证，不以文档数量、Agent 数量、代码生成量或 AI 自评作为成功证明。人类减少日常执行劳动，同时保留业务决策、与版本绑定的审批和最终验收责任。

## 当前规划位置

自动推送分支并创建 PR/MR、可评审 PRD 自动送审、Git/Multica 数据归属、GitLab（含自建）/GitHub 平台选项、Multica 内审核及产品人员仅需 Multica 账号均已确认；D7 于 2026-11-12 按用户意图调整为产品批准后系统受控自动合并。系统使用预先授权的物料仓合并权限，核对当前获批版本与原生 Git 门禁，保存真实审核人与系统执行身份。存在额外原生审批、冲突或权限阻塞时显示原因，不绕过规则。当前待明确平台交付顺序、实际仓库策略与首期范围；参见 [设计草案](../design.md) 和 [实施顺序草案](../implement.md)。

D8 已确认后续方案启动由项目级开关统一控制，默认开启；关闭后生成待办等待手动启动。自动与手动两条路径均引用已核对的获批需求基线，技术方案与任务计划先审核再进入编码。该决策不意味着首期范围已定或自动执行已实现，重新开启对已有待办的影响仍待明确。
