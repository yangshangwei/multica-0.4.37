# 产品人员在 Multica 中探索工程并提交需求

状态：规划建议与源码核查，未实现、未调用真实 Agent、未写入外部 Git。

2026-11-26 更新：按用户明确的产品版本管理目标补充版本入口、提交归属、按需初始化及复用运行时的建议；具体合同见 [产品版本与接入设计](product-release-workflow.md)。以下源码依据保留原研究时的结论，本轮不宣称已重新验证现有运行时的完整发布能力。

已记录决策（2026-11-12 更新）：自动提交包括推送需求分支、创建或更新 PR/MR，不直接写入默认分支。AI 完成澄清并形成可评审 PRD 后自动送审，产品人员直接审核，无须先点击提交按钮；按修订后的 D7，产品批准后由已授权系统核对条件并自动合并，核对实际结果后形成正式需求基线。

数据归属已确认（D3）：Git 保存需求、设计、任务和缺陷的定义及获批版本；Multica 保存讨论、分派、进度和运行记录。

平台选项已确认（D4）：GitLab（含自建）或 GitHub；按项目配置需求输出仓。审核入口已确认（D5）：产品在 Multica 内阅读、评论、批准或退回。审核账号已确认（D6）：产品人员仅需 Multica 账号，系统同步可追溯记录，原生 Git 审批独立满足。合并职责按本轮意图修订（D7）：产品批准后系统受控自动合并。首期交付顺序与范围仍待确认。

后续启动已确认（D8）：项目级开关默认开启，需求合并并核对后自动启动技术方案生成与任务拆解；关闭则建立待办，等待手动启动。编码等待方案审核通过。重新开启对既有待办的处理尚待确定。

## 用户意图

产品人员在 Multica 中工作，能探索相关工程、理解现有能力与限制，将讨论结果形成需求文档，并自动提交到指定的需求管理 Git。当前问题是工作方式与现有设计是否兼容。

## 判断

与已确认的 D3 分工兼容。现有项目、任务讨论、产品分析与架构角色、执行环境和项目资源可以复用。但目前不能把这条完整路径描述为已经开箱可用：需要明确仓库输入/输出、需求编写与发布职责、提交凭据和版本回填。

正式文档展示来自 Git 版本，Multica 编辑中的内容是候选草稿，不构成第二份正式定义。实时分派与进度不逐次写 Git；更改定义需经过新一轮版本与评审。Multica 内的业务审核决定保留人类身份与对象版本；Git 平台原生 PR/MR 审批记录属于托管平台元数据，需保留引用及来源。两者不能混为同一个布尔值，也不能声称普通 git clone 已包含这些记录。具体数据合同见 [设计草案](../design.md)。

## 建议用户流程

1. 管理者绑定目标需求仓。建议已有默认环境、认证和能力齐备时只需填写仓库地址，其余路径/分支规则由可信配置或模板提供；缺失项由系统明确提示。运行时可承担 Git 执行，读取、推送、PR/MR 和合并能力分别核对；初始化规则文件另走维护授权，不要求手工预建目录。项目成员身份不能替代 Git 授权，原生仓库门禁继续满足。
2. 产品人员在物料项目的目标版本（例如 V1.8.1）中新建需求探索事项，说明目标，交给产品分析角色或需求预研小队。版本由入口或明确选择传入，未指定则保持待规划，不猜最新版本。当前 Observer 不适用“让 Agent 自动新建事项”；可以先手工建事项再指派。
3. Agent 先读工程文档、代码、测试与关联讨论，给出已有能力、可复用部分、限制、未核实点和代码版本依据，再向产品人员提问。
4. 在同一事项中形成可审阅的 PRD 草稿：问题与用户、目标、范围、场景、验收条件、工程依据和待决策项。当前行为和目标行为必须分别表述，尚未开发的内容不能写成现状。
5. AI 完成澄清并形成可评审 PRD 后，受控提交自动将冻结草稿写入独立分支的 `requirements/<id>/prd.md`，并在同一 PR/MR 中加入 `releases/<version>/release.yaml` 的需求关联；执行 commit、push、创建或更新评审并回填真实结果。产品人员直接审核正文和版本归属，无须额外点击提交。目录、字段和版本冻结规则仍为新增待评审方案。
6. 产品人员仅凭具有项目审核权限的 Multica 账号，对该版本阅读、评论、批准或退回（D5/D6）；批准操作明确将触发系统合并当前需求版本。系统向 Git 同步审核记录，不冒充审核人的原生 review；核对批准仍有效且覆盖当前修订、完整变更均在授权范围、系统合并权限与原生门禁满足后，自动执行合并。无需负责人逐份操作，阻塞时显示原因，Multica 核对实际结果后更新正式需求基线（D1/D7）。发布文档或合并需求 PR 不应自动代表功能已经开发完成，也不默认启动实现工作。
7. 基线核对后按项目自动启动开关处理方案阶段（D8）：默认开启时启动技术方案生成与任务拆解；关闭时任务进入待办，可在之后手动启动。两条路径引用同一固定 PRD，保留验收条件与来源，不复制出新的需求身份；方案审核之前不开始编码。

产品人员使用 Multica 的讨论、文档预览、版本比较与审核界面，后台执行被授权的 Git 操作；Git 链接用于追溯。以上交互尚待实现，不能冒充现有按钮。批准只绑定被阅读的修订，旧批准不自动覆盖新提交；退回意见保留并驱动后续修订。

## 可评审条件草案

以下条件用于细化 D2，尚需在完整方案评审时确认，不表示用户逐项批准，也不是已经实现的校验：

- 用户目标、范围与不做的内容明确；不存在会改变核心目标、范围或验收标准的未回答业务问题。
- 主流程、相关异常场景与可观察的验收条件齐全；不以章节存在或字数达到阈值代替内容完整。
- 现有工程行为、拟新增行为和未核实假设分别表述；工程依据有对应版本与来源。非阻塞未知项可以保留，不要求用猜测填满。
- 草稿对应的讨论修订、工程来源与文档版本被冻结；实际送审前发现其已过期则重新核对，不提交被后续讨论否定的版本。

AI 负责给出内容达到可评审程度的判断及依据，系统检查结构、阻塞项、版本、目标仓和授权。结构检查不能证明语义正确；最终需求判断仍由产品审核完成。满足这些条件仅授权送审，不授权合并或开始实施。

日常讨论与未完成草稿留在协作流程，不逐条写 Git。首次及后续送审以一个可评审的文档修订为单位；同一未结束评审中的修订复用关联 PR/MR，并保留差异。合并后发生新的需求变更，应保留旧基线并发起新一轮变更评审，不能继续写入已结束的评审。

## 角色合同的实际冲突

- 产品分析师允许读任务、仓库与讨论，输出澄清、验收标准、风险和拆分建议，但交付格式为事项评论，角色为 Observer。
- 系统级 Observer 明确禁止写仓库文件。不能仅为该角色增加一段“生成后提交 Git”的提示词，否则与运行时注入的权限合同冲突。当前该文件限制主要是行为合同，不应把它误称为已强制的文件系统沙箱。
- 技术文档工程师虽然为 Contributor，可在隔离分支写文档，但其职责明确禁止描述尚未实现的预期行为。它用于记录已发生变更，与面向未来的 PRD 目的不同。
- 需求预研小队交付供人决策的结果，明确不自动创建实现任务。需求入库应作为文档交付阶段，不应顺带突破这一边界。
- D8 的待办不能仅靠现有 `todo` 状态阻止执行：[创建流程](../../../../server/internal/service/issue.go#L219) 与 [派发判断](../../../../server/internal/service/issue.go#L905) 会为已指派且非 `backlog` 的事项启动 Agent/小队。需在服务端明确保留等待手动启动并覆盖后续指派、恢复及领取入口；[项目中文约定](../../../../apps/docs/content/docs/developers/conventions.zh.mdx#L226) 中 `todo` 是待办、`backlog` 是待规划，不能通过换状态偷换用户要求。现有预研角色也不能直接代替方案生成与任务拆解阶段的角色合同。

建议保留产品分析师的只读职责，由明确授权的工作流操作执行文档入库。该动作只接受确定的文档版本、目标仓和路径，执行校验与 Git 提交，不需要再引入一个替产品重新做决定的 Agent。它不能由 Observer 使用其他身份绕过自身限制；应由产品人员授权的系统流程或有权限的协调者启动。若改用可写的产品 Agent，则需同时调整角色、技能和执行边界，不能只改一个提示词。

## 多仓库与提交链路的核查

- 一个 run 可以使用多个远端 Git 仓库。运行上下文列出仓库，Agent 按需重复执行 checkout。普通运行初始目录是任务 workdir，checkout 不会自动把“需求仓”设为主目录；写入目标必须显式指定。
- 同项目、同 daemon 最多绑定一个本地执行目录，但可关联多个远端 Git 资源。本场景可复用现有多远端资源能力，无须先突破本地目录约束。
- 当前资源只有 URL/ref 等字段，没有输入工程/需求输出用途，也没有按资源限制只读或允许写入路径的合同。设置名称或提示词不能当成已实现的权限隔离。
- fetch/clone 与 Agent Git 工具可使用运行主机已有认证，独立于只读 GitHub App 集成。本次未读取任何真实凭据，不能断言目标主机的具体访问权限。
- 自动 commit 收尾仅是本地 worktree 的防丢失措施，失败运行也可能保存改动；它不自动 push、创建 PR 或 merge。普通远端 checkout 的 Git 提交由 Agent/显式工具执行。需求发布需要确认远端结果，不能以 run 退出或存在本地分支为成功。

## 需要新增或明确的合同

| 合同 | 要解决的问题 |
| --- | --- |
| 仓库用途 | 哪些是工程探索输入，哪个是需求文档输出；不能凭列表第一项或自然语言猜目标仓 |
| 产品版本 | 从可信任务上下文取得版本身份；正文与版本范围共同评审，延期、冻结与历史交付不混淆 |
| 接入与初始化 | 已有配置齐备时只填仓库地址；能力缺失明确提示，按需建文件，规则初始化和空仓首提交单独定案 |
| 实际权限 | 工程读取与需求写入分别授权；仓库用途标签不会自动产生权限隔离 |
| 文档版本 | 稳定需求 ID、草稿修订、工程来源版本、需求提交版本与审批关系 |
| 发布结果 | 本地保存、远端推送、PR 创建、审核合并分别记录；不能只凭 Agent 的“已提交”评论成功 |
| 重试与并发 | 一个提交意图只有一个结果；同一需求复用关联 PR；人工修改或基线变化时显式冲突 |
| 阶段语义 | 需求文档交付完成、需求获批、开发任务完成是不同事实，文档 PR 不得关闭后续开发父事项 |

自动提交分支并创建 PR 与审核合并是不同阶段。可评审 PRD 自动送审，产品在 Multica 业务批准后触发受控合并意图；系统核对当前版本、授权及原生门禁后执行合并，核对结果后生效。普通同步和通知重放只恢复原意图，不能伪造产品批准或重复派发研发。

## 候选验收

- 版本管理和接入的新增验收对应 PRD 的 PAC16–PAC19：明确目标版本、问题多版本关系、延期与发布基线、初始化与运行时能力边界；具体例子见新增研究。
- 产品人员仅通过 Multica 完成提出目标、澄清和审阅；最终可打开需求仓中实际存在的文档及提交。
- 可评审 PRD 自动送审；产品人员无需额外确认“开始提交”，日常对话和有阻塞问题的草稿不触发。
- 探索两个已授权工程时，文档能分别引用其实际读取版本；不能把“当前工程”作为模糊来源。
- 文档提交落在配置的需求仓和允许路径，工程仓没有被发布动作改写。
- 同一草稿发布重试不重复创建文档或 PR；push 或 PR 创建失败展示真实阶段，允许恢复。
- 审核后修改草稿或工程依据变化时，能够标识受影响内容与过期审批。
- 需求文档 PR 合并不误将尚未实现的功能标为完成。
- 当前产品业务批准在授权与门禁满足时触发系统自动合并，无需额外人工操作；权限不足、冲突、版本变化、批准撤回或额外原生审批未满足时不越过条件。重复批准、通知重投或合并成功但响应丢失可恢复；实际合并事实、获批内容与基线对应，未经审核的外部合并不冒充正式获批基线。
- 有审核权限的产品人员无需 Git 账号、个人 Git 授权或跳转 Git 平台即可完成审核；系统同步记录保留真实审核人与版本回链，仓库原生审批独立核对。伪造审核人、机器身份批准、审核中内容变化及同步半成功均能按真实状态处理。
- 项目自动启动默认开启，显式关闭与其他项目隔离；关闭时方案任务在待办等待手动启动，创建、预分派、通知重放与恢复均不自动执行。手动启动复用原任务且核对固定基线和权限；重复启动不重复派发，未获当前方案审核不得编码。

这些是候选产品验收条件，本轮未执行。
