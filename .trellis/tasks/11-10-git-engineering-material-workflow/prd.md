# Git 工程物料与 Multica 全流程协作需求深化

## Goal

深化“以 Git 承载需求、设计、任务、缺陷，与 Multica 联动的 AI 自动化开发插件”这一题目，明确需要研究的核心机制、原始证据、方法与外部验真方式。优先把一条产品到交付的链路讲深，不增加系统接入数量或功能范围。

## Background

- 用户设想覆盖产品、设计、研发、测试，AI 自动澄清和拆解，人主要回答问题、审核方案。
- 用户明确“工程物料仓库就是 Git”，希望研究其与 Multica 的连接方式。
- 用户要求先回答：专家额外做什么、从哪些原始素材入手、使用哪些方法工具、由什么外部证据证明正确，然后重写题目。
- 2026-11-10 用户明确同意创建 Trellis 任务并进入规划；未授权产品实现。
- 当前工作树已有大量其他任务修改，本任务只写本目录内的规划与研究资料。
- 源码核查确认项目资源、业务 Issue、Agent 运行和 PR/CI 集成已有基础；当前插件 Action API、事件可靠性和交付完成条件不足以直接证明所需完整闭环。具体证据及适用限制见研究文件。
- 用户进一步明确首个工作场景：产品人员在 Multica 内探索相关工程，生成需求文档，并自动提交到指定的需求管理 Git；需要评估与现有设计/实现是否冲突。该补充未授权代码实现。
- 用户进一步明确后续启动方式：需求合并并核对后，按项目统一的开关决定自动启动技术方案生成与任务拆解，默认开启，关闭则先进入待办。该选择记为 D8；首期交付范围与完整研发流程仍需收敛。
- 用户要求参考 DeepSeek Harness，设计产品需求与测试问题在物料 Git 仓中的目录及管理方式。已补充固定版本的一手资料和目录协议建议；具体目录兼容、QA 问题审核与修复启动规则仍待定案。
- 用户描述目标使用方式：模块对应普通 Multica 项目，整体是多代码仓的分布式系统；计划中的产品/测试物料仓也作为一个普通项目的仓库资源，该项目同时承接系统需求与协调工作（D9）。这是功能设计，不表示当前已有业务仓库地址、已创建项目或正在要求接入。支持一条需求/问题关联多个模块，不按模块复制正式需求；自动编排尚未获准实施。

## Confirmed Decisions

- D1（2026-11-11）：用户确认“自动提交”定义为自动推送需求分支并创建或更新 PR/MR，合并后形成正式需求基线；不直接写入默认分支。自动送审本身不授权合并，产品批准后的合并策略以修订后的 D7 为准。该决定不等于批准实施。
- D2（2026-11-11）：用户确认触发时机为 AI 完成澄清并形成可评审 PRD 后自动送审，产品人员直接审核，不增加人工点击“提交评审”的前置步骤。日常讨论不逐条生成 Git 提交；“可评审”的具体判定需在方案中明确。
- D3（2026-11-11）：用户确认 Git 保存需求、设计、任务和缺陷的定义及获批版本；Multica 保存讨论、分派、进度和运行记录。实时业务状态不逐次写入 Git，也不要求只凭 Git 恢复全部业务历史。
- D4（2026-11-11）：用户明确需求仓可使用 GitLab（含自建），也可以使用 GitHub。两者均为目标平台选项；建议先以 GitLab 验证闭环，再对 GitHub 验证同一流程。具体实施先后与首期是否同时交付两个适配尚未确认，不能把建议当作已批准范围。
- D5（2026-11-11）：用户确认采用 Multica 内审核。产品人员在 Multica 阅读、评论、批准或退回需求，后台关联 GitLab/GitHub 评审记录，不以跳转 Git 平台作为日常审核的必需步骤。账号要求及业务审批与原生 review 的关系由 D6 补充，审核后的合并策略由 D7 确定。
- D6（2026-11-11）：用户确认产品人员仅需 Multica 账号，无需拥有或绑定 GitLab/GitHub 账号，即可在具备审核权限的项目内完成业务审核。Multica 保存真实审核人、决定与所审版本；系统向 Git 同步可追溯记录，明确实际执行身份，不冒充审核人的原生 Git review。仓库要求的原生审批及其他门禁仍须独立满足；身份选择本身不构成仓库合并授权，系统合并所需授权与条件由 D7 确定。
- D7（2026-11-11 确认；2026-11-12 调整）：按用户本轮意图，将此前“研发/仓库负责人单独手动合并”改为“产品在 Multica 批准后，由系统受控自动合并需求 PR/MR”，正常流程无需另一人逐份点击合并。系统使用项目预先授权、具有目标物料仓合并权限的集成身份，核对批准仍有效且覆盖当前修订、目标仓与允许路径未变、原生门禁满足，再执行合并；存在冲突、权限不足或额外原生审批未满足时保留批准并显示阻塞原因，不绕过仓库规则。Multica 核对实际合并结果与获批内容后才更新正式基线，保留真实产品审核人与系统合并身份。此次调整不要求产品绑定 Git 账号，不自动改变仓库规则，也不授权研发代码自动合并；后续方案阶段的启动按 D8 单独处理，任务仍处于规划阶段。
- D8（2026-11-12）：用户确认提供按项目统一设置的自动启动开关，默认开启。需求已审核合并且正式基线核对通过后，开启时自动启动技术方案生成与任务拆解；关闭时仍建立关联该基线的后续任务，放入 Multica 待办，等待有权限的人手动启动，不自动运行 Agent。产品先前选择“自动启动”，本次进一步细化为可关闭的项目配置；不设置每条需求的独立开关。沿用上一轮明确的阶段边界：编码等待技术方案与任务计划审核通过，需求合并不直接启动编码。该决定只更新产品规划，不表示功能已实现或当前会话获准执行真实 Agent。
- D9（2026-11-12；同日澄清）：用户计划在功能投入使用时，将产品和测试提交需求/issue 的物料 Git 仓关联到一个普通 Multica 项目，该项目本身承接系统级需求、测试问题、总体方案、协调记录与整体联调验收，不再增加一层独立协调项目或协调仓库。模块项目分别关联代码仓，通过稳定物料 ID 和版本与总体需求关联。项目名称“系统需求与测试”仅为建议，不引入特殊项目类型。此前将它描述为“现有仓库及已有项目待接入”属于误解；当前开发阶段无需用户提供真实仓库地址或预建业务项目。仓库/项目的创建或选择、绑定和访问配置属于功能使用时的流程。此决定是产品组织模型，不代表已执行接入或批准本任务进入实现。

- D10（2026-11-12）：用户在目录、完成/修复状态及归档说明后确认接受目前设计。需求和问题采用稳定 ID 与固定目录，完成、关闭、重新打开或归档均不移动 Git 文件，不增加按状态划分的 `done/`、`fixed/`、`archive/` 目录。Multica 分别管理物料审核、需求交付、问题处理状态，并将归档作为独立的展示/管理维度，归档后仍可搜索和追溯。需求须整体验收通过才完成；问题修复后先待复测，通过后关闭，复测失败可重新打开。Git 保留定义、版本以及修复/验收证据引用，实时状态以 Multica 为准。具体业务阶段见目录研究中的 D10 表；与现有状态的映射、转换权限和自动归档时机仍待细化。此次确认不决定 QA 入库审核/修复启动、D8 重开策略或首期范围，任务保持 planning。

## Requirements

- R1：交付四项研究框架和可直接复用的重写题目；区分已核实事实、建议及待验证假设。
- R2：从本地源码、测试与官方资料说明 Multica 的可复用能力和能力边界，不把存在代码等同于已经上线或全面可用。
- R3：按 D3 区分 Git 文件、Git 托管平台对象、Multica 业务对象及运行状态的权威来源，定义标识与版本绑定；Git 承载物料定义与获批版本，Multica 承载讨论和实时工作流。
- R4：用一条真实需求或缺陷的端到端样本定义澄清、设计、拆解、执行、审核、验证的产物和责任，重点覆盖需求变更、并发冲突、重试与审批过期。
- R5：定义独立于生成内容的验收证据，并测量人类总投入、返工和交付质量。
- R6：首轮范围建议必须标为待用户决定；不将“全流程”扩展为一次性接入所有办公系统或默认自主发布。
- R7：产品人员能在 Multica 中提出目标、回应问题、查看工程依据并审阅需求草稿；工程探索通过已授权项目资源和执行环境完成。
- R8：区分探索输入的工程仓与需求文档输出的目标仓。需求文档需引用所依据的工程版本，提交成功后回填需求 ID、文件、提交及评审链接。
- R9：明确现有只读产品分析角色与文档写入动作的职责衔接，不通过扩大所有工程的写权限解决需求仓提交。
- R10：按 D1/D7 自动 commit、push 到需求分支并创建或更新 PR/MR；产品业务审核通过后，由已授权系统核对当前版本与原生门禁并自动合并，实际结果核对通过后才生效为正式需求基线。无需额外的人工合并动作；门禁、冲突或权限阻塞需显示真实原因。须区分各阶段，失败不能误报成功，重试不能创建重复需求、评审单或合并意图。
- R11：按 D2 在澄清完成且 PRD 达到可评审条件后自动启动送审。送审资格与产品验收必须分开：AI 判定可送审不能替代人的审核，也不能使需求直接生效。
- R12：Multica 中的 Git 物料展示保留来源版本与同步状态；编辑定义产生新的候选修订，不直接覆盖已获批基线。Git 物料变化和 Multica 进度变化不得互相递归触发提交或 Agent 执行。
- R13：需求输出仓按项目选择 GitLab 或 GitHub，保持 D1–D3 的统一产品语义；自建 GitLab 需明确实例地址与实际支持能力。不得将只读集成的连接成功当作具备需求提交或人工审批权限。
- R14：按 D5/D6 提供 Multica 内的文档阅读、修订差异、评论、批准与退回；产品人员仅需具备相应项目审核权限的 Multica 账号，不要求个人 Git 账号或授权。审批记录绑定真实审核人、权限范围、文档修订和对应提交，不能把模型结果或集成账号动作当作人工批准。
- R15：区分 Multica 的业务审批、Git 平台原生审核条件和实际合并。系统以明确的集成身份向 Git 同步审核摘要与原始记录引用，不计作审核人的原生 review。同步失败、内容版本变化或原生门禁未满足时展示真实状态；批准不能直接显示为已合并或正式基线。
- R16：按 D8 提供项目级自动启动配置，默认开启，保存的关闭值必须持续生效且不影响其他项目。需求合并及版本核对成功后，开启则自动启动方案生成与任务拆解，关闭则建立待办并等待手动启动；两条路径使用同一需求身份与固定基线，关闭开关不影响需求文档自动合并。
- R17：待办、阶段启动意图与实际 Agent 运行分别记录。关闭时不得因创建待办、预分派、同步、恢复或重试而自动执行；手动启动复用同一任务并重新核对基线和执行权限。重复合并通知不重复建任务或派发；输入不可读、版本过期或权限不足时显示原因。技术方案与任务计划未审核通过前不得启动编码。

- R18：按 D10 保持需求/问题路径与身份稳定；在 Multica 分开表达物料审核、需求交付、问题处理与归档，修复待复测和需求待验收不可提前视为完成。归档保留搜索、关联和证据，不靠 Git 目录或实时状态字段承担看板职责。

## Product Acceptance Criteria — 待实现与验证

- [ ] PAC1（R7/R8）：产品人员能在 Multica 提出目标并回应问题，需求草稿保留所参考工程的版本与可核查来源。
- [ ] PAC2（R10/R11）：满足送审条件的 PRD 自动产生远端需求分支及关联 PR/MR，产品人员无需额外点击提交；Multica 回填实际文档版本、提交和评审链接。
- [ ] PAC3（R10/R11）：普通对话、未完成草稿和未解决的阻塞问题不触发送审；同一草稿修订的重复通知或恢复不创建重复评审单。
- [ ] PAC4（R9/R10）：需求提交只写指定目标仓和允许路径；提交失败展示真实阶段，不把本地 commit 或 Agent 完成当作远端送审成功。
- [ ] PAC5（R10/R11/R15）：仅送审不触发合并；具有项目审核权限的产品人员批准当前版本后，已授权系统在仓库门禁满足时自动合并需求 PR/MR，无需研发/仓库负责人再次操作。未满足条件时展示具体阻塞原因；批准失效或当前 HEAD 改变不得套用旧批准。重复批准、通知重投、合并成功但响应丢失均恢复同一合并意图；核对实际合并事实及获批内容后，基线才指向实际合并版本，仍不代表功能实现完成或已启动开发。
- [ ] PAC6（R3/R12）：修改分派或运行进度不生成物料提交；修改物料定义形成独立候选版本，经审核合并才更新正式基线。Multica 展示的正式内容可追溯到实际 Git 修订。
- [ ] PAC7（R3/R12）：同一物料多次修订仍关联同一业务身份；恢复物料索引或对账不重建重复事项、不重派发运行，也不声称恢复了只存于 Multica 的讨论与运行历史。
- [ ] PAC8（R13）：对宣称支持的每个平台分别验证提交、评审回链、版本变更、恢复与合并基线；能力不足或未验证的实例明确显示限制，不假定平台与版本具有相同审批策略。
- [ ] PAC9（R14/R15）：未绑定 Git 账号但具有项目审核权限的产品人员，在 Multica 能完成阅读、评论、批准与退回，不出现个人 Git 授权前置步骤；审核记录来自当前有权的人类身份，重复点击不重复记账，AI/插件不得伪造审核人。
- [ ] PAC10（R14/R15）：审核版本之后出现变更、Git 写回部分失败或原生审批条件未满足时，不显示为可直接生效；保留已发生的人工决定并标出其版本和有效性。退回要求进入修订流程，不能自动当作批准。
- [ ] PAC11（R14/R15）：Git 中的同步记录明确显示系统执行身份，可追溯到 Multica 原始审核决定、真实审核人与具体版本；同步成功不构成审核人的原生 Git review，也不绕过仓库要求的原生审批。

- [ ] PAC12（R16/R17）：项目首次配置物料流程时自动启动默认开启；获批需求实际合并且基线核对成功后，自动建立并启动一次方案生成与任务拆解任务，输入包含固定版本的完整 PRD 或可读只读文件、来源和验收条件，无需额外启动点击。仅产品批准、等待合并或基线核对失败均不提前启动。
- [ ] PAC13（R16/R17）：关闭项目开关并刷新后仍保持关闭；后续需求合并照常生效，关联的方案任务进入待办，未产生可执行的 Agent 派发。重放通知、恢复或预分派不绕过等待；有权限的人可手动启动该待办，复用原任务并重新核验输入与权限，不必开启整个项目的开关。其他项目的配置不受影响。
- [ ] PAC14（R17）：重复合并通知、任务创建后进程中断、派发回执丢失及重复手动启动不产生重复事项或并发重复阶段运行；错误版本、不可读正文或无执行权限时保留可解释状态。方案产出进入审核，方案或其依据变化使旧批准失效，未获当前方案批准的编码运行被拒绝。

- [ ] PAC15（R18）：同一需求/问题从进行中到完成/关闭、重新打开或归档，Git 路径、物料 ID 和旧版本引用不变，纯状态与归档操作不产生物料提交；归档记录仍可搜索和追溯。物料合并不等于需求完成，缺少对应版本验收或复测证据时不能完成需求或按已修复关闭问题，归档也不能替代这些验证。复测失败可回到问题处理流程，保留原现场、修复尝试和证据。

PAC1–PAC15 是当前方案的候选验证条件；本轮没有运行产品验收。
