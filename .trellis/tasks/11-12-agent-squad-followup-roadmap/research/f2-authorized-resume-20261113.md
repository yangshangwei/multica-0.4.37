## Report-wide withdrawal wire and transaction boundary

- Human-only POST `/api/issues/{report_uuid}/report-snapshots/withdrawals`, canonical original Idempotency-Key. Strict body `{protocol_version:1, scope:"report", expected_issue_revision:<positive int64>, expected_current_snapshot_id:<canonical UUID>, reason:<nonempty bounded text>}`. Reuse current human ordinary report-edit authority; Reporter/task/legacy/custom machine callers denied. First operation201, original same actor/key/input replay200; changed input/key collision or already-withdrawn new intent409. No automatic network retry.
- Success `{protocol_version:1, withdrawal_receipt:{withdrawal_id,request_key,report_issue_id,expected_current_snapshot_id,request_digest,withdrawn_at}, replayed:boolean}`. No snapshot/facts/digests of retained content. request_digest uses the same canonical typed intent envelope as capture, with the withdrawal body. Receipt is human-only, not a capability. API no-store on every result.
- One report-scoped mutable control row tracks active/withdrawn, revision, current snapshot ID/sequence and original withdrawal identity/receipt. Capture/correction/withdrawal must update this common row in their existing authorized RR transaction, so stale waiters get serialization failure and retry only if request context still live. Only locking an unchanged report row plus insert-only tombstones is insufficient. No FK/cascade; indexes CONCURRENTLY in their own migration files.
- Withdraw binds the exact current snapshot reviewed under the current frozen project; stale current or report revision refuses. Withdrawal first => pending capture/correction retries then refuses. Capture/correction first => stale withdrawal409 rather than silently withdrawing an unreviewed newer seal.
- Content GET checks control in the same R as authority/data. Withdrawn => uniform minimal404 for current and every explicit ID, no old-body fallback. Control absent for an existing sealed record => unavailable, never default active. Original capture-key recovery after withdrawal must not return content; a content-free refusal/known-withdrawn outcome is sufficient. Original withdrawal-key replay may return its own receipt after current human authority, regardless of capture content no longer readable.
- Terminal withdrawal has no restore and prevents new cycles/corrections/capture on this report. Report/workspace deletion cleans control and retained rows in the root transaction; source issue deletion/move preserves other reports' history. Project move-away/back does not undo withdrawn status. This is application read termination, not a claim of physical backup erasure.
- CLI add `issue report-snapshot withdraw <canonical-report-uuid> --request-key <UUID> --expected-revision <n> --current-snapshot <UUID> --reason <text> --accept`; explicitly refuse machine credential profiles locally and on server. Original request repeated is receipt recovery, never creates a second withdrawal. No extra Reporter GET or by-key inventory permission.

Receipt: `{request_key, report_issue_id, snapshot_id, request_digest}`; request_digest is SHA-256 of canonical `{report_issue_id, request_key, request:<exact strict capture body>}`. Human client knows these inputs and verifies the digest plus bound report/snapshot/key. Server's actor/workspace-scoped idempotency digest stays private and separate.
