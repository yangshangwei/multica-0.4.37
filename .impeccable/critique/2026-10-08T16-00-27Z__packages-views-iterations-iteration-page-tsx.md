**优先问题：0 个 P0，4 个 P1，4 个 P2**

**P1-1：进展首屏缺少主次。**

公共头部 5 个指标，面板内再列 3 个完成率／状态值及 8 个杂项指标，图表之前已经有 16 个独立指标。冻结提示出现两次；结束类型、原因和处理时间也排在图表前。900px 窗口中，标签仍在纵向约 441px 处，第一屏不能完整看到主要图表。

影响：用户先处理统计字段，再自行归纳交付结论；低频的零值计数与主要结果权重相同。

建议：公共头部保留名称、状态、日期和一次冻结说明；将面板需要的指标放回面板。进展默认突出完成 2/4、未完成 2、原始承诺完成 1/4 三组信息。详细计数、结束处理时间、原始数据按需展开。完成率只保留一个主展示位置。

位置：`packages/views/iterations/iteration-page.tsx:98`、`iteration-history.tsx:58`、`iteration-progress.tsx:37`。建议命令：`$impeccable distill`、`$impeccable layout`。

**P1-2：两个标签的信息职责错位。**

范围变动计数放在进展里，范围变化页却平铺创建、期前计划、原始承诺、普通状态更新、任务更新和结束事件。页面最先展示的是创建迭代和四条计划更新。

影响：想看交付的人遇到变动计数，想找范围变化的人先读大量准备阶段活动。

建议：进展回答“完成多少、承诺兑现多少、剩余怎样处理”；范围变化回答“开始之后范围如何改变、谁改、为什么”。范围页提供“仅范围变化／全部活动”过滤，默认显示与成员范围或有效范围有关的记录。取消、重开、某些状态变化也会影响有效范围，不能仅保留 join／leave。

位置：`packages/views/iterations/iteration-page.tsx:106`、`iteration-history.tsx:75`、`iteration-events-view.tsx:31`。建议命令：`$impeccable distill`。

**P1-3：事件条目缺少实际变化，技术字段又过多。**

真实界面反复出现 UUID、操作者、完整年月日、同一批量原因，以及“快照未记录 → 快照未记录”。状态变更事件没有展示保存的前后状态，任务更新也没有展示具体改了标题还是负责人。

影响：用户知道更新发生过，却不知道发生了什么；不适用的来源／去向被表达成了历史缺失。四条批量计划更新重复同一原因，增加滚动长度。

建议：按事件语义生成摘要。状态更新显示“待办 → 已完成”；负责人更新显示具体前后值；仅真实迁移显示来源／去向。同一次 operation 的批量记录聚合成一条可展开记录。主行优先展示任务标题和已有的可读编号，UUID 放入详情。按日分组并默认最近优先，同一日只重复时分。

历史编号缺失时，可以先展示已保存的历史标题；任何当前名称或编号的辅助解析都要与历史事实区分，不能回查当前任务来补造过去的状态。

位置：`packages/views/iterations/iteration-events-view.tsx:60`、`:67`、`iteration-catalogue.tsx:15`。建议命令：`$impeccable clarify`、`$impeccable layout`。

**P1-4：统计阶段和分母容易误读。**

同一页并列当前范围 5、有效范围 4、原始承诺 4、50% 和 25%，没有就近解释。结束原因写“D 移出”，而期间移出次数为 0。对已结束快照仍使用“当前范围”，也容易让人以为数字描述此刻的任务归属。

影响：用户容易把合法的不同统计口径当成数据错误。

建议：比例显示分子与分母；已结束页面采用“结束时范围”这样的状态化标签。明确区分“期间范围变化”和“结束时未完成任务去向”，分别解释期间移出 0 次、结束时 D 移出这两个事实。结束处置不改写冻结前的期间统计。

位置：`packages/views/iterations/iteration-page.tsx:101`、`iteration-history.tsx:61`、`packages/core/api/iteration-schemas.ts:57`。建议命令：`$impeccable clarify`。

**P2-1：单日数据占据完整趋势图，数据表默认重复展开。**

这期只有一个日期，三条序列落在两个位置，原始承诺与有效范围重合；240px 高的图没有形成可读趋势。下方又有只有一行的“图表数据”。

建议：单日状态展示紧凑的当日结果和“本期仅有 1 天记录”；多日数据才展示趋势。数据表保留在可键盘展开的“查看每日数据”入口中。图例使用与曲线一致的实线／虚线示意。

位置：`packages/views/iterations/iteration-progress.tsx:14`、`iteration-history.tsx:109`。建议命令：`$impeccable layout`。

**P2-2：活动分页只有向前替换，缺少返回路径。**

活动迭代的事件组件只保存一个 cursor，“下一页”直接替换当前页，没有上一页、追加或返回首页。keepMounted 会在切换标签后保留这个位置。

建议：改为追加式“加载更多”，或提供带游标栈的前后翻页；给出当前显示范围。

位置：`packages/views/iterations/iteration-page.tsx:121`。这是共享组件的代码发现；本次已结束快照直接展示 19 条事件，不走该分页路径，未对该分支执行浏览器复现。建议命令：`$impeccable harden`。

**P2-3：事件加载、真实为空和后台刷新失败没有完整区分。**

活动迭代中，任意 events.error 都替换掉已有列表；带 cursor 时“重试”先清空游标，初次加载还会同时挂载空事件内容。真实空列表也没有独立说明。

建议：区分首次加载、无事件、后台刷新失败和权限失效；临时刷新失败保留已有数据与位置，重试当前页。提供明确的空状态和加载完成反馈。

位置：`packages/views/iterations/iteration-page.tsx:123`。同样是活动分支的源码发现，未在本期冻结快照中伪装成已复现问题。建议命令：`$impeccable harden`。

**P2-4：原始承诺线及图例的低透明度削弱辨识。**

曲线使用 strokeOpacity=0.6，图例使用 muted-foreground/50。根据 token 合成推算，浅色曲线约 2.51:1、浅色图例约 2.10:1、深色图例约 2.67:1，低于常用的图形 3:1 对比度目标。

建议：使用足够对比度的实色 token，以虚线区别原始承诺；图例同步使用线型。以上是 token 分析，不能视为浏览器实测或完整 WCAG 判定。

位置：`packages/views/iterations/iteration-progress.tsx:24`、`:32`、`packages/ui/styles/tokens.css:180`。建议命令：`$impeccable polish`。

**应保留的基础**

现有中性色、标准标签、选中下划线、蓝色完成序列适合工作型产品；900px 自动收起侧栏且没有横向溢出。改进应沿用这些基础。

冻结事实、原始承诺与有效范围的区别、任务数说明，以及带 caption、行列标题的数据表都有实际价值。重新分配位置与默认展开状态即可保留核对能力。

**实施时必须保持的语义**

- 原始承诺完成率使用 original_completed / original；不能使用全部已完成任务作为分子。
- 净有效范围变化使用 effective - initial_effective，不能直接减 original。
- 新增按不同任务数统计；移出、重入、取消、重开按事件次数统计，不能包装成可直接相减的同单位数字。
- started 表示已开始过的任务，不能改名为“进行中”。
- 结束时任务去向与期间范围变动属于不同阶段。
- 历史缺失值、分母为零的“不适用”不能改为 0。
- 折叠零值和批量记录只改变默认展示，完整事实与可访问数据仍然保留。

**使用者影响**

协调人需要快速判断交付结果，当前要先浏览统计字段；初次使用者可能把两种完成率、两类移出数据当成矛盾；辅助技术用户需要继续保有文字摘要和可键盘展开的数据表。改进后的阅读路径应是“先判断结果，再核对原因”。

**建议的优化顺序**

1. `$impeccable distill`：明确两个标签的职责，收起低频指标、去除重复说明。
2. `$impeccable clarify`：解释完成率分母、结束时范围、期间变动及真实事件差异。
3. `$impeccable layout`：压缩公共头部，采用紧凑结果区与可展开时间线，适配单日数据。
4. `$impeccable harden`：处理共享活动分支的分页、加载和错误恢复。
5. `$impeccable polish`：统一字号层级、间距、图例线型、对比度及焦点反馈。

复审验收重点：无需滚动就能读懂本期完成结果；19 条原始记录仍可完整访问；默认事件不再包含不适用的迁移箭头；50%／25% 及移出阶段各有明确解释；900px 保持无横向溢出；单日数据不展示无法成立的趋势。

本轮没有业务代码改动，因此未运行构建、lint 或测试。键盘／读屏全流程、网络失败、多页活动、手机 Web 和深色实机效果仍需在实施阶段验证。此报告与五张截图是本轮新增的审计产物。
