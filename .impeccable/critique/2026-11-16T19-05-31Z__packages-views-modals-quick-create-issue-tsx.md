# 「通过智能体创建」弹窗评审

Method: dual-agent (A: critique-a-design · B: critique-b-evidence)

日期：2026-11-17。对象：`packages/views/modals/quick-create-issue.tsx` 及同目录的 `quick-create-actor-picker.tsx`、`creator-recommendations.tsx`、`issue-description-assist.tsx`，源码位于 `6b7130b1d`。模式：Operate。

两路评估互相隔离：设计评审先交卷，检测器和像素证据之后才并入。浏览器叠加层没有做，因为 Web 开发服务是停的，唯一在运行的界面是用户正在用的 Desktop，没有去附着它。像素数据都取自用户提供的截图（2 倍屏，弹窗 672×440，空状态：未选智能体、未写描述），其余状态来自读源码；没在运行中验证的地方下面会标出。

**有优化空间，而且最值得改的不是视觉。** 这个弹窗卡住用户的时候不说话：灰色的「创建」不告诉人缺什么，⌘↵ 被拦下时毫无反应。规范层面反而很干净，四个文件里没有越级字号，也没有硬编码颜色。

## 设计特异性判断

**评审判断。** 骨架是任务编辑器的通用样式：面包屑、无边框编辑区、属性 pill、底部的附件、连续创建和主按钮。对操作型界面这是对的，键帽和定宽提交按钮这些细节也到位。但这个弹窗真正属于 Multica 的想法，是把事情交给智能体、由它去建任务，而它只落在一个 12px 的灰色「交给」上。"不用填标题、异步执行、完成后收件箱通知"这份约定，提交前在这个弹窗里看不到，只出现在手动模式的切换提示和提交后的 toast 里。全页最有产品特征的决定，是全页最安静的一处。

**确定性扫描。** `impeccable detect` 对四个文件都返回 0 条（退出码 0）。这不等于没问题：检测器不会把 Tailwind 类解析到 `tokens.css`，对本仓库的 TSX 是已知盲区。所以证据评估改用 token 计算加截图取样，两者逐项吻合，最大偏差 0.02。没有误报需要剔除。深色主题只有 token 计算，没有截图。

**叠加层。** 没有，原因见开头。

## 总体印象

安静、克制，编辑区拿到了该有的空间。问题集中在三处边缘：顶部一行、编辑区下方的辅助行、底部按钮，它们各说各话。最大的机会是把"为什么不能创建、下一步做什么"说出来，手动模式已经有现成的做法可以照搬。

## 做得好的

1. **推荐理由可以核对。** 每条推荐都带「职责依据：」和该智能体职责描述的原文摘录，描述变了就作废，采纳必须点一下。用户是在核对理由，不是在盲信 AI。
2. **自治等级拦截的提示是范本。** 它说清了是什么、为什么、下一步，按钮一键带着草稿切到手动并预选好负责人。其他失败状态都该向它看齐。
3. **底子扎实。** 「帮我完善」替换描述后可撤销，也不会覆盖中途改过的内容。提交按钮定宽，文字变化时底栏不跳。窄屏和触屏下控件都有 44px 点击区，减弱动效时光效会关掉。

## 优先问题

### [P1] 卡住时不说原因；没有可用智能体时没有出路

**现象。** 截图这个状态下，「创建」是原生 `disabled`，没有任何原因说明（`packages/views/modals/quick-create-issue.tsx:1090`，只有自治等级和版本两种拦截才带 `title`）。按 ⌘↵ 会在 `packages/views/modals/quick-create-issue.tsx:497` 直接返回，界面没有任何变化。

**对截图的推断（未在运行中验证）。** 代码会自动选中一个可用的智能体：默认的、上次用的，或者第一个可用的（`packages/core/issues/creator-selection.ts:32`）。所以「选一个智能体...」如果一直停在那里，要么列表还没加载完，要么这个工作空间里没有可以接手的智能体。后一种情况下，选择器里只有一句「暂无可用智能体或AI小队。」，没有按钮；「帮我选智能体」也没有针对零候选的处理（`packages/views/modals/creator-recommendations.tsx:56`）。如果工作空间其实有可用的智能体而这里没选上，那是选人逻辑的问题，严重程度另算。

**为什么重要。** 智能体模式是默认的新建入口。最不会排查问题的新用户，打开的第一个新建弹窗可能永远点不亮「创建」，而且没人告诉他为什么。

**怎么改。**
1. 普通拦截照搬手动模式已有的做法（`packages/views/modals/create-issue.tsx:897`）：缺内容时用 `aria-disabled`，按钮仍可聚焦，Tooltip 说明缺什么；原生 `disabled` 只留给提交中和上传中。点击或 ⌘↵ 被拦下时，把焦点送到缺的那一项。
2. 没有可用智能体时，按自治等级拦截提示的写法做一个状态，给两个出口：去配置智能体，或「切换到手动」。现成的 `switchToManual` 会带上草稿。

**建议命令：** `/impeccable harden`

### [P2] 两个 AI 辅助按钮是两套做法

| | 帮我选智能体 | 帮我完善 |
|---|---|---|
| 禁用时的文字对比度（浅色） | 3.74:1 | 2.13:1，比旁边自己的提示（5.9:1）还淡 |
| 取消 | 状态文字旁单独的「取消」 | 按钮自己变成「取消」 |
| 出错 | 灰色文字，没有重试 | 红色文字加「重试」 |
| 描述被改动后 | 结果悄悄清空 | 提示"内容已更新" |

动词也不统一：按钮叫「帮我完善」，状态却写"请重新优化""AI 优化暂不可用""优化失败"（`packages/views/locales/zh-Hans/modals.json:187`）。

**为什么重要。** 用户在一个按钮上摸清的规律，换到另一个就不成立；同样是失败，一个像警告，一个像备注。

**怎么改。** 定一套做法。色调统一：现在「帮我完善」是灰字再叠 50% 透明度，所以比自己的提示还淡（`packages/views/modals/issue-description-assist.tsx:250`）。取消都用独立按钮，出错都用红色加「重试」，内容变了都给一句说明，动词统一成"完善"。

**建议命令：** `/impeccable harden`，动词部分用 `/impeccable clarify`

### [P2] 必填的"交给谁"是全页最弱的文字，而且先要答案后给问题

**现象。** 「交给 选一个智能体...」是 12px 灰字、没有边框，旁边选填的「无项目」反而有边框和深色字。它下面那句「默认由所选对象负责…」离选择器 15.5px，离下方的「任务描述」只有 12.5px，看上去像是描述的说明。顶部先问交给谁，可是帮你选的按钮要等描述写完才可用。采纳推荐后焦点停在选择器上，这时 ⌘↵ 不起作用。

**为什么重要。** 阅读顺序、Tab 顺序和推荐的用法互相打架：先在下面写，再回到上面选，然后发现按钮上印着的快捷键不灵。

**怎么改。** 已记录的决定都不动：「交给」、常驻提示、推荐前提始终可见（`.trellis/spec/views/frontend/quick-create-actor-picker.md:136`）。在这个范围内做四件事：
- 给选择器一个和「无项目」一样的外框，选中后的名字用正文色。
- 提示贴近选择器，和「任务描述」之间拉开距离。
- 把 ⌘↵ 绑到整个弹窗。
- 空状态下两个辅助按钮改成 `aria-disabled` 且可聚焦，点击时把焦点送进编辑器，键盘用户也就能读到那两句前提。

**建议命令：** `/impeccable layout`

### [P2] 一个动作四种说法，一个位置三个名词

**现象。** 同一件事先后叫「通过智能体创建」（标题）、「交给」（标签）、「创建」（按钮）、「发送中...」和「已发送」（进行中和计数）、「已交给智能体」（完成提示）。同一个位置叫「智能体」（选一个智能体）、「助手」（使用此助手、默认助手）、「对象」（所选对象、没有匹配的对象）。词表里只有"智能体"和"AI小队"。

**为什么重要。** 按钮写的是"创建"，可点下去并没有建出任务。任务是智能体稍后建的，建好了才进收件箱，这件事要等完成提示弹出来才知道，会有人去列表里找一个还不存在的任务。

**怎么改。** 动词沿用已经定下的「交给」，贯穿按钮、进行中和计数。名词需要负责人定：要么选一个统称写进词表，三处统一；要么不用统称，直接写"智能体或 AI小队"。提示那句的措辞在规格里有记录，要求不暗示立即执行，所以要在里面补"完成后收件箱通知"得由负责人点头。

**建议命令：** `/impeccable clarify`

### [P3] 对齐与节奏

**现象（截图实测，CSS px，从弹窗左边起算）。** 左边缘有五条：属性 pill 边框 16、正文列 20、附件图标 23、「交给」28.5、「帮我完善」图标 31.5。右边关闭图标离边 31，「创建」离边 17。「任务描述」在这里是 13px 中粗深色，手动模式的描述标签是 12px 灰色（`packages/views/modals/create-issue.tsx:1005`），切换模式时标签会变样。

**为什么重要。** 每一处都不大，叠在一起就让一个很安静的界面显得没对齐。

**怎么改。** 全部内容收到同一条 20px 的列上，属性行和底栏的 `px-4` 改成 `px-5`。没有边框的控件按文字对齐到这条列上，做法是调整容器或控件自身的内边距，不用负外边距：规格 `.trellis/spec/views/frontend/quick-create-actor-picker.md` 记录过，宽度随内容变化的触发器配负外边距会挤占文字空间。（2026-11-17 更正：这一句原先写的是"用等于自身内边距的负外边距"，与规格记录冲突，也不是设计评审的原意。）两种模式用同一种描述标签样式。

**建议命令：** `/impeccable layout`，收尾用 `/impeccable polish`

## 小问题

- 键帽图标实际渲染 14px，不是组件设定的 12px：Button `sm` 的 svg 规则优先级更高，盖掉了键帽的 `size-3`（`packages/views/common/shortcut-keycaps.tsx:117`、`packages/ui/components/ui/button.tsx:49`）。
- 同一行里「无项目」高 26px，「···」高 24px。
- 这里的提示用原生 `title`，手动模式用的是真正的 Tooltip。
- 属性行缺少手动模式有的 `role="group"` 和名称。
- 「任务描述」是 `<p>`，点它不会聚焦编辑器。
- 语言包里 `select_agent_aria` 没有任何引用；`AI小队` 与 `AI 小队` 并存，词表写的是前者；英文里 `…` 和 `...` 混用。

## 值得想一想

1. 这一条是在质疑负责人 2026-10-11 定下的决定，没有当作问题处理，也不建议去掉。离开这个模式的「切换到手动」每 4.2 秒闪一次光，就在主按钮旁边；而"交给谁"这个模式自己的核心，却是全页最淡的文字。强调的预算是不是花在了出口上？
2. 既然要说两遍"先写描述"，「交给」加「帮我选智能体」这一组要不要整体挪到描述下面，让表单读成：写清楚，交给谁，交给？
3. 自治等级不够的智能体会灰着列出来并说明原因，没绑定运行环境或不可分配的却直接消失。"我的智能体去哪了"为什么只在一种情况下有答案？
