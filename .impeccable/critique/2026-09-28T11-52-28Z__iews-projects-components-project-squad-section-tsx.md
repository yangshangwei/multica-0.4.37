# 项目多 AI 小队页面：业务与交互优化建议

项目页应优先帮助用户推进任务：找到当前工作、处理阻塞、提交下一条任务。小队配置用简短摘要保留可见性，完整配置按需展开。

本次依据用户截图、项目组件与业务约定进行评审。截图中的 8 个小队约占主内容区四分之三高度；每队重复展示说明、运行时和操作，而没有任务的区域位于页面底部。建议保持现有暗色主题、组件和任务视图，调整信息层级。

## 已核实的业务边界

- 多个小队构成项目的有序候选列表。每条任务只选择一个负责人，不会向所有已选小队广播。
- 第一项为项目内新任务的默认候选；显式负责人、分组和保存视图约束的优先级更高。调整默认不会重新分配已有任务。
- “交给AI小队”打开普通新建任务窗口，预填项目、小队和待办状态，后续使用既有触发预览。按钮本身不立即执行。
- “可以接收任务”表示当前通过可用性检查。在线或成员 working 状态不能证明这个项目有任务正在执行。
- 项目本身已有任务总数和完成数；任务视图有按状态分类的统计与筛选基础。待审批、执行失败和需要当前用户处理的汇总，需要接入对应的真实执行与权限数据，不能从 readiness 推断。

## 启发式暂评

0–4 分，越高越好。交互状态根据源码暂评；没有完成浏览器动态、键盘或读屏验证。

| 项目 | 分数 | 主要依据 |
| --- | --- | --- |
| 状态可见 | 2 | 可用性清楚，项目实际工作不突出 |
| 现实匹配 | 2 | 配置与交付场景混在一起 |
| 用户控制 | 2 | 有取消和更换；默认规则不够明确 |
| 一致性 | 3 | 复用既有任务表面和控件 |
| 错误预防 | 3 | 有权限、运行时、成员检查和禁用状态 |
| 识别优于记忆 | 2 | 队名可识别，但职责说明与默认含义不足 |
| 操作效率 | 2 | 多个等权入口，管理操作过度曝光 |
| 简洁设计 | 1 | 每队重复内容挤压主要工作区 |
| 错误恢复 | 3 | 有错误说明、重试与运行时连接路径 |

| 合计 | 22/40 | 主要问题集中在信息组织 |

设计具有真实的 AI 小队业务内容，但页面结构未随单小队扩展为多小队重新组织。正常状态下的信息密度和操作权重缺乏差异。CLI detector 扫描目标组件成功，退出码 0、命中 0；它没有发现机械规则违规，不能据此推断业务体验良好。

## 值得保留

- 可用性同时使用文字与颜色，并提供离线、权限和机器匹配等恢复路径。
- 任务已有列表、看板等统一视图，属性已有侧栏；改善布局时可以继续复用。

## 优先调整

### P1：让任务重新成为主体

顶部常态只显示一至两行摘要，例如：

`AI小队 8 · 8 个可接收任务 · 新任务默认：特性交付小队 · 管理`

完整名单进入专门的管理面板。点击管理可展开面板；关闭后回到原任务位置。摘要高度不随小队数量线性增长。桌面与窄屏都应在第一屏看到任务内容或空状态的下一步。

正常状态简短显示。若有小队不可用，摘要保留异常数量和处理入口；默认小队不可用时明确说明影响。不要把错误一起折叠消失。

对应后续工作：`$impeccable layout`、`$impeccable distill`。

### P1：统一任务创建入口

有任务时，工具栏保留一个主按钮“新建任务”。没有任务时，主按钮放在空状态中央。创建窗口显示当前项目与默认负责人，可切换到其他可用小队、智能体或成员，保持现有负责人类型与权限规则。

建议流程：描述任务 → 查看或更换负责人 → 查看触发预览 → 确认创建。不要把进入窗口等同于开始运行。

管理面板每行可以保留次级的“用此小队新建任务”快捷入口，但不再呈现 8 个等权主按钮。

对应后续工作：`$impeccable clarify`、`$impeccable onboard`。

### P1：按项目状态安排焦点

| 项目场景 | 主内容 |
| --- | --- |
| 已配置小队、尚无任务 | “AI小队已就绪，创建第一条任务”，提供创建和关联已有任务 |
| 已有任务 | 任务列表或看板，以及可点击的真实状态筛选 |
| 有需要人工处理的事项 | 明确事项、原因和下一步操作；处理后回到任务 |
| 默认小队不可用 | 解释原因，允许明确选择其他可用小队或修复配置 |
| 数据尚未取得 | 显示检查中或重试；未知不能显示为零或就绪 |

项目级“进行中”“阻塞”等使用任务状态；“正在执行”“待审批”等使用对应运行数据。统计限定当前项目，不能把该小队在其他项目的活动纳入。按小队展示时，应先明确父任务、子任务与单次执行的归属口径，避免重复计数。

对应后续工作：`$impeccable shape`、`$impeccable harden`。

### P2：在选择与管理时展示真正有用的信息

管理列表每行以“小队名称 / 职责 / 可用性 / 新任务默认 / 更多操作”为主。职责优先读取已有小队说明。例如需求预研帮助澄清范围，缺陷修复处理问题，发布小队承担发布相关工作；这些是选择提示，不意味着系统会自动路由或按阶段串联。

- 将“默认”明确为“新任务默认”，提供显式“设为默认”操作；不能把视觉排序无意变成业务默认。
- 小队名称可进入详情；运行时和机器信息放在详情或配置展开区，发生故障时就地展示相关信息。
- 更换、移除等低频动作放在可用键盘访问的菜单中，不能仅在鼠标悬停时可达。
- 移除文案说明是解除项目关联，并保留既有“不删除共享小队、不改派已有任务”的语义。
- 右侧继续放属性、描述、资源与自动化；空的可选区收起，需要时仍可找到。

对应后续工作：`$impeccable clarify`、`$impeccable distill`。

## 当前空项目的建议布局

```text
项目 / test                               属性面板开关

AI小队 8 · 8 个可接收任务
新任务默认：特性交付小队                       管理

                  创建第一条任务
       描述要完成的事情，创建时可以选择承接小队。

                  [ 新建任务 ]
                   关联已有任务
```

有任务以后，同一主体位置恢复现有任务列表/看板，主按钮移到工具栏。属性面板仍可打开，任务区域获得主要宽高。

## 用户与认知负担

项目负责人每天来判断进度和处理阻塞，目前必须反复越过完整配置区。首次用户选完小队后看到多个“交给”按钮，需要理解默认与提交的关系，配置完成未自然衔接到第一次产出。

独立评估认为单一焦点、分块、层级、分步决策、选项控制、渐进披露这六项存在问题。名称与行末操作横向距离过远，也增加对应成本。改版后的情绪路径应是：确认资源就绪 → 明确下一步 → 提交任务 → 看到进展或具体待处理事项。

## 落地顺序与验收

第一步只调整现有能力的组织：压缩顶部摘要、提供完整管理入口、统一任务创建入口、改善空状态。保留已有权限、readiness、错误恢复和触发预览行为。第二步接入真实的项目执行与待处理汇总。

验收重点：

1. 配置 1、8、20 个小队时，首屏都能看到主要任务内容；正常摘要不随数量持续增高。
2. 每个页面状态只有一个主要任务创建入口。
3. 默认含义明确，可显式切换；已有任务的负责人保持原语义。
4. 所有配置操作仍可通过管理入口完成，键盘可达。
5. 离线、无权限、检查失败、机器不匹配不会因压缩布局失去处理入口。
6. 所有计数基于当前项目的真实数据，未知与零明确区分。

待后续方案细化的问题：管理面板与现有属性侧栏的占位方式；当前用户“待处理”应包含哪些业务事件。第一步的层级调整无需等待这些统计细节决定。

本次没有实现产品改动。下一步设计与实现验证可依次应用 layout/distill、clarify/onboard、harden，最后进行一次 polish。
