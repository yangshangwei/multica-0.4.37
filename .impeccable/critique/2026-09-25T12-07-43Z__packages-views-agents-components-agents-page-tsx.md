# 智能体页面业务易用性审阅

目标：packages/views/agents/components/agents-page.tsx。
证据：用户提供的 22 个智能体截图、当前页面及近邻源码、智能体与 AI小队产品文档、角色模板指令。当前页面没有完成实时交互验证，以下结论区分静态事实与设计建议。

## 核心判断

页面应帮助用户完成“找到合适的人 → 判断能否使用 → 发起工作”。当前组织方式偏向资产管理，用户主要依赖角色名称和一行说明，在 22 个平级成员之间自行判断。最大优化机会是把用途、职责层级与小队关系放到第一层。

## 已有优势

- 角色名称贴近业务，描述已经包含产出与职责边界，现有两行列表适合作为基础。
- 已有名称/描述/拼音搜索、五类筛选、排序、自定义列、批量管理及按工作区记忆设置。
- 列表已有虚拟滚动，详情已有私信及分配工作。此次困难不能归因为缺少性能优化或完全没有使用入口。

## 优先问题与改进

### P1：缺少按任务找到角色的入口

事实：列表平铺；筛选涵盖可用性、访问权限、运行时、owner、模型，没有职责、小队或用途维度。搜索主要匹配名称与描述。
影响：用户知道“修复缺陷”“推进发布”，未必知道该搜索哪个角色名称。
建议：默认按用途组织浏览，例如澄清与设计、开发与修复、验证与审查、发布与运维；提供按 AI小队查看关系的方式。利用现有八类小队模板，完整工作交给小队，由 leader 调度，明确步骤交给专业智能体。一个成员可以属于多个小队，不因分组创建副本。
证据：agents-page.tsx:170；agent-list-toolbar.tsx；apps/docs/content/docs/squads.zh.mdx。
后续方向：impeccable shape / layout。

### P1：统筹与专业角色缺少显著区分

事实：截图同时列出发布负责人、发布工程师、合并门禁负责人等角色，职责层级主要埋在描述中。
影响：用户难判断是把整项工作委派出去，还是自行逐个选择执行者和审查者。
建议：在身份旁显示真实职责标签，例如“统筹”“实现”“审查”；类型来自明确的角色元数据或用户配置，不靠名称猜测。描述统一为适用场景与交付结果，权限边界在预览中展示，且与真实配置保持一致。
例子：发布负责人协调验证、文档和发布步骤；发布工程师准备发布及回滚方案、执行获批动作；合并门禁负责人组织审查并汇总门禁结论。负责人不应被描述为能代替人类验收或审批。
证据：agents-page.tsx:411；server/internal/service/builtin_agent_templates/release-lead/INSTRUCTIONS.md；release-engineer/INSTRUCTIONS.md；review-gate-lead/INSTRUCTIONS.md。
后续方向：impeccable clarify。

### P2：默认列的区分价值偏低

事实：截图可见行的 owner、访问范围、运行时、在线状态、近期活动大量重复；描述较弱，姓名与状态相距很远。已有显示设置，但入口外观主要表现为当前排序“最近活跃”。
影响：阅读面积很大，却不能快速比较适合做什么。
建议：默认突出“名称和职责、一句交付说明、工作状态、常用动作”；运行时、owner、访问范围、次数保留在清楚命名的“显示”设置或管理视图。沿用现有表格，不必全量改为占地更大的卡片。收紧列间关系、提高说明的可读性，用少量类别标识辅助扫读。
证据：agents-page.tsx:411；agent-list-toolbar.tsx:513；packages/core/agents/stores/view-store.ts。
后续方向：impeccable distill / layout。

### P2：模板与成员的概念边界不清

事实：“内置智能体 14”实际为角色模板目录；下方 22 是当前工作区未归档实例数。模板用途说明折叠后不可见，目录只用 find 关联一个已有实例。
影响：用户容易疑惑 14 与 22 是否相加、是否是两组可用成员，以及是否需要重复创建。
建议：改用清楚的“角色模板”入口，归入创建流程；需要保留在当前页时明确它是可创建的角色，并显示已有实例数量和入口。保留现有成员列表用于日常使用。
证据：builtin-agent-catalog.tsx:17；packages/views/common/builtin-template-catalog.tsx；packages/views/agents/create/use-role-templates.ts。
后续方向：impeccable clarify。

### P2：重复使用与首次委派路径偏长

事实：列表行进入详情，详情提供私信与分配工作；行菜单以管理动作为主。没有常用置顶，默认最近活跃排序在无近期活动时不能提供选择依据。
影响：熟练用户每次仍需找人，新用户创建完角色后缺少首项工作指引。
建议：增加个人常用入口；选中行后用预览呈现适用任务、输入、产出和真实边界，并复用已有分配与对话入口。冷启动按用途提供稳定顺序，有记录后再提供“我最近使用”；不得把全工作区活动当作个人最近使用。把现有对话开场建议用于首次使用引导。
证据：agents-page.tsx:1149；agent-detail-page.tsx:308；agent-detail-page.tsx:558；agent-row-actions.tsx；view-store.ts。
后续方向：impeccable shape / onboard。

## 状态与数据表达

- “在线”表示运行时可达，工作负载是另一个维度，运行权限还受 Access 控制。“在线”和近期 0 次同时出现可以成立，不是状态错误。
- 现有状态会显示活动 task 总数；如果用户需要安排工作，可进一步明确运行与排队的区别，不能把总数解释为全部正在运行。
- 私有或管理员仅可管理的成员，应在使用入口解释当前用户能否运行。业务状态展示不能替代后端权限判断。
- “运行次数”和“最近活跃”使用 30 天窗口。标题宜明确“近 30 天运行次数”；0 不等于从未运行，不能据此推荐删除或自动归档。
- 在“我的”范围添加筛选会自动切到“全部”，返回“我的”会清空筛选。后续交互验证应确认这是否符合使用预期，优先保持“在当前范围内筛选”的直觉。

## 适用用户与认知负荷

新成员需要按目的缩小候选集；熟练成员需要常用入口与快速委派；管理员需要现有表格、权限、运行时与批量操作。三类需求可以用不同默认信息密度承接。

主要认知负荷来自四处：缺少业务分组、相近角色同级、重复属性竞争注意力、需要进入详情才能建立角色边界。不能把“超过四项”直接当作列表错误，关键是用户能否有依据地排除不相关候选。

用户的情绪低点是已经创建很多角色却不知道先用谁。首次成功委派应成为使用引导的结束点。

## 推进顺序与验收

1. 先提高识别：职责标签、结果导向描述、用途/小队浏览、模板命名、默认列和显示入口。
2. 再缩短使用：个人常用、选中预览、列表附近复用分配/对话、首次使用示例。
3. 再按证据扩展：用真实任务上下文推荐候选并解释理由；复用当前权限及小队调度，避免凭使用次数推断能力。

用三种场景测量改动：新用户为具体工作找到合适成员；熟练用户再次使用同一成员；管理员定位不可用或访问受限成员。采集正确选择率、选人耗时、详情往返次数、首次任务启动率，先测现状再定目标，不能把点击数或运行次数直接当作业务成功。
