# 根因分析

## 何时使用

有一个可观察的失败（测试失败、报错、行为不符、线上异常），但**还不知道原因在哪**时使用，包括间歇性或暂时无法复现的异常。目标是查明失败机制和触发条件，交给实现工程师去修；根因也可能在依赖、配置或环境中。

原因已经明确到可以直接修复时，不必再走完整流程，说明依据并交接即可。这个 skill 负责**定位**，不负责提交修复。

## 与相邻工作的边界

- 与 `multica-test-report`：test-report 验证变更是否可用，包括修复后的回归验证；本 skill 在修复**之前**定位已观察到的失败——为什么失败、缺陷在哪。
- 与 `multica-code-review`：code-review 静态读 diff 找潜在问题；本 skill 针对一个**已观察到的**失败，动态复现并定位。
- 与缺陷修复流程：缺陷修复要求 "先复现再修"，本 skill 填的是 "最小复现 → 修复" 之间那段系统定位——在猜测式改动之前先锁定根因。

## 提交调查前先读什么

1. 失败本身：预期与实际行为、完整报错、堆栈、失败测试名、复现步骤、发生环境与时间；
2. 相关任务、评论与链接，以及近期改动该区域的提交或 PR；
3. 涉及的代码及其测试——测试往往比任务描述更准确地说明契约。

读不到的关键信息（日志、环境、权限）直接标为待确认，不要用猜测填补。

## 工作范围

即使单独挂载本 skill，也只在当前角色授权范围内调查；skill 不授予权限。需要写文件时，`contributor` 在隔离分支上复现、插桩和写测试。只读角色不能借本 skill 写文件，应交接需要改动的实验。生产数据、真实凭据和生产插桩仍需交给有授权的人员。

## 复现与最小化

- 在隔离分支上调查，保留用户和其他人的已有改动；不要为获得干净环境而覆盖或清理这些改动，不向默认分支提交或推送。
- 先稳定复现。无法稳定复现时，记录已知触发条件与复现率，不要假装已复现。
- 把复现收敛到最小：去掉与失败无关的输入、数据和步骤，直到再删就不复现为止。最小用例既是定位工具，也是给实现工程师的回归测试起点。
- 可自动化时，编写并实际运行无修复时失败的回归测试；确认失败来自目标现象，而非环境或测试装配错误。交付测试文件或补丁、命令、退出码和失败输出。无法自动化时交出可执行的最小复现步骤并说明限制；尚未复现时记录缺口，不编造结果、不降低断言或把跳过当通过。
- 记录复现所需的确切条件（输入、数据状态、时序、环境）。

## 形成并验证假设

- 基于证据提出**具体、可证伪**的假设（"X 在 Y 为空时越界"），而不是笼统方向（"并发问题"）。
- 逐个验证，优先能一次排除最大范围的：二分（git bisect、缩小输入、砍代码路径）、临时插桩（日志、断言、打印中间态）、对照实验（只改一个变量看结果）。
- 实验记录包含提交号、命令、退出码、关键输出或证据文件路径，以及改变的唯一变量。二分只在隔离工作树中进行，记录好 / 坏提交和判断依据。
- 插桩和对照改动是临时手段，只加不提交；先保存必要证据，再在调查结束或交接前清理自己的改动，保留复现用例。只在开发 / 测试环境操作，绝不在生产环境插桩或读生产数据；日志和报告不得包含凭据或敏感原始数据。
- 一个假设被证据推翻就记录并排除，不要绕回已排除的方向。

## 结论必须有证据

每个根因结论都要能追溯到你亲自看到的复现、观测或插桩输出。区分三档并如实标注：

- **已确认根因**：有从触发条件到失败机制的因果证据链，定位到代码位置或依赖 / 配置 / 环境。报错行、时间上的相关性或一次对照通过都不足以单独证明根因；说明验证如何支持该机制并排除竞争解释。间歇失败需记录对照条件和运行次数，证据不足仍标疑似。
- **疑似**：有指向性证据但未完全证实——写成假设，列出还差哪一步验证。
- **未查明**：说明已排除什么、卡在哪、需要什么（权限/环境/信息）才能继续。

没查到根因是有效结果，不要为了给结论而把疑似说成已确认。

## 交接字段

在 bug-fix、maintenance 或 incident 小队中交接时，评论应明确 `route`、`cause_state`、`reason`、`downstream_repair_issue`。已知原因直达修复必须写 bypass reason；maintenance 的未知原因必须创建诊断后续；incident 必须写明 `mitigation_complete` 和 `separate_follow_up`，让止血与 RCA 保持独立。

## 输出

```text
## 失败现象
- <可观察的失败，含预期与实际行为、报错/失败测试/环境/提交号>

## 复现
- 最小复现：<步骤或输入> — 复现率 <x/n；未复现也写出尝试数>
- 触发条件：<输入·数据状态·时序·环境>
- 回归测试：<文件或补丁、命令、退出码、失败输出；无法自动化时说明原因>

## 调查过程
- 假设 <A> — 验证方式（二分/插桩/对照） — 结论（确认/排除，附证据）

## 根因
- <已确认根因，代码位置或依赖 / 配置 / 环境机制> —— 证据：<复现/插桩/对照输出及路径>
- （或）疑似 <...>，还需 <验证步骤>；或 未查明，已排除 <...>

## 建议修复方向
- <交给实现工程师的方向，不含实际改动；附最小复现用例作为回归测试起点>

## 未确认 / 未覆盖
- <缺的权限·环境·信息；临时插桩清理结果和保留的复现文件>
```

## 以下情况停止并询问人工

- 复现或定位需要生产数据、真实凭据或你没有的访问权限。
- 失败涉及数据丢失、安全缺陷或凭据泄露：报告后停止调查，交由人工决定后续处理。
- 继续调查需要超出当前授权的依赖或外部服务访问：说明已有证据和所需行动；本地可验证的依赖、配置和环境问题仍可继续定位。
- 连续调查没有新增证据、重复同一方向，或达到任务约定的时间 / 资源预算：交付疑似 / 未查明报告，说明已排除范围和所缺支持。排除假设本身是进展，不因验证了两个假设就停止。
