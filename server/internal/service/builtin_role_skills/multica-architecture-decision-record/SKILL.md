# 架构决策记录

## 何时使用

当一项决策在任务关闭后仍会影响代码时，起草 ADR，例如模块边界、数据模型、其他客户端
需要解析的数据契约、依赖，或团队今后必须遵循的规则。

完全局限在一个函数内的选择无需起草 ADR；已有记录的决策也不必重写，链接原记录即可。

## 交付位置

将完整草案写入任务评论。查找已有的 ADR 目录（`docs/adr/`、`docs/decisions/`、
`doc/arch/`），按现有编号和文件名规范提出建议保存路径。如果仓库没有 ADR 目录，
在评论中提出建议位置，交由人工确认。

默认架构师的权限为 `observer`：不得编辑仓库文件或创建目录。将草案和建议保存路径
交给实现工程师或人工，由其保存到仓库。建议路径不代表文件已经存在，不能作为现有文件的链接。

## 写作依据

动笔前，从已读材料中整理两类信息，可用简短列表，不必增加冗长章节：

- **已知事实与约束**：注明任务描述、具体评论、真实文件及必要行号。核对来源确实支持
  该陈述；文件存在或采用某个框架，不等于它采用了该框架常见的架构。
- **待确认信息**：缺失、矛盾或仅能推测的现状。没有源码时直接说明，不能补成项目背景，
  也不能用未经确认的假设否决方案。

背景和备选方案中对现状的描述都遵守这一区分。拟议规则与预期影响可以推导，但应写明
前提，不能反过来当作已经发生的事实。材料少时允许背景简短；不要为了填满模板或增加
备选方案而编造现状。若缺失信息决定方案能否成立，列为阻塞性问题；其余草案继续完成。

## 结构

```markdown
# <编号>. <用陈述句表述决策>

Date: <YYYY-MM-DD>
Status: proposed

## 背景

<有来源的项目现状与约束，以及它们为何形成需要权衡的决策。注明依据；未知现状写为
待确认，不作为决策前提。只有材料支持时才描述保持现状的结果>

## 决策

<用现在时说明要采取的做法，写明实际模块和路径>

## 影响

<哪些事情变得更容易、哪些变得更难、今后需要维护什么，以及这一决策排除了哪些选择>

## 考虑过的备选方案

### <备选方案>
<为什么它原本可行，以及哪项具体权衡导致它被否决>
```

以下规则比模板更重要：

- **初始状态必须是 `proposed`。** 只有人工可以将其改为 `accepted`。
  这份记录正是为了防止智能体自行接受自己的决策。
- **背景中的约束必须有依据**，不能只概述功能。说明为什么合理的工程判断也可能得出
  另一种选择；缺少依据时保留待确认项，不补造约束。
- **至少提供一个实际可行的备选方案。** 只有保持现状确实可行时，"不做任何改动" 才算备选方案。
- **影响必须包含代价。** 只列好处的 ADR 是宣传材料。

## 输出

在任务评论中给出标记为 `Status: proposed` 的完整 ADR 草案，并用一句话概括决策及其权衡。
说明建议保存路径，交给实现工程师或人工保存。只有 ADR 文件已经存在时才能提供链接；
不得声称草案已经保存或获接受。

交付前逐条核对草案中的现状陈述，包括备选方案里的背景：能否指出支持它的已读材料？
无依据的陈述应删去或在原处标为待确认。末尾统一写一句 "请核对" 不能替代这一步。

## 契约兼容场景

涉及 API、事件、插件或桌面客户端时，ADR 必须附旧/新消费者矩阵：响应字段的可选性、枚举未知值、`parseWithFallback` schema、旧桌面版本和插件边界。说明兼容窗口、弃用顺序和回滚时的解析行为；不能只写“向后兼容”而没有一个旧客户端的验证输入。

## 失败样例

如果旧客户端仍发送旧字段，而新端点既没有 fallback 解析也没有兼容窗口，ADR 结论必须是 `hold`，并创建兼容性修复任务；不能用“客户端最终会升级”替代证据。

## 以下情况停止并询问人工

- 决策需要引入新的依赖、数据存储，或不可逆的迁移。
- 决策会推翻已接受的 ADR，或缩小其适用范围。
- 两个备选方案的主要差别在于成本或团队偏好，而非正确性。
