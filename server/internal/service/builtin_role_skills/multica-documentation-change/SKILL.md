# 文档更新

## 何时使用

变更改变了可观察行为、命令、API 字段、配置键、限制，或其他人需要遵循的规则时使用。

## 判断实际需要更新什么

以 diff 中的实际改动为依据，不以任务中承诺的内容为依据：

| 变更内容 | 需要更新的文档 |
|---|---|
| 用户可见的行为 | 该功能面向用户的说明页面 |
| API 字段或端点 | 对应参考条目及兼容性说明 |
| CLI 命令或参数 | 命令参考，以及所有使用它的示例 |
| 运维步骤 | 操作手册中发生变化的步骤 |
| 他人必须遵循的规则 | 规范文档 |
| 没有行为变化的缺陷修复 | 通常无需更新，应明确说明 |

"无需更新文档" 是有效且常见的结果。将它作为核查结论写明，不要为了交付内容而硬写一页。

## 保证内容准确

- 每条陈述都必须能追溯到代码、测试或已记录的决策。推断出来的内容应先验证，否则不要写入。
- 阅读测试。测试对实际契约的描述通常比任务更准确。
- 使用项目术语表中的词，不用同义词替换。代码与文档命名不一致时，报告差异，不要再引入第三种名称。
- 与上下文文档保持一致，包括结构、详细程度和术语；面向用户的文案还应保持语气和语言一致。
- diff 表示变更，不等于当前文件。路径、行号和 "文件中写了什么" 的陈述必须核对对应文件；
  不得把 diff 的上下文或评论归到另一个文件。

## 搜索旧说明，并核对最终文件

编辑前，用可用的只读搜索工具查找旧字段名、参数、默认值或限制，记录关键词、搜索范围
和真实命中位置。修正范围内仍推荐旧行为的说明；范围外的问题列出位置及所需修改。

最后一次编辑后重新搜索，覆盖刚修改或新增的文档以及本次相关的源码、测试和历史材料。
按命中行的实际含义区分：仍待修正的旧用法、应保留的弃用/兼容性说明、测试或历史记录。
旧词仍出现不等于文档错误；不要为了让搜索清零删除合理说明或修改代码、测试。

摘要中的路径、行号和残留数量取自这次最终检索，逐项核对 "已移除"、"仅剩"、"全部修正"
等结论。只在搜索完整覆盖所声明的范围且没有命中时，才能说该关键词在该范围内已不存在。
若仍有合法保留项，应写清其位置和用途，例如 "已无推荐旧参数的示例，弃用说明仍保留"。

工具结果被截断、有文件无法读取，或未覆盖某个目录时，明确写出未核验范围，不能声称
完成全仓核查。没有搜索工具时，只能逐一读取明确列出的文件，并按实际读取范围报告。

## 禁止事项

- 不得修改代码、测试或配置，包括为了与文案一致而重命名。
- 不得描述尚未实现的行为。
- 不得给摘要再写摘要、添加 "结论"，或留下空标题。

## 以下情况停止并询问人工

- 代码与预期行为不一致，应作为缺陷报告。
- 如实记录会暴露安全敏感细节。
- 面向用户的命名需要产品决策。
